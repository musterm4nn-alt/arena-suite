Private macOS application · architecture & implementation plan

Arena Model Archive

An owner-only macOS desktop application that embeds a dedicated browser for Arena (arena.ai), records the owner's own conversations, backfills existing history where feasible, stores everything locally with strong provenance and per-account isolation, and exposes essentially all functionality to an LLM through MCP — with local model-behavior analysis as a later objective.

Audienceowner + autonomous implementation agents
Scopetext mode v1; modalities extendable
HardwareApple Silicon (M3 Pro, 18 GB)
Distributionprivate — no App Store, no telemetry

Architecture Decision

Recommended v1: Electron + Chromium (Chromium 113+) with TypeScript. One persistent Electron Session partition per Arena account, separate BrowserWindow / WebContents per active account, Chrome DevTools Protocol capture attached as early as possible. Live capture is the primary source of truth; authenticated replay is the backfill mechanism.

Primary escalation: CEF (Chromium Embedded Framework). If the falsification spike proves that Electron's maintained CDP / Session surfaces cannot observe an architecture-critical traffic class but CEF's native CefResponseFilter can, switch to CEF.

Last resort: a custom Chromium fork, only if neither maintained Electron nor CEF exposes a required capability. RECOMMENDATION

2 · Why Electron, and the exact reversal condition

2.1 What Electron gives us today VERIFIED FACT

Electron exposes a main-process-controlled CDP surface via webContents.debugger, which "can attach to a WebContents" and receive instrumentation events, and issues CDP methods via debugger.sendCommand(...). Commands can be scoped to a CDP session ID. VERIFIED FACT (source: Electron debugger).

Electron provides a credible partition primitive: session.fromPartition('persist:...') returns a persistent Session; partitions without the persist: prefix are in-memory. VERIFIED FACT (source: Electron session).

Each Session exposes cookies, serviceWorkers, storagePath, webRequest, protocol, netLog, and a will-download event. Session.clearData({ dataTypes, origins }) can selectively clear cookies, localStorage, serviceWorkers, and cache per origin. VERIFIED FACT

2.2 What Electron does not give us HYPOTHESIS TO TEST

The CDP Network domain exposes Fetch, XHR, EventSource, WebSocket, and ordinary HTTP resources, but whether Arena's actual response streams (in particular any service-worker-mediated streams or unusual transport) are fully observable through maintained CDP + Electron Session APIs without page-world JS cooperation is not confirmed. This is the subject of the falsification spike.

2.3 Reversal condition

The Electron choice is conditional. The decision rule is:

  • Continue with Electron if the spike demonstrates reliable observation of (a) fetch/XHR/EventSource/WebSocket traffic; (b) streamed response reconstruction where Arena uses streams; (c) worker/service-worker-related traffic; (d) target lifecycle and early attachment; (e) downloads; (f) per-partition isolation; (g) post-vote reveal evidence association; (h) clean coexistence of two signed-in accounts.
  • Switch to CEF if and only if (b) or (c) is unobservable through maintained Electron/CDP but CEF's native CefResourceRequestHandler::GetResourceResponseFilter (operating on the IO thread, covering service-worker and CefURLRequest originated requests) demonstrably solves it.
  • Only then consider a custom Chromium fork. Do not preemptively choose it.

The existing extension baseline (musterm4nn-alt/arena-exporter) is rejected as the primary architecture: page-world interception, extension lifecycle fragility, awkward artifact management, and dependence on in-page instrumentation are exactly the failure modes this plan must eliminate. RECOMMENDATION

5 · Process & trust architecture

5.1 Process boundaries

Figure 5.1 — Process and trust boundaries. Remote Arena renderers are explicitly untrusted content; they cannot reach archive state, encryption material, MCP, or Node.

5.2 Trust rules RECOMMENDATION

  • Remote Arena content is untrusted: no archive DB access, no encryption key access, no filesystem, no MCP, no Node, no privileged IPC, no destructive archive actions.
  • Renderer posture: nodeIntegration: false, contextIsolation: true, sandbox where compatible, navigation/new-window restrictions, no privileged preload into Arena-controlled content.
  • Archived Arena prompts, responses, and tool traces are untrusted data; they cannot authorize destructive application actions.
  • IPC is allowlisted and strongly typed; handlers validate envelope shape and provenance before acting.

6 · Simultaneous multi-account partitions

6.1 Per-account partition

Each Arena account gets its own persistent Electron Session. The partition identifier is an internal opaque token, never derived from the owner's email or other sensitive identifiers:

// pseudo — do not bake email into partition names
persist:arena-acct-<uuid v4>

Per partition: cookies, local storage, session storage, HTTP cache, service workers, code cache, download history, shared dictionaries. Each account is a separate BrowserWindow / WebContents with its own capture coordinator and its own auth authority. VERIFIED FACT (Electron Session surface). RECOMMENDATION

6.2 Isolation guarantee

The hard requirement is that one account signing out, expiring, encountering a CAPTCHA, changing identity, or failing synchronization must not corrupt or rebind the other account. Account / session identity is part of every archived record's provenance; cross-account source-ID collisions cannot cause records to merge; identical text is not enough to prove two records are the same. RECOMMENDATION

6.3 Authentication ownership

Arena's own authentication UI remains authoritative. The embedded Chromium handles email verification, one-time codes, MFA if encountered, CAPTCHA / challenges, redirects, and popups normally. RECOMMENDATION

Browser-managed persistent auth state may persist in each isolated partition. Native sync logic may transiently reuse credentials belonging to the correct app-owned Arena session, but copied bearer tokens / cookies must never be persisted into the archive database, logs, fixtures, exports, or diagnostics. RECOMMENDATION

Google OAuth, passkeys, and other third-party sign-in methods are not requirements and do not disqualify a stronger browser architecture. Cookie / token import from Safari, Chrome, or other applications is not used. RECOMMENDATION

7 · Discovery & protocol catalog

Discovery is treated as a maintained product capability, not a one-time scrape. The product maintains a machine-readable protocol catalog of observed first-party Arena traffic. Each entry describes:

interface ProtocolCatalogEntry {
  operation_id: string                  // stable internal id, e.g. "chat.completion.stream"
  origin: "first_party" | "internal_undocumented"
  owning_partition: string              // partition uuid; never email
  url_family: string                   // host + path family; no secrets
  method?: "GET" | "POST" | "WS" | ...
  transport: "http" | "fetch" | "xhr" | "eventsource" | "websocket" | "unknown"
  read_or_mutation: "read" | "suspected_mutation" | "unknown"
  schema_family: string                // inferred schema family label
  adapter_id: string                   // parser/adapter version
  first_observed_at: ISODate
  last_observed_at: ISODate
  capture_mechanism: "cdp_network" | "cdp_target" | "dom_secondary" | "unknown"
  sanitization_status: "ok" | "degraded" | "unknown"
  confidence: "verified" | "strong" | "weak"
  evidence_status: "live" | "replayed" | "ui_only" | "imported"
  drift_status: "stable" | "drifting" | "unknown"
  completeness_notes: string
}

7.1 Sanitization before persistence

Credentials and sensitive headers are sanitized before durable persistence. Explicitly excluded from durable raw evidence:

  • authorization headers, bearer tokens, cookies, CSRF tokens
  • passwords, OTPs, OAuth codes, passkey responses
  • sensitive signed URLs / query parameters (one-time download URLs, signed S3-style URLs, magic-link signatures)
  • unrelated private response fields not needed for parsing or provenance

Retain only enough sanitized raw evidence for parser debugging, drift detection, reparsing, and provenance. RECOMMENDATION

8 · Live-capture architecture

Live capture is the primary source of truth. For each active account partition the capture coordinator:

  1. Auto-attaches CDP to the page target and to each new target spawned within the partition (frame, worker, service worker where exposed) using Target.setAutoAttach. HYPOTHESIS TO TEST — verify exact current CDP method.
  2. Enables Network domain with a request-pipeline wait to capture request bodies, response bodies (where supported), headers, and timing for ordinary HTTP, XHR, fetch, EventSource, and WebSocket frames.
  3. Reconciles CDP Network / Window events with rendered DOM / UI evidence (text diff, structural fingerprint) only as secondary corroboration. Page-world JS is not the primary capture mechanism.
  4. Routes every event through a sanitizer then a parser adapter (versioned), tagged with capture mechanism, target id, and partition.
  5. Persists sanitized observations plus a normalized live-update. Reconciliation rules apply (§ 9).

8.1 What "capture mechanisms exist outside page JavaScript" actually means

For every architecture this report states the same thing explicitly: Electron provides main-process access to CDP via webContents.debugger, with access to the Network domain across XHR, fetch, EventSource, WebSocket, and ordinary HTTP resources, plus Session APIs for cookies, storage, service workers, downloads, and netLog. This is materially deeper than page-world interception — it sits in the Chromium network stack — but it is still not a privileged kernel-level capture. RECOMMENDATION

9 · Capture completeness & reconciliation

9.1 Completeness states

Archived material carries an explicit completeness state, never silently labelled "complete" when inferred:

  • completed — response finished normally
  • stopped — owner intentionally stopped the generation
  • backend_failure — model/backend reported an error
  • network_interrupted — connection / page loss
  • missed_beginning — observer attached after the start
  • missed_ending — observer lost the end (target destroyed, navigation)
  • parser_unsupported — schema drift or unrecognized shape
  • schema_drift — known shape changed; evidence preserved
  • ui_only_reconstruction — reconstructed from rendered UI alone
  • backfilled — obtained via history replay
  • live — live capture
  • conflicting_evidence — multiple non-equivalent observations disagree

9.2 Reconciliation rules

Network evidence and rendered DOM / UI evidence are separate observations reconciled by an idempotent ingestion pipeline. Observations may arrive more than once, out of order, after navigation, after reconnect, after a model reveal, or during an overlapping history sync. Newer weaker inference must never overwrite stronger historical provenance. A reveal event adds an identity observation rather than retroactively pretending the model name was known earlier. RECOMMENDATION

10 · History synchronization (backfill)

10.1 Strategy

Backfill is treated as a separate falsification gate from live capture. Preferred order:

  1. Primary: if the capture/discovery phase identifies stable authenticated owner-history LIST and DETAIL reads and empirically proves them non-mutating and correctly account-bound, they become the primary sync adapter.
  2. Fallback: automated browser/UI traversal + capture, with visibly lower completeness guarantees.
  3. Future: official export (none documented at the time of this plan), user-imported archive, future documented API.

"GET" is not proof of read-only. Absence of mutation must be empirically verified in an owner-session acceptance test before any endpoint is treated as a sync source. RECOMMENDATION

10.2 Sync contract

Sync supports: one selected account; multiple selected accounts; per-account progress and resume; cancellation; idempotent page processing; overlap / repeated-page handling; auth expiry handling; challenge / CAPTCHA handling; rate-limit backoff; source-ID collision handling; live-capture overlap; partial histories; drift detection. "Synchronized" has a precise per-account meaning with explicit known coverage gaps. RECOMMENDATION

Concurrency: if two accounts can sync concurrently without partition isolation violations, do so; otherwise schedule independently. The hard rule is that one account's failure never corrupts the other.

11 · Data & provenance model

The store is normalized current state plus a sanitized observation layer needed for provenance and reparse. Full event sourcing is not gratuitously adopted; if the observation layer is rich enough, it can serve reparsing without bloating the operational state. RECOMMENDATION

11.2 Uniqueness, transactions, lifecycle

Internal UUIDs are stable local identities. Arena source IDs are scoped source identifiers, never universal primary keys; account scope participates in uniqueness rules so collisions across accounts cannot merge. The store uses SQLCipher + WAL with transactional ingestion, crash-safe checkpoints, FTS5 index maintenance on commit, parser reprocessing against stored sanitized observations, schema migrations as versioned SQL with back-out, backup/restore that round-trips encryption, and deletion cascades across rows, FTS, blobs, sync checkpoints, dedup markers, and analysis derivatives. RECOMMENDATION

12 · Model-identity evidence

Identity is never silently equated across these distinct concepts: participant position A/B, blind Arena label, selected marketing model, provider label, route/model string, post-vote revealed identity, owner annotation, and inferred stylistic identity. Each identity observation is stored with source, owning account, scope, timestamp, evidence mechanism, and confidence. Inferred model identity from text must never overwrite observed or revealed identity. RECOMMENDATION

A vote or reveal event adds an identity observation; it does not rewrite earlier turns. Earlier observations remain visible with their original evidence class so the owner can see what was known at the time.

13 · Encryption, storage, deletion

13.1 Key & store

  • A random 256-bit archive key is generated at first run and stored in the macOS Keychain (random key entry, no human password as primary archive key).
  • The main database is SQLCipher 4.x with raw-key mode (256-bit AES-CBC, per-page IV, HMAC-SHA512 integrity, encrypted WAL and rollback journal, statement journals encrypted when temp store is configured). VERIFIED FACT (SQLCipher design).
  • FTS5 search index lives inside the same encrypted DB.
  • Large artifacts (images, generated files, attachments) are stored as encrypted files using a subkey wrapped by the archive key; the DB holds only content references and hashes.

13.2 Realistic plaintext exposure

The following are explicitly addressed:

  • SQLCipher temp store is configured to keep temporary data in memory and not on disk unencrypted. VERIFIED FACT
  • Crash logs are scrubbed before persistence; capture sanitization removes auth headers / tokens / cookies / OTPs before raw evidence is stored.
  • Spotlight indexing is excluded from the archive directory.
  • Time Machine and external backups are not under the application's control; the report does not promise perfect deletion of external backups.
  • Swap and unavoidable OS-level residual exposure are acknowledged.

13.3 Browser profile state

Per-partition browser state on disk contains Arena authentication cookies because persistent sign-in requires it. This browser-managed state is not the same thing as deliberately copying credentials into the research archive. Each Electron Session partition has its own storagePath; the owner-data directory is protected by OS account permissions. Residual risk: any process running as the owner, or any backup tool, can read that directory; the report acknowledges this honestly. RECOMMENDATION

13.4 Deletion

Supported scopes: one archived conversation, all local archive data associated with one Arena account, the whole local archive. Local deletion must not automatically delete the owner's Arena cloud conversations; a separate explicit remote operation is required for that, and is out of scope for v1.

Account-wide / archive-wide deletion requires a trusted explicit user directive, not anything derived from archived content. Concretely: a two-step destructive-intent token — a trusted client asks for deletion preparation; the service returns the exact scope and a nonce / confirmation token; the trusted client must submit that token with an explicit destructive command. Archived content can never mint or satisfy this authorization. RECOMMENDATION

Deletion cascades across DB rows, source observations, FTS, analysis derivatives, blobs, sync checkpoints, and dedup markers. Future re-sync behavior must respect deletion: re-sync must not silently re-pull records that the owner has deleted locally unless the owner explicitly opts in.

14 · MCP / LLM interface

The LLM interface is primary. Everything available in the GUI has an equivalent machine interface unless it is literally an owner interaction with the remote Arena webpage. GUI and MCP share the same application service layer; they do not implement different behavior. RECOMMENDATION

Every tool declares its required scope (account_id or partition token) and refuses if scope is ambiguous. Errors distinguish NEEDS_OWNER_INTERACTION from generic UNAUTHORIZED. 15 · Deterministic analysis

v1 analysis is local, deterministic, and transparent. Profiles may include response length, sentence and paragraph length, code-block length, lexical diversity, recurring n-grams, punctuation, casing, Markdown habits, headings, list/table usage, citation patterns, code / prose ratio, opening phrases, transitions, conclusions, qualifications, hedging, refusal/apology language, and uncertainty markers. RECOMMENDATION

Stratification by model identity evidence, mode, prompt type, topic, language, date, conversation context, and Arena account (where relevant to sampling). Every profile reports its cohort and sample counts explicitly. RECOMMENDATION

15.1 Confounders

The plan names the major confounders rather than ignoring them:

  • one-user selection bias
  • repeated prompting habits
  • topic and conversation context
  • Arena hidden prompts and model system prompts
  • decoding parameters, tools, and routing
  • aliases and label renaming
  • temporal model updates
  • safety / post-processing layers

15.2 What v1 does not include

Embeddings and heavyweight local ML are not part of v1. They are added only after an empirical gate shows deterministic methods are insufficient for the question the owner actually wants to ask. RECOMMENDATION

16 · Fingerprinting experiments (later)

Stylistic similarity is treated as a hypothesis, never proof of model identity. Experimental protocol:

  • held-out conversations
  • leakage-resistant splits (branches and near-duplicates kept in the same split)
  • prompt / topic controls
  • negative controls
  • calibration and unknown-class rejection
  • temporal validation
  • reproducible preprocessing
  • preserved observed-vs-inferred identity separation

No universal minimum sample threshold is invented. Empirical power / stability analysis determines whether an experiment is worth continuing. RECOMMENDATION

17 · Later modalities

Text first. Extension points for later modalities:

  • search responses and citations
  • Arena Code / web-dev generated files, previews, DB metadata, tool events
  • images and image metadata
  • video / workflow artifacts
  • agent sessions and tool traces
  • uploads and derived artifacts

v1 builds shared observation / artifact provenance primitives plus modality-specific adapters, not a universal content framework. RECOMMENDATION

18 · Acceptance-gated implementation phases

Phases are organized around evidence, not calendar time. Each phase declares its purpose, deliverables, prerequisites, machine-checkable acceptance criteria, falsifying evidence, and continue / change / stop decision. RECOMMENDATION

Phase 0 — reproducible toolchain & fixture harness

  • Purpose: lock the build, lint, typecheck, test, package, and run paths so every later phase is reproducible.
  • Deliverables: monorepo skeleton, ESLint / Prettier, Vitest, a fixture harness that produces synthetic stream / reconnect / drift / dedup / encrypted-blob fixtures.
  • Acceptance: a single command reproduces a clean build, runs all synthetic tests, and produces a verifiable artifact hash.
  • Decision: continue when green on three consecutive runs.

Phase 1 — dedicated-browser falsification spike HYPOTHESIS TO TEST

  • Purpose: attempt to disprove Electron's suitability before building the full app.
  • Deliverables: minimal harness with two persistent partitions (Account A, Account B), email sign-in flow for both, capture + sanitization, reconcile with DOM evidence.
  • Acceptance — every item must be machine-checkable:
    • Arena email sign-in works on both accounts without cross-partition leak.
    • Cookies, local storage, session storage, cache, and service-worker state do not leak across partitions.
    • CDP attaches before / through relevant Arena navigation.
    • Fetch / XHR traffic is observable with request and response bodies where Chromium exposes them.
    • Streamed response content can be reconstructed where Arena uses streams.
    • WebSocket frames are observable if Arena uses WebSockets.
    • Worker / service-worker related traffic does not disappear silently.
    • Capture survives navigation and target changes.
    • Stopped / failed / partial Arena generations are distinguishable in archived state.
    • Late model-reveal / vote evidence is associated with the correct participant and turn.
    • Downloads and generated artifacts can be captured directly.
    • Sanitizer proves no credentials are retained in durable raw evidence.
    • Disconnecting or signing out Account A does not damage Account B.
    • Where practical, the same workflow is run against the existing extension baseline for comparison.
  • Outputs: capture manifest, event counts, source / target IDs, sanitized payload hashes, response reconstruction digest, expected-vs-observed workflow markers, gaps list.
  • Decision:
    • Continue with Electron if all acceptance items pass.
    • Switch to CEF if a critical traffic class is unobservable and CefResourceRequestHandler::GetResourceResponseFilter demonstrably solves it.
    • Stop / revisit if neither covers the requirement and a custom Chromium fork becomes necessary.

Phase 2 — sanitized observation & protocol catalog

  • Purpose: turn raw capture into a maintained, machine-readable protocol catalog.
  • Acceptance: every entry has sanitization status, capture mechanism, confidence, evidence status, drift status; secret-pattern tests find zero authorization headers / cookies / tokens in durable storage.

Phase 3 — normalized live-capture vertical slice (text mode)

  • Purpose: prove the live path end-to-end on a real conversation.
  • Acceptance: a Battle, a direct-model conversation, a side-by-side, a stopped generation, and a failed generation are all archived with correct completeness states and identity observations; cross-account collision tests pass.

Phase 4 — encrypted archive & search

  • Purpose: ship the local encrypted store with working search.
  • Acceptance: a raw hexdump of the DB file contains no recognizable Arena content; FTS5 search returns correct results within budget; crash recovery round-trips; schema migration round-trips.

Phase 5 — authenticated backfill validation & sync HYPOTHESIS TO TEST

  • Purpose: prove backfill against a real owner session. Opening one known conversation does not prove backfill viability.
  • Acceptance: operation belongs to current authenticated account; listing behavior matches UI; pagination works; conversation detail retrieval works; read-only / non-mutating behavior verified in an owner-session test; checkpoint / resume works; overlap handling works; account isolation preserved through auth expiry / challenges; completeness boundaries are explicit.

Phase 6 — full v1 text-mode coverage

  • Purpose: cover everything listed in Initial text release (battle, direct, side-by-side, completed / stopped / failed / partial, history, pagination, model labels, reveals, votes, titles, timestamps, Arena source IDs, branches, revisions, regenerations, capture state, source / provenance, owning account).
  • Acceptance: a comprehensive owner-session scenario runs end-to-end with no missing fields and no silent inferences.

Phase 7 — MCP completeness & diagnostics

  • Purpose: every GUI capability has a machine equivalent; diagnostics surfaces capture gaps and drift.
  • Acceptance: GUI-vs-MCP equivalence test passes for the full v1 surface; destructive-intent flow requires the nonce; long-running jobs expose cancel tokens.

Phase 8 — deterministic model profiles

  • Purpose: produce the first local style / behavior profiles with explicit cohort and sample counts.
  • Acceptance: profiles stratify correctly; no inferred identity overwrites observed identity.

Phase 9+ — later modalities / fingerprinting experiments

  • Purpose: extend modality adapters and, only if an empirical gate justifies it, run leakage-controlled fingerprinting experiments.

21 · Resource envelope (M3 Pro, 18 GB)

Concrete quotas and backpressure are used rather than invented numbers. Per active Arena partition renderer, the plan budgets memory at a configurable target (start small, observe, adjust); the main process budgets for capture queues, sanitizer buffers, and SQLite page cache; capture queue size is bounded with backpressure to the renderer; encrypted blob storage is size-capped per conversation with explicit overflow policy. Concurrency for sync jobs is bounded by partition count and observable load. Background sync is throttled while the owner is actively using a partition. At least two Arena sessions remain usable simultaneously; if pressure forces a reduction, lower-priority accounts degrade visibly rather than silently corrupting. RECOMMENDATION

22 · Minimum supported macOS

Minimum macOS version: macOS 14 (Sonoma).

This is a private application with no distribution constraint to support very old releases. macOS 14 provides the Keychain APIs the plan relies on, current Apple Silicon support, and is the floor where recent Electron releases ship native binaries without legacy compatibility shims. macOS 27 (Tahoe) on the development machine is the latest line; setting the minimum to macOS 14 keeps older machines eligible without artificial restriction and avoids pinning to unreleased SDKs. RECOMMENDATION

23 · Repository layout

A monorepo keeps process boundaries and module ownership explicit and is well suited to autonomous-agent maintenance:

arena-model-archive/
├─ apps/
│  └─ desktop/                 # Electron main + GUI shell (renderer for app UI only)
├─ packages/
│  ├─ browser/                 # per-account BrowserWindow/Session lifecycle, partition tokens
│  ├─ capture/                 # CDP attach, target auto-attach, Network domain observers
│  ├─ protocol/                # protocol catalog, adapter registry, drift detection
│  ├─ domain/                  # ArenaAccount, Turn, Revision, IdentityObservation (pure types)
│  ├─ storage/                 # SQLCipher migrations, FTS5, encrypted blob store
│  ├─ sync/                    # backfill adapters, sync cursor, concurrency, retry policy
│  ├─ mcp/                     # stdio MCP server; same service layer as GUI
│  ├─ analysis/                # deterministic profiles, cohort selectors, report render
│  ├─ sanitizer/               # secret-pattern scrubbing, payload hashing
│  └─ test-fixtures/           # synthetic streams, drift fixtures, encrypted-blob fixtures
├─ tools/                      # build scripts, packaging, drift diagnostics, secret scanner
├─ docs/                       # this report, owner manual

Process ownership: apps/desktop owns the Electron main / browser process and the GUI renderer; packages/browser owns per-account partition lifecycle; packages/capture owns CDP wiring and target auto-attach; packages/protocol owns adapter versions and drift signals; packages/storage owns SQLCipher migrations, FTS5, and blob crypto; packages/sync owns backfill adapters; packages/mcp owns the stdio server; packages/analysis owns deterministic profiles. RECOMMENDATION
