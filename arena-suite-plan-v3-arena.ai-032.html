Section 01

Executive architecture decision

Decision · ADR-001

Build the archive around an application-owned Electron/Chromium browser runtime, driven from TypeScript, with one persistent Chromium Session partition per Arena account and a main-process Chrome DevTools Protocol (CDP) capture coordinator attached per account. Normalised conversation state, sanitized observations and full-text search live in a single SQLCipher database whose random key is held in the macOS Keychain; large artifacts live in an encrypted blob store on disk. Every capability is exposed to an LLM through a local MCP server on stdio that calls the same application-service layer the GUI calls.

Reversal condition: if the first falsification spike shows that maintained Electron/CDP/session surfaces cannot reliably observe an architecture-critical class of Arena traffic (see §3.4), escalate to CEF and use CefResourceRequestHandler::GetResourceResponseFilter for native response-body observation. A custom Chromium fork is a last resort and is not currently justified.

The problem in one paragraph

The owner already has an extension-based recorder (arena-exporter) that misses parts of conversations and streams, depends on page-world interception, suffers from extension lifecycle weaknesses, and needs awkward companion machinery for artifacts. The fix is not a better content script. The fix is to stop observing from inside the page and start observing from a process the application controls — the browser process itself — where request/response lifecycle, target lifecycle, worker lifecycle and downloads are first-class events that exist whether or not page JavaScript cooperates.

Owning the window is not the point

Embedding a browser buys nothing by itself. What buys capture depth is the specific privileged mechanism each runtime exposes outside page JavaScript. Every candidate in §4 and §5 is judged on that, and only that, first. Electron is recommended because webContents.debugger gives a main-process CDP transport into Chromium's own network instrumentation, and session.fromPartition('persist:…') gives real per-account browser state isolation — both documented, both re-verified during this run.

Ten commitments this plan makes

  1. Dedicated browser, no extension. The application owns the runtime; no MV3 extension, no chrome.debugger extension, no native-messaging companion as the primary path.
  2. Simultaneous accounts. Two or more Arena accounts stay signed in at once in fully separate partitions with separate capture coordinators and separate sync authority.
  3. Arena's own auth UI stays authoritative. Email sign-in, codes, MFA, CAPTCHAs and redirects are handled by the owner inside the embedded browser. No cookie import from Safari/Chrome. No credential scraping into the archive.
  4. Network evidence and UI evidence are separate observations that get reconciled, never silently merged.
  5. Nothing is ever labelled "complete" by inference. Completeness is an explicit, evidence-backed state machine (§10).
  6. No invented Arena protocol. This document contains zero guessed Arena endpoints, field names or stream formats. Protocol knowledge is produced by a discovery capability (§8) and gated by owner-session acceptance tests.
  7. Sanitize before durable write. Credentials never reach the database, logs, fixtures, exports or diagnostics; the sanitizer fails closed.
  8. MCP is a first-class interface, not a bolt-on: GUI and MCP share one service layer, one permission model, one job model.
  9. Destructive actions require a two-step intent token that archived Arena content can neither mint nor satisfy.
  10. Analysis starts deterministic. No embeddings, no local ML in v1; heavyweight methods require an explicit empirical gate.

Minimum supported macOS

Recommendation macOS 14.0 (Sonoma) as the hard floor; macOS 15+ as the "supported and tested" target; develop on macOS 27, Apple Silicon only (arm64), no Intel/universal build.

  • Recent Electron majors have moved their macOS floor upward over time; targeting macOS 14 keeps the app comfortably inside the supported range of current Electron releases without pinning the project to a single OS version that would break the moment the owner upgrades or restores to a slightly older machine.
  • Everything the app needs from macOS — Keychain item storage with access control, Data Protection / FileVault-backed file permissions, code signing and notarisation-free local execution, `arm64` native module builds — has been stable since well before macOS 14. Nothing in the design requires a macOS 26/27-only API.
  • Setting the floor at 14 rather than 27 costs nothing (no API is given up) and buys robustness: the falsification spike, fixtures and CI can run on an older OS image, and a spare Apple Silicon machine can run the archive.
  • Hypothesis to test If a chosen native dependency (SQLCipher binding, Keychain binding) turns out to publish prebuilt arm64 binaries only for a newer deployment target, raise the floor to match that dependency rather than building bespoke binaries. Recorded as risk R-09 in §20.

2.3 Unknown — and deliberately left unknown

No authenticated Arena session was ever connected

Neither the previous run nor this one observed a signed-in Arena session. Therefore every statement about Arena's actual wire behaviour is Unknown and must be produced by the discovery capability rather than assumed:

  • whether conversation streaming uses SSE/EventSource, chunked fetch, WebSocket, or a mixture that differs per mode (battle / side-by-side / direct / Code);
  • the message, turn, participant, vote and reveal payload shapes and field names;
  • whether history list/detail reads exist as separable operations, how they paginate, and whether they are non-mutating;
  • whether a service worker participates in any conversation or history traffic;
  • how model reveals are delivered relative to the conversation stream;
  • how stopped / failed / partial generations are represented on the wire;
  • rate-limiting, challenge and anti-automation behaviour under owner-driven use.

Two named gates resolve these: the capture falsification spike (§19.1) and the backfill gate (§19.2). Until they pass with owner-session evidence, the corresponding product capability ships disabled or degraded, never speculative.

2.4 Also verified: the CDP body-retrieval question is not closed

Hypothesis to test Obtaining response bodies — as opposed to request/response metadata — is the single riskiest technical assumption in the recommended architecture. Network.getResponseBody is the classic mechanism and depends on Chromium still holding the body in its resource buffer; newer Chromium exposes a streaming alternative (Network.streamResourceContent paired with Network.dataReceived chunks) intended to recover bodies the buffer path can miss. During this run these method names were seen only in third-party clients and tools, not in an official protocol page (the official viewer is a client-rendered SPA and returned a redirect stub). Therefore the exact body-retrieval method set is to be confirmed against the Electron build's own protocol output in Phase 1 by issuing Schema.getDomains/protocol introspection and recording the available Network.* and Fetch.* methods into the capture manifest. The architecture does not depend on any one of them: the spike enumerates what the shipped Chromium actually offers and the capture coordinator selects a strategy from what exists.

Section 03

Why Electron — and the exact condition that reverses it

3.1 The capture-surface argument

The requirement that dominates every other consideration is: observe the owner's Arena conversations completely and provably, including streams, including traffic the page's own JavaScript may not expose, including traffic that starts before any injected script could run. Against that requirement the runtimes separate cleanly.

3.2 The seven concrete improvements over the extension baseline

  1. Attachment before navigation. The main process can create the WebContents, attach the debugger, enable domains, and only then load Arena. A content script can never precede the page it lives in. This removes the largest known class of "missed the beginning" failures.
  2. Target-lifecycle following. Target.setAutoAttach(..., waitForDebuggerOnStart=true, flatten=true) attaches to related targets — including workers — and can hold them paused until instrumentation is on. Verified for the method's documented semantics; Hypothesis to test for whether Arena creates such targets at all.
  3. Process-owned lifetime. The capture coordinator is a main-process object whose lifetime the application controls. No service-worker eviction, no MV3 idle termination, no "extension was disabled by an update".
  4. First-class downloads. 'will-download' on the account's Session gives the DownloadItem and the initiating frame, so generated artifacts are captured as archive objects rather than scraped out of a Downloads folder. Verified.
  5. Real account isolation. Separate persist: partitions give separate cookie jars, storage, cache and service-worker registrations, with per-partition erasure via clearData. Verified. An extension shares one browser profile.
  6. Independent diagnostics. Per-session netLog can be started for a bounded reproduction window to answer "did the request happen at all?" without trusting the capture pipeline that is under suspicion. Verified that the API exists; NetLog output is treated as sensitive and handled under the rules in §8.4.
  7. Reconciliation rather than substitution. Because the app owns both the network view and the DOM view, it can run them as two independent observers and flag disagreement, instead of hoping one of them was right.

3.3 Why not CEF first

CEF's response filter is genuinely deeper (§4). It is also a C++/Objective-C++ project with a bundled Chromium framework, a heavier build and debug loop, and version-management work on every Chromium bump. The owner's stated constraint is that AI coding agents perform most implementation, maintenance and diagnosis. Agent throughput on a TypeScript/Electron codebase with fast rebuilds, ordinary Node tooling and JSON-shaped protocol objects is materially higher than on a CEF native shell, and the cost of being wrong is bounded because the reversal is a swap of one package (packages/browser) behind a stable interface — see §6.3. Recommendation: pay the lower cost first, and buy the option to escalate.

3.4 The reversal condition, stated precisely

Escalate to CEF if and only if

Phase 1 demonstrates, with owner-session evidence recorded in a capture manifest, that at least one architecture-critical traffic class is not reliably observable through maintained Electron surfaces. Architecture-critical classes are:

  1. the transport that carries assistant response content for any supported Arena mode;
  2. the read that yields conversation history list or detail during backfill;
  3. the delivery of model-reveal / vote-result information;
  4. generated-artifact bytes for Code Arena outputs.

"Not reliably observable" means one of: body retrieval fails or truncates for that class in ≥1 of 20 scripted repetitions; the request never appears in any CDP session despite appearing in per-session NetLog; or capture requires a CDP method that the shipped Electron/Chromium build does not expose.

Then: run the focused CEF spike (§19.3). If GetResourceResponseFilter observes the missing class across the same 20 repetitions, switch packages/browser to CEF and keep every other package. If neither runtime can, and only then, evaluate a patched Chromium — and re-scope the product before doing so.

3.5 What "Electron wins" does not mean

  • It does not mean Arena capture works. That is §19.1's job.
  • It does not mean CDP returns bodies for streamed responses. That is explicitly Hypothesis to test (§2.4).
  • It does not mean the DOM observer can be skipped. Reveals, vote state, blind labels and error banners may exist only in rendered UI; the DOM observer is a required second evidence source (§9.4), just never the primary transport record.

Reading of the table. CEF is better at exactly one thing that matters enormously — guaranteed in-band access to response bytes, including for service-worker-originated requests — and worse at nearly everything else that determines whether this project stays maintainable. Electron is better at WebSocket frame visibility, at attachment control, and at every operational dimension. The correct move is therefore not to choose the deeper tool preemptively but to measure whether the deeper tool is needed, which is precisely what Phase 1 does.

Hybrid options considered and rejected for v1

  • Electron + a local MITM proxy with an app-trusted CA. Would give unconditional body access, but it fabricates a TLS interception layer around the owner's authenticated sessions, complicates certificate trust on the machine, risks breaking pinning/anti-abuse behaviour, and stores decrypted traffic in a second place. Rejected on security-hygiene and fragility grounds; reconsider only if both Electron and CEF fail the gate.
  • Electron + CEF side by side. Two Chromium runtimes, two isolation models, double the maintenance. Rejected.
  • Custom Chromium fork. Last resort per ADR-001; unjustified today.
Section 05

Other candidates, and why they lose

5.1 Swift + WKWebView

Attractive on paper: smallest footprint, best macOS integration, native Keychain and file APIs, no bundled browser. It loses on the one criterion that cannot be traded away.

  • Strong inference There is no supported public API to observe HTTPS response bodies for ordinary web traffic in a WKWebView. WKURLSchemeHandler is for custom schemes and throws if registered for a scheme WebKit handles internally; navigation delegates see policy decisions, not bytes.
  • The realistic workaround is injected page-world JavaScript that monkey-patches fetch/XMLHttpRequest/EventSource — which is the same class of mechanism the rejected extension uses, with the same failure modes, plus no worker coverage.
  • Strong inference Multi-account isolation would rest on separate WKWebsiteDataStore instances since WKProcessPool separation is deprecated and inert; plausible for storage, but it does not restore capture depth.
  • Net: strong host platform, weak observation platform. Rejected as primary. (Its ideas survive: the app's storage, Keychain and file handling are deliberately as "native-shaped" as an Electron app can be.)

5.2 Tauri / Wry

Verified Tauri uses the preinstalled macOS WKWebView. Everything in §5.1 applies, plus the archive would be written in Rust while the capture story stays weak. The small binary is not worth a permanent capture ceiling. Rejected.

5.3 Browser extension + native companion (the rejected baseline)

This is the owner's current arena-exporter shape and is excluded by requirement. It is documented here because it defines the bar to clear.

The extension remains useful for exactly one thing: as a comparison oracle in Phase 1 (§19.1, check 15). Running both recorders over the same scripted workflow and diffing coverage is the cheapest available proof that the new architecture is materially better rather than merely different.

5.4 Export / import only, with no embedded browser

A "paste your export file" archive would be simple, robust and entirely dependent on an Arena-provided export existing, being complete, and including the structure this project cares about (branches, participants, blind labels, votes, reveals, per-turn timing). Unknown whether any such export exists today. It also cannot capture live conversation dynamics at all. Rejected as the architecture — but retained as a feature: the sync layer defines an import adapter (§11.5) so that any official export, when it appears, becomes just another evidence source with its own provenance.

Because every other package consumes only RawObservation and RuntimeCapabilities, swapping Electron for CEF changes one package plus packaging. That is what makes the "try the cheaper runtime first" strategy safe.

6.4 Resource budget and backpressure

No benchmark numbers are invented here. The design instead makes consumption measurable and bounded on an 18 GB M3 Pro:

  • Measured, not assumed: the diagnostics package records, per sampling interval, main-process RSS, per-renderer RSS via Electron's process metrics, capture queue depth, unparsed-evidence backlog, DB file size, WAL size, blob-store size and open job count. These become the diagnostics.status payload and the basis for later tuning.
  • Hard floor on usability: at least two Arena renderers must remain interactive. Accounts beyond the active two may be kept signed-in but "parked" (window closed, session retained), reactivated on demand.
  • Configurable quotas (defaults chosen at first measurement, not now): max concurrent active renderers; max concurrent sync jobs overall and per account; max in-memory reassembly buffer per stream; max retained raw evidence bytes per observation before spilling to the blob store; max evidence backlog before capture switches to metadata-only degraded mode and raises a diagnostic.
  • Backpressure order: (1) spill bodies to blob store, (2) stop retaining raw evidence for low-value URL families, (3) pause background sync, (4) degrade to metadata-only capture with a loud state change, (5) never silently drop an observation without recording a gap.
  • Sync is background-polite: one in-flight history request per account by default, bounded concurrency across accounts, and an explicit "sync yields to live capture" rule so recording the owner's active conversation always wins.

8.4 Sanitization: fail closed

Never durably persisted

Authorization and proxy-auth headers · Cookie / Set-Cookie · CSRF tokens · passwords · one-time codes · OAuth codes and state · bearer/refresh/session tokens in bodies or URLs · signed-URL credentials and expiry signatures · any header or field on the deny list · unrelated private response fields not needed for transcript reconstruction.

Fail-closed rule: if the sanitizer cannot confidently classify a payload — unknown content type, unparsable structure, a high-entropy token pattern it cannot place — the payload is not written. Instead a quarantined observation is written with metadata only, byte counts, a hash of the redacted form, and the reason. Durable ingestion never proceeds on unsanitized bytes.

NetLog and crash logs are treated as raw-credential-bearing by default: written only to a temporary, owner-invoked diagnostic location, never into the archive, auto-expired, and excluded from exports. Diagnostic traces have a byte and time budget and a mandatory expiry.

Detection is layered: an allowlist for headers, a denylist plus entropy/format heuristics for body fields, JSON-path rules per adapter, and a final "sanitizer self-test" that runs the redacted output through a credential detector before write. Test SAN-01…SAN-06 in §19.4 make each layer falsifiable.

8.5 Drift detection

Each adapter declares the response shape family it expects. On every parse the pipeline computes a structural signature (key sets, nesting, array-of-object shapes — never values). A signature outside the adapter's known set marks the entry shape-changed, downgrades the adapter to degraded, keeps ingesting sanitized raw evidence for later reparse, and surfaces the change through diagnostics.drift. An operation that stops appearing for N supported workflows is marked disappeared. Nothing silently fails.

Live capture architecture

9.1 Attachment sequence (per account)

  1. Create/get session.fromPartition('persist:arena-<uuid>'); register the observer preload on that session; install download, permission and service-worker listeners. Verified APIs
  2. Create the BrowserWindow with that session and the hardened webPreferences, without loading a URL yet.
  3. webContents.debugger.attach(); record the negotiated protocol version. Verified API
  4. Introspect the protocol (available domains/methods) and compute RuntimeCapabilities: which body-retrieval strategies exist in this build. Persist to the capture manifest.
  5. Enable instrumentation: network domain(s) with an appropriate buffer configuration; page/lifecycle events; runtime events as needed.
  6. Target.setAutoAttach(true, waitForDebuggerOnStart=true, flatten=true), and re-apply recursively to each attached session so nested targets (iframes, workers) are also followed. For each auto-attached target: enable network instrumentation, then release the debugger pause. Verified semantics
  7. Only now loadURL() the Arena entry point. Every subsequent navigation re-checks that instrumentation survived; a lost debugger emits a detach event, which immediately marks a capture gap and triggers re-attachment. Verified that a detach event exists

9.3 Stream reassembly

Every stream gets a reassembly context keyed by (accountId, requestId|streamId) holding: ordered chunk records with byte offsets and timestamps; a duplicate filter; a gap list; a terminal marker (normal end, aborted, connection loss, target teardown); and the reassembled sanitized payload. Reassembly is deliberately transport-agnostic — SSE events, chunked JSON lines and WebSocket frames all reduce to "ordered, possibly incomplete byte/message sequences with explicit gaps". Parsers consume that abstraction, which is what makes the design survive Arena changing transports.

9.4 The DOM observer's job (and its limits)

  • It is required for evidence that may exist only in rendered UI: participant positions, blind labels, vote controls and their result state, reveal banners, error/stop messaging, "regenerate" affordances, and conversation titles as displayed.
  • It is never the primary transcript source when network evidence exists. Any content it contributes is tagged UI_ONLY_RECONSTRUCTION unless corroborated.
  • It runs in an isolated world, posts one-way, sends structured observations (not raw innerHTML dumps), and its selectors are versioned like adapters so DOM drift is detected rather than silently mis-parsed.

9.5 Recording control

Recording is per account and explicit: IDLE → RECORDING → PAUSED → RECORDING → STOPPED, with DEGRADED_METADATA_ONLY reachable from RECORDING under backpressure or sanitizer quarantine. Pausing stops durable ingestion but keeps lifecycle observation, so a gap is recorded with precise boundaries instead of a hole. Every transition is written as a capture-session event with a reason code, so a transcript can always answer "was the recorder even on?"

10.2 Reconciliation rules

  1. Observations are append-only; derived state is recomputable. Ingestion never destroys the evidence that produced current state.
  2. Strength ordering. Transport evidence > sync-replay evidence > DOM evidence > inference. A weaker later observation may add facts but may not overwrite a stronger earlier one; it creates a conflict instead.
  3. Reveals add, never rewrite. A post-vote model reveal creates a new identity observation with its own timestamp; the earlier "blind label only" state remains historically true. The transcript can be rendered either as-experienced or as-known.
  4. Idempotency. Ingestion keys are (account_id, mechanism, natural_key, content_hash). Re-delivery is a no-op; out-of-order delivery is ordered by per-account seq plus transport ordering, not by arrival time.
  5. Overlap with sync. If live capture and backfill both produce the same turn, the record keeps both source observations, prefers transport content, and records that both agreed (raising confidence) or disagreed (creating a conflict).
  6. Conflicts are first-class. A conflict row names the field, the competing values' hashes, both provenances, and a resolution state (open, auto-resolved-by-rule, owner-resolved). Conflicts are queryable over MCP; they are never auto-hidden.

11.2 The gate that must pass before strategy A ships

Backfill viability gate (owner-session evidence required)

  1. Ownership binding. Every replayed read is issued inside the owning account's browser context; a read issued in account A's context must return account A's data and must fail or return empty in an unauthenticated context. Opening one known conversation proves nothing.
  2. Listing semantics. The list operation enumerates the owner's conversations with a stable ordering key.
  3. Pagination. Cursor/offset behaviour is characterised, including behaviour at the end of the list and when new items appear mid-walk.
  4. Detail retrieval. A conversation detail read reconstructs turns/branches/participants for a conversation whose live capture is already in the archive — and matches it (this is the ground-truth comparison).
  5. Non-mutation. Before/after comparison of the account's own observable state (list ordering, titles, archived/unarchived flags, any "last viewed" style fields the UI exposes) across a bounded replay shows no change attributable to the replay. A GET verb is not evidence.
  6. Checkpoint/resume. Interrupting mid-walk and resuming from the stored cursor yields the same final set with no duplicates and no holes.
  7. Overlap handling. Re-processing an already-processed page is a no-op.
  8. Account isolation. Running A and B concurrently produces two disjoint, correctly attributed result sets.
  9. Auth expiry. Expiring the session mid-sync produces a clean EXPIRED pause with a resumable checkpoint, not a partial commit or a silent stop.
  10. Completeness boundary. The sync reports what it cannot see (e.g. deleted-server-side, inaccessible, or unsupported conversation kinds) as explicit coverage gaps.

If any of 1, 4, 5 or 9 fails, strategy A does not ship; the product falls back to C with a visibly lower completeness guarantee recorded on every record it produces.

  • Per-account lanes. One sync lane per account; accounts run concurrently (invariant I-8) within a global job limit; live capture always has priority.

Per account, complete-within-known-bounds means: the list walk reached a terminal condition defined by the adapter; every enumerated item has either a detail record or an explicit coverage gap; no page is left unprocessed; the checkpoint's high/low water keys bracket the walked range; and the account's auth state was continuously valid or every interruption is recorded as a gap. It never means "we think we have everything." conversations.search and sync.status both surface the coverage-gap list, so a query result can always be read alongside what is known to be missing.

11.5 Import adapter slot

An import path (official export, or a file produced by the owner's old extension) is modelled as strategy E: files are read, sanitized, parsed by a dedicated adapter, and ingested with provenance import plus the file's hash and an owner-supplied description. Imported records never outrank transport evidence, and are always distinguishable in queries.

Section 12

Normalised data and provenance model

12.1 Source-of-truth shape

Recommendation A hybrid: a normalised current-state model that queries fast and reads clearly, plus an append-only table of sanitized observations rich enough to re-derive current state after a parser fix. Full event sourcing of every UI tick is rejected — it would bloat an encrypted database for little benefit — but the observations that produced each fact are retained, because provenance is the product.

  • Derived-from links: every normalised row records the observation ids that support it.
  • Reprocessing: "reparse conversation X with adapter v(n+1)" replays its observations and rewrites derived rows inside one transaction, bumping a derivation_version.
  • No lossy overwrite: reparse never deletes observations; it can only change derived state (and must record the change).

12.2 Entities

12.3 Key rules

  • Internal UUIDs are the only primary keys. Arena identifiers live in source_id_binding(account_id, kind, source_id, entity_uuid) with a unique index on (account_id, kind, source_id). Cross-account collisions are structurally impossible to merge (invariant I-3).
  • Comparison structure is preserved. A battle turn is one turn with multiple participant_slots (positions A/B/…), each with its own generation chain. Nothing is flattened into alternating user/assistant messages; a flattened view is a render, produced on demand by conversations.transcript.
  • Branches and regenerations are explicit. branch captures forks (edited prompt, alternate path); generation captures revisions/regenerations within a slot, ordered, each with its own completeness assessment.
  • Timestamps: store both the Arena-reported time (when observed) and the local observation time, plus per-account monotonic sequence. They are different facts.

Section 14

Encryption, local-data realism, and deletion

14.1 Keys

  1. On first run generate a random 256-bit archive key from the OS CSPRNG. SQLCipher accepts raw binary key data specifically so that vaulted keys can be used. Verified
  2. Store it as a macOS Keychain item scoped to this application, non-synchronising (never iCloud Keychain), with an access control that requires the user to be unlocked on this device. Optionally require user presence for destructive operations.
  3. The key is never written to config files, environment variables, logs, exports, crash reports or fixtures. It exists in the main process's memory only while the DB is open.
  4. Do not use a human passphrase as the primary key even though SQLCipher supports PBKDF2 passphrase derivation: a random key removes password strength from the threat model entirely. A passphrase may be offered later solely as a wrapping mechanism for an exported backup key.
  5. Key rotation: supported via SQLCipher's rekey path plus blob-key re-wrapping, as an owner-invoked maintenance job with a pre-rotation snapshot.

14.2 Database configuration

  • SQLCipher build compiled with file-based temp stores disabled (SQLITE_TEMP_STORE=2, --enable-tempstore=yes) because "other transient files are not encrypted". Verified requirement
  • WAL journal mode is safe: WAL page data is encrypted with the database key. Verified The -wal and -shm files still live beside the DB and are handled by the same file-permission and exclusion rules.
  • Per-page HMAC-SHA512 means tampering or corruption surfaces as an error rather than silent garbage — the integrity check the archive's provenance claims depend on. Verified
  • Hypothesis to test Binding risk. The Node/Electron binding for SQLCipher is the single most fragile dependency (native module, Electron ABI, arm64 prebuilds). Phase 0 must prove: clean install on a fresh machine, rebuild against the pinned Electron, open/rekey/integrity-check a database, and run FTS5 queries. If maintenance proves painful, the documented fallback is to run SQLCipher in a small helper process with an IPC surface rather than to abandon encryption. No version numbers are asserted here; Phase 0 records the exact pinned versions in the lockfile and the capture manifest.

14.3 Blob store

blobs/<aa>/<bb>/<blob_id>.bin
  header: magic | format_version | key_id | nonce | aad_len | aad
  body:   AEAD ciphertext (per-blob content key, wrapped by the archive key)
  aad:    { blob_id, account_id, media_type, byte_len, created_at }
  • Per-blob content keys are wrapped by the archive key and stored in the DB, so deleting the row cryptographically retires the blob even before the file is unlinked.
  • AAD binds each blob to its account and identity, so a blob cannot be silently re-attributed to another account.
  • Streaming writes with chunked AEAD frames handle large artifacts without buffering whole files in memory; a truncated write fails verification on read and is reported as a corrupted-artifact diagnostic (tested by fixture SYN-BLOBCORRUPT).

14.4 Honest statement of residual exposure

What is not protected, and cannot be

  • Browser profile directories contain live Arena authentication state. Persistent sign-in requires it. Those partition directories are managed by Chromium, not by the archive's encryption, and are protected only by macOS file permissions (and FileVault, if enabled). This is materially different from copying credentials into the research archive — which this design never does — but it is a real local exposure. Mitigations: keep partitions inside the app's container, rely on FileVault, and provide per-account "wipe browser state" (clearData).
  • Plaintext exists in memory while the app runs: decrypted pages, reassembled streams, rendered content. Anyone with debugger access to the running process as the same user can read it.
  • Swap / memory compression may touch plaintext. macOS encrypts swap by default on modern systems, but this is an OS guarantee, not one this app can make.
  • Time Machine and other backups will copy the encrypted DB and blobs (fine) and may copy browser profile state (less fine). The app can set exclusion attributes on cache-like directories and document the rest; it cannot guarantee deletion from backups already taken.
  • Exports written by the owner leave the encryption boundary by definition. Exports are marked, logged in the destructive/sensitive-action audit, and default to a redacted profile; the app cannot recall them.
  • Spotlight: the archive directory is marked no-index and the DB is opaque anyway, but exported plaintext files placed elsewhere are indexable by the OS.
  • Crash logs may contain fragments of process memory. Crash reporting to any remote service is disabled; local crash logs are excluded from the archive and from exports.

14.5 Deletion

Three scopes, all local-only: one conversation, everything for one Arena account, the entire archive. Deleting locally never touches the owner's Arena cloud data; a remote delete would be a separate, explicitly-named future feature with its own confirmation.

  1. A trusted client (GUI or an MCP client the owner started) calls archive.prepare_delete_*. The service computes the exact scope and returns an intent with a nonce.

15.4 Cross-cutting semantics

  • Scope: every tool is account-aware; omitting accountIds means "all enabled accounts" only where that is unambiguous, and the response always echoes which accounts were used.
  • Pagination: opaque cursors, server-bounded limits, stable ordering keys; cursors encode the ordering key, never an offset into mutable data.
  • Idempotency: mutating/start calls accept an idempotencyKey; replaying it returns the original job rather than starting a second one.
  • Cancellation & disconnect: jobs live in the application, not in the MCP session. Client disconnect does not cancel a job; each job declares continuationPolicy. An agent that reconnects can re-discover its jobs via jobs.list with its idempotency keys.
  • Capabilities: system.capabilities reports which gates have passed (e.g. backfill.replayRead: false, reason: GATE_NOT_PASSED), so an agent degrades deliberately instead of guessing. Gated tools return NOT_IMPLEMENTED_GATED rather than pretending.
  • Untrusted content boundary: transcript text returned to an LLM is data. The server never interprets returned content as instructions, and destructive tools ignore anything not carried by an intent token.

Section 17

Later: fingerprinting experiments and additional modalities

17.1 Stylistic identity is a hypothesis, never proof

Any future experiment that attempts to associate text with a model identity must satisfy all of the following before its output is allowed anywhere near the archive's identity tables (it is stored as inferred_stylistic in a separate namespace regardless):

  • Held-out evaluation on conversations never seen during feature selection or threshold tuning.
  • Leakage-resistant splits: splitting at the conversation level at minimum; all branches, regenerations and near-duplicate generations of the same prompt stay in the same split; near-duplicate detection is part of the split procedure, not an afterthought.
  • Prompt and topic controls: compare like with like, or explicitly model prompt/topic as a covariate; report performance stratified by prompt type.
  • Negative controls: shuffled labels, same-model-different-session pairs, and different-model-same-prompt pairs must behave as expected before any positive result is believed.
  • Calibration and an unknown class: outputs are calibrated probabilities with an explicit rejection option; a classifier forced to choose among known models will confidently mislabel an unseen one.
  • Temporal validation: train on earlier periods, test on later ones, because models change under stable labels.
  • Reproducible preprocessing pinned by code version and recorded in the run.
  • Power/stability analysis decides viability — no invented minimum sample size. If bootstrap confidence intervals on held-out performance remain uninformative as data accumulates, the honest conclusion is "this archive cannot answer the question", and the experiment is stopped rather than tuned until it looks good.

19.2 Backfill gate

Implemented as an owner-session test suite that produces its own manifest, covering gate items 1–10 from §11.2. Two details deserve emphasis:

  • Ownership binding test: the same read is issued from account A's context, from account B's context, and from a fresh unauthenticated partition. Expected: A's data, B's data, and failure/empty respectively. Any other outcome halts backfill development immediately and is treated as a serious finding — not a feature.
  • Non-mutation test: snapshot the account's observable state, perform a bounded replay, snapshot again, diff. Run the same procedure with a control period of equal length and no replay, to separate replay effects from ordinary background change. Only a clean result promotes the operation's mutation field from unknown to read.

19.3 CEF spike (only if triggered)

Minimal CEF host with two request contexts and a CefResourceRequestHandler whose GetResourceResponseFilter records response bytes for the specific traffic class Electron failed on. Same manifest schema, same 20 repetitions, same digests. Decision: if CEF PASSes the failing class and matches Electron elsewhere (noting that WebSocket frame capture would still require CDP), switch packages/browser; otherwise stop and re-scope the product's completeness promise before considering Chromium patches.

Standing epistemic caveat

No authenticated Arena session was observed during the production of this document. Every statement in it about Arena's endpoints, schemas, transports, pagination, reveal delivery, worker involvement or mutation semantics is marked Unknown and is deliberately absent from the design as a concrete assumption. The architecture is built so that those facts arrive as measured data — through the capture manifest, the protocol catalog and the two owner-session gates — rather than as assumptions that would have to be unwound later.

Arena Model Archive — architecture & implementation plan. Private single-owner software; no distribution, no telemetry, no hosted backend. Recommended architecture: Electron/Chromium with per-account persist: session partitions and main-process CDP capture; reversal to CEF native response filtering is defined in §3.4.

Typeface: Departure Mono (Helena Zhang, SIL OFL), loaded as WOFF2 from the official project site with WOFF/OTF fallbacks. If the remote font cannot be loaded — offline rendering, blocked network, or a changed asset path — the document falls back to the system monospace stack (ui-monospace / SF Mono / Menlo / monospace) and remains fully legible; no substitute font source is invented.
