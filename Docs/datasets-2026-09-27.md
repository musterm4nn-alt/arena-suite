# §14 — Training/attribution datasets (2026-09-27)

Go decision: the user, 2026-09-25 ("get started on the §14 items"; order MCP, datasets,
maintenance). Scope from plan v3 §14: datasets built from the journal with v2 §12's hygiene rules
(label evidence tiers, grouping before splits, leakage audit). No automated voting or reveal, and
no use of fingerprints or model-identity features to influence voting.

## Acceptance criteria

1. **Recipe.** A versioned recipe (`arena-suite.dataset-recipe/1`) fully describes a dataset:
   - what it covers: selection, response statuses, accepted label tiers and mode classes;
   - how samples are built: the feature allowlist, and the quality and leakage policies;
   - how samples are divided: grouping and split parameters.

   Parsing is strict. Unknown keys and unsupported values are rejected, and omitted keys take
   documented defaults. The recipe is serialized canonically and identified by its SHA-256. Every
   build writes its recipe, and that recipe rebuilds the same dataset.
2. **Built from the journal, through ApplicationActions.** `DatasetService` reads one frozen view
   of the index in a single read transaction: every account's checkpoint, the decoder version, the
   projection content digest, and all the rows it uses. It then re-reads each source snapshot's
   journal record at its indexed location. The journal reader verifies the record's framing and
   stored SHA-256 record digest, and the record's sequence and envelope account must match. A
   sample whose record is missing, fails these checks, has no readable account, or names another
   account is excluded; it is never built from the index alone. The index holds no independent
   copy of the record digest, so the manifest's `record_digest` is the verified journal digest,
   recorded so that a later reader can check the journal against it.
   Nothing is written to the index or the journals.
3. **Labels are evidence tiers, never identities** (v2 §12).
   - A candidate sample is one assistant response in a conversation's latest snapshot.
   - Its label comes only from message-scoped claims: the message's own `modelId`
     (`message_model_id`), and pairwise-vote claims whose vote names that message
     (`pairwise_feedback`).
   - Conversation-level claims (`history_list` lane claims and the `detail_revealed` set) may
     corroborate or contradict a label. They are never propagated to a message.
   - Tiers:
     - `revealed_message_claim`: anonymous mode, and the conversation's revealed set contains the
       label.
     - `requested_selection`: a user-selected mode.
     - `message_claim_without_reveal`: anonymous mode with no revealed set.
   - Mode classes are recipe data. By default `battle` is anonymous, and `side-by-side` and
     `direct-battle` are user-selected. An unclassified mode yields no tier.
   - Any disagreement among the claims excludes the sample (`conflicting_claims`).
   - The default recipe accepts only `revealed_message_claim`. Every target carries
     `verified_identity: false`.
4. **Eligibility with reasons.** Every candidate is either included, or excluded with every
   reason that applies:
   - status not accepted, or lane not exposed;
   - ancestry that is unresolved or cyclic;
   - cross-lane ancestry: the recorded parent chain holds another lane's response;
   - parser warnings, or material unknown fields, for the source record;
   - source record unavailable;
   - no, conflicting or unaccepted label, or an unclassified mode;
   - origin not accepted;
   - empty response text;
   - own-label leakage.
5. **Features and leakage.**
   - Features hold only allowlisted text: `response_text` by default, with `prompt_text` and
     `reasoning_text` as opt-ins.
   - Text is kept verbatim. Several text blocks are joined by a declared blank line, and text is
     never rewritten.
   - Labels, groups, eligibility and provenance live outside `features`.
   - A recursive scan of the feature object checks two things:
     - structure: only allowlisted keys, with string or null values;
     - label terms taken from every claim in the archive: model IDs, display names, organizations
       and providers. Matching is case-insensitive and word-bounded, for terms of at least 3
       characters.
   - The sample's own model ID or display name is `own_label_term`. It is excluded by default;
     policy `flag` keeps it with a warning.
   - Its own organization or provider, or another model's terms, produce warnings only.
6. **Grouping before splitting.** Connected groups (union-find) join:
   - samples from the same conversation (lanes of one battle, branches, regenerations, later
     turns);
   - the same conversation ID in another account;
   - the same prompt family (exact match after normalization) and near-duplicate prompts;
   - exact and near-duplicate responses.

   Near-duplicates use `minhash-lsh/1`: character 5-gram shingles, 128 permutations, 32 bands,
   verified by exact Jaccard against the recipe threshold. Splits are then assigned per group
   (`group-hash/1`: seeded, integer percentages). An optional account or time holdout
   (conversation `updatedAt`) becomes the whole test split.
7. **Preview, validate, build** (v2 §12). `preview` returns the first N candidates with their
   decisions and reasons. `validate` returns the audit report. Neither writes anything. `build`
   writes a dataset folder:

   | File | Contents |
   |---|---|
   | `samples.jsonl` | `arena-suite.training/1`, included samples only |
   | `excluded.jsonl` | IDs and reasons, no text |
   | `audit.json` | the audit report |
   | `manifest.json` | recipe, source checkpoints, decoder, projection digest, per-snapshot record digests, label mapping, file hashes |
   | `recipe.json` | the recipe |
   | `run.json` | the only file with an execution time |
8. **Split audit.** The audit reports:
   - candidate, included and excluded counts, and exclusion reasons;
   - label tiers and claim sources;
   - leakage findings, context lineage and the origin distribution;
   - the number of groups and the largest group;
   - per split: samples, groups, labels, tiers, accounts and modes.

   Cross-split overlap is recounted from each sample's own fields and final split, independently
   of the grouping: conversations, the same conversation in another account, prompt families,
   exact duplicates, and near-duplicate prompt and response pairs. Near-duplicates are recounted
   by exact Jaccard over every pair of distinct included texts, so a pair the grouping's LSH
   missed is still counted. Above 2000 distinct texts the recount falls back to the grouping's
   LSH pairs, and the audit says so. `groups_across_splits` is a consistency check of the split
   assignment against the grouping. All of these are zero in a valid dataset, and `build`
   refuses to write one that is not.
9. **Deterministic and private.**
   - The same source and recipe give byte-identical files, except `run.json`.
   - Output uses sorted keys, UTF-8 and LF, with no floating-point numbers and no timestamps in
     sample lines.
   - The folder is staged, synced, and renamed into place without replacing anything. A failure
     or cancellation the builder sees leaves nothing behind. A process killed mid-build leaves an
     owner-only `.arena-suite-dataset-<uuid>.partial` folder; the next build in that folder
     removes it once it is an hour old.
   - Files are `0600` and folders `0700`.
10. **Surfaces.** Four Maintenance actions in the app: Validate Dataset, Preview Dataset, Build
    Dataset… and Build from Recipe…. There is no network access and no Arena action. Nothing here
    votes, reveals, or suggests a vote.
11. **Tests.** Cover v2 §17's dataset-leakage cases and the criteria above: denylisted names and
    IDs inside nested feature objects, the self-identification flag, overlapping battle, branch
    and prompt groups, time and account holdouts, and unverified labels excluded by default. An
    opt-in real-archive test prints counts only.

## Real archive, before building (N-015, counts only, 2026-09-27)

Measured on a scratch copy of the live index (never the live files):

- **Conversations:** 57 in total (51 with a detail snapshot, one snapshot each; 6 `agentic`
  list-only).
- **Modes:** `battle` 40 (chat 6, image 20, search 2, webdev 12), `side-by-side` 7,
  `direct-battle` 4.
- **Battles:**
  - 25 of 40 carry model claims, and exactly those 25 carry a pairwise vote. Model identity
    appears only after a vote.
  - No battle has a `history_list` model claim.
- **User-selected modes** (`side-by-side`, `direct-battle`): these carry `history_list` lane
  claims as well as `message_model_id`.
- **Claim agreement:**
  - All 148 vote-scoped claims agree with the message's own `modelId`.
  - All 217 message claims are members of the conversation's revealed set.
- **Assistant messages:** every one has exactly one parent, a user prompt. In multi-turn battles
  the next prompt's parent is one lane's response (113 lane `a`, 111 lane `b`), so the other
  lane's later responses have cross-lane ancestry.
- **Labeled `success` responses:** battle chat 8, battle image 122 (no text; image attachments
  only), battle webdev 18, `direct-battle` 5 and `side-by-side` 14.

## Output format

A build writes a new folder `Arena Suite Dataset <stamp>` (a numeric suffix if the name is taken).
JSON uses sorted keys and no floats; JSONL is one compact object per line, LF-terminated.

- **`samples.jsonl`** (`arena-suite.training/1`), one included response per line:
  - `sample_id`: a digest of account, conversation and message, stable across builds;
  - `split`: `train`, `validation` or `test`;
  - `features`: only the recipe's allowlisted keys (`response_text`, and optionally `prompt_text`,
    `reasoning_text`), each a verbatim string or null;
  - `target`: `model_id`, `evidence_tier`, `verified_identity: false`, `label_sources`,
    `corroborated_by`, and `evidence` (claim source, journal sequence as a string, and the
    feedback ID for vote claims);
  - `groups`: `split_group`, `conversation`, `turn`, `prompt_family`;
  - `eligibility`: `status: "included"` and any warnings;
  - `provenance`: account, conversation, message, lane, mode, modality, status, snapshot sequence
    (as a string), record digest, origin, decoder and recipe SHA-256.
- **`excluded.jsonl`** (`arena-suite.training-exclusion/1`): `sample_id`, `reasons`, `warnings`, the
  label it would have had, and the same provenance. It never contains text.
- **`audit.json`** (`arena-suite.dataset-audit/1`): the split audit of criterion 8, with a
  `violations` object whose values must all be zero.
- **`recipe.json`**: the canonical recipe. Building from it reproduces the dataset.
- **`manifest.json`** (`arena-suite.dataset-manifest/1`): the recipe and its SHA-256; the source
  (per-account checkpoints, decoder, projection digest, per-snapshot record digests, a scope
  statement and a description of the record check); the label table (model → the names,
  organizations and providers claimed in the selected accounts, and samples per split); counts;
  SHA-256, byte and line counts of the four content files; and a short usage contract.
- **`run.json`** (`arena-suite.dataset-run/1`): builder, app version and creation time.

## Limits

- **Small yield.** Image battles have no response text, and multi-turn battles mostly fail the
  cross-lane rule. What each lane's model actually received as history is not observable, so the
  conservative rule stays the default.
- **Labels are Arena's claims.** `verified_identity` is always false. The label-term scan only
  catches names that appear in some claim in this archive.
- **Near-duplicate grouping is probabilistic.** LSH can miss a pair above the threshold, which
  then is not grouped. The audit's exhaustive exact recount catches such a pair if it crosses
  splits, and `build` refuses. Above 2000 distinct texts the recount uses only LSH pairs.
- **Holdouts are by account or time only.** v2 §12 also names Arena harness and transport/app
  versions "where feasible"; the archive records no harness version, so this is a deliberate
  scope reduction.
- **Latest snapshot only.** Older snapshots of a conversation are not candidates (fixed recipe
  constant `snapshot_policy: latest`).
- **No MCP surface yet.** Dataset tools for the read-only MCP server are a possible follow-up. The
  boundary check forbids `build(recipe:` there; `preview` and `validate` write nothing and would be
  allowed.
- **Independent review:** `Docs/reviews/2026-10-18-datasets.md`.
