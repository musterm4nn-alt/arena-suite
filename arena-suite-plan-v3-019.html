SECTION 01

Decision

Recommended architecture

Electron (Chromium) as the dedicated capture shell. One shared Chromium engine hosts one sandboxed app-UI window plus one account-bound WebContentsView per Arena account, each pinned to its own persistent session.fromPartition("persist:arena-…"). Capture is performed by an app-owned capture controller that attaches the Chrome DevTools Protocol (CDP) to each session through Electron's documented webContents.debugger API — including Target.setAutoAttach with flattened sessions so worker and service-worker targets are captured as first-class sessions addressed by sendCommand(method, params, sessionId). A DOM observer plane in an isolated world reconciles network-derived state. Services run in the Electron main process and utilityProcess workers in TypeScript; the archive is SQLCipher-encrypted with the key held in the macOS Keychain; the primary automation surface is a local MCP server implemented with the official TypeScript SDK. This is not a browser extension and does not use one as the capture path.

1.1 Why this stack, in four sentences

Electron is the only eligible mainstream stack whose documented, maintained public API reaches all three planes this product needs: browser-process session partitioning (cookies, cache, storage, and service-worker state isolated per account in one process tree VERIFIED), target-level network observation with response bodies and streaming reconstruction via CDP (Fetch.takeResponseBodyForInterceptionAsStream, Network events, WebSocket frame events VERIFIED), and per-child-target command addressing (debugger.sendCommand(method, commandParams, sessionId) VERIFIED). It owns downloads through a first-class will-download API with app-chosen destinations VERIFIED, and it presents as a real Chromium browser, which keeps Arena's own email sign-in — including verification codes and any CAPTCHA — an ordinary, owner-driven in-window flow. Its decisive advantage over the deeper-but-heavier CEF is maintenance economics for an AI-agent-operated private app: mainstream documentation, a huge debugging community, MIT licensing, and no native build of Chromium itself. Its decisive advantage over WKWebView-based shells (native Swift, Tauri/Wry) is that WebKit on macOS offers no supported way to observe HTTPS response bodies at all VERIFIED, so those shells cannot beat the existing extension baseline without degenerating into page-world monkey-patching — exactly the failure mode this project is escaping.

1.2 What is decided now vs. discovered by probes

The stack is decided; Arena's protocol is not assumed. Nothing in this run observed Arena's authenticated traffic, so every claim about Arena endpoints, transports, payloads, or history APIs is carried as a labeled hypothesis with a defined probe (Appendix B). The architecture is built to make discovery cheap: a maintained protocol catalog (§6), dual-plane capture with reconciliation (§7), and a falsification-first spike (§12, G0) that is designed to kill the recommendation if specific, pre-declared evidence appears.

1.3 Minimum macOS version — recommendation made separately

Platform floor

Recommendation: minimum macOS 14 (Sonoma) for the app; design-verified on macOS 27. The app has no hard dependency on recent OS features, but a recent floor buys current WebKit-independent security posture, current Keychain behaviors, and the newest Chromium-supported SDKs. The binding constraint is the pinned Electron line's documented macOS support, which changes over time and must be checked at setup, not assumed from this document HYPOTHESIS (probe B-01). A floor of macOS 14 is conservative against current Electron/Chromium support windows and costs nothing for a single-owner machine already on macOS 27. If setup verification shows the pinned Electron line supports older systems, the floor still stays at 14 unless the owner chooses otherwise; lowering it buys nothing this product needs.

1.4 What "deeper than the extension" concretely means here

The existing MV3 extension (musterm4nn-alt/arena-exporter) is the yardstick, not a candidate. The new architecture must beat it on the specific wounds real use exposed: missed capture, incomplete streams, events lost across navigations, awkward downloads. The concrete deepening mechanisms are:

  • Attach before first byte. The capture controller attaches CDP to a webContents before the first navigation is allowed to start, and re-arms on every target creation, so the first request of a page load is observed — something a content-script world structurally cannot guarantee and an extension's service-worker lifecycle routinely breaks.
  • Worker and service-worker traffic is first-class. Target.setAutoAttach (flattened) makes every dedicated worker and service worker its own CDP session; Network/Fetch events from those sessions arrive with a sessionId the app explicitly addresses VERIFIED. An MV3 extension sees none of this without chrome.debugger banners and lifecycle races; this app has neither.
  • Body streaming without page-world hooks. Response bodies — including chunked and event-stream responses — are recoverable at the browser layer via Fetch interception streams and Network buffered reads VERIFIED, so capture no longer depends on patching fetch/XHR in the page, which Arena could change or defeat at any time.
  • App-owned downloads. Generated artifacts and exports flow through Electron's download pipeline to app-chosen paths VERIFIED — no extension download indirection or companion folder-watcher.
  • Capture that outlives page lifecycle. The capture controller runs in the privileged main/utility process, not in a suspensible extension service worker; pause/cancel/stop per account is real process state, not a heuristic.

One honest caveat, carried forward as a design constraint: owning the window is not the same as owning the protocol. Electron gives privileged vantage points; it does not guarantee any particular Arena payload is observable or parseable. That is what the protocol catalog and the falsification-first spike are for (§6, §12-G0).

SECTION 03

Product, constraints, and boundaries

3.1 The product in one paragraph

The owner uses arena.ai — a public platform for comparing frontier AI models through chat, side-by-side battle, voting, and code-oriented surfaces such as Arena Code VERIFIED (public positioning) — exactly as they normally would. While they do, a permanently private, single-user macOS application records accurate local transcripts of their own conversations, across multiple Arena accounts signed in and active simultaneously, and turns those recordings into an offline-searchable, provenance-preserving archive. The archive then supports local research into observed models' behavior, prose, formatting, and possible stylistic similarities. There is no distribution, no hosted backend, no telemetry, no App Store, and no second user — ever. The GUI is minimal and diagnostics-first; a local MCP server is the primary interface, and every GUI capability must also exist as an LLM-callable tool.

3.3 Trust boundaries and the three mechanism distinctions

The plan evaluates methods strictly on technical feasibility, security, robustness, and maintainability. To keep the mechanism space honest, three distinct things that are often blurred together are named and treated differently throughout:

  1. Authenticated read access. Sending requests to Arena endpoints — documented or not — with the session credentials that Arena issued to the app's own account-scoped browser session. Using an internal or undocumented endpoint with the correct owner session is not, by itself, an access-control bypass; the design still treats such endpoints as unverified until their read behavior is demonstrated in the owner-session context (§8.2).
  2. Automation compatibility. Presenting as a normal browser — because it is one — and aligning presentation details (for example, the documented session.setUserAgent to match the underlying Chrome rather than advertise an Electron-flavored UA) so that ordinary owner-driven flows, including any CAPTCHA or email verification, complete without automation-shaped failures. This is compatibility work, not evasion of an access control: the human owner performs the sensitive steps.
  3. Access-control workarounds. Any technique that works around a client-side restriction or other access control to reach data the owner's own accounts can see. The design does not need one for v1: its planned capture and backfill methods (CDP observation of owner traffic; replay of owner-visible reads; UI traversal) all operate inside the owner session's ordinary authority. If a workaround ever becomes necessary, §8.2's evidence checklist is the gate that establishes what the actual control is and what the mechanism does — "bypass" is not used as a synonym for "internal API".

3.4 Standing behavioral boundaries

  • Scope binding. Access only data associated with currently signed-in accounts; bind every operation to the correct account/session scope. A conversation URL or opaque ID never establishes ownership by itself.
  • No credential transplantation. Never import cookies or tokens from other browsers or apps; never guess or steal credentials; never enumerate unrelated private infrastructure.
  • Credential custody. Arena controls authentication. Native sync code may transiently reuse credentials issued to the app's own Arena session (including token refresh as the browser performs it) but must never persist copies to disk, exports, fixtures, or logs. Browser-managed session persistence inside the partition is treated separately and disclosed (§5.5).
  • Visible automation state. Recording and automation always have visible per-account and global state with meaningful pause, cancel, and stop semantics (§5.3, §7.5); pausing capture is never silently equivalent to completing it.
  • Fail-scoped degradation. Sign-out, session-authority loss, drift, challenges, rate limiting, or suspected unintended mutation degrade only the affected account; one account's failure must never invalidate, corrupt, or silently rebind another's records (§5.3, §8.5).

SECTION 04

Stack selection

4.1 Owning the window vs. owning the vantage point

Every dedicated-browser candidate is evaluated on which observation planes its documented APIs actually reach. Four planes matter:

  • P0 — browser process / network layer. Sees requests and response bodies as the network service handles them, for every target, before page code can interfere.
  • P1 — target/session instrumentation. Sees per-target events (navigation, lifecycle, console, network) and can drive the target; in Chromium's design this is CDP with attachable child sessions for workers and service workers.
  • P2 — page world. JavaScript injected alongside page code (content scripts, user scripts, monkey-patched fetch/XHR). Late, spoofable, and blind to anything the page does not route through patched surfaces — this is the extension baseline's home turf.
  • P3 — OS / app process. File system, Keychain, process metrics; the archive's own plane.

The brief's warning is taken as a design axiom: an embedded shell that reaches only P2 is not deeper than the extension baseline merely because it embeds the page. The comparison below is therefore about documented reach, not embedding per se.

4.3 Native Swift + WKWebView — rejected on capture depth

WKWebView is excellent for embedding content you control and unusable for observing content you don't. There is no supported API to read HTTPS response bodies of web content: NSURLProtocol registration does not apply to WKWebView VERIFIED, and WKURLSchemeHandler handles custom schemes only — it cannot intercept http/https VERIFIED. Out-of-process system proxies are not reliably honored by WKWebView for app-embedded traffic VERIFIED. WKNavigationDelegate exposes request/response metadata, WKContentRuleList is declarative blocking, and neither sees bytes. Service-worker support in WKWebView is gated behind app-bound-domain policies with no observation surface. The only remaining capture mechanism is page-world injection (user scripts), which lands the design back in P2 — strictly no deeper than the extension baseline it must beat, with a smaller tooling ecosystem. WKWebView also cannot deliver CDP-style per-child-target sessions at all. Verdict: best resource profile, disqualifying capture ceiling.

4.4 Tauri/Wry — rejected by inheritance

On macOS, Tauri's webview layer (Wry) is the system WKWebView VERIFIED, so everything in §4.3 applies unchanged. Tauri's Rust core is a genuinely pleasant services layer, but it adds no vantage point below the webview: there is no Rust-side API that reveals WKWebView's network bytes. Choosing Tauri would therefore couple the project to a capture mechanism (page-world injection) that the project's own reason for existing rejects. Verdict: rejected for the same reason as §4.3, plus double toolchain risk (Rust + WebKit quirks) for no capture gain.

4.5 Chromium Embedded Framework — technically strongest capture, maintenance-heavy

CEF is a real contender and is treated with respect rather than as a foil. Its browser-process handlers see the world at P0: CefRequestHandler/CefResourceRequestHandler expose request interception, and CefResponseFilter — CEF's documented response-content filtering interface VERIFIED — receives response body chunks as they arrive, including streaming bodies, without any page-world involvement. CefDownloadHandler owns downloads. Service-worker-driven requests flow through the same network service, so filters observe them at the byte level INFERENCE (mechanism-consistent; per-worker target metadata would still be app work). On raw capture depth CEF is equal or superior to Electron's CDP plane.

The costs are operational, and for this product they are decisive. CEF is consumed as large binary distributions tracking Chromium releases, with breaking API churn at each Chromium cadence; integrating it on macOS means an ObjC++ application shell with Chromium's NSApplication integration requirements; documentation beyond headers and forum threads is thin; and none of it composes with mainstream AI-agent operability the way Electron's does. A single-owner, agent-maintained app that must survive years of drift cannot afford a framework whose upgrade path is "re-integrate against a new Chromium distribution." CEF is therefore retained as the pre-declared escalation path (§4.12), not the primary.

4.7 Extension-based architectures — ineligible by requirement, useful as baseline

A Manifest V3 recorder is structurally confined to P2 plus a debugging API it may not use here: content scripts race page loads; chrome.debugger attaches with user-visible banners and lifecycle contention with other DevTools consumers; the extension service worker that hosts capture logic suspends under load; and downloads must traverse browser UI indirection or a companion watcher. The existing arena-exporter extension demonstrated exactly these limits in production use — incomplete capture, missing stream portions, lifecycle-dependent interception, awkward artifact handling — which is why the brief fixes a dedicated shell as a requirement. For completeness: bolting chrome.debugger and a native-messaging host onto that extension would indeed deepen it, and that is a different project; it remains ineligible here and serves only as the G2 measurement baseline. Note also the honest boundary the brief demands: Electron's CDP plane is not page-world monkey-patching — it observes at the target/session layer — but the DOM reconciliation plane (§7.4) is page-adjacent injection, and it is deliberately scoped to corroboration, never to primary content capture.

4.8 Explicit export/import without an embedded browser — rejected, then absorbed

An app that only imports Arena's own export files (if any exist — unverified HYPOTHESIS) would be robust and trivially safe, and captures nothing: no live recording, no streams, no reveal events, no completeness states, no multi-account simultaneity of capture. It fails the product. The idea survives as an adapter slot: if Arena offers a privacy-respecting export, a first-class import adapter will ingest it through the same sanitization and provenance pipeline as any other source (§8.1).

4.9 Custom Chromium fork — last-resort escalation only

A fork is justified only if a concrete required observation is impossible through maintained public embedding surfaces after both Electron and CEF paths have been exhausted — e.g., Arena moves conversation data into a transport Chromium instruments nowhere. The fork inherits Chromium's build complexity permanently and is therefore gated behind G2 evidence, an explicit owner decision, and a written statement of the unobservable capability. No current evidence points there.

SECTION 05

Accounts, partitions, and session model

5.1 Partition model — isolation as a documented primitive

Each Arena account is bound 1:1 to a persistent Electron session created with session.fromPartition("persist:arena-<accountId>") VERIFIED. Chromium guarantees that distinct persistent partitions maintain separate cookies, HTTP cache, local/session storage, IndexedDB, service-worker registrations and their caches, HSTS state, and permission state — in one process tree, on one shared engine. The app treats this as the isolation substrate and then tests it rather than trusting it: the G0 canary suite (§12) plants distinct markers (cookie, localStorage, SW registration, cache entry) in each partition and asserts zero cross-talk through both API inspection and CDP observation. Ownership of the account is not inferred from the partition — the account registry (below) is the authority; the partition is only its browser-state home.

5.2 What isolation covers — and what it cannot

  • Covered by partitions: all per-origin browser state listed above; capture context (each account has its own CDP attachment and evidence stream); sync state (per-account checkpoints, §8.4); destructive-action scope (every job and token carries account_id).
  • Not isolated, by design and disclosed: the browser-process code itself, the GPU process, the OS clock, and the machine's network identity (single IP for all accounts — inherent, since Arena sees one household/machine). The app makes no effort to disguise that the accounts share a machine, because that would be an anti-detection commitment the owner has not asked for; §3.3's compatibility posture (§5.4) is the extent of it.
  • Cross-account contamination controls: no record may reference two accounts; reconcilers assert single-account scope on every write; a source ID observed under two accounts produces a conflict record (§9.3) and never a merge; exports carry per-record account provenance (§9.6).

5.3 Lifecycle state machine

5.4 Sign-in and re-authentication — owner-driven by design

Sign-in happens inside the app, in the account's own partition, using Arena's ordinary email-based flow HYPOTHESIS for flow specifics (probe B-03). The app's role is hosting, not impersonation: the owner types their email, receives and enters verification codes, solves any CAPTCHA (reCAPTCHA Enterprise is referenced by Arena's public page bootstrap VERIFIED — expected to appear where Arena chooses), and completes any redirects. Popups and OAuth-style redirects are re-hosted in the same partition via the documented setWindowOpenHandler path so they share the account's cookie jar; third-party identity providers are not required by the brief and are supported only to the extent they keep working untouched. One disclosed compatibility measure beyond stock behavior: the session's user agent may be aligned to the underlying Chrome via setUserAgent VERIFIED so Arena does not treat the shell as a non-browser client — a presentation alignment, with the human completing all authenticated actions. Session cookies then persist inside the encrypted-at-rest container as Chromium manages them (§5.5), and re-auth events pause that account only (Figure 5-1).

5.5 Credential custody and browser-state persistence

The app's own services never persist Arena credentials: no cookie jars in our database, no tokens in logs or exports, no refresh-token copies on disk. What does persist is Chromium's own per-partition browser state — session cookies, and any long-lived cookies Arena sets — managed and (on macOS) encrypted by Chromium's platform integration INFERENCE (verify behavior on setup, probe B-02). This split is deliberate: the browser must keep its session to make simultaneous accounts usable day to day; our services treat those credentials as environment, not data. The partition directories live in the app container with 0700 permissions, excluded from Spotlight; Time Machine exposure is disclosed rather than promised away (§9.7). A "lock at quit" option (clear cookies on app exit) exists for owners who prefer session-less idle state, at the cost of daily re-auth for every account — off by default, documented, their choice.

5.6 Resource budget and measurement (18 GB shared RAM)

Resource use is measured, not asserted: no numbers are claimed here because none were observed. The plan instead installs the measurement harness in G0 and binds policy to it:

  • Harness: per-process metrics via Electron's app-metrics APIs (process-level RSS/CPU for browser, GPU, renderers, utilities), polled into a diagnostics ring buffer; exposed through diagnostics.metrics MCP tool and the GUI.
  • Quotas (policy, tunable): one shared engine (never per-account engines); per-partition disk-cache cap; HTTP cache disabled by default for capture partitions (leakage reduction, §9.7) with the network-cost trade-off documented; maximum simultaneously-active accounts default 3 (owner-adjustable); background tab throttling accepted.
  • Hibernation: an inactive account's WebContentsView is destroyed while its partition persists on disk; wake is on focus or schedule. Hibernated accounts are visible but not capturing — the GUI and MCP state says so explicitly, so completeness accounting stays honest.
  • Budget gate (G0): with two active accounts under normal heavy use, the harness reports the resident footprint; the owner sets the soft budget (proposed default: 10 GB app-wide including engine) and hibernation policy triggers against measured numbers, with the reversal path of Table 4-1 if the budget cannot be met.

Discovery and the protocol catalog

6.1 Discovery as a maintained capability, not a one-time hack

The first engineering objective is discovering what Arena's first-party traffic actually looks like across the owner's real workflows — and turning that into state the app maintains: a machine-readable protocol catalog that capture adapters bind to, diagnostics report against, and AI maintenance agents query when something drifts. Nothing about Arena's protocol is assumed: every operation enters the catalog through observation, starts as unknown, and is promoted only by classified evidence.

6.3 The classification pipeline

  1. Observe. All first-party traffic encountered in supported workflows is observed at the CDP plane (§7) with per-account binding. "All" means inventory coverage of every request class — conversation, auth, account, assets, analytics/config, mutations, and explicitly unrelated — not retention of everything: broad discovery must not become a raw credential-dumping console.
  2. Fingerprint. Each request/response is reduced to an operation identity: method + normalized route pattern + transport family (+ response shape hash for JSON). Identical operations across accounts collapse into one catalog entry; per-account observations remain separately countable.
  3. Classify. Heuristics (route shape, content-type, direction, whether the operation appears during conversation flows vs. sign-in vs. asset loads) propose a class; curation (owner or maintenance agent via MCP) promotes to curated. Unknowns stay unknown and visible — an unclassified operation is never dropped silently; it is counted as coverage debt.
  4. Bind sanitized evidence. A small, TTL-bounded, sanitized evidence envelope per operation class (§6.5) — enough to diagnose drift and support reparsing; never a persistent raw dump.
  5. Promote to adapter. When a conversation-relevant operation is understood well enough, an adapter version binds to it: parse rules, stream-reconstruction strategy, completeness semantics. Adapter versions are immutable; drift creates a new version decision, it never mutates history.

6.4 Coverage metering — inventory vs. retention

Coverage is a first-class report: per workflow (battle, direct, side-by-side, history browsing, voting), the catalog reports counts and byte-fractions of traffic by class, with unclassified as an explicit alarm row. The default diagnostic question — "what did we not understand?" — is answerable in one query (diagnostics.getCoverage, §10.6). Retention, by contrast, is deliberately narrow: raw packets are never stored; only sanitized envelopes for classified operations (plus quarantined parse failures) exist, under TTL.

6.5 Sanitization at the discovery boundary

Everything crossing from the capture plane into persistence passes the sanitizer (§9.7) with these discovery-specific rules: request/response headers are allowlisted (drop Cookie, Authorization, Set-Cookie, CSRF headers, and any header pattern-matched as credential-bearing); URLs are rewritten to route patterns with query parameters stripped unless individually allowlisted, so signed URLs never persist; bodies are truncated to evidence size caps with structure preserved; payloads that trip the secret scanner (JWTs, bearer tokens, key-shaped strings) are redacted in place with a marker; parser errors quarantine the sanitized remainder rather than persisting an unsanitized blob. Failure paths inherit this: a crashing parser produces a redacted diagnostic record, never a payload dump.

6.6 Drift as a routine event

Schema-shape hashes, route presence, and transport families are tracked over time. Drift signals — a shape-hash change on a bound operation, an operation disappearing, a new operation family appearing mid-conversation — raise the affected adapter's state to paused-drift for that operation only, keep capture observing (inventory continues), and surface a recovery task to GUI and MCP with the sanitized before/after evidence attached. Capture degrades explicitly and locally; it never silently mis-parses.

SECTION 07

Live capture

7.1 Design goal

Live capture must produce, for every conversation the owner actually has, a structured transcript with honest completeness accounting — while the owner uses Arena normally, across simultaneous accounts, with no interruption to their workflow. The design separates observation (network truth), corroboration (DOM evidence), and assertion (normalized conversation state), because conflating them is how archives end up silently wrong.

7.2 Plane A — CDP session capture (primary)

The capture controller, running in a utilityProcess, drives one CDP attachment per account session through Electron's documented debugger API VERIFIED:

  • Attach gating. The controller attaches and enables Network (+ Page, Runtime, Target) before the first navigation is permitted, and re-arms on every Target.targetCreated — including prerender and iframe targets. No page script runs before capture is armed; the app enforces this by ordering, not by hope. Residual early-attach risk (targets created between process spawn and attach) is measured in G0 as the "attachment gap" metric; any gap window is recorded as an explicit capture-gap marker, never silently filled.
  • Bodies, including streams. Conversation responses are recovered by transport-appropriate means: Fetch.enable with patterns scoped from the catalog, pass-through continuation to avoid latency, and takeResponseBodyForInterceptionAsStream for streaming bodies; Network.getResponseBody for buffered completions. WebSocket frames arrive as Network.webSocketFrame* events. Which mechanism applies to which Arena operation is a discovery output, not an assumption — the four transport families (SSE, chunked, WebSocket, plain JSON) each have a probe (Appendix B) and an adapter strategy.
  • Workers and service workers as first-class targets. Target.setAutoAttach (flattened) yields child sessions for dedicated workers and service workers; their network events arrive with a sessionId, and commands address them explicitly VERIFIED. Child-session topology (which worker handled which request) is part of the evidence envelope.
  • Capture-partition hygiene. Network.setCacheDisabled on capture sessions (leakage reduction, §5.6); request metadata additionally available from webRequest for cheap correlation — deliberately not used for bodies, which it does not expose VERIFIED.

7.3 Streaming reconstruction

Regardless of transport, the controller reassembles a canonical byte stream per request: ordered chunks keyed by (sessionId, requestId), with offsets and arrival timestamps preserved; WebSocket conversations keyed by frame sequence with direction flags; EventSource framed by event boundaries as received. Reconnects and retries are new stream instances linked to the same operation fingerprint; deduplication happens at the evidence layer by content hash of contiguous segments, never by silently overwriting. Late events after a response nominally ends (e.g., a late reveal pushed over the same channel) append to the stream with their own timestamps — the transcript model treats them as identity observations, not as rewrites of content (§7.6).

7.4 Plane B — DOM corroboration (reconciliation only)

An isolated-world observer (injected through the debugger's isolated-world evaluation, so it shares no JS realm with Arena's page code) watches the transcript surface, mode indicators (battle / direct / side-by-side), voting and model-reveal UI, stop buttons, and history navigation. Its output is a stream of assertions about rendered state — a message node exists with this text fingerprint at this time; the stop control was activated at this time; the reveal banner changed at this time. It never contributes primary content: DOM-derived text is stored only as fingerprint-and-excerpt evidence for reconciliation, and a transcript whose content exists only in DOM evidence is marked PARTIAL_OBSERVER, not complete. This is the honest boundary the brief requires the design to state: the CDP plane is browser-layer observation; the DOM plane is page-adjacent injection, scoped to corroboration and gap detection.

7.5 Conversation model and reconciliation

The reconciler merges both planes into normalized conversation state: turns, branches, participant positions, revisions/regenerations, titles, timestamps, and identity observations — keyed to (account_id, conversation_ref) with the account scope part of the record identity. Reconciliation rules:

  • Turn/branch boundaries are inferred from network operation structure (request/response pairing, stream starts) and cross-checked against DOM turn markers; disagreement raises a gap flag, not a guess.
  • Completeness states are explicit and never self-promote:
    StateMeaning
    COMPLETEStream terminations observed on the network plane for all participants' content; DOM corroboration agrees (or is absent without contradiction).
    STOPPEDOwner or platform stopped generation; termination evidence is a stop event, not a normal end-of-stream. Distinguished from COMPLETE forever — a stopped response is never presented as complete.
    FAILED_TRANSPORTNetwork plane observed failure (disconnect, error status, unrecoverable stream). The partial content captured is retained with a failure marker.
    PARTIAL_TRANSPORT / PARTIAL_OBSERVERData was missed — by the transport (never delivered) or by us (gap window, observer failure). Which plane missed it is part of the state; inferred content never fills the hole.
    RECONCILINGEvidence exists but boundaries are not yet resolved; a flagged work item, not a quiet background guess.
  • Navigation and target changes produce gap markers spanning the unobserved window; on return to a conversation, reconciliation compares captured evidence against a fresh owner-visible read (§8.2) to resolve gaps where possible — with the resolution's provenance marked as post-hoc, not live.
  • Late identity evidence (model reveals after votes, label changes) appends identity observations with their own timestamps and turn ranges; earlier states remain queryable (§9.4).
  • Account binding is structural: the evidence stream of partition A cannot write rows of account B — enforced by the reconciler's per-account instances, not by convention.

7.6 Operational controls and failure behavior

Capture state is per-account and global, always visible, with defined semantics: pause (evidence plane keeps observing network metadata but stops body retention; in-flight streams finish or fail on their own — nothing is half-captured into a "paused" record), stop (evidence plane disengages; open streams are finalized as PARTIAL_* with explicit stop markers), cancel (in-flight reconciliation work is dropped; already-persisted evidence remains with its markers). The documented Electron constraint that invoking DevTools detaches the debugger VERIFIED is handled operationally: the diagnostics GUI uses the app's own evidence views, not page DevTools; if DevTools is nonetheless opened on an Arena view, the account's capture state drops to DEGRADED with reason debugger-preempted and re-arms automatically on detach — a visible, logged event, not silent data loss. Observer crash recovery: the capture controller is supervised; on restart it re-arms from current target topology and writes a gap marker for the interruption window.

8.2 "Verified read" — the gate before replay is relied upon

An HTTP method or endpoint name alone never proves read semantics. Before the sync engine replays any operation, the catalog must show, in the owner-session context: (1) repeatable success (multiple 200-class completions with expected schema shape); (2) stable, observable pagination structure (cursor or page token behavior under repeated walks); (3) no mutation evidence — no state change in subsequent listings, no write-shaped side effects in the catalog's mutation ledger; (4) per-account scoping confirmed (the operation returns that account's data and only that); (5) the operation's shape hash stable across sessions. Until then the method's status stays read_or_mutation: unknown and backfill uses traversal. This checklist is the design's answer to "what establishes read behavior" — and it is deliberately an empirical gate, not a naming convention.

8.3 Sync jobs — model and semantics

Sync is a job system, not a background vibe. Sync now targets one account or a selected set; optional per-account automatic sync (owner-enabled, default off) reuses the same job machinery on a schedule. Each job:

  • Scope: one account_id; concurrent jobs for different accounts are independent by construction (separate partitions, sessions, controllers); correctness never depends on serializing accounts, but the scheduler caps concurrency against the resource budget (§5.6).
  • Checkpoints: per-account, per-listing cursor state with observed page fingerprints, so re-runs and interruptions are resumable and idempotent; checkpoint writes are transactional with the records they cover.
  • Bounded retries: exponential backoff with ceilings and jitter; rate-limit responses degrade pacing for that account only; a challenge or redirect interrupts the job and surfaces to the owner rather than attempting quiet evasion.
  • Overlap handling: re-walked pages deduplicate inside the correct account scope using the §9.3 reconciliation keys; pagination instability (shifting cursors, reordered entries) is detected by fingerprint comparison and handled by re-walking forward from the last stable fingerprint — never by deleting existing records that look "moved".
  • Live-capture interplay: sync writes through the same reconciler with capture-session mode sync; a conversation being live-captured while sync reaches it is merged by turn-level provenance (network evidence from both sessions), and any disagreement is a flagged conflict, not a last-write-wins.
  • Completion semantics: a job ends as complete, complete_with_gaps, degraded, or failed — and the gap report (§8.6) is part of the result, not an afterthought.

8.4 Per-account isolation of sync state

Checkpoints, cursors, dedup markers, and coverage ledgers are keyed by account_id first. Cross-account source-ID collisions — the same conversation opaque ID observed under two accounts — are recorded as explicit conflicts (§9.3); ambiguous ownership quarantines the records; nothing merges because IDs, titles, text, or timestamps look similar. A failed or signed-out account leaves every other account's sync state untouched; the scheduler marks the failed account's jobs degraded with reason and keeps scheduling the rest.

8.6 What "synchronized" means — and the honest failure story

A account is synchronized to the extent that a coverage ledger can prove: which listing ranges were walked with which adapter versions, which conversation records were reconciled from which evidence, and which gaps remain (unwalkable ranges, degraded adapters, conversations the UI never surfaced). The ledger is queryable (diagnostics.getSyncCoverage) and honest by construction. If no reliable listing endpoint or stable pagination can be verified, the standing answer is: live capture continues; backfill covers what traversal can reach; the ledger states plainly that full historical coverage is unknown — because one successfully opened known conversation never proved full coverage, and this design does not pretend it does. Feasibility without a listing endpoint is therefore "bounded, honest, incremental" — not "impossible", and not "complete".

9.1 Source-of-truth design — proportionate hybrid

Full event sourcing is not necessary and is not used. The archive is a three-part hybrid, sized to a private single-user app:

  • Normalized core — the queryable substance: accounts, conversations, branches, turns, revisions, participants, identity observations, sync ledgers, analysis runs. This is what search and transcripts read.
  • Append-only observations — sanitized evidence envelopes and per-operation coverage rows (§6), the ground truth the core was derived from. Bounded by TTL policy; expiry is configurable and the default retains enough to reparse under drift.
  • Encrypted artifact store — content-addressed large objects (attachments, generated artifacts, future modalities), envelope-encrypted, referenced by the core. Deduplicated by content hash within account scope.

Recompute policy: normalized fields derived from retained evidence can be recomputed after an adapter change (that is why evidence outlives adapter versions); after evidence TTL expiry, provenance rows persist while reparse capability ends — a stated trade-off, not a hidden loss.

9.3 Reconciliation keys and conflicts

Within one account, records deduplicate on stable external references when Arena provides them (external_ref); otherwise on a conversation fingerprint (observed title + first-turn content hash + observed time window), applied only within that account. Identical text is never sufficient evidence of duplication — two conversations can legitimately contain the same prompt — so content hashing participates only as part of the composite fingerprint, and near-identical conversations remain distinct records with a similar_to annotation for the owner's attention. Cross-account: no key may merge; collisions become conflicts rows with both provenances attached, resolved only by explicit owner action. Ambiguous ownership (evidence that could belong to either account) quarantines rather than guesses.

9.4 Model identity — observation, never equation

Participant position, blind label ("Model A"), displayed provider/model name, marketing name, route name, and exact model build are different facts and are stored as separate identity observations with scope (turn ranges), mechanism, and time. The identity view is a projection: it resolves the best currently-supported identity for a participant while preserving every earlier observation — a post-vote reveal appends a reveal observation; it does not rewrite history or retroactively attribute the blind label beyond its supported scope. Owner annotations are first-class observations (mechanism: owner). Conflicts (e.g., a reveal contradicting a displayed name) remain visible in the projection as unresolved tension, not silently resolved. Downstream analysis cohorts (§11) may only group by observed or revealed identity evidence, with uncertainty carried alongside.

9.5 Storage and encryption

  • Archive key: 32 random bytes, generated once at first run from the platform CSPRNG, never written to disk in plaintext, never logged, never exported. Custody: wrapped via Electron safeStorage (Keychain-backed on macOS) and stored only as the wrapped blob in the app container; the unwrapped key exists only in process memory while the app runs. Keychain item access follows the app's own code signature; a lost Keychain (profile reset) means a lost archive — documented, with restore guidance (§9.8).
  • Database: SQLCipher with PRAGMA key from the archive key; per-page AES-256 as documented VERIFIED. WAL and SHM files are SQLCipher-encrypted content (still protected, still excluded from indexing). FTS5 index lives inside the encrypted DB — there is no separate plaintext index.
  • Artifacts: per-file random DEK; content encrypted AES-256-GCM; DEK wrapped with the archive key; per-file header rows in the DB. Content addressing (BLAKE3) gives integrity and within-account dedup.
  • Search: FTS5 across transcripts with account-scope columns as filter dimensions, so cross-account search is possible while per-record account provenance stays mandatory in results and exports.

9.6 Provenance model

Every normalized field that matters analytically (content, identity, completeness, timestamps) carries provenance: which account/capture session produced the evidence, what was observed, when, through which mechanism and adapter version, and with what uncertainty. Retention: sanitized evidence 30 days by default (configurable), provenance rows forever, artifacts until deleted. Exports — the versioned machine-readable export (JSONL with per-record provenance and completeness) and the human-readable export — carry account scope per record and support one-account, selected-account, or all-account selections without collapsing boundaries; cross-account exports label every record's account rather than merging narratives.

9.8 Deletion semantics

Three scopes, one pipeline: conversation (logical delete → tombstone → evidence/artifact purge → FTS rebuild), account (all of the above for every record in scope, plus partition browser-state destruction, sync ledgers, and conflict rows referencing the account — with a 7-day staged grace window during which restoration is possible), whole archive (staged 72h grace, then executed as key destruction plus file erasure — crypto-shredding means even surviving ciphertext becomes unrecoverable). Sync interplay: tombstones make re-import impossible within scope — a backfill that re-walks a deleted conversation's listing sees the tombstone and skips; dedup markers are scoped so a deleted-then-recreated conversation can be re-captured as a new record rather than resurrecting the old one. Residual copies in prior exports and system backups are disclosed, not promised (Table 9-1). Destructive actions of account/archive scope additionally require the trusted-channel guard (§10.7).

9.9 Containment of Arena-controlled content

Arena's pages run in sandboxed renderers with no Node integration, no custom scheme handlers they can reach, no access to the archive key (which exists only in main-process memory), and no route to the MCP server or the UDS socket (which only the adapter process and app hold). Permission requests from content are denied by default through setPermissionRequestHandler VERIFIED. During errors, sign-outs, and concurrent use, the same rules hold by construction: one account's renderer process cannot read another's partition (Chromium isolation), cannot mint capture state, and cannot speak to services except through the same public interface the GUI uses — which carries no deletion authority without the §10.7 guard.

SECTION 10

Full LLM operability — the MCP contract

10.1 Surface choice

The primary automation surface is a local MCP server implemented with the official TypeScript SDK over stdio VERIFIED (SDK + transport documented; tools discovery via tools/list with readOnly/destructive annotations). stdio is chosen because MCP clients already manage that lifecycle well: the client spawns arena-archive-mcp, which authenticates to the running app over a 0700 Unix-domain socket using a per-run token the app generates. This decouples client lifetimes from app lifetimes (a client can query the archive while the app is closed for the parts that do not need the browser) and keeps the trust boundary clean: the socket accepts local connections only, from the owner's user, with the token.

10.2 Discovery and diagnosis

tools/list returns the full inventory with annotations (readOnlyHint, destructiveHint) and per-tool scope requirements in their schemas, so an LLM can tell before calling whether an operation needs an account scope, a running app, or a confirmation. Unavailable operations do not disappear: tools whose backing capability is degraded (e.g., sync while the app is closed) respond with structured errors naming the reason and the recovery path (§10.4), so diagnosis is a tool call, not a guessing game. Resources expose read-only views (catalog, coverage reports, audit log) for clients that prefer them.

SECTION 11

Local analysis and later modalities

11.1 Cohorts are identity-evidence-gated

Every analysis groups conversations only by observed or revealed identity evidence, never by participant position, blind label, or hunch. A cohort definition names its evidence rule (e.g., "turns whose participants carry a reveal observation of mechanism=reveal") and its uncertainty posture; blind-unknown participants form their own cohort and are eligible only for distribution-level questions, never for identity comparisons. Inferred identity — the output of later similarity experiments — is kept in a separate namespace from observed identity and never silently feeds back into cohorts (§11.4).

11.2 v1 profiles — transparent deterministic statistics

v1 ships deterministic, reproducible statistics per cohort, computed locally, with every result linked back to evidence and to representative excerpts:

FamilyMeasures
LengthsResponse, paragraph, sentence, and code-block distributions (per cohort × context slice)
LexicalType-token curves (windowed, not single-ratio), recurring phrases and n-grams, punctuation frequencies, casing patterns
StructureMarkdown shape: heading/list/table/citation densities, code-vs-prose ratio, code fence languages
DiscourseCommon openings, transitions, closings, qualification/hedging markers, refusal/apology/uncertainty phrasings — reported as observed phrase inventories with frequencies, not psychometric claims

Outputs are versioned analysis runs (code_version, params, cohort definitions stored), so any number in the archive can be traced to exactly the code and cohort that produced it. Runs are exposed via profiles.run/getResults/compare.

11.3 Corpus limits — stated, not footnoteed

The corpus is one heavy user's conversations; the design says so everywhere an analysis touches it. Selection bias (what the owner asks about), prompt/topic confounding (model A compared on coding prompts vs. model B on prose), conversation-history effects (multi-turn context, arena state), hidden system prompts, decoding settings, tools, safety layers, aliases/routing (the same displayed name may not be the same build over time), Arena post-processing, and label uncertainty all bound what comparisons mean. The plan commits to explicit statements of what each result supports (within-cohort descriptive structure) versus what it cannot support (population-level claims about models). Comparisons that the data cannot support are named misleading up front rather than quietly produced.

11.4 Embeddings and local ML — gated entry

Embeddings/local ML enter only when a stated question resists deterministic treatment (e.g., semantic topic clustering beyond keyword slices) and the packaging cost is accepted: pinned model weights (hash-verified at acquisition, downloaded once, fully offline thereafter), version tracked in every run, preprocessing fixed per model version. Entry is per-question, reversible, and recorded; if maintenance or reproducibility cost exceeds value, the gate closes and the deterministic layer remains the baseline. No embedding result ever overwrites an observed identity.

11.5 Later similarity / fingerprinting experiments — pre-registered protocol

Similarity-to-corpus is an unverified, confidence-qualified hypothesis — never proof of model identity or authorship. The protocol, pre-registered before any experiment:

  • Leakage-resistant splits: held-out conversations (never held-out turns), with near-duplicate and branch-aware exclusion so related texts don't straddle splits; topic blocking so a model's topic mix can't masquerade as style.
  • Controls: negative controls (pairs with no identity relationship), calibration curves for confidence statements, and an unknown-class/reject option (the archive contains models the experiment never saw; a claimant can be "none of the above").
  • Reproducibility: fixed splits by seed, versioned feature/code, environment capture; every run re-runnable from the archive.
  • Minimum evidence: established empirically per experiment via learning curves (stated as the smallest cohort size at which the metric stabilizes on held-out data) — no invented universal thresholds.
  • Stop rules: if protocol-faithful attempts cannot beat the pre-declared baseline (deterministic features + calibration) on held-out data, the experiment is abandoned and the result recorded; the archive keeps the negative result. Continuing, revising, or stopping is a written decision against these criteria, not a vibe.

11.6 Incremental modality support — extension points, not a universal framework

Text ships first; everything else enters through the same three extension points — artifact store (kinds, quotas, encryption already general), adapter interface (per-operation parse rules with versions and drift semantics already general), modality registry (per-modality schema families and analysis bindings):

  1. Search responses & citations — new schema families under the conversation adapter family; citation linkage stored as evidence references; no new infrastructure.
  2. Code/web-dev outputs — generated files and previews enter the artifact store (text-like dedup); tool/DB metadata as new op classes in the catalog; a code-arena adapter binds reveal/vote evidence to artifacts.
  3. Images & metadata — artifact kind with derived metadata rows (dimensions, source refs); quotas and per-kind size caps become binding here for the first time.
  4. Video & workflow artifacts — large-object handling already solved (envelope encryption, content addressing); incomplete-capture states extend per modality (partial upload observed ≠ complete artifact).
  5. Agent sessions & tool traces — treated as structured conversations with tool-call turns; the turn/revision model extends rather than forks.
  6. Uploads & derived artifacts — source/derived relationships as first-class edges (artifact → derived-from), so analysis can reason about provenance chains without a speculative universal artifact ontology.
