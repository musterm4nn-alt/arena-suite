Arena Model Archive

A plan for a private macOS application that owns its own browser, records the owner's own Arena conversations with strong provenance and per-account isolation, backfills existing history where an owner session allows it, stores everything locally under encryption, and exposes essentially all of its functionality to an LLM over the Model Context Protocol — so the archive can later be studied as a corpus of model behaviour.

Architecture decision

Electron + Chromium with a TypeScript service layer. One persistent Electron session.fromPartition('persist:…') per Arena account, one browser context per active account, and a per-account capture coordinator driven by webContents.debugger (Chrome DevTools Protocol) in the main process.

This is a dedicated-browser architecture: the application owns the browser runtime, the renderer, the network stack, the storage partition and the download path. It is not an extension, and it does not depend on page-world JavaScript as its primary observation mechanism.

Explicit reversal condition If the Phase 1 falsification spike shows that maintained Electron/CDP session surfaces cannot reliably observe an architecture-critical class of Arena traffic (in particular streamed response bodies or service-worker / worker-originated requests), and a focused CEF spike proves that CefResourceRequestHandler::GetResourceResponseFilter does observe that traffic, then switch the browser core to CEF and keep the TypeScript service, storage, sync, MCP and analysis layers unchanged. A custom Chromium fork is a last-resort escalation only, and is not part of this plan.

01Executive decision

One recommendation, one reversal condition, and an honest statement of what is and is not yet proven.

What is being built

A permanently private macOS application for one owner. The owner uses Arena normally — battles, direct-model conversations, side-by-side, Arena Code — inside an application-owned browser. While they do, the application records accurate local transcripts of their own conversations, plus enough sanitized evidence to know where each record came from and how complete it is. Over time the archive becomes a searchable local research corpus for studying model behaviour: prose habits, formatting, recurring phrases, response structure, coding style, variation over time and by prompt type.

The decision, in one paragraph

Recommendation Build v1 on Electron + Chromium, with TypeScript for every layer the owner's agents will maintain. Use Electron's session.fromPartition() with the persist: prefix as the isolation primitive for simultaneous multi-account Arena sessions; use webContents.debugger as the main-process CDP observation surface; use Electron Session APIs for download control and storage-scoped data management; persist into a SQLCipher database whose random key is wrapped by the macOS Keychain; expose the whole application service layer through a local stdio MCP server; and keep analysis deterministic and local until an empirical gate justifies anything heavier.

Why this is materially deeper than the extension baseline

The existing recorder (arena-exporter) is a browser extension. It observes from inside the page and from extension APIs, inherits the extension lifecycle, and needs companion mechanisms to get artifacts out. The replacement moves the observer outside the page and into the browser's owner process Verified fact: Electron documents webContents.debugger as “an alternate transport for Chrome DevTools Protocol” that attaches to a WebContents, emits instrumentation events, and can send CDP commands. That is a different class of vantage point — browser-side rather than page-side — and it is controlled by code the owner ships, not by a lifecycle the browser vendor grants to extensions.

The distinction that must never be blurred

Owning the browser window is not the same as having deeper capture privileges. Electron owns the window, the renderer, the network stack and the storage partition; it does not automatically see inside TLS payloads that Chromium itself decrypts only in the network service, nor does it see anything a service worker fetches unless a maintained observation mechanism covers that target. The exact mechanisms available outside page JavaScript are enumerated in §8 and the gaps are turned into acceptance tests in §19.

The three gates that decide everything

  1. Capture gate (§19). Can Electron/CDP reconstruct real Arena streams, including stopped, failed and partial generations, with worker/service-worker traffic accounted for? If not → CEF spike.
  2. Backfill gate (§11). Can stable, non-mutating, account-bound owner-history list/detail reads be identified and replayed? If not → UI-traversal fallback with visibly lower completeness.
  3. Isolation gate (§19). Can two Arena accounts remain signed in simultaneously in separate persistent partitions without leakage or cross-account rebinding? If not → the whole premise is broken and the plan must be re-opened.

None of these three has been tested against an authenticated Arena session. No owner-session Arena testing has occurred. That absence is the single most important fact in this document, and it is why the implementation sequence is ordered by evidence rather than by convenience.

03Constraints that bind the design

These are not preferences. Each one eliminates candidate architectures.

Dedicated browser, required
The application must own its browser runtime. Manifest V3 extensions, chrome.debugger extensions, extension + native messaging, and extension + companion daemon are all ineligible as the primary architecture.
Two accounts, simultaneously
Not a switcher. Both signed in and usable at once, with isolated cookies, storage, cache, service-worker state, capture pipeline, auth authority, provenance and sync state.
Arena's own auth UI is authoritative
Email-based sign-in with owner-driven email verification, OTP, MFA-if-present, CAPTCHA, redirects and popups. No credential import from Safari/Chrome. Google OAuth and passkeys are explicitly out of scope and must not disqualify a stronger browser architecture.
Owner-data boundary
Authenticated first-party reads with the owner's session are in scope. Access-control workarounds and other users' data are not. A conversation ID or URL is not proof of ownership.
Private, single-user, no backend
No App Store, no distribution, no hosted service, no telemetry, no analytics, no multi-user accounts, no required public updater.
Agents do the work
AI coding agents implement, maintain and diagnose. Favour mainstream dependencies, explicit schemas, machine-readable diagnostics and tests an agent can run. Build complexity is a real cost.
Apple Silicon, M3 Pro, 18 GB
At least two Arena sessions must remain comfortably usable at once. Quotas come from measurement, not from invented benchmarks.
MCP is primary
Everything in the GUI has a machine equivalent, except literally interacting with the remote Arena page as the owner.

What these constraints eliminate immediately

  • Extension-first designs. Not eligible by requirement, and the owner already has one; the new architecture must change the vantage point, not re-skin it.
  • Headless HTTP replay with imported cookies. Forbidden by the auth constraint (no cookie import) and fragile as a primary mechanism because it depends on undocumented endpoints and on credentials being copied out of the browser session.
  • Export/import only, no embedded browser. Rejected as a primary design because there is no verified general-purpose Arena export today, and because it cannot capture live sessions at all. It survives as a complementary input adapter and is the correct fallback if both the capture and backfill gates fail.
  • Native Swift + WKWebView. Not eliminated by ideology — eliminated by the WebKit public surface verified above: no general HTTPS response interception, and WKProcessPool is no longer an isolation primitive. See §4.

Trust posture of remote content

The Arena renderer is untrusted content with a network connection. It must never hold archive keys, database handles, filesystem authority, Node, MCP access, or the ability to trigger destructive archive actions. Archived prompts, responses and tool traces are untrusted data: they are text to be analysed, never instructions to be obeyed. This drives the process split in §6 and the destructive-action guard in §13.

Why the two WebKit-based options lose

Verified fact Two facts from the WebKit public header settle it. First, WKProcessPool is deprecated with the note that “creating and using multiple instances of WKProcessPool no longer has any effect” — so the historic native isolation primitive is gone and isolation must rest on WKWebsiteDataStore alone. Second, setURLSchemeHandler:forURLScheme: throws an exception when the scheme is one WebKit handles internally, which means it is a custom-scheme facility and not a general HTTPS interception hook. Verified fact Tauri confirms the coupling directly: “Tauri uses WebKit on macOS (through WKWebView)”, and the shipped WebKit version is tied to the OS release.

Neither fact says WebKit is bad. They say that on macOS, WebKit-based runtimes have no maintained public path to HTTPS response bodies, which is the core requirement of this project. Lower memory use and better macOS integration do not compensate for the missing primitive. Both options are therefore rejected as primary architectures while remaining reasonable choices for a different product.

Why export/import is a fallback, not an architecture

It cannot record live sessions at all, and today there is no verified general-purpose Arena export. It earns a place in the plan as an input adapter (and as the graceful degradation path if the capture and backfill gates both fail), because an adapter boundary is cheap to keep and expensive to retrofit.

05Electron vs CEF

The only two serious contenders. They differ on exactly one axis that matters — how deep the maintained observation surface goes — and on how much that depth costs.

The mechanism each one actually uses

Electron
webContents.debugger is a CDP transport owned by the main process. Attach to the WebContents, enable the domains you need, receive instrumentation events, and issue commands. Network observation happens in the browser's instrumentation layer, not in page JavaScript.
CEF
CefResourceRequestHandler is implemented by the host application and runs on the IO thread. GetResourceResponseFilter() returns a CefResponseFilter that sees resource response content as it streams. The same header states that browser and frame may be NULL for requests originating from service workers or CefURLRequest — i.e. the hook is explicitly documented to fire for non-page-originated traffic.

The decision, stated as a rule

Reversal rule

Start with Electron. Escalate to CEF if and only if the Phase 1 spike produces a reproducible, architecture-critical observation gap that CEF's GetResourceResponseFilter is shown to close. “Architecture-critical” means: without it, a required v1 behaviour (§9 completeness states, streamed generation capture, worker-originated traffic, or artifact capture) cannot be met. Cosmetic gaps, gaps that only affect rare surfaces, and gaps closed by a secondary mechanism do not trigger escalation.

The escalation is cheap by construction: the browser core sits behind a BrowserCore interface (§17), and every layer above it — capture events, sanitization, adapters, domain model, storage, sync, MCP, analysis — is transport-agnostic and written in TypeScript. Swapping cores changes packages/browser, not the product.

Hypothesis to test The specific hypothesis that would kill Electron v1 is: “Arena's generation traffic for some required mode is invisible to CDP as exposed through webContents.debugger, because it originates in a target the coordinator does not attach to.” The spike in §19 is designed to test exactly this, with the null result (Electron is sufficient) as the expected outcome and the positive result as the escalation trigger.

A custom Chromium fork is not recommended at any point in this plan. It would only enter consideration if both maintained surfaces failed on the same architecture-critical class, and even then the correct response would be to reduce the product's completeness guarantees rather than to fork a browser.

06Process & trust architecture

One trusted core, one or more untrusted renderers, and a narrow typed bridge between them.

Process boundaries

  1. Main process (trusted, Node). Owns sessions, windows, the capture coordinators, the sanitizer, adapters, the service layer, storage access and the Keychain call. The only process permitted to hold the archive key in memory.
  2. Renderer processes (untrusted). One per active account partition, running remote Arena code. nodeIntegration: false, contextIsolation: true, Chromium sandboxing left on, no privileged preload beyond the tiny typed bridge, navigation and window.open restricted to Arena-owned origins, and no archive, MCP or filesystem capability of any kind.
  3. MCP server. In-process by default, exposed over stdio so there is no listening socket at all. If a loopback HTTP transport is ever added for a specific operational reason, it binds 127.0.0.1 only, validates Origin, and carries no additional authority.
  4. Analysis worker. Separate thread or utility process, given a read-only snapshot or explicit read queries, never the key and never write access outside its own result tables.
  5. Optional browser-side utility process. Only if measurement shows capture parsing is competing with the owner's interaction. Quota-driven, not speculative.

IPC rules

  • Allowlisted channel names, typed payloads validated at both ends with a schema check.
  • Every renderer-originated call carries its accountId and partitionId, and the main process re-derives the account from the sender's WebContents — it never trusts the renderer's claim.
  • No channel in the allowlist begins, cancels, or confirms a destructive archive action.
  • Archived content is data. No schema in this system accepts a natural-language field that can authorise deletion, credential use, or cross-account access.

07Multi-account partition design

Two Arena accounts signed in at once, each with its own browser universe and its own capture authority — and a provenance model that makes cross-account merges structurally impossible.

The descriptor

// packages/browser — account partition descriptor (representative, not implementation-complete)
export interface AccountPartitionDescriptor {
  /** Stable internal identity. Never derived from the email address. */
  accountId: string;                 // UUIDv7 — the archive's primary account key
  partitionId: string;               // `arena-<uuid>` — opaque, non-identifying
  electronPartition: string;         // `persist:${partitionId}`
  storageRoot: string;               // app-managed directory, 0700, inside the app's data container
  createdAt: string;                 // ISO-8601
  authState: 'unauthenticated' | 'authenticating' | 'authenticated'
           | 'needs_owner_interaction' | 'expired' | 'disabled';
  /** Set only after an owner-session verification step; see §7 "identity binding". */
  verifiedArenaIdentity: {
    /** Opaque hash of the Arena-side identifier string, not the raw value. */
    identityFingerprint: string;
    verifiedAt: string;
    verificationMethod: 'owner_attested_ui' | 'owner_attested_read' | 'unverified';
  } | null;
  captureAuthority: 'enabled' | 'paused' | 'revoked';
  /** Bumped whenever identity is rebound; forces re-verification of in-flight jobs. */
  identityEpoch: number;
}

Rules that make isolation real

  • Opaque partition names. persist:arena-<uuid>. Never derive a partition name from an email address, handle, or any other unnecessarily identifying string — partition names appear in on-disk paths and in diagnostics.
  • One coordinator per account. Each account has its own CDP attachment, its own event queue, its own sanitizer instance seeded with that account's redaction policy, and its own backpressure budget.
  • Account scope participates in uniqueness. Local primary keys are internal UUIDs; Arena source IDs are scoped source identifiers. Uniqueness is (account_id, source_kind, source_id), never source_id alone.
  • Collisions create conflicts. If two accounts present the same source ID, ingestion raises a SOURCE_ID_CONFLICT and records both observations without merging. Identical text is not evidence of identity.
  • Identity epoch. Any change of authenticated identity inside a partition bumps identityEpoch, cancels in-flight jobs for that account, and blocks new ones until the owner re-verifies. This is the mechanism that prevents a silent rebinding of an archive to a different Arena account.
  • Independent failure. Sign-out, expiry, CAPTCHA, rate limiting or sync failure in one partition changes only that partition's authState and pauses only its jobs.
  • Destructive scope is per-account. “Delete all data for account A” never touches account B's rows, blobs, checkpoints, FTS entries or analysis derivatives.

Identity binding: how the archive knows whose data it is

The archive never infers account ownership from a cookie, a URL, or a conversation ID. It binds a partition to an Arena identity by an explicit owner-attested step: the owner signs in inside that partition and confirms (in the trusted GUI, not in the renderer) that “this window is account X”. The Arena-side identifier string is stored only as a salted fingerprint for continuity checks; the display label is a local alias the owner chooses. Every subsequent capture and sync operation for that partition carries accountId + identityEpoch, and every backfill read is executed inside that partition's browser context so it can only ever succeed with that account's credentials.

On “do not import cookies from Safari/Chrome”

Honoured by construction: the archive never reads another browser's profile. Browser-managed authentication state lives only inside the app's own persistent partition, protected by the macOS user account's file permissions. Native sync may transiently reuse the credentials belonging to the correct app-owned session by performing the read inside that session — but copied bearer tokens and cookies are never written to the archive database, logs, fixtures, exports or diagnostics. The sanitizer enforces this, not convention.

Sanitization, before anything is durable

Sanitization runs in the trusted main process, before the ephemeral raw window is allowed to become a durable observation. It is allowlist-driven: a field is retained because it is on the retention list, not because it was not recognised as secret.

Always removed
Authorization, Cookie, Set-Cookie, CSRF/XSRF tokens, passwords, OTP/verification codes, OAuth codes and state, bearer tokens, API keys, signed URL query parameters, and any response field whose name matches the secret-name patterns.
Replaced by placeholders
Conversation/message identifiers inside URL templates (kept as structured values in their own columns, replaced by <conversationId> in the pattern).
Hash-only
Anything needed for continuity or drift detection but not for reading: salted fingerprints of identity strings, payload digests for dedup.
Retained
The minimum needed to parse, reparse, detect drift and prove provenance: status, content type, timing, ordering, target identifiers, and a bounded sanitized body excerpt for architecture-critical operations.
Fail closed
If a field cannot be classified, the raw evidence is discarded, an UNKNOWN observation is retained with a digest, and a sanitizer incident is recorded. No best-effort partial persistence.

Reconciliation

Network evidence and rendered-UI evidence are stored as separate observations attached to the same participant response, then reconciled by an explicit rule set. Observations may arrive more than once, out of order, after navigation, after reconnect, after a model reveal, or during an overlapping history sync.

  transport obs ───▶ │                              │
  (CDP, ranked 3)    │      RECONCILER              │ ──▶ COMPLETE
  ui obs        ───▶ │  dedup by (account, source,  │ ──▶ PARTIAL_*

  backfill obs  ───▶ │  rank by provenanceStrength  │ ──▶ UNSUPPORTED_SCHEMA

  RANKING RULE (provenanceStrength):
    3 = transport evidence with full stream and terminal marker
    2 = authoritative first-party read (backfill) with complete payload
    1 = rendered UI text with no transport confirmation
    0 = inference (never stored as content; stored as a hypothesis record)

  UPGRADE RULE:  a higher-strength observation may complete a lower-strength one.
  DOWNGRADE RULE: a newer, weaker observation may never replace a stronger stored one.
  It may only be appended, and only marked CONFLICTING if it disagrees materially.

Idempotency. Ingestion is keyed by a deterministic digest of (accountId, sourceKind, sourceId, turnRef, participantRef, bodyDigest). Re-delivery is a no-op. Reordering is resolved by ordering.streamSeq / chunkIndex plus observation timestamps, never by wall clock alone.

Reveals are additive. A post-vote model reveal adds an identity observation with its own timestamp and mechanism. It does not retroactively edit the participant record to pretend the model was known from the start. The archive must always be able to answer “what did we know, and when?”

11History backfill & synchronization

Backfill is a separate product surface from live capture, with a separate falsification gate. Nothing about it has been verified against an authenticated Arena session.

Adapter preference order

  1. Verified authenticated owner-history reads (list + detail), executed inside the owning account's own partition. Preferred only after the gate proves three things: the operation belongs to the current authenticated account, it is non-mutating in practice, and it is correctly account-bound.
  2. Automated UI traversal + capture through the owner's signed-in session, with visibly lower completeness guarantees and an explicit coverage report.
  3. Official export / user import, if and when it exists — as an input adapter with its own provenance class.
  4. Documented public API, if Arena ever publishes one. Preferred the moment it exists.
Backfill gate — must pass before this path is trusted
  • Ownership: a probe with a deliberately wrong/inaccessible conversation reference must fail in a way that proves account binding, not merely 404.
  • Non-mutation: the candidate read is executed N times against a known conversation; a checksum of the conversation, its title, timestamps and ordering must be identical before and after. A GET is not evidence of read-only; this test is.
  • Listing: listing must be complete and stable across two consecutive passes with no new activity in between.
  • Pagination: forward and resume-from-cursor must produce the same set as a full walk, with overlap handled idempotently.
  • Checkpointing: killing the process mid-sync and resuming must produce the same final state as an uninterrupted sync.
  • Auth expiry: expiring the session mid-sync must pause that account only, preserve the cursor, and resume cleanly after re-authentication.
  • Isolation: running two accounts' syncs concurrently must produce no cross-account rows and no shared cursor advancement.
  • Completeness boundary: the sync report must state what it could not retrieve, not only what it did.

Opening one known conversation proves none of this. That is explicitly not an acceptable gate result.

Concurrency model

Two accounts may sync concurrently, and the reason is structural: each sync job is bound to one (accountId, identityEpoch), writes only rows keyed by that account, advances only that account's cursor, and holds no shared mutable state beyond the single-writer SQLite connection. The database is a serialization point by design — jobs interleave at transaction boundaries, not inside them.

Even so, concurrency is configurable and defaulted conservatively: the default is one active sync job at a time, with an opt-in per-account concurrency limit (default 2). This is a politeness and rate-limit decision, not a correctness requirement, and it must be tunable without code changes.

Operational rules

Source of truth
Normalized tables are the queryable truth. Sanitized observations explain it and allow reparse. Observations are append-only; corrections are new rows that reference what they supersede, never in-place edits of evidence.
Transactions
Single writer. Each ingestion batch is one transaction spanning domain rows, observation rows, FTS updates and checkpoint advancement. Either the whole batch lands or none of it does. WAL mode with synchronous settings chosen for crash safety over throughput.
Crash recovery
On startup, any job in running is reconciled against its checkpoint and marked interrupted; it resumes or waits for the owner. No job is silently considered complete because the process restarted.
Migrations
Ordered, forward-only, numbered migrations recorded in a schema_migration table with checksums. Every migration runs inside a transaction and is tested against a synthetic fixture database. The database is never opened by a build that does not recognise its schema version.
Reprocessing
Adapters are versioned. A new adapter version creates a reprocess job that reads stored sanitized observations, produces candidate domain rows, and proposes changes ranked by provenance. Stronger existing provenance still wins.
FTS
The index lives inside the encrypted database — no plaintext side index. It is updated in the same transaction as the content and can be rebuilt from content at any time.
Artifact lifecycle
Large blobs go to the encrypted blob store; the DB holds metadata, digests and references. Deleting a conversation decrements references; orphan blobs are reaped by an explicit maintenance job, never opportunistically during a read.
Backup / restore
A backup is a consistent copy of the database file set (DB + WAL + sidecar) plus the blob store plus a Keychain reference note, taken while the app holds a read transaction. Restoring a database without its Keychain entry is impossible by design; the owner must also restore the Keychain item. This is disclosed, not hidden.
Deletion cascades
Explicit and enumerated per scope (§13). Cascades are defined in one place and covered by a test that asserts zero residual rows, FTS entries, blobs and checkpoints for the deleted scope.

13Encryption, security & deletion

A random key, wrapped by the Keychain, protecting a database whose entire file — including indexes, journals and WAL — is ciphertext. And a deletion model that no archived text can trigger.

Key hierarchy

random 32-byte archive key  (generated once, on first run, from a CSPRNG)
        │
        ├──▶ stored ONLY as a Keychain item (kSecClassGenericPassword,
        │    accessible when the app is unlocked by this macOS user)
        │    · never in config files, env vars, logs, or the database
        │    · never derived from a human password as the primary path
        │
        ├──▶ SQLCipher database key
        │    · supplied as RAW KEY MATERIAL, not a passphrase
        │      (SQLCipher documents raw binary key support precisely for
        │       "vaulted keys" — this is that case)
        │    · no PBKDF2 passphrase path in the primary design, because the
        │      key is already high-entropy and random
        │
        └──▶ blob-store key
             · a distinct key DERIVED from the archive key via HKDF-SHA256
               with an info string, so blobs and DB never share a key directly
             · per-blob random nonce; AEAD (AES-GCM or ChaCha20-Poly1305)
             · header records the key id so rotation is possible later
What SQLCipher does and does not cover — verified this run

Documented design: 256-bit AES-CBC, each page encrypted individually with its own random IV regenerated on write, and an HMAC-SHA512 of ciphertext+IV verified on read. WAL pages and rollback-journal pages are encrypted with the database key. Transient temporary files are not encrypted unless file-based temp storage is disabled at build time — so the build must set SQLITE_TEMP_STORE=2 (and the equivalent configure flag) and the acceptance test must assert it. Statement journals, temp indexes for FTS builds and any spill files are the exposure this controls.

Plaintext exposure, stated honestly

  • In memory: decrypted pages exist in the process; SQLCipher locks and wipes memory where it can. There is no defence against an attacker with the same macOS user's privileges and a debugger attached. This is an accepted residual risk for a local, single-user research tool.
  • Browser profile data: persistent Arena sign-in requires the browser to keep Arena authentication cookies. Those live in the app's own partition directory, protected by macOS user-account file permissions (directory 0700), and are never copied into the archive. This is materially different from deliberately storing credentials in a research database, and the report draws that line explicitly rather than pretending the cookies do not exist.
  • Swap and hibernation: the OS may page decrypted memory to encrypted swap; the app should keep its memory profile bounded (§23) but cannot eliminate this. Documented, not solved.
  • Spotlight and Time Machine: the archive directory is excluded from Spotlight indexing and is marked so backups do not copy it by default. Once a file has reached an external backup, this app cannot delete it — and this document does not claim otherwise.
  • Exports and fixtures: exports are written encrypted by default; a plaintext export is an explicit, separately-confirmed owner action with a warning, and fixtures never contain real owner data.

Destructive-action guard

Deletion is authorised by a trusted client presenting a token — never by archived content. The two-step design makes the scope visible before it is executed and makes replay impossible. 

// packages/mcp + packages/domain — destructive intent
export interface DestructiveIntent {
  scope:
    | { kind: 'conversation'; accountId: string; conversationId: string }
    | { kind: 'account';     accountId: string }
    | { kind: 'archive_all' };
  /** Server-generated, single-use, short-lived, cryptographically random. */
  nonce: string;
  /** Human-readable, server-computed exact scope: counts of rows, blobs, FTS entries, checkpoints. */
  scopeSummary: {
    conversations: number; turns: number; revisions: number;
    observations: number; artifacts: number; blobBytes: number;
    analysisResults: number; checkpoints: number; accountsAffected: string[];
  };
  /** SHA-256 of (scope + nonce + issuedAt + server secret). Recomputed on confirm. */
  confirmToken: string;
  issuedAt: string;
  expiresAt: string;
  /** The client must echo this exact string back to confirm. */
  requiresTypedConfirmation: 'DELETE';
}
  1. archive.prepare_delete_* → returns DestructiveIntent with the computed scope and a short expiry. Nothing is deleted. The call is logged.
  2. archive.confirm_delete_* → accepted only with the unexpired nonce, a matching recomputed confirmToken, and the literal typed confirmation. One use, then invalid.
  3. Execution runs as a job with progress, and deletes: domain rows, source observations, FTS entries, analysis derivatives keyed to the scope, blob references and (after reference counting) the blobs themselves, sync cursors and dedup markers, and the job's own cached artifacts.
  4. Local deletion never deletes the owner's Arena cloud conversations. Remote deletion, if it is ever implemented, is a separate, separately-confirmed remote operation that the archive does not imply.
  5. Post-deletion re-sync: a deleted account keeps a tombstone marker (deleted_at, salted fingerprint only) so a future sync does not silently resurrect it. Resurrect is a distinct, explicit owner action.
  6. Archived text cannot mint, guess, or satisfy this authorisation. There is no code path from a parsed response body to a deletion call.

Operational semantics an agent can rely on

  • Account scope is explicit. Every tool that touches data takes account scope; nothing is inferred from “whichever window is focused”.
  • Long work is a job. Sync, export, analysis and deletion return a jobId immediately. Progress is pollable, and cancellation is a defined state transition rather than a socket closure.
  • Client disconnect has defined semantics. Because stdio termination is indistinguishable from a crash, jobs continue by default, and each job declares onClientDisconnect: 'continue' | 'cancel' | 'pause' at creation. The default for sync is continue; for deletion it is continue only after confirmation, otherwise cancel.
  • Capability negotiation. When a capability depends on an unproven mechanism, the tool returns CAPABILITY_UNAVAILABLE with a reason instead of failing cryptically or returning half-truths.
  • No secrets cross the boundary. Tool results are drawn from sanitized, allowlisted projections. There is no tool that returns a header bag, a cookie, or a raw token.

Cohorts, stratification, and disclosure

Every analysis run is defined by a cohort: the explicit filter set (account, mode, date range, prompt type, language, topic heuristic, identity-evidence class) plus the provenance rules used to select records (for example “only provenanceStrength >= 2” and “exclude UNSUPPORTED_SCHEMA”). Results always include the cohort definition, sample counts, excluded counts and the reason for each exclusion. A profile without its cohort is not a result.

Confounders this design refuses to hide

  • One-user selection bias: the owner's own prompting habits shape every response.
  • Topic and conversation context; prior turns condition later ones.
  • Arena's hidden prompts and system scaffolding; model-side system prompts.
  • Decoding parameters, tools, routing and model aliases the archive cannot observe.
  • Temporal model updates and safety-layer changes: a model's style is not stationary.
  • Arena's own post-processing and UI rendering between model output and observed text.
  • Capture artefacts: partial records must be excluded or bucketed, never averaged in silently.
Gate for anything heavier

Embeddings, classifiers and local ML are not in v1. They arrive only after an empirical gate: a documented research question that deterministic statistics provably cannot answer, a baseline deterministic result to beat, and a reproducibility plan. Choosing not to ship a large local model is a decision, not a gap.

16Later work & extension points

Text first, with the seams left in the right places so new modalities are adapters rather than rewrites.

Fingerprinting experiments — as hypotheses, never proof

Stylistic similarity is evidence about style. It is not proof of model identity, and this system must never present it as such. Any experiment that attempts attribution must satisfy all of the following before its output is trusted even tentatively:

  • Held-out conversations and leakage-resistant splits: branches and near-duplicate regenerations are kept in the same split, or the result is meaningless.
  • Controls: prompt family and topic controls, plus explicit negative controls.
  • Calibration and unknown-class rejection: the system must be able to say “this does not look like anything I have a profile for”.
  • Temporal validation: train on older data, test on newer, because style drifts.
  • Reproducible preprocessing recorded with the run: tokenisation, truncation rules, exclusion rules, capture-completeness filters.
  • Observed-vs-inferred separation preserved end to end: an inferred label never enters the training set as if it were an observed label.

No invented sample-size threshold. Whether an experiment has enough data is answered by a power and stability analysis on the actual corpus — variance across bootstrap resamples, stability across date buckets, and sensitivity to cohort definition. If the analysis says the corpus cannot support the question, the correct output is “not answerable yet”, not a confident guess.

Dependencies, and where the native-build risk actually is

The stack is deliberately mainstream: Electron, TypeScript, Node, better-sqlite3-style native binding compiled against SQLCipher (or an equivalent maintained SQLCipher binding), SQLite FTS5 for search, zod-style runtime schema validation, vitest-style tests, and the official MCP SDK for the server surface. No version numbers are asserted here; the lockfile and the Phase 0 toolchain check are the authority.

There is exactly one meaningful native-build risk in v1: the SQLCipher binding, which must be rebuilt for each Electron ABI and for arm64. That risk is handled by (a) pinning Electron and the binding together in Phase 0, (b) a build-verification test that opens an encrypted database in a packaged app build — not just in dev — and (c) a documented fallback (pure-JS encryption is not an acceptable fallback; if the binding cannot be built reliably, the correct response is to fix the toolchain, because encryption at rest is a requirement). A CEF core would add a second, much larger native surface, which is one more reason to start with Electron.

23Platform, resources & minimum macOS

Measure, then configure. No invented benchmarks and no invented capacities.

Minimum macOS version

Decision

Minimum supported macOS: 14 (Sonoma).

Reasoning: every Apple Silicon Mac — including the M3 Pro target — supports Sonoma; the Keychain and file-protection APIs this design relies on are long-stable and unchanged in the relevant range; SQLCipher's crypto providers on macOS are unaffected by the choice; and because this is private software there is no reason to carry compatibility for operating systems the owner does not run. Going lower buys nothing and costs testing surface. Going higher would needlessly restrict future hardware moves.

Phase 0 verification action: confirm that the pinned Electron major's documented minimum macOS is at most 14. Electron supports a rolling window of recent macOS releases, so this must be checked against the pinned version rather than assumed. If the pinned Electron requires 15 or newer, raise the floor to match — the floor follows the dependency, not the reverse.

Resource posture on an M3 Pro with 18 GB

No numbers are asserted here, because honest numbers require measurement against the real Arena pages. What is specified is the instrumentation and the controls, so that the first measurement becomes a configuration rather than a surprise.

  • Measure continuously: per-partition renderer memory, main-process memory, capture queue depth and drop count, database and WAL size, blob-store bytes, active job count, and event-processing latency percentiles. All exposed through diagnostics.status.
  • Control with quotas, not hope: maximum simultaneously rendered partitions (default 2, since two usable accounts is the requirement); bounded per-account capture queue with an explicit drop policy that records a gap when it engages; maximum retained sanitized body-excerpt bytes per operation family; blob-store high-water mark with a warning; concurrent sync job limit (default 1).
  • Backpressure, not loss: when a queue nears its bound, capture prefers dropping low-value chatter over architecture-critical streams, and every drop increments a counter that appears in diagnostics.capture_gaps. Silent loss is the failure mode being designed out.
  • Inactive partitions: a signed-in account whose window is backgrounded may have its renderer suspended while its session state and capture authority persist, so signing in is not the same as paying full renderer cost.
  • Background sync: throttled, pausable, and never allowed to compete with an active owner-driven conversation for the same account.
