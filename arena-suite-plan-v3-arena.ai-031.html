VAULT/ARENA — a dedicated Chromium archive runtime for arena.ai

Plan for a permanently private macOS application that hosts my own arena.ai sessions — two or more signed in at once, in isolated partitions — records complete local transcripts out-of-band from the browser process, backfills existing history, and exposes every capability to an LLM through a local MCP server. 00 Verdict & reversal conditions

Build the archive as an Electron application whose main process owns the Chromium browser session and attaches the DevTools Protocol to every Arena target before its first navigation. Capture is out-of-band: response bodies, streamed chunks, WebSocket frames and sub-target traffic are read from the browser process, not from patched page-world globals. Each Arena account gets its own on-disk Chromium session partition, its own observer, its own sync scheduler and its own deletion scope. Storage is a SQLCipher database plus an encrypted content-addressed artifact store, keyed by a random archive key wrapped in the macOS Keychain. The primary human/LLM surface is a local MCP server over a 0600 UNIX socket; the GUI is a thin diagnostics console over the same application services.

Why this and not the alternatives

  • Deeper than the MV3 baseline by mechanism, not by vibe. The observer attaches with webContents.debugger (a main-process binding, V) before loadURL, uses Target.setAutoAttach{flatten:true} to follow OOPIFs and workers, and pulls bodies with Network.streamResourceContent as they arrive (V both exist in the published protocol). No page global is replaced; an extension content script cannot do any of this, and its own service worker can be evicted mid-stream.
  • WKWebView-based shells (native Swift, Tauri) have no equivalent. WebKit gives no supported out-of-band API for response bodies, worker targets, or per-frame network events in an embedded view; capture would collapse back into page-world monkey-patching — the exact failure mode being escaped.
  • CEF matches the capture depth but not the operating cost. Same Chromium, same DevTools protocol, worse Node/TypeScript ergonomics for agent-driven maintenance, heavier build. See §02.
  • Downloads and generated artifacts are app-owned via session.on('will-download') (V) — no extension download restrictions, no companion bridge.
  • Backfill never touches cookies in JavaScript: ses.fetch() issues requests through that partition's own Chromium network stack (V), so owner credentials stay inside the browser session.

Honest limits of the recommendation

  • Network.streamResourceContent is marked experimental in the protocol (V); it can change between Chromium majors. Fallback chain is specified in §05.4.
  • Whether CDP auto-attach reaches Arena's service worker target inside Electron, and whether SW-mediated response bodies are retrievable, is H — the first spike must answer it (Gate G1).
  • Opening DevTools on an instrumented webContents detaches our debugger (V, documented). Human debugging of an Arena view is therefore a deliberate, capture-degrading action with its own UI state.
  • Arena fronts the app with Cloudflare and reCAPTCHA Enterprise (V, observed headers/scripts). Automated traversal must be owner-attended when challenged; the plan never auto-solves a challenge.
  • No Arena owner-history API contract was verified in this run (no authenticated access was available). Every backfill claim is conditional on the discovery protocol in §06 succeeding.

Scope discipline used throughout

Only data belonging to my own signed-in Arena accounts is touched, and every read is bound to the partition that owns the session. Arena's legal documents are explicitly out of the planning criteria per the assignment; the evaluation here is technical. Undocumented first-party endpoints used with the correct owner session are treated as authenticated reads, not as access-control bypasses, and the report labels which is which (§07.2).

03.3 The browser-level CDP escalation, and its honest cost

--remote-debugging-port opens a loopback HTTP/WebSocket endpoint that any local process can connect to, with full browser control including cookie read. It is therefore off by default. It is enabled only when a capability gap demands it (e.g. if per-target auto-attach cannot reach service-worker or early-navigation targets), and then: bound to 127.0.0.1 on an ephemeral port chosen at launch, the port number never written to logs or exports, the endpoint closed as soon as the diagnostic window ends, and a persistent, unmissable GUI + MCP state flag browser_debug_endpoint: OPEN that also blocks all destructive operations while open. If the spike shows the escalation is permanently required, that fact — not a preference — becomes part of the threat model and is recorded in the architecture decision record.

Declared minimum: macOS 14.0. Electron's floor is Ventura (13) V; there is no reason to claim support for a version that will never be tested, and 14 keeps Keychain/code-signing behaviour in a range the agent can reason about. 04 Simultaneous accounts: isolation, sign-in, ownership binding

04.1 The partition model

Each Arena account is an AccountProfile row with a stable local UUID and a dedicated directory vault/partitions/<uuid>/ passed to session.fromPath() (V). That single call separates cookies, HTTP cache, local/session storage, IndexedDB, service-worker registrations and their caches on disk. Everything else in the app is made account-scoped by construction:

One sessionCreated once at profile creation; ses.storagePath recorded and asserted at every startup.
One observerA CaptureObserver instance bound to that session's views; it stamps account_id on every event before the event can reach any queue.
One schedulerSync jobs, retries, backoff state, rate-limit state and checkpoints are per account; a 429 for A never throttles B, and an auth failure in A never cancels B's jobs.
One download sinkwill-download is registered on that session only; artifacts are written with the account id in their provenance before the file is linked.
One deletion scope"Delete this account's data" maps to: DB rows where account_id = ?, artifacts referenced only by those rows, that partition directory, and that account's Keychain-wrapped sub-key. Nothing else can be reached by that operation.
EnforcementAn AccountScope capability object is the only way to obtain a session, a DB writer or a fetcher. A lint rule plus a unit test forbid session.defaultSession, bare net.fetch, and any SQL on scoped tables without an account_id predicate.

04.2 Sign-in: owner-driven, inside the app

Sign-in happens in a normal, visible Arena view inside the target partition. The app does not script it, does not read the email code, and does not store Arena credentials. Requirements that follow from the observed stack (Cloudflare + reCAPTCHA Enterprise, V):

  • Ordinary browser presentation. Do not advertise automation: no --disable-blink-features=AutomationControlled-style tells needed because Electron is not driven by WebDriver, but the user-agent must be a coherent Chrome-on-macOS string consistent with the embedded Chromium version, and the window must be a real, focusable, correctly sized window. Any UA override is recorded in the protocol catalog so drift in Arena's client checks is attributable.
  • Challenges are owner-attended. When a Turnstile/reCAPTCHA interstitial or an email-code prompt is detected (navigation to a challenge URL, or a challenge frame on the page), the account enters state=owner_action_required: capture keeps recording, all automated traversal for that account pauses, and the GUI/MCP report exactly which account needs attention.
  • Popups and redirects opened by the sign-in flow are routed into the same partition so the cookie jar matches, and are closed automatically when they return to an Arena origin.
  • Google/OAuth/passkeys are not requirements and are not exercised by acceptance tests; if the email flow works, the gate passes.

04.3 Ownership binding and the "who is this?" problem

A conversation URL or opaque id proves nothing about ownership. The binding rule is:

account_key := stable identifier of the signed-in Arena account as reported by an
             owner-session read inside that partition   (shape unknown — see H-02)

on every observation:
  observation.partition_id  = <local uuid of the session that produced it>
  observation.account_key   = <account_key last confirmed for that partition>
  observation.binding_state = confirmed | stale | mismatch

rules:
  1. No record is written with binding_state = mismatch. It is quarantined.
  2. account_key change on a partition  → capture halts for that partition,
     a SessionIdentityChanged conflict row is written, and the owner must confirm
     whether this is a new profile (create) or a re-login (re-confirm). Never auto-rebind.
  3. Same source_conversation_id under two account_keys → CrossAccountIdCollision
     conflict row. Both records stay. No merge, ever.
  4. Sign-out detected (auth-state transition observed in traffic or UI probe)
     → that account degrades to read-only archive; other accounts unaffected.

The cheapest source for account_key is the identity object Arena already embeds in its RSC document payload — verified to exist for anonymous users as userId/userState (V); that the authenticated document carries the real account identifier is H (test H-02, §13.2). Fallbacks, in order: an account/profile read observed in owner traffic; the account email/handle rendered in the account menu, captured by the isolated-world DOM probe and stored as a display attribute with lower trust.

05.5 Reconciling network evidence with what was on screen

The network is authoritative for content; the DOM is often the only source for what the owner actually saw: which side was A vs B, that a vote was cast, that a reveal happened, that a regeneration replaced a turn. The reconciler therefore keeps both, and joins them on (account, conversation, target, monotonic time window, position):

  • Network turn text wins over DOM text; a mismatch beyond whitespace raises a ContentDivergence conflict rather than overwriting.
  • DOM-only facts (vote clicked, reveal shown, participant position label) are stored as identity/interaction observations with source:"ui", never as transcript content.
  • Late reveals are appended as new identity observations with their own timestamps; the "current identity view" is a projection, and the earlier blind label stays intact (§08.4).
  • Repeated events (reconnect replays, duplicated frames) are deduplicated within a request by sequence/offset, and across requests only by (account, source ids) — never by text similarity.

05.6 Known coverage gaps this architecture still has

  • Pre-attach navigation in a brand-new target created by the page (e.g. window.open before auto-attach completes) — mitigated by waitForDebuggerOnStart, but a residual race is possible and is recorded rather than hidden.
  • Service-worker-authored responses if worker targets prove unattachable (Gate G1): metadata only.
  • In-page state never serialized (pure client-side derivations) — visible only via the DOM probe, with the lower provenance tier that implies.
  • Encrypted/opaque payloads, if Arena ever ships them: the catalog records the operation as opaque; no speculative decoding.
  • DevTools use by the owner detaches the observer (V): the app marks the whole window a capture gap for that period and says so.

06 Discovery as a maintained capability: the protocol catalog

Discovery is not a one-off reverse-engineering session; it is a table the app keeps current and an agent can query. Every first-party operation the owner's sessions touch gets a row. Unknown stays unknown until investigated — the catalog's value is that it distinguishes "we understand this" from "we have seen this".

06.1 Catalog record

operation {
  op_id            stable local id, e.g. "op.history.list"
  fingerprint      method + normalized path template + discriminating body/response keys
  first_party      arena.ai | *.arena.site | third_party_noise | unrelated
  seen_under       [{account_id, first_seen, last_seen, count}]  — per-account, never merged
  transport        document | fetch_json | sse | websocket | download | upload
  classification   conversation | history | account_auth | asset | config_analytics
                   | mutation | unknown
  read_status      read_verified | read_presumed | mutation | mutation_suspected | unknown
  schema_family    hash of the observed key-shape; list of variants with counts
  adapter          name@semver | null
  completeness     how often parsing succeeded; last N failures (sanitized)
  drift            {new_keys[], missing_keys[], type_changes[], first_seen_at}
  retention        full_body | redacted_body | metadata_only | forbidden
}

Inventory coverage is broad; payload retention is narrow. Every request the owner's sessions make is classified (host, path template, transport, size, timing). Bodies are retained only for operations whose classification is conversation/history and whose retention policy says so. Auth, account, challenge and analytics operations are recorded as rows with counts and shapes — never with bodies. This is what keeps discovery from degrading into a credential-dumping network console.

06.2 Sanitization happens before persistence, including on the failure paths

CDP event ──▶ classifier ──▶ sanitizer ──▶ envelope ──▶ encrypted observation log
                  │                 │
                  │                 ├─ strip: Cookie, Set-Cookie, Authorization, X-CSRF*,
                  │                 │         API keys, bearer tokens, signed query strings,
                  │                 │         reCAPTCHA/Turnstile tokens, email one-time codes
                  │                 ├─ intern URLs: store (host, path_template, param_keys,
                  │                 │   secret_params_hashed) — never the raw signed URL
                  │                 └─ on sanitizer exception: drop payload, keep a typed
                  │                     error row {op_id, reason, byte_len, no content}
                  └─ third_party_noise ⇒ metadata row only, body never buffered

parser error path: the offending body is re-sanitized and truncated before being stored as
a drift sample; parser errors never log raw bodies to stdout or to the NDJSON log.

Retention of sanitized evidence is time- and size-bounded (policy knobs in §12.4): enough to reparse after an adapter fix and to diagnose drift, not an indefinite second copy of the archive. When an adapter version changes, the app can replay retained envelopes to rebuild projections; envelopes past their retention window leave their derived records in place with reparse_possible:false.

06.3 Drift detection under a flag-gated frontend

Because Arena varies the frontend per user by feature flag (V), drift is not global. The catalog therefore stores schema variants with counts and the account under which each was seen, and the alert rule is: a new variant that the current adapter cannot parse, not merely a new variant. Signals: parse failure rate over a rolling window, unknown-key ratio, disappearance of a key the adapter marks required, a new op_id in the conversation class, a change in the deployment id observed in asset URLs (?dpl=…, V) correlated with parse failures. Each raises a diagnostics event with the smallest sanitized sample that shows the difference, retrievable through MCP (diag.drift_samples).

07.2 Evidence required before any replay is allowed

HTTP method or endpoint name proves nothing about read-only behaviour. An operation may be promoted to read_verified and used for backfill only when all of the following are recorded in the catalog:

  1. Observed in owner traffic first. The app never invents a URL. The operation must have been seen at least k times during ordinary owner use of the history surfaces, in the partition of the account that will replay it.
  2. Account-scoped response. The response carries an owner/account discriminator consistent with that partition's account_key, or the listing's ids are provably disjoint from the other account's listing (two-account disjointness check, which the multi-account design makes cheap).
  3. Idempotence probe. Replayed twice inside a short window, the response is structurally identical modulo cursors/timestamps, and no observable state changes: no new items in the listing, no updated_at movement on the touched conversation, no side-effect events on the realtime channel during the probe window.
  4. Mutation tripwire armed. During replay, the observer watches for any first-party mutation-classified operation originating from the app's own fetches; one occurrence demotes the operation to mutation_suspected, aborts the run, and requires re-verification.

Anything not meeting all four stays read_presumed and is reachable only through the UI-traversal fallback, where Arena's own client decides what to call.

07.3 Job model: Sync now, per account or several at once

sync_run { run_id, account_id, mode: full|incremental, method: replay|traversal,
           state: queued→running→(paused|blocked_auth|blocked_challenge|
                                   rate_limited|cancelling)→(done|failed|cancelled),
           cursor, pages_seen, items_seen, items_new, items_updated,
           conflicts, gaps, started_at, checkpoint_at, idempotency_key }

checkpointing:  after every page → {cursor, page_digest, last_item_key}
resume:         re-request the checkpoint page, compare digest;
                digest mismatch ⇒ pagination instability ⇒ widen overlap window,
                switch to key-set dedupe, record PaginationUnstable diagnostic
cancellation:   cooperative; in-flight request is awaited or aborted, the partial page is
                discarded (never half-written), checkpoint stays at the last complete page
retries:        bounded per page (e.g. 3) with jittered backoff; a page that fails its budget
                is recorded as a gap and the run continues, so one bad page ≠ failed sync
  • Concurrency: accounts sync concurrently by default (separate sessions, schedulers and cursors — correctness does not depend on serialization), with a global in-flight cap so two heavy syncs cannot starve live capture or the machine. Database writes are serialized through the single writer; each page is one transaction.
  • Interaction with live capture: live capture always wins for a conversation that is currently streaming. Sync skips conversations with an open capture, and revisits them after the capture closes. When sync and live capture both produce evidence for a turn, the reconciler keeps both observations and prefers the more complete one for the projection — never blending text from two sources into one string.
  • Deduplication is conservative and account-scoped: upsert key is (account_id, source_conversation_id) and (account_id, conversation_id, branch_id, source_turn_id|position). Repeated pages are harmless. Identical text under different ids is not a duplicate. Identical ids under different accounts is a conflict row, never a merge.
  • Automatic sync is off by default and enabled per account, with an explicit interval and a "only while that account is signed in and idle" condition.

07.4 What "synchronized" means, precisely

account A is synchronized as of T ⇔
   every conversation id observed in any listing page during the run at T
   has a detail record whose capture_state ∈ {complete, complete_stopped_by_user,
   failed_upstream} for all of its turns,
   AND no unresolved gap rows reference that conversation,
   AND the listing walk reached a terminal page (not a page budget or a cancel)

Everything else is enumerated in coverage_gaps with a reason:
   page_budget_exhausted | pagination_unstable | auth_expired | challenge |
   rate_limited | parse_failed(adapter@v) | detail_unavailable | observer_loss

Opening one known conversation successfully proves nothing about historical coverage; the gate for backfill viability (G3) is defined in terms of listing termination and gap counts, not in terms of "a conversation was archived".

07.5 Degrading safely

Every failure class maps to an account-scoped state, never a global stop: blocked_auth (session expired — pause, keep checkpoint, notify), blocked_challenge (owner-attended solve, then resume), rate_limited (backoff with jitter; lower that account's concurrency to 1), drift (adapter can't parse — stop that operation, keep raw sanitized evidence for reparse, continue with others), unexpected_redirect (treat as ownership-ambiguous: stop, record, require owner review), mutation_suspected (hard stop of replay, catalog demotion).

07.6 If no reliable listing can ever be verified

Then the product is still viable but its promise changes, and the app must say so in the UI and in MCP responses: the archive becomes complete for everything used or opened since installation plus whatever traversal reaches, with an explicit, queryable gap ledger. No heuristics fabricate a "full history" claim; the archive.coverage_report tool returns the difference between "conversations I have" and "conversations I have evidence exist".

08.1 Source of truth: sanitized observations + deterministic projections

Not full event sourcing, not bare normalized rows. Three tiers, each with a different lifetime:

Tier 1 — Observations
Append-only, encrypted envelopes of sanitized evidence (network bodies, WS frames, DOM probe reports, sync pages). Time/size-bounded retention. Rebuildable source for projections.
Tier 2 — Projections

Tier 3 — Artifacts
Content-addressed encrypted blobs (downloads, generated files, images later). Referenced by hash; never inlined into the DB.

08.4 Model identity: keep the layers apart

participant slot "left"           ← position, not identity

    it adds a row and updates the view, with the turn range it actually covers

Analysis cohorts are built from identity_view plus an explicit confidence floor, and every profile reports how many responses came from each evidence kind. A provider name is never treated as a model build; an alias is never merged with a concrete model unless the owner annotates the mapping, and that annotation is itself an observation with source owner_annotation.

08.5 Transactions, recovery, migration, backup

  • Transactions: one transaction per logical evidence unit — a completed response, a sync page, an artifact link. Streaming turns are written as an open row plus appended chunk envelopes; the terminal transaction sets the completeness state. A crash therefore leaves an open turn, which startup recovery closes as truncated_observer_loss with a gap row.
  • Crash recovery: WAL mode; startup runs integrity check, closes orphan captures, re-derives job states, and re-attaches observers.
  • Migration: numbered SQL migrations in one transaction, preceded by an automatic encrypted snapshot; failure rolls back and the app starts in read-only mode with a diagnostic instead of a half-migrated archive.
  • Backup/restore: VACUUM INTO a new encrypted file plus an artifact manifest; restore validates schema version, key availability and artifact hash coverage before switching over. Backups are encrypted with the same archive key (portable only with the Keychain-wrapped key export, which is an explicit, separately confirmed action).

Safe resource references: a secret-bearing URL is stored as {host, path_template, object_key_sha256, expires_seen_at}; re-fetching later requires re-deriving a fresh URL through an owner-session read, which is the correct behaviour because an expired signed URL is worthless anyway.

09.4 Keeping Arena content away from local privilege

  • Arena renderers are sandboxed, context-isolated, node-free, and have no preload bridge beyond a one-way DOM-observation channel that accepts no commands.
  • The MCP surface is a UNIX socket with 0600 permissions inside the vault, not a TCP port: page content cannot reach it with fetch even if it tried, and no CSP/localhost trick applies.
  • The GUI never renders Arena-controlled HTML; transcripts are displayed as text/Markdown with a sanitizer, links are non-navigable by default, and images render from the artifact store only.
  • Archived text reaching an LLM through MCP is wrapped as untrusted data with an explicit content-origin marker (§10.4).

Server

10.5 Authorization is not content

Guard for destructive actions

  1. All retrieved text — prompts, responses, titles, tool traces, diagnostics, drift samples — is returned wrapped with content_origin:"archived_untrusted" and is never interpreted by the app as a directive.
  2. archive.delete_account_data and archive.delete_everything require a confirmation token minted only by the GUI Danger Zone (the trusted control channel): the owner sees the exact scope, the exact counts and the account label; the app mints a single-use token bound to {scope, account_id, counts, partition_path_sha256, expiry ≤ 5 min}.
  3. The tool recomputes the scope digest at execution time. Any drift in counts or scope → E_SCOPE_MISMATCH, no deletion. A reused or expired token fails closed.
  4. No MCP call can mint a token. No archived text can mint a token. The GUI cannot be driven into minting one through MCP (browser.* tools cannot reach the local GUI view).
  5. Single-conversation deletion is lower risk but still requires {account_id, source_id, expected_title_sha256} so a hallucinated id cannot delete a different record.

10.6 GUI ≡ MCP

Both call one ApplicationServices façade (accounts, capture, sync, archive, export, analysis, diagnostics, deletion). The GUI adds only: sign-in windows, the Danger Zone token minting, and human-readable rendering. A contract test enumerates the façade's methods and fails the build if any method lacks a corresponding MCP tool — that is the mechanical guarantee that nothing becomes GUI-only.

11 Local analysis: defensible profiles first

11.1 Cohorts before statistics

A cohort is a set of responses grouped by identity_view at or above a stated confidence, restricted to capture_state ∈ {complete} by default. Every report prints its cohort card: n, evidence-kind breakdown (revealed / selected / displayed / blind-only), date range, mode mix, surface mix, language mix, and the share of responses excluded for incompleteness. A profile without a cohort card is a bug.

11.2 Deterministic metric set (v1)

Shape
Response length (chars, words, sentences); paragraph and sentence length distributions; code-block count and length; list/table/heading counts; Markdown feature usage; code-to-prose ratio; citation/link density.
Texture
Type-token ratio and MTLD; repeated n-grams (2–5) with document-frequency weighting; punctuation profile (em-dash, semicolon, ellipsis, quote style); casing patterns; emoji use; heading phrasing patterns.
Rhetoric
Opening/closing templates; transition inventory; hedges, qualifications, apologies, refusals and uncertainty markers by regex + curated lexicon, each reported with example excerpts and a false-positive caveat.
Conditioning
Every metric sliceable by prompt type, topic cluster, mode (battle/direct/side-by-side), surface, language, conversation position (first vs later turn), and time bucket, so drift and confounds are visible rather than averaged away.

The comparison the corpus actually supports is the paired one: battle and side-by-side modes give the same prompt to two participants at the same moment. Paired within-conversation comparisons (Wilcoxon signed-rank on paired metrics, bootstrap CIs) are far more defensible than cross-cohort means over a single user's unbalanced corpus, and they are the default presentation.

11.4 Embeddings and local ML: gated, not assumed

Entry gate: (a) deterministic features cannot separate cohorts that the owner has a concrete reason to compare; (b) at least a stated minimum of labelled, complete responses per cohort exists; (c) a reproducibility plan is in place. Only then: node-llama-cpp with a pinned GGUF embedding model, weights downloaded once and pinned by SHA-256 in the repo, model id + quantization + preprocessing version recorded in analysis_runs, everything offline afterwards. Vectors live in the encrypted DB. If the gate is not met, this stays unbuilt — it is packaging and reproducibility cost with no analytical return.

11.5 Similarity / fingerprinting experiments (later, hypothesis-only)

protocol:
  split      : group-aware by conversation and near-duplicate cluster (MinHash/LSH on
               shingles) so branches, regenerations and re-asked prompts cannot straddle folds
  controls   : (a) negative control — same model, different weeks, must not be trivially
                   separable from itself; (b) prompt/topic control — train on one topic
                   cluster, test on another; (c) shuffled-label control must collapse to chance
  calibration: probability calibration on a held-out fold; report ECE alongside AUC
  unknowns   : abstention class with a threshold chosen on validation, reported coverage
  reporting  : every result is "similarity to an archived corpus, confidence X", never
               "this is model Y"; inferred identity is stored in a separate table from
               observed identity and can never feed identity_view
stop rule  : if the lower bound of the held-out, topic-controlled AUC CI does not clear a
             predeclared threshold after the predeclared corpus growth, the experiment is
             abandoned and the result recorded as a negative finding — not iterated until
             it looks good.

12.3 Modality extension points (text ships first)

  1. Search responses & citations — structured citation rows attached to turns; entry condition: citation payloads appear in captured bodies, not only in DOM.

12.4 Measurement and quotas (values set from measurement, not invented)

The app ships a measurement harness from G1: sampled per-process RSS (app.getAppMetrics), DB file size, artifact bytes, observation-log bytes, capture lag (first byte → envelope persisted), parse failure rate, and per-account request rates — all exposed through diag.health and recorded to a local time series. Quota knobs whose defaults are chosen after a week of real use: max retained body bytes per response; observation retention window (days); artifact bytes per conversation and per account; disk-cache size per partition; max concurrent sync requests globally and per account; log rotation size. Each knob has a documented behaviour when exceeded (metadata-only downgrade, oldest-evidence eviction, or job pause) — never silent truncation.
