01Executive architecture decision

Decision

Build v1 as an Electron application that owns its Chromium runtime, with one persistent Electron Session partition per Arena account and Chrome DevTools Protocol attached from the main process as the primary capture surface.

The application service layer, capture pipeline, storage layer and MCP server are TypeScript running in the Electron main process (or in dedicated child processes it supervises). Arena renderers are treated as hostile content with no Node, no privileged bridge, and no path to the archive, the keys or the MCP interface.

Reversal condition (single, explicit): if the first falsification spike shows that maintained Electron/CDP/session APIs cannot reliably observe an architecture-critical class of Arena traffic — most plausibly streamed response bodies or service-worker-originated requests — and a focused CEF spike shows that CefResourceRequestHandler::GetResourceResponseFilter does observe it, the browser layer is rebuilt on CEF and the rest of the architecture (storage, domain model, sync, MCP, analysis) is retained unchanged.

The one-paragraph argument

The existing extension recorder fails because it observes Arena from inside a page-world/extension runtime that Arena's own code controls and that the browser can tear down at any moment. The fix is not "more page JavaScript"; it is to move the primary observation point below the page, into the browser process that the application itself owns. Electron gives that with the smallest credible engineering surface: a main-process CDP transport, per-account persistent browser state partitions, session-level download control, and a mainstream TypeScript ecosystem that an AI coding agent can maintain without a C++ toolchain. CEF offers a deeper native interception primitive but costs a C++/Obj-C++ build, framework bundling and Chromium version management; it is the fallback, not the default.

03Why Electron is recommended, and the exact reversal condition

The five properties v1 actually needs

  1. An observation point outside page JavaScript. Electron's webContents.debugger is a main-process CDP transport that receives instrumentation events and sends commands VF. The observer is therefore not code Arena's page can unhook.
  2. Durable, app-owned, per-account browser state. session.fromPartition('persist:…') gives a persistent, app-managed store per partition VF, which is the primitive for simultaneous signed-in accounts.
  3. A real security boundary. Electron's documented renderer posture (context isolation, no Node integration, sandbox, navigation restrictions) lets untrusted Arena content run with no route to archive, keys or MCP SI.
  4. Artifact control. Session-level download interception routes Code Arena outputs and other files into the archive rather than the owner's Downloads folder SI.
  5. Agent maintainability. One language (TypeScript), one package manager, one test runner, no C++ build, no Chromium branch tracking. This dominates for software that AI agents must diagnose and repair autonomously.

What Electron does not prove

HYP That CDP Network instrumentation from the main process yields complete, reconstructable Arena response streams, including any traffic that originates from a service worker or a dedicated worker rather than the top-level frame. CDP's body-retrieval mechanisms are documented for ordinary resources, and streaming bodies historically require either incremental data events plus a body fetch at completion, or request interception. Whether Arena's real streams can be reconstructed byte-accurately, with no dropped prefix and no dropped tail, is precisely what Gate B3/B4/B6 exist to falsify.

Reversal gate — write this into the repository as a decision record

Escalate from Electron to CEF if, and only if, all three hold

  1. Gate B3, B4 or B6 fails: a class of Arena traffic that is required to reconstruct conversations (streamed assistant output, a WebSocket frame stream, or worker/service-worker-originated requests) cannot be observed or reconstructed reliably through maintained Electron/CDP/session APIs, after a bounded, documented attempt that includes request interception and target attachment, not merely passive Network events.
  2. A focused CEF spike observes that same traffic class through GetResourceResponseFilter (whose callbacks explicitly contemplate requests with NULL browser/frame originating from service workers VF) or through GetResourceHandler.
  3. No maintained Electron workaround — page-world instrumentation as secondary evidence, protocol-level Fetch-domain interception, or a local proxy — reaches acceptable completeness.

If the requirement is unmet by both Electron and CEF, only then investigate Chromium customization. A custom Chromium fork is a last resort; for single-owner private software the maintenance cost of tracking upstream security releases is likely to exceed the value of the missing capture class, and the honest alternative is to record the gap as a known completeness boundary.

Cost of reversal, stated up front

The architecture is deliberately layered so that reversal is expensive but bounded. Only packages/browser and packages/capture's transport adapters are runtime-specific. The sanitizer, protocol catalog, domain model, storage, sync, MCP and analysis packages consume a runtime-neutral CaptureEvent stream. A CEF build replaces the producer of that stream and the shell process, plus an IPC hop from a native host into the TypeScript services (or a port of the service layer's host process). That is a serious rewrite of one layer, not of the product.

Specific rejections

Swift + WKWebView — rejected as primary
Native does not mean deeper. The public interception surface is the weak point: WKURLSchemeHandler exists for custom schemes and throws if registered for a scheme WebKit handles internally SI, so it is not a hook for Arena HTTPS; and the historical multi-process-pool isolation trick is deprecated to a no-op SI. Isolation via distinct WKWebsiteDataStore instances is plausible, but the core requirement — reliable body-level capture of streaming first-party traffic outside page JS — would fall back to injected JavaScript, i.e. the failure mode of the rejected extension with extra steps. It keeps its genuine advantages (lowest footprint, best OS integration) and remains the right answer for a hypothetical future variant that does not need network capture.
Tauri / Wry — rejected as primary
On macOS it renders with the system WebKit webview SI, so it inherits the WKWebView capture ceiling. Lightness is not the first priority; capture correctness is. Choosing Tauri would mean building bespoke interception machinery (e.g. a local TLS-terminating proxy) whose complexity and fragility exceed the Electron path.
MV3 extension + native companion — rejected, and it is the baseline being replaced
This is the owner's current arena-exporter situation. Structural problems: the observer depends on page/runtime interception, the extension service worker can be suspended mid-stream, artifact handling is indirect, a companion process is required anyway for durable storage, and the browser profile is not app-owned so two Arena accounts cannot be guaranteed isolated capture pipelines. It is excluded by requirement, and independently it is the weaker design.
Explicit export/import with no embedded browser — rejected as the product
It cannot capture live streams, cannot observe stopped/failed generations, cannot see post-vote reveals as events, and depends on an export facility whose existence and completeness are UNK. It survives in the architecture as an import adapter (see §11) so that any future official export can be ingested with clearly-labelled provenance.

  • Every channel is declared in a single typed registry: channel name, direction, zod-style runtime validator, required capability, whether it is destructive.

Minimum supported macOS

Minimum: macOS 14 (Sonoma), Apple Silicon only, arm64-only build. REC

Rationale: (a) recent Electron release lines have been raising their macOS floor, and targeting a floor at or above the current Chromium requirement avoids fighting the toolchain; (b) macOS 14 is comfortably modern for Keychain/Secure Enclave-adjacent APIs, hardened runtime and notarization-if-ever-needed, so no legacy code paths are required; (c) the development machine runs macOS 27, so choosing a floor several major versions below gives room to defer OS upgrades without an emergency port, while not committing to supporting genuinely old releases that no one will run; (d) arm64-only removes universal-binary size and native-module cross-build complexity on an M3 Pro. If a future Electron upgrade raises its own floor above macOS 14, the floor moves with it and the ADR is updated — this is cheap because there is exactly one deployment target: the owner's machine.

Partition naming and identity

REC Partition names must not embed email addresses; the partition UUID is an opaque local identifier, so the on-disk directory name leaks nothing about which Arena account it serves.

Isolation rules

  • One Session per account via session.fromPartition('persist:arena-…'); because fromPartition returns the existing session for a partition string VF, the partition manager is the single owner of that mapping and no other module may call it.
  • Cookies, local/session storage, HTTP cache and service-worker registrations are partition-scoped by Chromium's own storage partitioning SI — Gate B2 exists to verify this empirically rather than trust it.
  • Each partition gets its own capture coordinator, its own CDP attachment, its own gap ledger, its own job queue and its own sync cursor.
  • Account authority transitions are local: A going EXPIRED pauses A's sync and marks A's live capture PAUSED_AUTH; B is untouched and this is asserted by Gate B14.
  • Identity change detection: if the identity fingerprint observed in a partition changes, the coordinator halts capture for that partition and raises IDENTITY_MISMATCH. It never rebinds existing records to a new account automatically; rebinding requires an explicit owner directive with a destructive-intent token, because rebinding is effectively a provenance rewrite.
  • Cross-account merge is structurally impossible: source identifiers are stored as (account_id, source_id_namespace, source_id) and uniqueness constraints always include account_id.

Authentication workflow

Arena's own UI is authoritative. The owner signs in with email inside the partition's renderer; verification links, one-time codes, MFA, CAPTCHA and redirects are handled by the owner in that window exactly as in a normal browser. Persistent sign-in state lives in the partition's browser-managed storage — that is the point of persist:. Google OAuth and passkeys are explicitly not requirements; if a third-party flow misbehaves in the embedded browser it is recorded as a limitation, not a blocker. Cookies and tokens are never imported from Safari or Chrome, and never copied into the archive; native sync requests, if they exist at all after Gate H1, execute inside the correct partition's network stack so that credentials are supplied by the browser rather than handled by application code.

08Discovery and the protocol catalog

Arena's internal endpoints are undocumented and will change. Rather than hard-coding assumptions, discovery is a maintained product capability: the app builds and continuously updates a machine-readable catalog of the first-party operations it has actually observed in the owner's own sessions.

Terminology discipline

  • Authenticated first-party read — a request to Arena's own origin, made with the owner's own live session, of the kind the Arena web app itself makes.
  • Internal/undocumented endpoint — such a request whose contract Arena does not publish. This is normal and is not a bypass.
  • Automation/anti-bot compatibility — making an app-owned browser behave like a browser (real navigation, real headers supplied by Chromium, owner-driven challenges).
  • Access-control workaround — attempting to reach data the owner's session is not entitled to. Out of scope, never implemented, and any adapter that appears to require it is deleted rather than shipped.

Sanitization is a precondition for durable persistence

Fail closed. If the sanitizer cannot classify a header, a cookie-like field, or a query parameter, the observation is not persisted durably; it is counted, a SANITIZER_FAILED marker is written with no payload, and a diagnostic is raised. A credential-dumping HAR is never produced.

Always stripped before durable write: Authorization, Cookie/Set-Cookie, CSRF tokens, bearer/refresh tokens, OTP values, OAuth codes, password fields, signed-URL query parameters (detected by entropy + known parameter-name patterns + allowlist-only retention of parameters), and any response field not required by an adapter. Retention is allowlist-shaped: an adapter declares the fields it needs; everything else is dropped or replaced by a structural placeholder (`{"__redacted":"string","len":42}`) that preserves shape for drift detection without preserving content.

Drift detection

Each observation contributes a structural fingerprint (sorted key paths + value type kinds, not values). When a fingerprint diverges from an adapter's expected family, the entry flips to DRIFTING, the adapter is marked degraded, the raw sanitized observation is still retained for reparse, and diagnostics.drift exposes it over MCP. Parsing never silently coerces unknown shapes into the normalized model.

09Live capture architecture

Attachment strategy

  1. Create the partition session, then the WebContents, then webContents.debugger.attach() before the first navigation to Arena VF (the API is a plain main-process object with attach/sendCommand/message).
  2. Enable the instrumentation domains required for network observation, and enable target discovery/auto-attach so that child targets (iframes, workers, popups) are attached and flagged for their own sessions. HYP The exact CDP method names and parameters for auto-attach must be read from the shipped Chromium's own protocol descriptor at spike time, not assumed; the spike records the resolved names in the ADR.
  3. Route every CDP message with its sessionId so that events from child targets are attributed to the right frame/worker and to the right account partition.
  4. On detach, immediately write a gap record covering the detach window and attempt reattachment with bounded backoff. Because opening DevTools on the attached WebContents detaches the debugger VF, the app controls DevTools access and treats manual DevTools use as an explicit, logged capture interruption.

Stream reconstruction

The assembler keeps a per-request buffer keyed by (sessionId, requestId) with: first-chunk timestamp, ordered chunk records (offset, length, rolling digest), an end reason, and flags for "attached after start" and "terminated without completion". Three outcomes are possible and are recorded distinctly: fully reconstructed with a verifiable digest; reconstructed with a known missing prefix or suffix; or metadata-only, where the transport was observed but content was not retrievable. HYP Which outcome dominates for Arena's assistant streams is the single most important unknown and is Gate B4.

Secondary DOM evidence

A small, read-only observer may run in the Arena renderer to record rendered-state markers (a turn reached a terminal rendered state, a stop control was pressed, a reveal element appeared). It is explicitly labelled DOM_SECONDARY, it carries lower provenance rank than network evidence, it is never the sole basis for marking a response complete unless the completeness rules in §10 permit a UI-only reconstruction, and it uses no privileged bridge — it posts structured messages that the main process validates and rate-limits. If Arena's CSP or scripting policy prevents this, the app loses secondary evidence but not primary capture.

Downloads and artifacts

Session-level download interception routes files produced by Arena Code and other surfaces into the encrypted blob store with an artifact record bound to the account, conversation and turn where known SI. The owner's Downloads folder is not used as an intermediate staging area, which removes one of the rejected baseline's operational pain points.

10Completeness states, reconciliation and idempotency

Completeness is a state machine, not a boolean

type CaptureCompleteness =
  | 'COMPLETE'                 // terminal stream marker observed + digest verified
  | 'STOPPED_BY_OWNER'         // explicit stop evidence
  | 'BACKEND_FAILED'           // server/model error evidence

  | 'BACKFILLED'

  evaluatedAt: IsoTimestamp;
  adapterVersion: number;

Reconciliation rules

  1. Observations are append-only; current state is derived. The reconciler recomputes a turn's current state from its observation set, so replaying observations after a parser fix is always possible.
  2. Provenance rank. Network-verified > backfilled-detail-read > DOM-secondary > owner annotation for content; for identity, revealed > observed-in-payload > UI label > owner annotation > inferred. Lower ranks never overwrite higher ranks; they are stored alongside.
  3. Additive reveals. A post-vote model reveal creates a new identity observation with its own timestamp. The archive never rewrites history to pretend the identity was known during the blind phase.
  4. Idempotency. Every observation carries a deterministic key: hash(accountId, sourceIdNamespace, sourceId, mechanism, transportRequestKey, contentDigest). Re-ingestion is a no-op. Out-of-order arrival is fine because ordering is by observed sequence number plus server-provided ordering fields when present.
  5. Conflicts are data. If two high-rank observations disagree on content, the turn moves to CONFLICTING_EVIDENCE, both are retained, and diagnostics.capture_gaps surfaces it. Nothing is silently chosen.
  6. Overlap with sync. Live capture and backfill can produce observations for the same turn concurrently; the deterministic key plus a per-turn advisory lock makes this safe, and the backfilled observation does not downgrade a live-captured COMPLETE.

Sync engine

interface SyncCheckpoint {
  accountId: Uuid;
  adaptorId: string;            // which list operation produced this cursor
  adaptorVersion: number;
  cursor: string | null;        // opaque; whatever the observed listing uses
  highWaterMark?: IsoTimestamp; // newest item fully ingested
  lowWaterMark?: IsoTimestamp;  // oldest item fully ingested (backward paging)

  itemsSeen: number; itemsIngested: number; itemsSkippedDuplicate: number;
  overlapPolicy: 'REPROCESS_IDEMPOTENT';
  lastError?: { category: SyncErrorCategory; at: IsoTimestamp; retryAfterMs?: number };
  coverageGaps: Array<{ fromTs: IsoTimestamp; toTs: IsoTimestamp; reason: string }>;
  state: 'IDLE'|'RUNNING'|'PAUSED_AUTH'|'PAUSED_CHALLENGE'|'RATE_LIMITED'|'CANCELLED'|'FAILED';
}
  • Per-account schedulers. Concurrency across accounts is safe because each scheduler uses a different partition, different credentials, different cursors and different DB rows keyed by account_id; the only shared resource is the database, which is protected by short transactions and WAL. REC Default to at most one in-flight request per account and at most two accounts syncing concurrently, both configurable; this keeps request rates polite and memory bounded on 18 GB.
  • Within an account, requests are serialized to avoid tripping rate limits and to keep cursors coherent.
  • Resume restarts from the checkpoint and re-processes the boundary page deliberately; idempotent keys make overlap free.
  • Cancellation is cooperative and leaves a valid checkpoint.
  • Auth expiry / challenge pauses that account only, sets NEEDS_OWNER_INTERACTION, and surfaces it in sync.status and the diagnostics UI.
  • Rate limiting uses bounded exponential backoff with jitter, capped retries, and a per-account circuit breaker.

What "synchronized" means, precisely

For account A at time T: every conversation returned by the verified listing operation between A's low- and high-water marks has a stored conversation record; for each such conversation, a detail read has been ingested at adapter version V; and the account's coverageGaps list is empty for that range. Any other state is reported as "partially synchronized" with the explicit gap list attached. The MCP surface returns this structure rather than a green checkmark.

Operational semantics

Transactions

One ingestion unit = one transaction: sanitized observation insert + derived normalized upserts + FTS update. WAL mode; short write transactions; readers never block on the capture path.

Crash recovery

In-memory stream buffers are volatile by design. On restart, any turn last seen in STREAMING is promoted to MISSING_SUFFIX with a gap record rather than left ambiguous. SQLCipher encrypts WAL pages VF, so recovery does not leak plaintext.

Migrations

Numbered, forward-only SQL migrations with a recorded schema version; each migration ships a synthetic fixture DB and a round-trip test. Adapter version changes are data-level, not schema-level, so reparsing does not require migration.

Reprocessing

reparse(adaptorId, fromVersion) replays retained sanitized observations through the new parser into a shadow transaction, diffs against current state, and writes only additive corrections; it never deletes stronger evidence.

Backup/restore

Backup = consistent SQLCipher copy (via the backup API or a checkpointed file copy) + blob directory + a manifest with digests. Restore verifies digests and refuses to mix a DB with a mismatched blob manifest.

Deletion cascades

Foreign keys cascade from account → conversation → branch/turn/revision/artifact; FTS rows, blobs, checkpoints, dedup keys and analysis results are removed by explicit deletion steps enumerated in §14, not left to chance.

14Encryption, local data protection and deletion

Key hierarchy

Secure Enclave-backed access control (biometry/passcode policy, app-scoped)
        │
   macOS Keychain item  ── stores ──▶  ARCHIVE_ROOT_KEY (32 random bytes, CSPRNG)
        │                                   │
        │                                   ├─▶ SQLCipher raw key  (PRAGMA key = "x'…'")
        │                                   ├─▶ HKDF → blob-store key-wrapping key
        │                                   └─▶ HKDF → idempotency/fingerprint salt
  • VF SQLCipher accepts raw binary key data instead of a passphrase, which is exactly what is wanted: no human password, no PBKDF2 stretching of a weak secret, and the Keychain provides the access control.
  • REC The root key is generated once with a CSPRNG, stored in the Keychain with a restrictive access control (this-device-only, app-scoped), and never written to configuration, logs, exports, diagnostics or fixtures. The application refuses to start durable ingestion if the key cannot be retrieved.
  • VF SQLCipher encrypts page data in rollback journals and in WAL files, and warns that other transient files are unencrypted unless file-based temporary storage is disabled. The build therefore must disable file-backed temp stores (SQLITE_TEMP_STORE=2 / PRAGMA temp_store = MEMORY) — this is a build-configuration acceptance check, not a preference.
  • FTS5 indexes live inside the encrypted database, so search content is protected by the same page encryption.

Large artifacts

Blobs above a configurable threshold are stored as individual files in an application-support directory, each encrypted with a per-blob random key using an AEAD, with the per-blob key wrapped by the HKDF-derived wrapping key and stored in the DB alongside the digest and nonce. Benefits: the database stays compact and fast to back up, deletion is a file unlink plus row delete, and a corrupted blob cannot poison the DB. Integrity failures surface as `BLOB_CORRUPT` rather than silently returning garbage.

Deletion with a two-step destructive intent token

interface DestructiveIntent {
  intentId: Uuid;
  action: 'DELETE_CONVERSATION' | 'DELETE_ACCOUNT_DATA' | 'DELETE_ALL';
  scope: { accountId?: Uuid; conversationId?: Uuid };
  // Exact, pre-computed impact so the caller confirms a known blast radius:
  impact: { conversations: number; turns: number; revisions: number;
            artifacts: number; artifactBytes: number; analysisRuns: number;
            syncCheckpointsReset: string[] };
  nonce: string;            // random, single-use
  issuedAt: IsoTimestamp; expiresAt: IsoTimestamp;  // short TTL
  requiresOwnerUiConfirmation: boolean;             // true for ACCOUNT_DATA and ALL
}
  1. Caller invokes archive.prepare_delete_*; the domain layer computes the impact and issues an intent with a nonce.
  2. Caller invokes archive.confirm_delete_* with intentId + nonce; the impact snapshot is re-validated, and if the scope changed the intent is rejected and must be re-prepared.
  3. For account-wide and archive-wide deletion, a trusted local UI confirmation is additionally required. Archived Arena content can neither mint nor satisfy an intent: intents are issued only to authenticated local callers over the trusted IPC/stdio channels, and no parser or analysis code path can call the issuing API.

What deletion actually removes

  • Normalized rows via cascade (conversation → branch → turn → revision → artifact rows, votes, identity observations).
  • Sanitized source_observation rows in scope, plus their payload blobs.
  • FTS5 entries (explicit delete, since external-content FTS does not clean itself).
  • Analysis runs/results whose cohort intersects the deleted scope — these are derivatives and are recomputable.
  • Encrypted blob files (unlink) and their wrapped keys.
  • Sync checkpoints and dedup/idempotency markers for the scope, so a future re-sync re-ingests rather than skipping as duplicate.
  • Optionally, on account deletion: the browser partition directory, which signs that account out. This is a separate, explicitly-flagged sub-option because it is a different kind of destruction.
  • Then VACUUM (or an explicit rebuild) so freed pages are reclaimed.

Deletion never touches Arena's servers. Local deletion is local. Remote deletion would be a separate, explicitly-built feature performing a distinct remote operation, and it does not exist in v1. Backups and prior exports are outside the application's reach and are reported as such.

Cross-cutting semantics

Jobs & disconnect

Long-running work returns a jobId immediately. Jobs are owned by the application, not by the MCP connection: a client disconnect does not cancel a job. jobs.events streams progress while connected; on reconnect the client replays from a job sequence number. Cancellation is explicit via jobs.cancel.

Idempotency

Mutating tools accept idempotencyKey; a repeat with the same key returns the original job/result rather than starting a second one. Destructive tools additionally require the single-use nonce, which is deliberately not idempotent-safe: a replayed nonce is an error.

Capabilities

Every result may carry capability.available=false with a reason such as ADAPTER_DEGRADED: arena.history.list drifting. Agents are expected to read this instead of guessing why data looks thin.

Pagination

Opaque cursors, stable ordering by (timestamp, id), truncated flag when a result set was clipped by limits. No offset pagination.

16Deterministic local analysis

v1 analysis is entirely deterministic, transparent and cheap — no embeddings, no local LLM, no GPU dependency. Every number must be explainable by reading a function, and every run records its code version, parameters and cohort so it can be reproduced exactly.

Structure metrics

Response length (characters, words, tokens-by-a-fixed-rule), paragraph count and length distribution, sentence length distribution, heading counts and depth, list usage and nesting, table usage, code-block count and length, code-to-prose ratio.

Lexical metrics

Type-token ratio with length correction, hapax rate, recurring n-grams (n = 1–5) with document-frequency weighting, vocabulary overlap between cohorts, function-word frequency profile.

Surface habits

Punctuation frequencies (em dash, semicolon, ellipsis, parentheses), quote style, casing patterns, emoji use, Markdown emphasis habits, bullet glyph and numbering habits, citation/link formatting patterns.

Discourse habits

Opening phrase families, transition markers, conclusion/summary markers, qualification and hedging markers, uncertainty markers, refusal/apology language, "as an AI"-class disclaimers, direct-address frequency.

Cohorts and stratification

A cohort is an explicit, serialized filter: identity evidence (with the kind of evidence required, e.g. "revealed only"), mode, prompt-type label, topic label, language, date range, conversation position (first turn vs later turns), account, and completeness floor (e.g. exclude anything not COMPLETE). Every result carries the cohort definition and n at each stratum. A profile that cannot report its sample counts is a bug.

Confounders — stated in every report the app generates

  • Single-user selection bias: the corpus reflects what this owner asks, not what models do in general.
  • Prompt-habit correlation: recurring personal phrasings induce recurring response shapes.
  • Topic and language imbalance across models.
  • Conversation context length and position effects.
  • Arena-side hidden prompts, model system prompts, decoding parameters, tool availability, routing and aliasing — all unobservable from the client.
  • Temporal model updates behind a stable label; safety-layer changes; Arena post-processing of output.
  • Comparison-mode effects: a response generated in a battle may differ systematically from a direct conversation.

REC Embeddings or local ML enter only after an explicit empirical gate: a deterministic-feature baseline is built, its held-out discrimination and stability are measured, and only a documented, repeated shortfall justifies the dependency. "It sounds sophisticated" is not a gate.

17Later fingerprinting experiments and other modalities

Fingerprinting discipline

Stylistic similarity is a hypothesis about text, never proof of model identity. Any experiment must implement all of the following or it does not run:

  • Held-out conversations, not held-out turns — and all branches, regenerations and near-duplicates of a conversation stay in the same split, or the evaluation leaks.
  • Prompt/topic controls: compare within matched prompt families, and report performance both matched and unmatched.
  • Negative controls: shuffled labels, and a same-model-two-time-periods control to detect temporal rather than model signal.
  • Calibration: report calibrated probabilities, not raw scores; include a reliability check.
  • Unknown-class rejection: the classifier must be able to answer "not confidently any known class".
  • Temporal validation: train on earlier data, test on later data, to expose model-update drift.
  • Reproducible preprocessing pinned to a code version and recorded in analysis_run.
  • Strict separation preserved: any output is written as INFERRED_STYLISTIC and cannot overwrite observed or revealed identity.

No universal minimum sample size is invented. Instead each experiment reports bootstrap confidence intervals and a stability curve over subsample sizes; if the curve has not stabilized, the honest conclusion is "insufficient evidence", and the experiment either collects more data or stops.

21Testing strategy

Synthetic tests (no Arena, no network)

  • Stream chunk splitting at adversarial boundaries (multi-byte UTF-8 split across chunks, zero-length chunks, chunk after terminal marker).
  • Duplicate and out-of-order observation delivery; assert idempotent convergence.
  • Reconnect mid-stream; assert MISSING_PREFIX/MISSING_SUFFIX, never COMPLETE.
  • Truncated streams and never-terminated streams with timeouts.
  • Parser drift: mutate a fixture's shape; assert catalog flips to DRIFTING and no coerced parse occurs.
  • Sanitizer failure injection; assert fail-closed and zero payload persistence.
  • Cross-account source-ID collision: identical source ids and identical text in two accounts; assert two records, zero merges.
  • Crash recovery: kill during transaction; assert consistency and correct completeness downgrade.
  • Deletion: assert rows, FTS, blobs, checkpoints, dedup keys and analysis derivatives all disappear; assert re-sync re-ingests.
  • Migrations: forward migration over a populated fixture DB; digests before/after.
  • Corrupted encrypted blob: assert BLOB_CORRUPT, not silent garbage.

Platform tests (Electron, no Arena)

  • Debugger attach/detach lifecycle against a local test server, including the DevTools-detach hazard.
  • Partition isolation using a local server that sets cookies/localStorage/SW registrations.
  • Download interception into the blob store.
  • Streamed-response reconstruction against a local SSE/chunked/WebSocket server with known digests — this is the rehearsal for Gate B4 and can run in CI.
  • Child-target attachment against a local page that spawns iframes, workers and popups.

Owner-session Arena acceptance tests

Required for every claim about real Arena behaviour: stream transport per mode, capture completeness, reveal association, email sign-in, backfill, simultaneous account use. These are run manually by the owner with the harness recording machine-readable results; they are not in CI, and their absence is what keeps the corresponding claims labelled HYP throughout this document. Synthetic tests can never substitute for them.

Fixture hygiene, enforced in CI: no real credentials, no raw owner traffic, no real conversation text in the repository. A pre-commit and CI scan rejects files containing cookie/authorization-shaped strings, JWT-shaped strings, or high-entropy blobs above a threshold in fixture directories.

No benchmark numbers are invented here. Instead the application ships instrumentation and configurable quotas, and the Phase 1/3 harness records actual figures on the owner's M3 Pro / 18 GB machine.
