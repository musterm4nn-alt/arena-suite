Arena Archive

A dedicated macOS browser application that records, backfills, encrypts, and analyzes the owner's own arena.ai conversations across multiple simultaneously signed-in Arena accounts — operated primarily by AI agents through a local MCP server.

One-run architecture & implementation plan · Apple Silicon (M3 Pro, 18 GB) · deliverable of a planning task, not an implementation. Evidence labels used throughout: Verified fact confirmed against a primary source or direct observation during this run · Strong inference indirect evidence, missing confirmation named · Hypothesis to test unverified, smallest test specified · Recommendation a design choice, not an empirical claim · Unknown no useful evidence either way.

0Decision summary

Selected architecture

An Electron application owning a full Chromium runtime, with one persistent Chromium session partition per Arena account, and a capture plane built on the Chrome DevTools Protocol (CDP) attached from the privileged main process — Fetch-domain pause-at-response for request/response bodies and streams, Network domain for WebSocket frames and EventSource messages, Target.setAutoAttach for workers, and an escalation path to a browser-level CDP connection for full target coverage. Downloads are owned by the app via session.will-download. Storage is a SQLCipher-encrypted SQLite database plus per-file encrypted artifacts, keyed from the macOS Keychain. The primary operating surface is a local MCP server; the GUI is a thin diagnostics shell over the same services.

The one-sentence reason: among maintained, agent-friendly stacks, only a Chromium-embedding runtime gives out-of-band, network-layer access to response bodies, streamed chunks, WebSocket frames, worker traffic, and downloads across isolated concurrent profiles — the exact capabilities whose absence broke the Manifest V3 extension baseline. WKWebView-based shells (native Swift, Tauri/Wry) own the window but not the network plane: their capture story collapses back to page-world monkey-patching or TLS interception, which this project explicitly set out to escape. CEF matches Chromium's capability but at a C++ integration and build cost that is hostile to autonomous agent maintenance. Section 3 defends this in detail and states the evidence that would force a change.

Application shape
Single Electron app, single Chromium instance; per-account WebContentsView tabs; no second browser engine, no resident helper daemons.
Capture plane
CDP from main process (out-of-band, pre-page); DOM evidence from an isolated-world observer (secondary evidence only — not page-world patching).
Backfill
Replay of discovered owner-history read endpoints inside the owning account's session partition (cookies never extracted); UI-traversal fallback. §7.
Storage
SQLite + SQLCipher-compatible cipher (better-sqlite3-multiple-ciphers), FTS5 inside the encrypted DB, per-file AEAD-encrypted artifact store. §8–9.
Key custody
Random 256-bit archive key held in macOS Keychain (@napi-rs/keyring; Electron safeStorage as fallback wrapper). §9.
Automation surface
Local MCP server (official TypeScript SDK), stdio launcher bridging to a Unix-domain socket with a 0600 token; ~26 tools covering 100% of GUI capability. §10.
Analysis
Deterministic corpus statistics in a Node utility process first; embeddings/ML behind an explicit entry gate. §11.
Minimum macOS
Recommendation macOS 14 (Sonoma) as the app's declared minimum — comfortably above Electron's documented floor, low back-compat surface, no benefit in supporting older releases for a single machine running macOS 27. Strong inference current Electron supports macOS 11+; confirm the exact floor of the pinned Electron major at pin time (test: read the pinned release notes).
Fixed requirement honored
The recommendation is not a browser extension, chrome.debugger extension, extension + native host, or extension + companion. The extension baseline appears only as a rejected comparator (§3.3) and a capture-depth benchmark (§13, gate G2).

What would reverse this decision

  • R1. If the falsification spike (gate G1/G2, §13) shows Electron's CDP surface cannot observe Arena's service-worker or worker-mediated traffic and the browser-level CDP escalation (§6.2) also fails → move to CEF (capability-equivalent, higher cost), and only past CEF to a Chromium fork (explicit last resort, §3.2).
  • R2. If Arena's delivery hardens against embedded Chromium specifically (e.g., attestation that a stock Chromium build cannot satisfy) → re-evaluate toward driving a stock desktop Chrome via its DevTools pipe from a native controller app; this keeps the dedicated-runtime posture while changing the embedding. Hypothesis to test no evidence today that Arena deploys such attestation; the spike records challenge behavior.
  • R3. If steady-state memory with two live account views demonstrably cannot be held under the §4.4 budget on 18 GB → shrink to one live view + hibernated partitions before changing stacks; a stack change on memory grounds alone is not justified (WKWebView saves engine memory but forfeits the capture plane that is the point of the project).

1What was actually researched in this run

This plan was produced in a sandboxed environment without access to a signed-in Arena session, without macOS, and without the ability to run Electron/CEF/WKWebView experiments. That constrains what can honestly be labeled verified. The discipline applied:

  • Consulted during this run (details and URLs in §15): the public identity and rebrand history of the platform at arena.ai; the official Departure Mono distribution (asset downloaded and self-hosted for this report); Electron primary documentation for session partitions and will-download (via a verbatim documentation mirror surfaced in search); community-documented behavior of Electron's webContents.debugger with the CDP Network and Fetch domains, including a known failure mode of Network.getResponseBody under webContents.debugger and the working Fetch-domain pattern.
  • Not performed this run: any authenticated observation of Arena traffic; any measurement of Arena transports, endpoints, payload schemas, or streaming framing; any resource benchmark. Every Arena-protocol statement below is labeled Strong inference or Hypothesis to test and is paired with the first-session test that confirms or kills it.
  • Prior-knowledge claims about platform capabilities (CDP domains, WKWebView API surface, CEF handler model, SQLCipher, MCP SDK) are labeled Strong inference when not re-confirmed against a primary source during this run, each with the named missing confirmation. None of the architecture-critical ones is left without a test and a consequence (§13).
the largest honest gap

The single most consequential unknown is Arena's actual transport mix and worker topology (§2.3). The architecture was chosen to be robust to any answer — fetch-streamed SSE, WebSocket, service-worker-mediated fetch, or a mixture — precisely because that answer is unknown. Gate G1 (§13) exists to replace this uncertainty with owner-session evidence before anything is built on top of it.

2.3 Transport-coverage requirement derived from the unknowns

Because A2/A5 are unresolved, the capture plane must observe, without redesign: fetch/XHR with streamed chunked bodies; EventSource; WebSocket frames; requests initiated by dedicated workers, shared workers, and service workers; and navigations/target swaps mid-stream. This requirement — not any single Arena fact — is what drives the stack choice in §3. A stack that covers all of these is robust to every plausible answer; a stack that covers only page-context fetch (the extension baseline's effective position, and WKWebView's) is a bet on the friendliest answer.

3Architecture selection

The decisive question for every candidate is the same: does owning the window buy deeper capture privileges, or just a window? For each stack below, the assessment separates (a) out-of-band browser/network/target APIs the stack itself provides, (b) what still depends on page injection, and (c) what can miss worker/service-worker or early-navigation traffic.

3.1 Candidates

C1 — Native Swift + WKWebView

Strong inference (Apple's WebKit API surface; not re-read this run — confirming test: 30-minute API audit of WKWebView/WKWebsiteDataStore headers at G0): WKWebView provides navigation delegation, cookie store access, per-webview WKWebsiteDataStore isolation (good multi-account primitives), script injection into page or isolated content worlds, and custom-scheme handlers. It provides no API for reading HTTPS response bodies, streamed chunks, or WebSocket frames at the network layer, no CDP equivalent, and no worker/service-worker observation surface. The two available escalations are both disqualifying:

  • Page-world patching of fetch/ReadableStream/WebSocket/EventSource — exactly the technique whose fragility motivated this project. Owning the window would change nothing about the capture mechanism. Per the task's own framing: this shell would rely primarily on page-world monkey-patching, and is called out as such.
  • Local TLS-intercepting proxy (macOS 14+ can set per-datastore proxy configurations) with an app-local CA. Technically real, but it adds a MITM component, breaks if Arena ever pins certificates, mangles HTTP/2/3 semantics through the proxy, complicates WS frame reassembly, and moves the hardest engineering into the least maintainable place. Hypothesis to test only if Chromium embedding were eliminated; no reason to reach it.

Verdict: rejected. Lightest resident footprint of all candidates (system WebKit, no bundled engine) and excellent Keychain/App Sandbox integration — but it fails the project's defining requirement. Retained influence: its WKWebsiteDataStore-per-account isolation model is mirrored in the Chromium partition design (§4.2).

C2 — Tauri / Wry

Strong inference (Wry's documented backend choice; test as C1): on macOS, Wry is WKWebView. Every capture limitation of C1 applies verbatim, plus a Rust IPC layer between the app and an engine that still cannot see the traffic. Tauri's small-binary advantage is irrelevant when the binding constraint is observation depth, not disk size. Verdict: rejected for the same reason as C1; it would be a WKWebView plan wearing a smaller jacket.

C3 — Electron (Chromium embedding, TS integration) — selected

Out-of-band surfaces the stack itself provides, with no page injection involved:

  • Verified fact (Electron session documentation consulted this run via a verbatim mirror, §15 S6): session.fromPartition('persist:…') yields isolated persistent sessions — separate cookies, storage, cache — and each session emits will-download, letting the app own every download/artifact path directly. This is the multi-account primitive and the download primitive in one API.
  • Verified fact (community-documented behavior with worked code, consulted this run, §15 S7–S8): webContents.debugger attaches a CDP client from the main process. The Fetch domain with requestStage:"Response" patterns pauses responses and yields bodies via Fetch.getResponseBody; notably, Network.getResponseBody is reported unreliable under webContents.debugger in exactly the scenarios that matter, and the Fetch-domain pattern is the documented working alternative. This plan builds on the pattern reported to work and treats the known-flaky call as excluded by default (§6.2).
  • Strong inference (CDP domains are Chromium-upstream engine features, not Electron features — confirming test in the G1 spike): Network.webSocketFrameReceived/-Sent, Network.eventSourceMessageReceived, Fetch.getResponseBodyAsStream for large/streamed bodies, Target.setAutoAttach (+ waitForDebuggerOnStart) for dedicated workers and out-of-process iframes, and Page.lifecycleEvent for navigation bracketing are available to an attached CDP client.
  • Hypothesis to test (the load-bearing uncertainty of this stack, attacked at G1): service-worker targets may not be reachable from a per-webContents debugger, because SWs are session-scoped, not page-scoped. The escalation is designed in from day one: an app-internal browser-level CDP connection (Electron's remote-debugging pipe/port, consumed only by the app itself, never exposed beyond a local pipe) with Target.setDiscoverTargets, auto-attach to SW targets, and Network enabled per target. If both paths fail → reversal R1.
  • Strong inference (Electron API set; confirm at pin time): session.serviceWorkers exposes SW registration/lifecycle visibility, and ses.fetch() issues requests through a session's own network stack and cookie jar — which is what lets backfill reuse the correct account's credentials without ever extracting a cookie (§7.2).

What still depends on injection: only the secondary DOM-evidence plane (§6.3) — reveal banners, vote UI state, rendered labels — running in an isolated content world (Electron preload world, invisible to page JS). No page-world patching anywhere in the design. What can miss traffic: pre-attach races at navigation, and SW-mediated fetch — both have designed answers (attach-before-navigate discipline §6.2; the SW escalation above) and both are exactly what the G1 spike tries to break.

Costs, stated plainly: a bundled Chromium (hundreds of MB on disk; a multi-process runtime in memory — budgeted in §4.4); Electron's release cadence obliges a disciplined periodic major bump; and the security posture must be deliberately configured (§4.3 — contextIsolation, sandboxed renderers, zero Node in any Arena-facing surface). Real but bounded — and it buys the only capture plane that satisfies §2.3 on a maintained, agent-legible stack.

C4 — Chromium Embedded Framework

Strong inference (CEF's long-stable handler architecture; confirming test: build the cefclient sample on Apple Silicon, only if C3 is abandoned): capability-equivalent to Electron at the engine level, with one genuine advantage — CefResourceRequestHandler/response filters sit in the network layer as C++ callbacks, arguably cleaner than CDP pause-and-read; CEF also exposes CDP anyway. Full comparison in §3.2; verdict: runner-up, not winner — a small capability delta against a large, adverse maintenance delta for an agent-operated project.

C5 — MV3 extension + native companion (the existing baseline)

Ineligible by task definition; dissected as a comparator in §3.3.

C6 — Explicit export/import, no embedded browser

Zero capture risk, zero session risk — and it cannot do the job: no live stream capture, no completeness states, no reveal-event timing, and it depends on unverified A7 (an export existing at all). Rejected as primary; retained as a supplementary backfill source with its own provenance class if an official export is discovered (§7.2).

C7 (considered) — driving stock desktop Chrome over its DevTools pipe from a native controller

Included because it is the natural R2 fallback: identical CDP capture plane, real consumer Chrome binary (best anti-detection posture), but the "app" degrades into a controller of an external browser — profile lifecycle, window management, and download ownership all get worse, and daily use becomes two applications. Not selected; preserved as the reversal path if embedded Chromium is ever specifically penalized.

4System topology, trust boundaries, and the multi-account model

4.1 Processes and boundaries

4.2 The multi-account session model

  • Each registered Arena account gets a stable local UUID (acct_…) and Chromium partition persist:arena/<acct_uuid>. Verified fact (S6): partitions isolate cookies, storage, and cache per session. Strong inference (Chromium storage model; asserted empirically at G1): service-worker registrations and CacheStorage are partition-scoped too. The G1 spike includes a leak probe: sign into two accounts, then verify from each context that the other's cookies, localStorage, IndexedDB, SW registrations, and CacheStorage are invisible.
  • Everything downstream is keyed by acct_uuid: CDP client, capture stream, sanitized evidence, catalog entries, sync checkpoints, DB rows, jobs, exports, destructive-action scopes. Account scope is part of record identity (§8.1); no code path writes a conversation row without an acct_uuid.
  • Visible account identity (the email/handle Arena displays) is captured as an identity observation of the partition, re-verified at session start and after auth-shaped traffic. If the identity observed in a partition changes — the owner signed out and into a different account in the same tab — the app freezes capture for that partition, marks the boundary, and requires an explicit owner decision: bind the partition forward to a new acct_uuid, or restore the previous session. Silent rebinding is prohibited; pre-freeze records keep their original scope permanently.
  • Failure isolation: each partition's capture pipeline is an independent state machine. A challenge, sign-out, or CDP detach in one partition pauses that partition only; global pause/stop sits above per-account controls (§6.7).

4.3 Hardening posture

  • Arena views: sandbox:true, contextIsolation:true, nodeIntegration:false, no @electron/remote, webSecurity on, permission-request handler default-deny, setWindowOpenHandler allowlisting Arena-origin and auth-flow popups only — kept in-partition so email-verification redirects and popups complete naturally (and OAuth-style popups are merely not blocked, per the non-requirement).
  • The preload exposes exactly one one-way channel — observerEvidence.emit(payload) → main — in the isolated world. No filesystem, no generic IPC invoke, no archive API. Main treats every payload as untrusted Sanitizer input.
  • MCP is unreachable from any renderer: Unix domain socket under ~/Library/Application Support/ArenaArchive/run/ (0700 dir, 0600 socket, rotating bearer token file); renderers have no socket capability at all.
  • Archive key: only KeyCustodian in main-process memory; utility processes receive purpose-scoped derived subkeys (§9.1), never the master.

5Discovery and the protocol catalog

5.1 Discovery is a product feature, not a phase

The first engineering objective is an instrumented inventory of all first-party traffic across the supported workflows, per account partition, that stays alive for the life of the app. Every observed operation is classified into: conversation (turn create/stream/list/detail), auth/account, vote/reveal, asset, analytics/config, mutation-other, or unknown. Unknown stays unknown until an agent or the owner investigates; the catalog never guesses a classification to look complete.

5.2 Catalog entry shape (machine-readable; served over MCP)

CatalogEntry {
  op_key:            string   // normalized: method + origin + path-template (ids templated out)
  classification:    enum     // conversation | auth | vote_reveal | asset | analytics | mutation_other | unknown
  transport:         enum     // fetch_json | fetch_stream | sse | websocket | doc | other
  read_or_mutation:  enum     // read_verified | read_presumed | mutation | unknown   (§7.4 for how "verified" is earned)
  first_party:       evidence // origin match + initiator chain from CDP, per observation
  seen_in_accounts:  acct_uuid[]          // inventory only; payloads stay partition-scoped
  payload_family:    string   // fingerprint of sanitized JSON shape (key-paths + types, no values)
  adapter:           { name, version } | null      // parser that consumes it, if any
  completeness:      enum     // fully_parsed | partially_parsed | inventoried_only
  drift:             { last_shape_change, unexpected_fields, parse_failure_rate }
  samples:           sanitized_evidence_refs[]     // §5.3 — bounded, sanitized
}

Drift signals — a shape fingerprint change, a rising parse-failure rate, a new unknown op on a conversation-critical path — flip the affected adapter to degraded, which (a) pauses any dependent sync jobs for affected accounts with reason codes, (b) keeps live capture in evidence-spooling mode (raw sanitized evidence still recorded, normalization deferred), and (c) surfaces a diagnostic an LLM can read and act on (§10). This is the designed answer to frontend/protocol drift: capture degrades to evidence collection, never to silence.

5.3 Sanitization before persistence — inventory breadth without a credential dump

  • The Sanitizer sits between CDP/observer events and every sink (spool, DB, catalog samples, diagnostics, logs). Nothing bypasses it, including parser-error paths: a failed parse persists the sanitized body plus the error, never the raw event.
  • Always stripped, allowlist-style: Cookie/Set-Cookie and all credential-bearing headers (Authorization, CSRF headers), request bodies of auth operations, OAuth codes, signed URL query strings (URL is stored as origin+path with a had_signed_params:true flag and a content-hash reference §9.3), and any JSON field matching a deny-pattern set (token, secret, password, cookie, key-shaped high-entropy strings) unless an adapter explicitly allowlists that field as content.
  • Retained: conversation payload bodies (they are the product), operation metadata, timing, sizes, initiator chains, and bounded samples for unknown ops (default: first 3 sanitized samples per op_key per adapter version, then counters only).
  • Retention: sanitized raw evidence follows the §4.4 rolling window; normalized records and provenance are permanent until deleted. Within the window, adapters can be re-run over evidence after a fix ("reparse"); outside it, §8.2 states exactly what is and is not recomputable.
  • Sanitizer failure is fail-closed: if the Sanitizer throws, the event is dropped, a sanitizer_failure gap marker with op_key (no payload) is recorded, and the affected partition's capture state shows degraded.

6Live capture

6.1 Coverage targets for the first complete text release

Battle, direct, and side-by-side modes; completed, stopped, failed, and partial responses; conversations opened from history including search, pagination, and archived views; selected model labels, blind labels, visible votes, post-vote reveals; titles, timestamps, source IDs, branches, revisions/regenerations, participant positions, completion state where observable — every observation bound to its acct_uuid. Structure is preserved: a battle turn is a prompt plus N positioned participant responses plus vote/reveal events, never flattened alternating text.

6.2 The network plane (primary)

  1. Attach-before-navigate discipline. A partition's WebContentsView never receives a URL until its CDP client is attached and Fetch.enable/Network.enable/Target.setAutoAttach have acknowledged. Attachment failure = the view shows a capture-off interstitial instead of Arena; browsing without capture is an explicit owner choice, never a race outcome.
  2. Bodies via the Fetch domain, paused at Response stage for first-party API patterns; small bodies via Fetch.getResponseBody, large/streamed via getResponseBodyAsStream. Verified fact (S7–S8) that this pattern works under webContents.debugger where Network.getResponseBody is reported to fail. Hypothesis to test (G1, critical): whether pausing at Response stage buffers or delays incremental SSE token rendering. If pause-at-response breaks streaming UX or chunk timing, the fallback per-op is Network-domain chunk events (dataReceived) plus end-of-stream body retrieval, with the trade-off recorded per op_key in the catalog; chunk-timing metadata may then be coarser. The spike measures both modes.
  3. WebSocket and SSE: Network.webSocketFrameSent/Received and Network.eventSourceMessageReceived as first-class evidence streams, timestamped per frame/message.
  4. Workers: Target.setAutoAttach (flatten) from each page session; per-target Network enabling. Service workers: attempted via session-level target discovery; if per-webContents scope cannot reach SW targets, activate the app-internal browser-level CDP connection (remote-debugging pipe consumed by the app only) and attach there. Both are exercised at G1; if neither observes SW-mediated fetch → R1.
  5. Navigation bracketing: Page.lifecycleEvent/frameNavigated bracket every capture segment. A response in flight at teardown yields an observer_gap marker (§6.4), not an invented completion. Late attach after a crash-relaunch also opens with a gap marker.
  6. Downloads/artifacts: session.will-download intercepts per partition; bytes stream into the encrypted artifact store with content-hash naming; the DownloadItem's metadata (sanitized URL, declared filename, byte count, completion state) becomes provenance.

6.3 The DOM plane (secondary evidence, isolated world)

A MutationObserver-based observer in the preload's isolated world emits: rendered turn/branch boundaries, visible model labels and blind labels, vote clicks and reveal banners, stop-button usage, and history-list snapshots. It is reconciliation evidence and fallback, never the primary transcript source, and it patches nothing in the page world. When the network plane is degraded (drift, SW blindness pending escalation), DOM-plane capture continues and its records carry capture_mechanism: dom_observer with reduced-fidelity flags — this is where fallback capture loses information: exact token timing, unrendered metadata, and raw payload fields are absent, and that loss is recorded rather than papered over.

6.4 Completeness and capture states

response_record.completeness ∈ {
  complete          — terminal event observed (stream end marker / finish reason / UI settled + network idle)
  stopped_by_user   — owner stop action observed (UI evidence) and/or server stop marker
  failed_upstream   — error frame/status from Arena observed
  partial_transport — connection dropped mid-stream; last chunk timestamped; no terminal marker
  observer_gap      — the app knows it wasn't watching (late attach, teardown, sanitizer failure,
                       spool backpressure, SW blindness) — bounded by gap markers
}
conversation.capture_state ∈ { live, paused_by_owner, frozen_identity_mismatch, degraded_drift, closed }

Promotion rules: nothing moves to complete without a terminal marker; DOM-only records can reach at most complete(dom_confidence), a visibly distinct grade. Reconciliation prefers network evidence for content, DOM evidence for user actions (votes, stops) and rendered labels; disagreements persist as conflicts on the record (§8), not as silent overwrites. Repeated/replayed events (reconnects, React re-renders) are deduplicated by (acct_uuid, op identity, content hash, position), and dedup decisions are themselves logged.

6.5 Spooling and crash safety

CDP/observer events → Sanitizer → an append-only WAL spool (plain SQLite table inside the encrypted DB) → normalizer consumes asynchronously. Crash mid-stream loses at most the unflushed tail; on relaunch the normalizer replays the spool and the boundary is marked. Backpressure beyond the §4.4 watermark drops lowest-value classes first (analytics, assets) with counters, then pauses capture with an observer_gap — conversation payloads are the last thing shed.

6.6 Owner controls

Per account and globally: pause capture (stops persistence; in-flight sanitized events complete their write; browsing continues, gap marker opens), stop capture (detaches CDP, view shows capture-off state), pause/cancel sync (§7.5), and panic stop (global: detach all CDP, halt jobs, lock archive — DB key dropped from memory after in-flight transactions commit). Every control's effect on in-flight work is exactly the above; all state is visible in the GUI status strip and via MCP capture.status.

6.7 Challenges, redirects, and anti-detection posture

The shell presents as what it is: a Chromium runtime. UA/brand strings are normalized to the embedded Chromium's stock values (removing the Electron token from the UA is a supported, ordinary configuration); no deeper fingerprint spoofing is attempted in v1 — the owner's usage is interactive and low-rate, and heavy anti-detection is a maintenance tarpit with no current evidence of need (A6). Bot challenges, unexpected redirects, and verification interstitials: capture pauses for that partition with reason challenge_pending, the view is brought to the owner's attention, the owner completes it by hand, capture resumes with the boundary marked. Automation (sync traversal) never attempts to complete a challenge.

7.2 Credential handling in sync

Sync requests execute through the owning partition's own network stack — ses.fetch() on the account's session (or, if that proves insufficient for some endpoint, a CDP-driven fetch inside the page context as a measured fallback). Cookies and tokens are therefore used where they live and never read out, copied, persisted, exported, or logged by app code. Strong inference — ses.fetch availability and cookie semantics confirmed at pin time; fallback path exists either way. Browser-managed session persistence on disk is a separate concern handled in §9.4.

7.3 UI-traversal fallback, specifically

Scripted scrolling/clicking of the history surface via CDP Input/Runtime in the owner's visible session, with live capture doing the actual recording. Rules: visible progress overlay; owner can cancel instantly; traversal halts on any challenge, redirect, or identity change; pacing is human-scale with jitter and a hard request budget per run; every conversation it opens is recorded by exactly the same pipeline as manual browsing (one pipeline, two drivers).

7.4 Earning read_verified

An operation is treated as a safe sync primitive only after, in the owner's session: (1) it was observed issued organically by the Arena frontend for the same purpose; (2) its replay with identical semantics produces no observable state change — checked by re-reading adjacent state (history list unchanged, timestamps unchanged, unread/flag states unchanged) before and after; (3) its response binds to the expected account identity (§7.5). HTTP method alone proves nothing; a GET stays read_presumed and unusable by sync until it passes this protocol. Any suspicion of unintended mutation → the op is quarantined, dependent jobs pause, and the event is surfaced as a top-priority diagnostic.

7.5 Job model, account binding, and concurrency

  • Sync now per account or for a selected set; optional per-account auto-sync is off by default and explicitly enabled per account.
  • Every sync job is bound to one acct_uuid and starts by re-verifying partition identity (whoami-shaped evidence: the account identity the frontend itself displays/receives). Identity mismatch → job aborts account_mismatch, partition capture freezes (§4.2), other accounts unaffected.
  • Checkpoints: opaque cursor + page-overlap window persisted per account. Overlapping/repeated pages and pagination instability are expected: item-level reconciliation dedupes by (acct_uuid, source_conversation_id, content-hash) — conservative: same source ID + same account + differing content ⇒ keep both versions as revisions with a conflict flag, never merge-and-discard.
  • Cross-account collisions: identical source IDs appearing in two accounts' scopes are recorded as two records plus an explicit cross_account_collision conflict for owner review. Never auto-merged — matching IDs, titles, text, or timestamps are not ownership evidence.
  • Concurrency: jobs for different accounts may run concurrently (isolated partitions, isolated checkpoints); a global rate governor caps combined request rate, and correctness never depends on concurrency — the scheduler can serialize accounts under governor pressure. Live capture and sync interleave safely because both feed the same reconciliation layer; a conversation half-captured live and then backfilled reconciles by turn-level keys with source-priority rules (network-live > backfill-detail > DOM) and conflicts kept.
  • Failure handling: bounded exponential retries for transport errors; auth expiry pauses the account's jobs with reauth_required (owner signs in again in the view; job resumes from checkpoint); rate-limit signals stretch pacing before pausing; drift flips the adapter to degraded and pauses dependent jobs (§5.2).

7.6 What “synchronized” means — and the no-listing-endpoint world

Per account, sync status reports: newest/oldest confirmed history boundaries, item counts by completeness class, known gaps (unfetched details, degraded parses, challenge interruptions), and the last full reconciliation pass — all inspectable via MCP sync.status. Opening one conversation proves nothing about coverage, and the status model never claims “complete”; it claims “no known gaps in the traversed range.” If no reliable listing, stable pagination, or complete representation can be verified at G4: the archive remains fully useful as a go-forward recorder (passive layer + manual traversal assist that turns the owner's own scrolling into coverage), and the coverage report says exactly where confirmed coverage ends. That outcome degrades scope, not integrity.

8.1 Source-of-truth design

Recommendation A hybrid, proportionate to a single-user app: (1) an append-only sanitized evidence layer (bounded retention, §5.3); (2) normalized records as the queryable source of truth; (3) provenance links from every consequential normalized field back to evidence + adapter version. Full event sourcing is rejected as ceremony: replayability is preserved where it pays (the evidence window) without making every read a projection.

8.3 Model identity

Identity is a set of observations about a participant position, never a single column. identity_obs preserves blind labels, selected labels, revealed names, provider strings, and owner annotations, each with mechanism, timestamp, evidence link, and validity range. A usable view (participant_identity_view) computes the best-supported identity per participant per turn range with an explicit basis — e.g. “revealed post-vote at T+42s, applies to turns 1–6; turns 7+ unobserved” — and never back-propagates a reveal beyond its supported scope. Position ≠ blind label ≠ provider ≠ marketing name ≠ exact build: conflicts between sources are preserved and queryable; a later reveal adds an observation and updates the view; it never rewrites earlier evidence. Aliases and routing indirection mean even a revealed name is a label observation, not ground truth about weights — this caveat propagates into every analysis cohort (§11).

9Encryption, exposure, and deletion

9.1 Keys

  • One random 256-bit archive master key, generated at first run, stored in the macOS Keychain (@napi-rs/keyring), ACL'd to the app. A one-time recovery phrase (BIP39-style encoding of the key) is shown once for the owner to store offline — the restore path for backups on a rebuilt machine.
  • Purpose-scoped subkeys via HKDF: k_db (SQLCipher key), k_artifact (wraps per-file random AES-256-GCM keys stored in artifacts.enc_key_wrapped), k_export (optional passphrase-wrapped export encryption). Utility processes receive only the subkey they need. Lock/panic-stop zeroizes key material in main memory.

10.4 The destructive-action guard (content is never authority)

Archived prompts, responses, tool traces, and diagnostics are data; no string retrieved from the archive can authorize anything. Account-wide and archive-wide deletion (and tombstone lifting) require a confirmation token minted only by a trusted control channel — the GUI's confirmation dialog or the local arena-archive confirm CLI run by the owner — bound to the exact scope displayed at minting (acct_uuid/archive + item counts), single-use, short-TTL, delivered out-of-band from the MCP conversation. The MCP server verifies token↔scope binding cryptographically (HMAC over the scope descriptor with a key the MCP client never sees). An agent — or an archived instruction masquerading as one — can request deletion, which produces a pending confirmation the owner sees; it can never complete one. Single-conversation deletion, being recoverable via re-sync in most cases, requires only the normal tool call but is rate-limited and journaled. This is a mechanism, not an admonition to be careful.

11Local analysis

11.1 v1 model profiles — deterministic, transparent, cohort-honest

All analysis runs locally in a utility process against the encrypted archive. Profiles group responses only by observed or revealed identity evidence; unknown/blind responses form their own explicitly-unknown cohorts. Every run records its corpus selector, cohort sizes, code version, and exclusions (analysis_runs), so results are reproducible and their basis inspectable via MCP.

  • Structure: response/paragraph/sentence/code-block length distributions; Markdown feature rates (headings, lists, tables, citations), code/prose ratio.
  • Lexicon & surface: type-token curves, recurring n-grams/phrases, punctuation and casing habits.
  • Discourse: openings, transitions, conclusions, hedges, qualifications, refusal/apology/uncertainty markers (pattern lexicons, versioned).
  • Conditioning: every metric sliceable by prompt type, topic cluster, mode, language, time window, and conversation depth — because the owner's prompt mix is the dominant confound.
  • Excerpts: representative samples linked to source turns and provenance, never detached quotes.
what this corpus can and cannot support

A single heavy user's archive has selection bias (one person's prompts), sparse cells for many models, topic-model confounding, unknown hidden system prompts, unknown decoding settings, invisible tool/safety layers, alias and routing indirection, temporal model drift, and possible platform post-processing. Supportable: descriptive profiles per identity-cohort with confidence bounds, within-cohort drift over time, and paired comparisons where the same prompt hit multiple models in one battle (the platform's structure is a gift here — side-by-side responses share the prompt, history, and moment). Misleading and therefore refused by default: cross-cohort claims from unpaired samples, small-N “fingerprints,” and any claim that style similarity identifies a model. The paired-battle design is the analysis backbone.

11.2 Embeddings/ML entry gate

Deterministic stats ship first and alone. Local embeddings (ONNX/llama.cpp) enter only when: a concrete question needs them (e.g., topic clustering for confound control at scale); ≥ some predeclared paired-sample threshold set from observed corpus growth (not invented here); weights pinned by hash, preprocessing versioned, fully offline after acquisition; and 18 GB co-existence measured. Until all four hold, the answer to “should we add ML?” is no.

11.3 Later similarity/fingerprinting experiments

Similarity-to-corpus is an unverified, confidence-qualified hypothesis about a label, never proof of identity or authorship; inferred identity lives in separate, clearly-marked fields, never in identity_obs. Method preconditions: splits by conversation family (branches/near-duplicates never straddle train/test); prompt/topic-controlled pairs; negative controls (shuffled labels, held-out unrelated models); calibration on held-out reveals; an explicit unknown class with abstention; minimum evidence thresholds derived from observed calibration error, not universal constants. Stop rule: if calibrated accuracy on held-out revealed data fails predeclared criteria after two methodological revisions, the experiment is archived as negative — recorded, not retried indefinitely.

13Implementation sequence and acceptance gates

Each gate lists deliverable → machine-checkable acceptance → falsifying evidence → decision. Fixtures never contain credentials or unrelated private data; synthetic fixtures validate harness logic only — every gate that claims Arena behavior requires signed-in owner-session evidence, and the three evidence kinds (synthetic protocol tests, documented platform behavior, owner-session observation) are never substituted for one another.

G0 · Toolchain & pin

Deliverable: repo scaffold; Electron + native deps pinned; better-sqlite3-multiple-ciphers built against Electron ABI on arm64; Keychain round-trip; CI-style local check script (npm run gates:g0). Accept: clean build from empty machine via one bootstrap script; encrypted DB create/open/FTS query; key survives reboot. Falsifies: native-module build failure → swap DB binding per §4.5 before proceeding.

G1 · Browser & capture-depth viability — the falsification spike

Deliverable: the §6.8 vertical slice, plus a battery designed to break the architecture:

  • email sign-in completes in-shell (A3); session survives relaunch in its partition;
  • two accounts signed in simultaneously; leak probe (§4.2) passes in both directions;
  • late-attach test: attach after navigation deliberately → gap markers appear (proves gap honesty), then attach-before-navigate → no gaps;
  • streamed body capture with pause-at-response ON and OFF; measure UX/timing impact (§6.2 item 2);
  • worker/SW census (A5): enumerate targets during a conversation; if SW-mediated fetch exists, per-webContents attach vs browser-level CDP attach compared;
  • forced mid-stream navigation, manual stop, network-cut → the three distinct completeness states recorded, no silent promotion;
  • download of a generated artifact lands in the encrypted store via will-download;
  • challenge behavior recorded if encountered (A6).

Accept: all of the above with structured evidence in diagnostics. Falsifies architecture (→ R1/R2): SW-mediated conversation traffic invisible to both CDP paths; or pause-at-response and Network-chunk modes both break streaming capture; or embedded Chromium is hard-blocked by the platform. Decision: continue / escalate CDP plane / reverse per §0.

G2 · Deeper-than-baseline, measured

Deliverable: same scripted Arena workflow (battle with stop, regen, vote+reveal, history open, artifact download) captured by the MV3 baseline and by Arena Archive; item-level evidence diff. Accept: Archive strictly ⊇ baseline evidence, and strictly > on at least: stream completeness, navigation-window events, reveal timing, artifact path; resource budgets (§4.4) measured and recorded — replacing proposals with numbers. Falsifies: parity or worse → project premise fails → stop and reassess (this is the honest exit).

G3 · Capture correctness at breadth

Deliverable: full §6.1 coverage; reconciliation network↔DOM; dedup under reconnects/re-renders. Accept: replayed evidence corpus normalizes idempotently (re-run ⇒ byte-identical records); branch/revision/position fidelity spot-checked against the live UI on N owner-chosen conversations; zero cross-account rows under two-account concurrent use (SQL assertion: every record's evidence acct = record acct). Falsifies: any silent loss/duplication/contamination → fix before any sync work.

G4 · Backfill viability

Deliverable: A4 evidence; read_verified protocol (§7.4) executed on candidate ops; sync jobs with checkpoints. Accept: interrupt/resume mid-page produces no loss or duplication; overlapping pages reconcile; two-account concurrent sync isolates state; live-capture overlap reconciles; suspected-mutation quarantine fires in a staged test. Falsifies: no verifiable listing path → adopt §7.6 posture (degraded scope, intact integrity) and continue.

G5 · Data & trust integrity

Accept: sanitizer fuzz (malformed/hostile payloads) never persists a secret-classified field (automated scan of all sinks); kill -9 during capture/sync/migration recovers to consistent state; backup/restore round-trip on a second machine via recovery phrase; per-scope deletion verified by re-query + tombstone behavior under re-sync; identity-change freeze fires on a staged account switch. Falsifies: any secret in any sink → fail-closed redesign of the offending path before proceeding.

G6 · Agent operation

Accept: a scripted MCP client (and then a real LLM agent) completes: search→transcript→provenance; sync trigger→monitor→pause→resume; drift diagnosis from a staged adapter break; export; single-conversation delete; and fails to delete an account without a trusted-channel token — including a prompt-injection fixture in an archived conversation that attempts it. Falsifies: any GUI-only capability discovered → close the gap; any content-authorized destructive action → redesign guard.

G7 · Analytical validity

Accept: profiles reproduce byte-identically from a frozen corpus + code version; every reported metric carries cohort size and selector; paired-battle comparisons flagged as the only cross-model claims; a null-cohort (shuffled labels) run shows no spurious "style signal" from the pipeline itself. Falsifies: pipeline finds "signal" in shuffled labels → fix before any real claim; fingerprinting experiments additionally governed by §11.3's stop rule.

Fatal-assumption ordering

G1 attacks the two assumptions that could kill the architecture (SW visibility, stream capture mode) before any archive/analysis code exists. G2 attacks the project's premise (deeper than baseline). Everything after G2 is incremental risk. Nothing in G3+ requires rework of a passed G1/G2 surface except through the catalog's drift mechanism, which is itself a supported path.
