01Executive architecture decision

Recommendation — v1 architecture

Electron + Chromium, TypeScript application layer, one persistent Session partition per Arena account, main-process CDP/network observation, SQLCipher archive, stdio MCP server.

The application owns its browser runtime. Each Arena account gets its own persistent Electron Session partition and its own WebContents. Capture is performed outside page JavaScript by main-process Chrome DevTools Protocol attachment, supplemented by Electron's per-session webRequest, per-session netLog for gap forensics, per-session service-worker introspection, and per-session download interception. Page-side DOM instrumentation is permitted only as secondary, independent evidence for reconciliation — never as the primary transport. The remote Arena renderer is untrusted: no Node, no IPC, no archive access, no MCP access.

What this plan is. A complete architecture and acceptance-gated implementation plan for one private macOS application. It specifies the browser ownership model, capture mechanisms, isolation model, sanitization, normalized provenance data model, sync, encryption, deletion, MCP contract, and analysis layers, with explicit falsification gates and a documented reversal path.

What this plan is not. It is not a claim that Arena's wire protocol has been reverse-engineered. No authenticated Arena session was connected while producing this document. Arena-specific behavior — endpoint families, pagination, stream transport, message schema, reveal payloads, backfill reads — is Hypothesis to test and is gated behind owner-session acceptance tests defined in §19. Nothing in this document asserts that an Arena endpoint is read-only.

The argument in seven lines

  1. Owning the window is not the same as deeper capture. The architecture must state, per option, exactly which capture mechanisms exist outside page JavaScript. See §5.
  2. Electron exposes a main-process CDP transport (webContents.debugger) plus per-partition session APIs — a materially larger observation surface than an MV3 extension, and account-partitioned by construction. Verified fact
  3. CEF exposes one deeper primitive — CefResourceRequestHandler::GetResourceResponseFilter, invoked for requests whose browser/frame are NULL, explicitly including service-worker-originated requests. Verified fact This is the single strongest reason to escalate.
  4. Therefore the decision is conditional, not dogmatic. Electron is chosen for v1; a defined falsification spike can flip the decision to CEF. The reversal condition is stated verbatim in §3.4.
  5. Two accounts must be simultaneously live and mutually non-interfering, with identity scoped into every record's uniqueness rules. See §7.
  6. Capture is not truth. Completeness, provenance, and confidence are first-class columns, and inferred content is never labeled complete. See §10.
  7. The LLM interface is the primary interface. Every GUI capability has an MCP equivalent, implemented on the same service layer. See §15.
Rejected as primary architecture

Manifest V3 extensions, chrome.debugger extensions, extension + native messaging, and extension + companion daemon are not eligible primary architectures. The owner's existing arena-exporter recorder remains useful only as the rejected baseline and as an A/B comparison target in the Phase 1 spike. See §5.5.

03Why Electron is recommended, and the exact reversal condition

3.1 The decision rule

Recommendation Choose the architecture that maximizes observable capture completeness for architecture-critical Arena traffic first, then minimize implementation and maintenance cost. Capture correctness dominates footprint, startup time, and binary size for this product, because an archive that silently misses stream bodies is worthless as a research corpus regardless of how pleasant it is to run.

Electron wins on the composite because it is the only option that simultaneously provides: Chromium web-platform fidelity (so Arena behaves normally), a maintained main-process instrumentation transport, per-partition persistent browser state as a first-class primitive, per-partition network observation and netlog forensics, per-partition download control, and a TypeScript ecosystem an AI coding agent can maintain without a C++ toolchain.

Deliberate non-mechanism. Page-world monkey-patching of fetch/XMLHttpRequest/EventSource is not part of the primary design. It is exactly what an extension must do and what an adversarial or simply evolving page can defeat.

3.3 Why not a lighter stack

Strong inference Electron's runtime cost is real and duplicated (Chromium per app, one renderer per active partition, plus main and helper processes). For an M3 Pro with 18 GB of unified memory running at most two live Arena partitions plus a small diagnostics UI and an MCP server, that cost is affordable and bounded by explicit quotas (§21.2). The counterfactual — a lighter native shell with a materially weaker interception surface — is the failure mode this project exists to avoid.

3.4 The reversal condition (verbatim, non-negotiable)

Escalation gate — Electron → CEF

If the Phase 1 falsification spike demonstrates that Electron cannot reliably capture an architecture-critical class of Arena traffic through maintained CDP / Session surfaces — specifically any of: (a) streamed generation response bodies for a supported mode, (b) worker- or service-worker-originated first-party request/response pairs, (c) an Arena surface whose traffic never appears in Network events or in netLog, or (d) target-graph attachment across Arena navigations — and a focused CEF spike using CefResourceRequestHandler::GetResourceResponseFilter demonstrably observes that same class, then the architecture switches to CEF for v1. The switch is a documented, budgeted reversal, not a failure.

A custom Chromium fork is a last resort only: permitted solely if a specific required capability is impossible through maintained Electron and CEF surfaces. It is not recommended here, because no known requirement currently exceeds those surfaces.

Cost asymmetry to record honestly. Reversing after Phase 3 means discarding the Electron capture package (roughly the browser binding layer and capture coordinator) while keeping the domain model, sanitizer, protocol catalog, storage, sync, MCP, and analysis packages intact — provided they were written against internal interfaces rather than Electron types. That constraint is enforced in §21.3.

04Electron vs. CEF — the serious contenders

This is where the report spends its detail. Both are Chromium-based, both can host a dedicated browser, both can isolate per account. The difference is where the observation hook sits and who has to maintain it.

4.1 The one primitive that matters

Verified fact CEF's CefResourceRequestHandler runs on the IO thread and, among its callbacks, offers GetResourceResponseFilter(browser, frame, request, response) returning a CefResponseFilter — a streaming response-body filter. The header documentation repeatedly states that browser and frame "may be NULL for requests originating from service workers or CefURLRequest". That is the difference: CEF can hand you bytes for requests that have no page frame at all.

Strong inference Electron's maintained public surfaces give equivalent byte-level access most reliably for frame-initiated traffic via CDP, and give partition-scoped metadata, netlog forensics, and download control for everything else. Whether that combination covers Arena's worker/service-worker-originated generation traffic is precisely the empirical question Phase 1 exists to answer.

4.2 Why Electron first despite CEF's deeper hook

  1. Option value. Electron's extra cost is a spike. CEF's extra cost is a permanent build surface, permanently on an M3 Pro development machine maintained largely by autonomous agents.
  2. Diagnostics depth. Verified fact session.netLog gives a browser-level record for offline forensics. That single API substantially reduces the "why did we miss it?" debugging burden that made the extension approach painful.
  3. Partition primitive. Verified fact Persistent partitions are one string away, per account, covering cookies, storage, cache, and service workers together.
  4. Risk of CEF's advantage being unnecessary. Arena may deliver generations over ordinary frame-initiated streamed responses — the case CDP handles comfortably. Paying CEF's tax preemptively would be speculative.
How to keep the option open

The capture package (packages/capture) and browser package (packages/browser) are the only modules permitted to name Electron types. Everything downstream consumes a transport-neutral CaptureEvent union. If the spike reverses the decision, those two packages are replaced by a CEF implementation emitting the same union, and the rest of the system is untouched.

5.1 Swift + WKWebView

Previous-run evidence Apple's WKURLSchemeHandler is documented for custom URL schemes, and WebKit's own configuration header states that registering a handler for a scheme WebKit handles internally throws. It is therefore not a general interception hook for ordinary Arena HTTPS traffic. Previous-run evidence Multiple WKProcessPool instances are deprecated and no longer produce isolation. Do not read "native" as "deeper". Native integration, memory footprint, and macOS polish are genuine advantages; the core requirement — reliable response-body observation for Arena's real traffic — is not met by the public surface. Disqualified as primary; retained as a possible future thin client for viewing archive data, never for capture.

5.2 Tauri / Wry

Previous-run evidence On macOS, Tauri/Wry uses the system WebKit webview. The small footprint is real and attractive, but Tauri inherits WKWebView's interception limits unless substantial custom native interception machinery is added — at which point the footprint advantage is spent and the maintenance profile approaches CEF's without CEF's documented response filter. Not selected. Lightness is not the priority; capture correctness is.

5.3 CEF

Retained as the escalation target (§3.4), not eliminated. See §4.

5.4 Explicit export / import with no embedded browser

Structurally the safest and cheapest option, and worth keeping as a permanent complementary capability (archive.import / export.create in §15). It cannot satisfy the product requirement, because the owner wants to use Arena normally inside the application while it records, and because any official export facility's availability, schema, and completeness are outside our control. Retained as an import adapter for future official exports and as a recovery path.

06Process and trust architecture

The remote Arena renderer is untrusted content. Verified fact Electron's own security guidance is explicit that displaying arbitrary remote content in Electron is a severe-risk scenario and prescribes: no Node integration for remote content, context isolation, sandboxing, a permission handler for remote-content sessions, webSecurity untouched, restricted navigation and window creation, validated IPC senders, custom protocols instead of file://, and no raw IPC exposed to untrusted web content. Every one of those is adopted below as a hard rule.

6.1 Hard rules for the Arena renderers

  • nodeIntegration: false, nodeIntegrationInWorker: false, sandbox: true, contextIsolation: true, webSecurity untouched, experimentalFeatures off, allowRunningInsecureContent off.
  • No privileged preload in Arena content. A session-registered preload may exist for DOM observation, but it must expose zero contextBridge surface. Observation is one-way (a message to main only, on a channel Arena cannot read) — and if that channel cannot be proven unreachable, the preload is dropped and only transport capture is used.
  • A per-partition setPermissionRequestHandler that denies everything except what Arena demonstrably requires, recorded in the protocol catalog.
  • App UI is served through a privileged custom protocol, never file://.
  • Navigation and setWindowOpenHandler allowlists are per-account: Arena first-party origins plus the authentication/mail flows the owner needs, with popups kept in the owning partition.
  • Electron fuses are set to disable runAsNode and CLI inspection paths; the shipped binary is not a general script runner.
  • Archive, storage, MCP, and key modules are never importable from a renderer. They are separate packages with an enforced dependency-direction rule; violating imports fail the build, not a review.

6.2 IPC discipline

IPC exists only between the trusted app UI renderer and main. It is an allowlist of named channels with typed payloads validated on both sides, every handler asserting the sender frame's origin. There is no generic invoke passthrough. The MCP server does not use IPC at all: it is a separate process/interface that calls the same in-process service layer as the GUI — never a parallel implementation with divergent behavior.

07Simultaneous multi-account partition design

Two or more Arena accounts must be signed in and usable at the same time. This is not an account switcher: each account is an independently failing subsystem.

7.1 Isolation inventory

Verified fact session.fromPartition('persist:…') yields a persistent session shared by all pages using the same partition string; a non-prefixed partition is in-memory. Each account therefore receives a distinct persistent partition string, and clearData can target that partition's data types — including serviceWorkers, cache, cookies, indexedDB, and localStorage — without touching the other account.

7.2 Identifier hygiene

Partition names use the form persist:arena-<internal-account-uuid>, never an email address or any other owner-identifying string. The mapping from the owner-facing label (which may be the account email, stored encrypted and only for display) to the internal UUID lives in the archive DB, not in the filesystem path.

7.3 Cross-account source-ID collisions

Non-negotiable

Arena source identifiers (conversation IDs, message IDs) are scoped, not global. The stable local identity is always an internal UUID. Uniqueness is (account_id, source_namespace, source_id). Two records with identical text, identical timestamps, and identical source IDs from different accounts must not merge; if the same source_id appears under two accounts, that is recorded as a SOURCE_ID_CONFLICT observation pair, never resolved silently. Conversely, identical text within one account is also insufficient proof of duplication — dedup requires matching identity observations, not text hashes.

7.4 Independent failure

  • A signs out → A's capture authority becomes UNAUTHENTICATED, A's sync pauses, A's queued events are retained and marked AWAITING_REAUTH. B continues unaffected.
  • A hits a CAPTCHA/challenge → A reports NEEDS_OWNER_INTERACTION with a deep link to A's view. B unaffected.
  • A's parser drifts → only A's affected protocol family is degraded; B keeps full capture.
  • A's identity appears to change → A halts and requires explicit owner verification before rebinding. No automatic rebind, ever.
  • MCP client disconnects → long-running jobs continue server-side with explicit continuation and cancellation semantics (§15.6).

8.2 What the catalog is for

  • Coverage accounting. The set of catalog entries with evidenceStatus: 'observed' defines what the archive claims to understand. Anything outside it is a declared gap, surfaced by diagnostics.capture_gaps.
  • Drift detection. When a response no longer matches responseSchemaFamily, the entry flips to schema-drift, the adapter is marked degraded, and ingestion continues into UNKNOWN_OBSERVATION rather than dropping data.
  • Mutation safety. mutationClass becomes 'read' only after the owner-session non-mutation test in §11.4 passes for that specific operation. Until then sync refuses to use it as a backfill adapter.
  • Agent maintainability. A coding agent reads the catalog to learn the current wire surface without ever needing credentials, and can regenerate fixtures from the retained sanitized evidence.
Owner-data boundary — vocabulary discipline

This system performs authenticated first-party reads using the owner's own Arena session inside the owner's own browser partition, and it maintains ordinary browser automation/anti-bot compatibility by behaving like a real browser. It does not perform access-control workarounds. Not every undocumented endpoint is a "bypass"; that term is reserved for deliberately circumventing authorization, which is out of scope by policy. A conversation ID or URL alone does not establish ownership: every backfill and capture operation is bound to a verified account/session partition, and no attempt is made to read data not belonging to the authenticated owner.

09Live capture architecture

9.1 Attachment strategy

  • Earliest practical. Enable CDP domains at WebContents creation, before the first navigation, so a generation request is never pre-dated by our own attach.
  • Re-attach defensively. Handle detach events (explicit detach, DevTools invocation, crash) with bounded re-attach and a recorded gap covering the detached interval.
  • Follow the target graph. New frames, popups, and workers must inherit capture policy. Unknown The exact CDP auto-attach method must be confirmed against the current protocol version during Phase 1; until confirmed, the fallback is per-WebContents attach plus explicit handling of contents created by the window-open handler.
  • Survive navigation. Capture state is keyed by logical operation, not by page lifetime, so a mid-generation navigation or reload does not orphan the stream.

9.2 Streaming reconstruction

Hypothesis to test Arena may stream generations over streamed fetch, SSE, or WebSockets, and it may differ by mode. The design is transport-agnostic: a StreamAssembler accepts ordered chunks tagged with (account_id, target_id, request_id, sequence), tolerates gaps by recording them, and produces a reconstruction digest. If Arena uses SSE, the reconstructor must handle multi-line events, retry:, and interleaved commentary events. If WebSocket, it must handle fragmentation and bidirectional frames. None of these specifics are asserted here; they are the spike's output.

Stopped and failed generations are signal, not noise. A stop produces a distinguishable terminal event; a backend failure a different one; a network drop a third. Each yields a different completion_state and a different completeness claim (§10).

9.3 Downloads and generated artifacts

Verified fact The partition-scoped will-download event fires with the DownloadItem, the originating webContents, and the initiating frame (which may be null), and may be cancelled via preventDefault(). Artifacts are therefore either (a) allowed to download into a quarantine directory and then encrypted into the blob store, or (b) intercepted and re-fetched through the owner's session. Filenames are treated as untrusted strings; MIME sniffing and size caps apply before any blob write.

9.4 Secondary rendered-UI evidence

A DOM observation channel exists so that transport evidence can be corroborated or contradicted by what the owner actually saw: visible model labels, blind labels, participant positions, post-vote reveals, stop-button state, error banners. It is recorded as a separate observation type with its own evidence mechanism, never merged into transport observations, and never allowed to fabricate text that transport capture did not deliver. Where UI text is the only source, the record is explicitly UI_ONLY_RECONSTRUCTION with lower completeness — never silently presented as complete.

10.2 Idempotent ingestion

Observations may arrive duplicated, out of order, after navigation, after reconnect, after a model reveal, or during an overlapping history sync. Rules:

  1. Every observation carries a stable observation_id derived from (account_id, target_id, request_id, sequence); re-inserting the same observation is a no-op, not an update.
  2. Normalized rows are updated only by observations of equal or higher evidence strength. Ordering: transport terminal > transport partial > history replay read > rendered UI > inference.
  3. Newer never beats stronger. A late UI observation cannot overwrite an earlier transport observation of the same field.
  4. All writes are transactional: normalized row + FTS update + observation insert + completeness advance together, or none of them.
  5. Every mutation of a normalized row appends to a per-record revision history so reparsing is replayable and auditable.

10.3 Reveals are additive, never retroactive

Identity rule

A post-vote reveal produces a new identity observation with its own timestamp and evidence mechanism. It must not be applied backwards to claim the model's identity was known when the turn was produced. The turn's earlier state — "blind label known, identity unknown" — remains a first-class historical fact, which is exactly the property that makes the corpus useful for studying blind-versus-revealed behavior.

Credential rule

Copied bearer tokens, cookies, CSRF values, and signed URLs must never be persisted into the archive database, logs, fixtures, exports, or diagnostics. 11.3 Sync semantics

  • Scope. One selected account or several selected accounts, each with its own job, cursor, and concurrency budget.
  • Per-account progress and checkpoint. sync_cursor stores an opaque server-issued position token plus the last N observed item identities for overlap detection. The token is opaque: we never parse it, only store and replay it.
  • Cancel / resume. Cancellation is cooperative at page boundaries; resuming re-derives overlap from item identities, so re-processing a page is safe and expected.
  • Bounded retries. Exponential backoff with a hard attempt ceiling per page; a page that exceeds it becomes a declared gap rather than an infinite loop.
  • Idempotency. Page processing is idempotent by observation identity; duplicate pages cannot duplicate rows.
  • Concurrency. Accounts may sync concurrently only because every partition, cursor, coordinator, and job is disjoint and no mutable state is shared between them. If Phase 1 shows any shared contention (for example a rate signal attributable to the owner rather than the account), sync falls back to serialized per-account scheduling with no change to correctness.
  • Auth expiry and challenges. Detected per account; that account's sync pauses with an actionable reason and does not affect other accounts.
  • Live-capture overlap. A backfilled record and a live-captured record for the same logical turn reconcile by evidence strength; backfill never overwrites a live observation.
  • Partial histories and drift. Coverage gaps are recorded per account per workflow, and "synchronized" is defined per account as: every observed list page up to the checkpoint was processed without gaps, for the workflows we can observe, as of timestamp T, with the declared gap set attached. It is never a global boolean.

11.4 Backfill falsification gate

Acceptance gate — authenticated history replay

Opening one known conversation does not prove backfill viability. The gate requires, in a signed-in owner session, for each candidate operation: (1) the operation returns data attributable to the currently authenticated account and no other; (2) listing behavior and pagination are understood and reproducible across at least two runs; (3) conversation detail retrieval returns content matching what the owner sees in the UI for the same conversation; (4) non-mutation is demonstrated by capturing before/after state of the account's conversation list, titles, and message counts and showing no change; (5) checkpoint and resume produce results identical to an uninterrupted run; (6) overlap/repeated pages produce no duplicate rows; (7) account isolation holds when two accounts sync; (8) auth expiry produces a clean pause rather than partial or misattributed data; (9) completeness boundaries are documented — specifically, what the operation does not return.

12.3 Operational concerns

  • Transactions. One transaction per ingested turn: normalized rows, revision, capture state, observation inserts, FTS update. Blobs commit first to a staging path and are referenced only after the DB commit succeeds.
  • Crash recovery. On startup, orphaned staging blobs are reconciled against the DB: referenced blobs are promoted, unreferenced ones quarantined then purged. Interrupted jobs resume from their checkpoint or are marked failed with a reason.
  • Migrations. Forward-only, numbered, applied in a transaction, with the schema version recorded in the DB and reported by diagnostics.status. Every migration has a rollback-by-restore plan rather than a down-migration.
  • Parser reprocessing. Because observations are immutable and adapters are versioned, a new adapter version re-derives normalized rows from observations, records a reparse_run, and never mutates the observations themselves. Completeness states are recomputed, not copied.
  • Backup/restore. The archive is a directory: encrypted DB (plus WAL), blob store, and a manifest with schema version, key id, and blob count. Restore verifies the manifest against reality before opening.
  • FTS updates. FTS5 lives inside the encrypted database; content is indexed in the same transaction as the source row. Because Verified fact SQLCipher does not encrypt transient temp files, file-based temporary storage must be disabled at build and runtime so FTS and sorter spills never touch disk in plaintext.
  • Artifact lifecycle. Blobs are content-addressed by digest with per-blob keys; unreferenced blobs are collected by a sweeper after a grace period; deletion cascades from artifact to blob.

14Encryption, local data, and deletion

14.1 Key hierarchy

Verified fact SQLCipher is a modified SQLite build that encrypts each database page individually with 256-bit AES-CBC, uses a per-page random IV regenerated on write, appends an HMAC-SHA512 of ciphertext and IV checked on every page read, derives keys from a passphrase with PBKDF2-HMAC-SHA512 and a per-database random salt, and — critically for this design — supports supplying raw binary key data for vaulted or PKI-based keys. It also documents that WAL and rollback-journal pages are encrypted with the database key, while transient temp files are not encrypted unless file-based temp storage is disabled.

Recommendation Therefore:

  1. Generate a random 32-byte archive key with the OS CSPRNG at first run.
  2. Store it as a generic-password Keychain item, protected by the macOS account; the app unlocks it when needed and never writes it to disk.
  3. Open SQLCipher by supplying that raw key, not a human passphrase. A human password is neither the primary key nor a fallback key.
  4. Do not use SEE/other codecs or a pluggable extension: Verified fact SQLCipher is not a loadable plugin and must be linked, which makes the native binding the project's only required native module.

Native-module risk, stated plainly. Recommendation Use a maintained Node binding for SQLCipher that compiles against a SQLCipher build, pinned to exact versions in the lockfile and rebuilt in CI for the target architecture. Because only one native module is needed, the blast radius is small — but it is real, and it must be re-validated on every Electron major bump (which also changes the Node ABI). A pure-JS fallback is not offered: silently degrading to an unencrypted database would violate the product's core promise. Instead, if the binding cannot be built or opened, the application refuses to start and says so.

14.2 Blob store format

Large artifacts (code files, previews, images, exports) do not belong in the database. Format per blob:

// packages/storage/src/blob.ts — design sketch
header = magic(4) || version(1) || nonce(12) || tag(16) || ciphertext(...)
blobKey = HKDF-SHA256(
  ikm  = archiveKey,                     // never persisted, never logged
  salt = blobSalt(random 16B, stored in DB row),
  info = "arena-archive/blob/v1/" + blobId,
  len  = 32
)

  • Authenticated encryption (AES-256-GCM) so truncation and tampering are detected on read, not silently accepted.
  • Plaintext is never written to disk, never placed in a temp directory outside the encrypted volume, and never placed in a swap-friendly mapping.
  • Size caps and quarantine-then-promote: downloads land in a staging file inside the app container, are sniffed and size-checked, then encrypted into the blob store; the staging file is securely removed.
  • Key rotation is a defined operation: re-wrap the archive key in Keychain, and (for blobs) re-derive by rewriting each blob, since per-blob keys derive from the archive key. Rotation is expected to be rare and explicitly manual.

14.4 Browser profile data vs. archive credentials

A distinction that must be stated precisely

Persistent sign-in requires each account's partition to hold browser-managed authentication state (cookies, storage, service-worker state) on disk. That is browser state the browser itself manages. It is materially different from the application deliberately copying credentials into the research archive. The archive never contains a cookie, token, CSRF value, or OTP.

Protection: profile directories live under the app container, protected by macOS per-user file permissions and (if the owner enables the App Sandbox) by sandbox entitlements; partition names contain no owner-identifying strings; and the archive is not searchable by other applications. Residual risk is that anyone with access to the owner's macOS user session can open the application and use the signed-in Arena sessions — the same exposure as any browser the owner is signed into. That risk is accepted and stated, not engineered away.

14.5 Deletion

Three scopes: one archived conversation, all local archive data for one Arena account, and the whole local archive.

Deletion never touches Arena's cloud

Local deletion does not delete the owner's Arena conversations remotely. Any future remote-deletion feature must be a separate, explicitly named operation with its own authorization, its own confirmation, and its own audit record. Nothing in v1 performs a remote destructive action.

Two-step destructive intent. Archived Arena content is untrusted data and can never authorize a destructive action:

// packages/domain/src/delete.ts — flow
// 1. Trusted client (GUI or MCP, both trusted) prepares.
prepareDelete({ scope: 'account', scopeTargetId: accountId })
  -> resolves scope to a concrete row/blob/observation set
  -> returns { intentId, scopeHash, nonce, expiresAt, affectedCounts }
     // nonce is unguessable, single-use, short-lived, stored server-side

// 2. The same or another trusted client confirms, presenting the token.
confirmDelete({ intentId, nonce, explicitConfirm: true })
  -> requires nonce match AND scopeHash match AND confirmedBy === 'trusted-client'
  -> replays affectedCounts for display, then executes in one transaction:
       rows → source_observations → FTS entries → analysis derivatives → blobs
       → sync cursors → dedup markers → destructive_intent
  -> records an audit entry describing what was deleted and by whom/when

Requirements: the token cannot be minted from archived content; a token minted for one account cannot satisfy another account's scope; the token expires; confirmation is idempotent (a second confirm of a consumed token fails cleanly); and the operation reports exactly what it could not delete (for example, previously created plaintext exports, external backups).

Per-scope effects.

  • One conversation: conversation, branches, turns, revisions, participants, identity observations, capture states, artifacts and blobs, FTS entries, and analysis results that reference only that conversation (others are recomputed, not silently altered).
  • One account: everything above for that account, plus its sync cursors, coverage ledger, job history, and the account row. Optionally, as a separate confirmed step, the browser partition's site data — because that signs the owner out and is a different kind of consequence, it is never bundled implicitly.
  • Whole archive: all accounts, all blobs, the database file, WAL, FTS structures, cursors, analysis runs, restricted netlog artifacts, and the Keychain archive-key item (so the archive cannot be reopened). Backup and export residue is reported, not hidden.
  • Future re-sync behavior: deleting a conversation removes its dedup markers too, so a later sync may legitimately re-archive it; deleting an account removes its checkpoint, so re-adding the account requires a fresh verified sign-in. Both behaviors are documented in the confirmation dialog.

15MCP — the primary LLM interface

Verified fact The MCP specification defines stdio and Streamable HTTP transports, states that clients SHOULD support stdio whenever possible, requires newline-delimited UTF-8 JSON-RPC on stdio with logging confined to stderr, and (for HTTP) mandates Origin validation and recommends binding only to localhost. Recommendation stdio is the default and only transport in v1.

  • Why stdio. The agent launches the server as its own child process; there is no listening socket, no LAN exposure, and no DNS-rebinding surface at all. The MCP spec's own HTTP guidance — validate Origin, bind localhost — exists precisely to close the hole that stdio never opens.
  • No loopback HTTP in v1. It would add an attack surface for no operational advantage in a single-user, single-machine application. If a future need arises (for example a browser-based MCP inspector), it binds to 127.0.0.1 only, validates Origin, requires a per-launch token, and exposes only read-only tools. Destructive and browser-controlling tools stay stdio-only.
  • Shared service layer. GUI and MCP call the same functions. There is no MCP-specific behavior and no GUI-specific behavior. A capability is either available to both or to neither.

15.4 Owner-only actions (deliberately absent from MCP)

Completing email verification, entering an OTP, solving a CAPTCHA, and approving any challenge are owner interactions with the remote Arena page. They have no tool, no resource, and no automation path. MCP can report that an account needs them and can focus the account's view; it cannot perform them. Anything else would either be unreliable or would cross into circumventing anti-automation controls.

15.5 stdio hygiene

Exactly one JSON-RPC message per line; nothing but messages on stdout; all logging to stderr; messages never contain embedded newlines. Startup performs capability advertisement and a capability query so an agent learns the archive's current state before acting.

15.6 Client disconnect and job continuation

Jobs are server-side entities. If the MCP client disappears, running jobs continue to completion or to a declared pause, and their state is queryable by the next client. A job is cancelled only by an explicit jobs.cancel — never inferred from a disconnect. If the Streamable HTTP transport is ever added, the spec's rule is honored explicitly: disconnection is not cancellation, and cancellation is signalled with an MCP CancelledNotification.

16Deterministic local analysis

All analysis runs locally, deterministically, and transparently. v1 adds no embeddings, no local model inference, and no ML dependency. Every number must be reproducible from stored observations by re-running the same code version.

16.1 v1 metric families

Length & structure

Response length; paragraph count and length distribution; sentence length distribution; code-block count and length; prose/code token ratio; heading usage and depth; list and table usage; presence of preambles and conclusions.

Lexical

Type-token ratio and moving-average diversity; hapax ratio; recurring n-grams (n = 1…5) with document frequency; distinctive-phrase lists versus cohort baseline.

Punctuation & casing

Em dash, en dash, semicolon, colon, ellipsis, exclamation density; quote style; Oxford-comma rate; sentence-initial capitalization patterns; ALL-CAPS usage; title-case headings.

Markdown habits

Fenced versus indented code; language tag frequency; bold/italic usage; inline code density; bullet marker style; numbering style; horizontal rules; link and citation patterns.

Rhetorical shape

Opening-phrase clusters; transition-phrase inventory; conclusion templates; qualification and hedging markers; uncertainty markers ("might", "typically", "it depends"); refusal and apology language; directive versus explanatory voice.

Behavioral adjuncts

Stop-rate and stop position; regeneration frequency; response length versus prompt length; formatting variance within a conversation; reaction to code versus prose prompts.

16.2 Stratification

Every profile can be stratified by: identity evidence class (revealed / observed-selected / blind / unknown / owner-annotated / inferred); Arena mode (battle, direct, side-by-side); prompt type; topic; language; date bucket; conversation context; and Arena account where relevant to sampling. Every reported figure discloses its cohort definition and sample counts, and cohorts below a documented minimum displayable size are reported as suppressed rather than as a possibly-meaningless number. No universal minimum sample threshold is invented; power and stability are measured empirically per experiment (§17).

17Later fingerprinting experiments and later modalities

These are explicitly out of scope for v1 and are documented now only so the data model does not accidentally make them impossible.

17.1 Stylistic fingerprinting is a hypothesis, never proof

Any experiment claiming that text resembles a particular model is producing a hypothesis. Requirements before an experiment may report anything:

  • Held-out conversations with leakage-resistant splits; branches and near-duplicate turns must stay in the same split, since they share provenance and would inflate accuracy.
  • Prompt and topic controls: same-prompt comparisons wherever Arena permits, and topic stratification otherwise.
  • Negative controls: same model at different times, and different models on identical prompts.
  • Calibration and unknown-class rejection: the system must be able to say "unknown" rather than forcing a label.
  • Temporal validation: train on an earlier window, test on a later one, to detect drift rather than memorize it.
  • Reproducible preprocessing pinned to a code version, with the preprocessing recorded in the run.
  • Preserved separation of observed/revealed identity from inferred identity; inferred labels never become ground truth by being written into the identity fields.

No invented threshold. Whether an experiment has enough signal is determined by measured power and split-to-split stability, not by a pre-declared minimum sample count. An experiment that fails these checks is stopped and recorded as inconclusive.

21Platform floor, resource use, and repository layout

21.1 Minimum supported macOS

Recommendation Minimum: macOS 14 (Sonoma), Apple Silicon only.

Justification:

  • Do not inherit the dev machine's version blindly. The development machine runs a newer macOS; supporting only that version would needlessly narrow the floor and invite accidental reliance on very new APIs.
  • The real floor is Chromium's. Unknown Electron/Chromium's documented minimum macOS version must be checked at the moment the Electron version is pinned; the project floor is max(macOS 14, Chromium's documented minimum at pin time). This is a Phase 0 acceptance check with a falsifiable test: build a trivial Electron app and launch it on the chosen minimum version.
  • Apple Silicon only. No x86_64 slice, no Rosetta path, no universal-binary build matrix. This removes an entire class of native-module and codec-signing problems for the SQLCipher binding.
  • Keychain and modern APIs. macOS 14 comfortably covers the Keychain generic-password APIs used for the archive key, modern file-protection attributes, and hardened-runtime/notarization behavior.
  • Private software. No obligation to support old releases; supporting fewer versions reduces the maintenance surface that AI agents must keep green.

Process boundaries and ownership.

  • browser and capture own everything runtime-specific; they are the only packages a CEF reversal would replace.

  • domain has no dependencies on any platform package, which is what keeps the data model stable across an architecture reversal.
