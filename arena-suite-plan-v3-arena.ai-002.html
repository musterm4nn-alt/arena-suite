01 / Decision

Own Chromium’s session and observation surfaces.

Build a private Apple-Silicon Electron application. Each Arena account gets a persistent Chromium Session partition and its own browser view, target registry, capture state, sync queue, identity epoch, and destructive scope. Attach Chrome DevTools Protocol (CDP) before the first Arena navigation, maintain a session-wide metadata inventory, and use isolated-world DOM evidence only as corroboration—not as the primary network tap.

Selected eligible architecture

Electron / Chromium / CDP

  • Browser: Electron BrowserWindow or WebContentsView, default Chromium engine, one persist:arena:<partition_uuid> per Arena account.
  • Capture: pre-navigation CDP Network + Target; session webRequest inventory; will-download; isolated-world UI observer.
  • Services: TypeScript utility processes for normalization, sync, MCP adapter, and deterministic analysis.
  • Archive: SQLite FTS5 in upstream SQLCipher through @signalapp/sqlcipher; encrypted artifact envelopes; root key wrapped by Electron safeStorage on macOS Keychain.
  • Control: official TypeScript MCP SDK, stdio transport; shared application-service commands for MCP and the minimal React GUI.
Why this wins

It gives the strongest maintained observation surface that AI agents can implement without owning a C++ browser distribution.

It is materially deeper than the existing extension because capture is attached by the browser owner before navigation and survives page-world replacement, controls target/window lifecycle, uses partition-level session events, and owns downloads directly.

It is not omniscient: service-worker auto-attachment and live streamed-byte delivery remain falsification tests.

Reversal condition

Switch the browser shell to CEF—preserving the TypeScript service contracts and archive schema—if the signed-in falsification spike shows that Electron cannot observe the actual Arena response stream before page decoding, cannot attach to the worker/service-worker target that owns it, or loses events across target/navigation changes in a way that DOM reconciliation cannot detect and label. CEF’s documented browser-process response filters cover service-worker-originated requests, but accepting that path means a C++/Objective-C++ shell, a larger build surface, and more maintenance. A custom Chromium fork is considered only if both maintained CDP and CEF response-filter surfaces fail a concrete required observation.

Recommendation. Set the app’s exact deployment floor to macOS 14.0 Sonoma, Apple Silicon only. Current Electron documentation consulted says newer Electron lines require at least macOS 13; choosing 14.0 narrows the private test matrix without pretending the framework itself requires Sonoma. The owner’s macOS 27 machine is above this app minimum. Pin the latest supported stable Electron at implementation lock time rather than freezing a version in this plan. [E10]
02 / Evidence

What this run established—and what it did not.

Sources were treated as untrusted reference material. No authenticated Arena account, browser instrumentation session, local macOS runtime, or existing exporter repository was available to execute during this run. Accordingly, Arena-specific endpoints, payloads, streaming transport, pagination, model fields, and owner-history APIs remain unknown.

Verified fact—platform scope. Electron documents persistent session partitions; access to cookies, cache and service workers; a CDP debugger transport with child-session IDs; direct download control; isolated renderers; and utility processes. Chromium’s protocol schema includes response-body retrieval, streamed resource content, EventSource messages, WebSocket frames, target auto-attach, browser-target attachment, and service-worker-related target attachment. This verifies available mechanisms, not their Arena coverage. [E1–E7]
Verified fact—Arena public surface. Arena’s help center documents email signup followed by a verification link, saved chat history, Direct and Side-by-Side access for signed-in users, and archived chats exposed through Search with “Include archived chats.” Its Code Arena help documents paired options, previews, code blocks, database views, share links, and votes after both previews are viewed. The unauthenticated public shell fetched in this run loaded reCAPTCHA and exposed an anonymous/provisional UI. [A1–A4]
Strong inference. A normal, non-automated Electron window with owner interaction should be able to complete Arena’s email flow, verification redirects, popups and CAPTCHA because it embeds full Chromium and controls child windows. Missing confirmation: a real signed-in test with the current Arena flow and Electron’s user agent. If it fails, first remove Electron branding from the user agent and keep automation disabled; do not fabricate login tokens.
Hypothesis to test—decisive. The Arena text stream is visible through page/worker CDP Network events and either Network.streamResourceContent or a terminal Network.getResponseBody. Smallest test: send one owner-session prompt while recording all CDP target types and compare captured bytes/events with the rendered response. If the stream is owned only by an unattached service worker or protocol primitive that Electron cannot reach, execute the CEF reversal gate.
Hypothesis to test—backfill. Arena’s current UI may call account-scoped listing and detail reads that can be replayed with the correct partition session. Smallest test: capture Search/history navigation, classify candidate operations, repeat one against a disposable owner conversation while confirming no remote change, then verify authorization fails after sign-out and does not silently succeed under the other owner account. If no stable list exists, UI traversal becomes the bounded fallback and “fully synchronized” is unavailable.

Electron vs CEF: the close decision

Electron preserves

  • Mainstream TypeScript implementation and agent-readable diagnostics.
  • One maintained package combining Chromium, Node, windows, sessions and CDP.
  • Partition-aware session APIs and direct DownloadItem ownership.
  • Faster adapter iteration when Arena’s frontend drifts.

Cost: bundled Chromium memory/disk footprint; CDP experimental primitives; native SQLCipher module; eight-week Electron cadence and only three supported stable lines. [E9]

CEF preserves

  • Browser-process request/response filters, including service-worker-originated loads.
  • CDP, request contexts, download handlers, and the same Chromium compatibility class.
  • A path to stream-byte copying when target attachment is insufficient.

Cost: C++/Objective-C++ shell and threading rules; CMake/binary-distribution pinning; more browser UI/auth plumbing; separate Node/Swift services; substantially higher autonomous-agent repair burden. [C1–C3]

Partition and identity model

Partition identity

A random local UUID is created before login. It never changes and is not derived from email, URL, conversation ID, cookies, or visible name. All Chromium state and capture queues are keyed by it.

Session epoch

Every confirmed sign-in/account change creates an immutable epoch. Observations reference the epoch active at capture time. Sign-out closes authority but does not rewrite old provenance.

Arena identity

UI and network identity observations are stored separately with timestamp, source, parser and confidence. A human confirms the account display/email once; later mismatch pauses only that partition.

On every candidate read, sync, export, or deletion, the service requires an explicit archive_account_id; it resolves to exactly one partition and current epoch. A conversation URL or opaque source ID never establishes ownership. Same source ID under two accounts creates two records plus a diagnostic conflict. Text/title similarity is not a reconciliation key.

Credential boundary: prefer native requests that are explicitly bound to the existing Electron Session, allowing Chromium to apply its browser-managed cookies and refresh behavior without exporting them. If a verified owner read requires a bearer/CSRF value that cannot be reused through the Session, a partition-scoped credential broker may copy it from the correct renderer into locked process memory for one request, verify the current identity epoch before and after use, zero practical buffers, and discard it. Such copies are forbidden from disk, database, artifacts, exports, fixtures, errors, URLs and logs. Browser-managed persistence is different: each persistent partition retains its own cookie/storage profile on disk so simultaneous sign-ins survive restart; that profile is separately protected and deletable, and is not represented as SQLCipher archive data.

05 / Discovery

Inventory broadly. Retain narrowly.

Discovery is a permanent subsystem, not a one-time reverse-engineering notebook. It sees every first-party request encountered in supported workflows while persisting only sanitized metadata and bounded, approved exemplars.

Three observation planes

Session inventory

Electron session.webRequest records request/response timing, initiator, resource type, redirect chain, status and partition. It is broad enough to detect unknown traffic and service-worker-associated requests, but its documented API does not provide response bodies.

CDP capture

Attach before first navigation; enable Network; discover/auto-attach related targets recursively; record target type and session ID; collect response bodies, streamed resource data, EventSource events and WebSocket frames when supported. Renderer/target detach creates an explicit gap.

Rendered evidence

A context-isolated, sandboxed observer reads semantic UI and DOM mutations for visible turn text, positions, stop/failure affordances, votes and reveals. It never exposes Electron, filesystem, keys, MCP, or arbitrary IPC to Arena.

Operation identity is a deterministic tuple of sanitized origin class, path template or GraphQL operation name if directly observed, method/frame kind, transport, initiator and payload shape—not the raw URL. Query values, signed paths and opaque IDs are HMACed with a diagnostics subkey. Unknown remains unknown until an adapter test changes it.

Classification workflow

  1. Memory-only intake strips cookies, authorization, CSRF, passwords, OAuth codes, query strings, fragments, signed URL components, email values, unrelated form fields and full request bodies by default.
  2. Compute structural schema: JSON key paths with primitive types and counts; event names if parser-safe; content type; size; status; timing; target/partition; redacted path template.
  3. Known conversation adapters may extract allowlisted transcript fields into an encrypted evidence object. An unknown body never reaches disk merely because parsing failed.
  4. Parser exceptions log adapter/version, shape hash, byte count, bounded stack fingerprint and redacted field path—not the rejected buffer.
  5. An owner-enabled diagnostic window may hold a capped encrypted sample only after a second sanitizer pass and a canary secret test. NetLog includeSensitive/everything modes are forbidden in routine operation.
Recommendation—provisional quotas, not measurements. Start with a 512 MiB encrypted per-account capture spool, 64 KiB maximum sanitized exemplar, 20 exemplars per payload family, and 1 GiB global sanitized-evidence budget; make each configurable. Never evict normalized transcript text to satisfy these budgets. On pressure, drop oldest reparsing evidence, then unknown exemplars, while recording evidence_evicted. Artifact quota is separately owner-set after measuring daily byte growth. Display current bytes, daily growth, event rate, p50/p95 sanitizer latency, dropped events, queue depth, Electron process RSS, and per-partition cache size. These are planning defaults, not claimed workload measurements.

Production capture is passive: no request rewriting and no Fetch-domain pausing. For classified streaming requests, test Network.streamResourceContent, whose protocol schema returns buffered data and enables data-bearing dataReceived events. Use terminal Network.getResponseBody for bounded completed bodies. WebSocket and EventSource have distinct CDP events. Stream and turn reconstruction

  • Key each raw stream by (partition, session_epoch, target_epoch, request_id, logical_stream_id?). Request IDs are never assumed globally unique.
  • Adapters are transport-specific: concatenate ordered fetch bytes with a streaming decoder; parse SSE field framing across chunks; store WebSocket direction/opcode/frame ordinal; parse JSON event families incrementally. UTF-8 and protocol boundaries can span chunks.
  • Deduplicate repeated transport events only with adapter-defined event IDs or exact tuple (stream, ordinal, byte-range hash). Reconnects create a new physical stream linked to the logical response with explicit overlap evidence.
  • Network establishes candidate turn IDs and boundaries. UI establishes visible participant position and rendered result. Reconciler uses source IDs/parent references first, account-local timing and position only as constrained evidence, never identical text alone.
  • Late reveal creates a new identity observation scoped to supported participant and turn/time range. It changes a computed “best known identity” view without rewriting blind history.

Read and account-association proof

  1. Capture a candidate operation only while a confirmed account epoch is active and invoked through visible history UI.
  2. Snapshot visible remote state around a disposable owner conversation: title, archive state, vote state, count/order. Replay once, then repeat with the same cursor. Any state change or mutation-shaped response marks suspected_mutation and stops the adapter.
  3. Run with that account signed out: require an auth failure or no owner data. Run a known conversation belonging to owner account A through owner account B: require not-found/forbidden/no data; if data appears, mark ownership ambiguous and do not import. These tests use only the owner’s two accounts.
  4. Compare multiple pages with UI results; establish cursor semantics, ordering key, overlap, archived coverage, detail retrieval and end condition. A single successful ID is insufficient.
  5. Persist the test observation IDs, adapter version and confirmed visible account identity as the operation’s verified_read evidence.

Per-account scheduler

SyncRun(account_id, partition_id, session_epoch, adapter_version) {
  state: queued | verifying_authority | listing | fetching_details | reconciling |
         paused_rate_limit | paused_auth | paused_drift | cancelled | complete_with_gaps | complete,
  checkpoint: {cursor?, stable_sort_key?, page_fingerprint, overlap_window, detail_queue},
  progress: {pages_seen, unique_refs, details_ok, details_partial, conflicts, retries, gaps},
  coverage: {oldest_seen?, newest_seen?, archived_included, end_condition_evidence?}
}
  • Sync now: accepts one or selected account IDs. Each gets an independent job/checkpoint. Concurrent accounts are allowed only after tests show independent partition credentials and rate limits; otherwise a fair round-robin runs one network request at a time without coupling job state.
  • Resumption: commit each page’s normalized records, checkpoint, and page fingerprint atomically. On crash, replay an overlap window. Upserts use account-scoped source keys and field-level provenance.
  • Unstable pagination: detect repeated page fingerprints, non-monotonic sort keys, unexpected gaps and changing totals. Expand overlap; bound retries with jitter; finish complete_with_gaps rather than loop forever.
  • Live overlap: live capture has lower latency; sync may add missing evidence or stronger source fields. Reconciliation locks one account/conversation at a time, never overwrites a complete live revision with a weaker rendered scrape, and records conflicts.
  • Auth/challenge/drift: immediately pause only the affected account, leave checkpoint durable, surface owner action. Unexpected redirects or any suspected mutation stop that adapter before retry.
  • Automatic sync: off by default and enabled per account. It runs only with confirmed active authority, a verified read adapter, app awake, and no unresolved challenge.

Meaning of “synchronized”

Per account, synchronized means a verified listing adapter reached its verified end condition for both normal and archived views at a recorded cutoff, every listed item has a terminal detail status, overlap checks passed, and gaps/conflicts are enumerated. It does not mean remote data cannot later change. Without a reliable listing/end condition, the only honest status is visited coverage: known items and traversed UI ranges, with unknown total history. MCP exposes the gap list and evidence.

Observation retention and reparsing

Keep immutable structural observation metadata—partition/epoch, mechanism, operation, shape hash, timing, adapter, completeness, redaction result and normalized provenance—for the life of the associated conversation. Keep allowlisted sanitized conversation payload evidence for a provisional 90 days or until the configured evidence-byte budget is reached, whichever comes first; retain at most the newest 20 sanitized exemplars for each active protocol family. Both values are owner-configurable and reported per account. Eviction writes a durable marker with payload hash, size, reason and date. While payload evidence remains, a new adapter can reparse into a side-by-side projection and compare results before promotion. After eviction, only normalized text, structural metadata and provenance can be re-indexed/reanalyzed; original protocol fields cannot be recovered, and diagnostics must say source_payload_unavailable. Identity/reveal evidence that is necessary to support a surviving normalized assertion is retained in allowlisted normalized form rather than relying on an expiring raw body.

Model identity semantics

The archive computes a convenience best_known_identity_view by time/range and evidence rank, but the underlying observations are append-only until deletion. Example: “Model A” visible for turns 1–4 remains a blind-label observation; a post-vote “Provider X / Model Y” reveal applies only to the participant and range established by that reveal. It does not establish an exact build, route, decoding configuration, or all future branches. Conflicting network/UI/import/annotation values remain queryable.

Transactions, recovery and migration

  • Capture commit: observation metadata, allowlisted evidence blob reference, normalized conversation changes, provenance assertions and FTS row update commit in one SQLCipher transaction. Artifact file is written encrypted to a temporary .partial, fsynced, renamed, then linked; a recovery table tracks either side of the two-phase file/DB boundary.
  • Concurrency: one archive writer utility process, WAL mode, short transactions; browser capture queues apply backpressure and mark loss if the bounded spool overflows. Readers use read-only snapshots. SQLCipher documentation states DB pages and WAL page data are encrypted; verify the actual addon build and temp-store behavior. [D2]
  • Crash recovery: run cipher integrity check and foreign-key check; replay uncommitted spool segments by idempotency key; clean orphan .partial files; leave uncertain turns partial.
  • Migrations: forward-only numbered SQL, preflight free space, encrypted online backup, migration journal and post-migration invariants. Never auto-downgrade. Adapter reparsing writes a new projection version before atomically switching the current view.
  • Backup/restore: use SQLite’s online backup API to create a consistent encrypted snapshot, copy encrypted artifacts and manifest, then verify hashes and open with a separately wrapped backup key. Restore into a new directory, verify, then atomic directory swap; never overwrite the only good archive. [SQL2]

Offline capabilities

FTS5 indexes titles, prompts, responses, visible labels and safe filenames inside SQLCipher. Filters cover account, date, mode, observed/revealed model, response/completeness state and provenance mechanism. Results show account source and branch path. Transcript retrieval selects a branch or returns a branch tree—never a flattened alternating text fiction. Versioned JSON export includes IDs, account scopes, structure, identity observations and provenance; HTML/Markdown export is human-readable with uncertainty badges. Exports accept one, selected, or all accounts while preserving account containers.

09 / Protection

Encrypt the archive; acknowledge the browser profile.

Key hierarchy

random 256-bit archive root key (generated once with OS CSPRNG)
  ├─ HKDF("db")        → SQLCipher raw key
  ├─ HKDF("artifact")  → per-artifact AES-256-GCM wrapping keys
  ├─ HKDF("hmac")      → scoped IDs / safe URL fingerprints
  └─ HKDF("control")   → deletion-intent MACs

safeStorage.encryptStringAsync(root_key_encoding)
  → wrapped-key file (0600) + Keychain-held Electron app encryption key
  → plaintext root key exists only in archive utility-process memory while unlocked

Do not pass the key in command-line arguments, environment variables, SQL logs, crash reports, fixtures, exports or MCP results. Disable core dumps for archive processes; overwrite practical buffers; lock the archive when Keychain is unavailable or the app exits. Electron documents that macOS safeStorage protects its keys in Keychain from other apps absent user override and recommends a stable signed identity. It does not protect against compromise of this running app or the logged-in owner. [D3]

Remote-content boundary

  • Arena windows use nodeIntegration:false, contextIsolation:true, sandbox:true, webviewTag:false, secure content only, restricted permissions, and navigation/window-open allowlists. Electron explicitly recommends these controls for remote content. [E8]
  • No contextBridge API is exposed to Arena. Capture lives in main/CDP; the DOM observer can emit only a closed schema through an isolated preload channel whose sender partition/frame is validated. Prefer main-process DOM snapshots over any bridge if practical.
  • The local archive GUI is a separate renderer/origin and never shares a Session with Arena. Render transcript text as text, sanitize imported Markdown/HTML, disable scripts, remote images and navigation.
  • MCP uses stdio plus an app Unix socket under a mode-0700 directory and mode-0600 token file; there is no loopback HTTP listener for Arena JavaScript to reach. The main process does not accept archive commands from Arena webContents IDs.
  • Downloads are caught at the initiating partition; safe filename/MIME and initiator origin are recorded; bytes go directly into an encrypted artifact stream or an owner-selected export path. Signed URLs are reduced to origin + redacted path fingerprint and never retained raw.

Deletion semantics

Conversation

Delete normalized graph, observations/evidence, artifact envelopes, FTS rows and analysis cohort/results that depend on it in one logical job. Orphan file cleanup is resumable. Add an account-scoped local suppression marker only if the owner chooses “do not re-import.”

One account archive

Cancel that account’s jobs, close read snapshots, delete all account rows/artifacts/index entries and optionally its suppression markers. Browser partition removal is a separate explicit flag because it signs the account out and deletes browser-managed session state.

Whole archive

Stop all work, close DB, cryptographically erase by deleting wrapped root key, then remove DB/WAL/artifacts/backups under app control. Report failures; never claim erasure from external exports, Time Machine snapshots, or other backups.

Deletion jobs journal scope and item counts without transcript content. On crash they resume forward; they never restore a half-deleted record. Future sync respects retained suppression markers; if markers are deleted too, the report warns that remote conversations can return on later sync. Local deletion never mutates Arena remotely.

10 / MCP

One service contract, two local clients.

The primary interface is an MCP server launched by the LLM client over stdio. It forwards typed commands to the running app’s local control socket; if the archive service is not running it may start headless archive services, but browser authentication returns USER_INTERACTION_REQUIRED and opens the correct partition window.

Transport and discovery

  • Transport: MCP stdio; stdout contains protocol messages only, stderr receives sanitized logs. Direct process launch limits network exposure. The app control socket validates a random install token held in a mode-0600 file and enforces the same macOS UID/directory permissions.
  • Discovery: capabilities.list reports archive schema, adapter versions, feature flags, availability and reason codes. Resources include arena://accounts, arena://jobs/{id}, arena://protocol/catalog, arena://diagnostics/summary, and arena://conversations/{id}/provenance.
  • GUI parity: React views invoke the exact same Zod command schemas and application handlers as tools. No database calls live in GUI components. Browser open/auth commands are MCP tools; owner interaction is a reported state, not a hidden GUI-only capability.

11 / Analysis

Profiles first. Attribution claims remain experiments.

V1 deterministic model profiles

Run in a utility worker against a read-only archive snapshot. Cohorts are grouped only by identity observations selected through an explicit policy—such as revealed_display_name or owner_annotation—and always expose unknown/conflicting counts. Store preprocessing, Markdown parser, sentence segmentation, language handling, query, excluded revisions and source IDs.

Scale & structure

Response/paragraph/sentence/code-block lengths; Markdown headings, lists, tables, links/citations, fenced/inline code; code-to-prose ratios; branch/revision counts.

Lexical surface

Token/type counts with multiple diversity measures, recurring phrases/n-grams, punctuation, casing, openings, transitions and conclusions. Report sample support, not just averages.

Stance markers

Versioned transparent dictionaries for qualifications, hedging, refusals, apologies and uncertainty. Show matched excerpts linked to turn/revision provenance; never treat dictionaries as intent classifiers.

Stratify by prompt type, topic, mode, language, time bucket, turn depth and available conversation context. Use medians, quantiles, distributions and bootstrap intervals at conversation level when appropriate; retain representative excerpts selected by declared rules rather than cherry-picking.

What this corpus can and cannot support

It can describe patterns in this owner’s observed Arena responses under recorded contexts. It cannot estimate a model’s general population behavior or prove a model/provider/build identity. Selection bias, prompt/topic confounding, sparse cells, hidden system prompts, decoding settings, tools, safety layers, aliases/routing, temporal changes, Arena post-processing, branch dependence and uncertain labels all limit comparisons. Paired battle turns under the same prompt are stronger for within-prompt contrasts, but conversation history and position effects still matter.

Embeddings and local ML

Do not package embeddings or a local model in v1. Admit an embedding pipeline only when a named analysis cannot be answered with FTS/deterministic features, the owner approves model-weight storage, and a preregistered pilot improves held-out utility over lexical baselines. At entry: pin weight file and cryptographic hash, tokenizer, license, quantization, preprocessing, runtime (prefer ONNX Runtime arm64), batch/memory cap and offline cache; download once over an explicit owner action, then operate offline. Record failures and hardware measurements on the M3 Pro rather than inventing them.

Later similarity / fingerprinting protocol

  1. Predeclare target labels, candidate features, unknown class, confound controls and stop criteria. Inferred identity lives only in analysis_result, never in identity_observation.
  2. Group all near-duplicates, regenerations, branches, shared prompts and same-conversation turns before splitting. Split by conversation/prompts and time; keep a final untouched holdout.
  3. Use prompt/topic/language/length/context/mode/time controls; include negative controls (same model across topics/time and different models on matched prompts) and shuffled-label baselines.
  4. Calibrate probabilities on validation data; measure reliability, abstention/unknown rejection, temporal robustness and confidence intervals. No universal sample threshold is assumed—minimum evidence is learned from power/learning curves and stability.
  5. Continue only if leakage audits pass, performance beats transparent baselines on held-out conversations, calibration is useful, and results persist under confound-matched analysis. Revise if only narrow strata work. Abandon identity framing if unknown rejection/calibration fails or model identity is dominated by topic/template/time leakage.

Outputs must say “similar to cohort X under experiment Y” with calibrated uncertainty, never “is model X” or “authored by X.”

Implementation-agent handoff checklist

Start here

  1. Create G0 repository and evidence-bundle schema.
  2. Build synthetic transport fixture before Arena adapters.
  3. Implement immutable partition/epoch IDs before login.
  4. Attach CDP before navigation and deliberately test failure.

Non-negotiable invariants

  • Account ID is in every source/reconciliation/destructive key.
  • No raw auth material reaches persistence or diagnostics.
  • Observer loss can only reduce completeness.
  • Remote content has no archive or MCP privilege.
  • Unknown operations remain unknown.
  • Archived text cannot authorize destructive work.

Final consistency check

The selected architecture is a dedicated Electron/Chromium application—not an extension, chrome.debugger extension, native messaging host, extension companion, or explicit-import-only product. Email authentication is required and owner-driven; Google OAuth/passkeys are not requirements. Simultaneous accounts are isolated in browser partitions, account/session epochs, capture streams, sync jobs, record keys, MCP scopes and deletion intents. CEF is a triggered fallback, not an unresolved second recommendation.
