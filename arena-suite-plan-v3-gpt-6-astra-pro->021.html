Arena Model Archive

A private, account-isolated macOS application that records the owner's own arena.ai conversations from inside a dedicated Chromium-based browser shell, keeps a provenance-first encrypted local archive, and exposes every capability to an LLM through a local MCP server.

0 · Decision summary

Recommended architecture in one paragraph

Build Arena Model Archive as a single Electron application (Chromium-based) that is the browser: one account-scoped BrowserWindow per Arena account, each bound to its own persistent Chromium session partition (persist:arena-<account>), with the app's main process owning all privileged work — CDP capture through webContents.debugger (with a designed escape hatch to a browser-level CDP connection if worker/service-worker target visibility proves insufficient), SQLCipher storage, artifact encryption, the sync scheduler, and a local MCP server on loopback. Arena's own content runs in sandboxed renderers with contextIsolation: true, nodeIntegration: false, sandbox: true, and no archive-privileged preload, so remote page content can never reach the archive key, the filesystem, or the MCP surface. Capture is transport-agnostic (it observes Chromium's network stack, not JavaScript functions the page happens to call), attached before first navigation so early requests cannot be missed, and independent of any extension lifecycle.

Why Electron rather than CEF, in one sentence. CEF offers genuinely deeper native hooks — most importantly a browser-process response filter that is invoked even for requests whose browser and frame are null, i.e. service-worker-originated requests verified in CEF headers — but it costs a C++ application, a second non-browser runtime for storage and MCP, and a large binary, while browser-level CDP gives comparable observational reach for a fraction of the implementation and maintenance risk that an AI agent must carry. The escalation stays open and is triggered by evidence, not by preference.

2 · The decisive problem: capture depth

The assignment fixes one requirement above all others: the architecture must own or embed the browser deeply enough to be materially stronger than the extension baseline, and it must not confuse owning the window with having deeper privileges. This section separates those two ideas, states exactly what the baseline cannot do, and states exactly which mechanism closes each gap.

2.1 The baseline's failure modes, expressed mechanically

The existing exporter is a Manifest V3 extension whose capture “starts at document_start” and intercepts page-level transport per its own README. That design has four structural weaknesses, and they are structural — not bugs that a better extension would not have:

  1. A race it can lose. Injected script must win against the page's own script. If Arena's bundle defines or wraps fetch/XMLHttpRequest/EventSource before the interceptor installs, or installs its own transport shim later, the interceptor observes a different object than the one that carries the answer.
  2. Scope limited to the frames it reaches. Page-world patching reaches the windows the injection policy reaches. Worker, SharedWorker, and service-worker contexts are separate JavaScript globals; traffic that originates there is not observable by patching the document's globals.
  3. A lifecycle the extension does not own. MV3 background contexts are event-driven and terminable. Capture state that lives there is subject to teardown, and a service worker that stops is a gap the user cannot see.
  4. Downloads and artifacts routed through the browser's download machinery or a companion. The baseline notes an optional native host and a Downloads fallback per its own README.

2.3 Anti-detection and automation compatibility, stated plainly

This app does not attempt to hide from Arena; it presents as an ordinary browser because it is one. That is a design choice with a specific mechanical meaning:

  • No automation driver. The app drives its own webContents directly rather than through a remote-debugging automation stack; there is no WebDriver session and no navigator.webdriver flag to launder.
  • No injected stealth patches. The app does not ship scripts whose purpose is to falsify the environment. Its preload, if any, is omitted entirely from Arena windows.
  • Challenges are surfaced, not defeated. The public landing page loads reCAPTCHA Enterprise observed in page source. If a challenge appears, the app's job is to route it to the human — show the challenge, pause automation for that account, and record an unresolved_challenge state (§6.4) — not to solve it. This keeps the app inside ordinary account behaviour and keeps the failure visible.

Terminology discipline. This report distinguishes three things that are often conflated: (a) authenticated read access — using a first-party endpoint with the owner's own session credentials, whether or not it is documented; (b) automation compatibility — presenting normally and routing challenges to the human; and (c) access-control workarounds — circumventing a control that exists to gate access. The plan uses (a) and (b). It does not use (c), and if a proposed feature requires (c), the correct outcome is to record the gap and report it, not to build the workaround.

3.1 Native Swift with WKWebView — why it is not merely “worse Electron”

It is worth being precise, because this is the option most likely to be proposed by someone who values platform fit. A WKWebView app can observe navigations (decidePolicyFor), can inject scripts (WKUserScript at documentStart), can run a custom scheme handler, and on modern macOS can even host WebExtensions. None of those observe the response bodies of authenticated https requests. The realistic workarounds are a local proxy with TLS interception, or reading the WebKit network cache after the fact. The first is a maintenance and trust problem; the second is lossy, timing-dependent, and cannot see credential-scoped traffic on demand. The honest conclusion is that WKWebView gives an agent no supported way to answer the question “what exactly did the server send, and when did each chunk arrive?”

3.2 Electron vs CEF, head to head

The assignment asks for a focused comparison when both are plausible. They are. The difference is not capability — it is who absorbs the risk.

Where CEF is unambiguously stronger

  • A native response filter that streams response bytes in the browser process, and is documented to run even when the request has no associated browser or frame, i.e. service-worker traffic E4. That is a guarantee, not a configuration to discover.
  • Per-request control (redirect, replace handler, cancel, filter) at the IO thread.
  • No dependence on any Electron-specific bridge for target reachability; ExecuteDevToolsMethod plus a message observer is documented alongside the lower-level message API.

Where CEF costs more than it returns here

  • C++ implementation performed by agents: longer feedback loops, harder debugging, fewer training examples, and no natural home for the archive services. The plan would need a second runtime (Node or Swift) for SQLCipher/FTS, MCP, and the analysis layer — reintroducing exactly the “unnecessary resident runtimes” the brief asks to avoid.
  • Distribution weight is irrelevant for a private app; build complexity is not.
  • Feature velocity: the MCP surface, storage layer, and analysis layer are most of this project's surface area, and they would all live outside CEF anyway.

Resolution. Electron is chosen, but the plan does not pretend that CEF's native filter has an Electron equivalent. Instead it (a) makes browser-level target reachability an explicit, early, falsifiable gate; (b) specifies a loopback CDP fallback that reaches the same browser-level surfaces without leaving Electron; and (c) names CEF as the escalation with a trigger, preserving CEF's advantages if the gate fails. This is the honest version of “Electron, unless evidence says otherwise”.

3.3 A dedicated shell vs the assignment's fixed requirement

The assignment forbids an extension, chrome.debugger extension, extension + native host, and extension + companion as the recommended architecture or primary capture path. The recommendation satisfies this by construction: there is no extension component, and the primary capture path is a browser-process CDP session owned by the app. It is worth stating what is not claimed: this is not exotic. It is the same observation mechanism the platform's own developer tools use. Its advantage over the baseline is not access to a secret API; it is ownership of timing, scope, lifecycle, downloads, and per-account session state.

3.4 Custom Chromium fork — named, then set aside

A fork could in principle add observation that no embedding surface exposes. It is listed only so that the escalation ladder is complete, and it is explicitly not a plan: it would multiply build time, security-patch obligations, and unreviewable divergence for a single-user app. If a future gate proves that a required observation is impossible through CDP, through the loopback CDP connection, and through CEF, the correct response is still to document the missing observation and reduce scope — not to fork Chromium.

4 · Recommended architecture

4.1 Process and trust boundaries

Boundary rules, stated as invariants

  1. No Arena content in a privileged renderer. Arena windows are created with contextIsolation: true, nodeIntegration: false, sandbox: true, webSecurity: true, and no preload script. The archive UI lives in a different window with a different partition and its own minimal preload.
  2. IPC is a closed list. Every channel is explicitly registered in the main process, and every handler validates event.senderFrame against the set of frames the app itself created mechanism per Electron's security guidance. A message from an unexpected frame is dropped and recorded as a security event.
  3. Navigation is constrained. Arena windows may navigate within the Arena origin set and may open popups only into app-created windows with the same partition; external links open in the system browser after an explicit decision, never inside a privileged context.
  4. Secrets never round-trip through JavaScript. The archive key, MCP token, and SQLCipher passphrase are read in the main process and never serialized to a renderer.
  5. Untrusted text is labelled at every hop. Records carry a trust field from their origin (arena_remote, local_user, derived). Tools that echo content mark it; the destructive-action guard (§9.6) does not read it.

4.2 Session and partition model for simultaneous accounts

An Arena account in this app is a first-class object: it owns a partition, a capture engine, a sync scheduler namespace, provenance scope, and a destructive-action scope. Nothing is shared between accounts except the archive database itself, which is partitioned by account_id.

4.3 Capture architecture

4.3.1 Attach sequence — designed so that nothing early is missed

The ordering is the whole point. A webContents is created on about:blank, instrumented, and only then navigated to Arena:

1. win = new BrowserWindow({ show:false, webPreferences:{ partition:'persist:ama-<id>',
                                     contextIsolation:true, nodeIntegration:false,
                                     sandbox:true, webSecurity:true /* no preload */ }})
2. win.webContents.debugger.attach('1.3')          // before any Arena document exists
3. send Network.enable            { maxTotalBufferSize, maxResourceBufferSize,
                                    maxPostDataSize, enableDurableMessages:true }
4. send Page.enable · Runtime.enable · Network.setAttachDebugStack(false)
5. send Target.setAutoAttach      { autoAttach:true, waitForDebuggerOnStart:true,
                                    flatten:true, filter:[…App-relevant target types] }
6. (if gate C1 demands) Target.autoAttachRelated from a browser-level session
7. mark capture state = ARMED ; win.loadURL('https://arena.ai/…')   // first navigation

The exact CDP parameters are taken from the canonical protocol definitions consulted in this run: Network.enable accepts maxTotalBufferSize, maxResourceBufferSize, maxPostDataSize, and enableDurableMessages; Target.setAutoAttach takes autoAttach, waitForDebuggerOnStart, flatten, and a TargetFilter E2. enableDurableMessages deserves attention: the protocol note says it keeps response bodies alive across cross-process navigation, which is exactly the failure mode this project must not have. Hypothesis to test whether the Electron bridge surfaces that parameter and whether it materially changes survival of bodies across navigations; test in C1 with a navigation during an in-flight stream.

4.3.4 What the app will still get wrong, on purpose

Three failure modes are accepted and made visible rather than engineered away:

  • Bodies evicted before retrieval. Mitigated by durable messages and buffer sizing, but if the browser discards a body, the record becomes observer_gap with the request metadata retained.
  • Fragmented WebSocket logical messages. The adapter reassembles; if it cannot decide, it records partial_stream with the raw frames retained (sanitized) so a later adapter version can re-parse them.
  • A target that is never attached. Detected by comparing L1 target inventory with L0 request origins: if requests arrive whose requestId is never bound to a target the app attached to, the engine raises a coverage_suspect signal for that account. This is the app's way of noticing its own blindness.

4.5 Downloads, artifacts, and generated files

  • Interception. Each partition registers a will-download handler. The default behaviour is: cancel the browser's own write, stream the item through the app's artifact vault (chunked AES-256-GCM), then record an artifact row with hash, byte size, content type, source reference, and capture completeness.
  • Naming. The vault path is content-addressed (artifacts/<xx>/<sha256>.bin); the human-readable filename is metadata, never a filesystem path. This removes an entire class of path-traversal problems from untrusted filenames.
  • Partition isolation. An artifact carries the owning account_id. Content-addressed dedup happens only within an account; an identical hash in another account produces a second row plus a cross-account link record, never a shared blob.
  • Large media. Video and large images may be recorded as references with a capture state rather than bytes, depending on the retention policy in §14.2; the decision is per-modality and reversible (re-fetch on demand while the session is live).
  • Preview-host content (Arena Code / web outputs). Previews run in their own windows and their own partition by default, so the archive records the preview's existence, URL form, and any captured response payloads, but does not treat preview content as first-party conversation content. A preview window may be attached to capture for completeness of the generated artifact, and if so it is recorded with the preview's origin as the source.

4.6 What the app deliberately does not do

  • It does not install a proxy, custom CA, or root certificate.
  • It does not import cookies, tokens, or profiles from any other browser or application.
  • It does not enumerate or touch any Arena resource that the signed-in account's own UI and own requests do not already exercise.
  • It does not merge or reassign records across accounts, ever, regardless of how similar the content looks.
  • It does not treat “conversation URL/ID exists” as proof of ownership; ownership comes from observed evidence in an authenticated session.

5 · Discovery and the protocol catalog

Discovery is not a phase that ends; it is a maintained capability. The first engineering objective is not to write a parser for a guessed endpoint — it is to build the machinery that discovers, classifies, records, and re-validates what the app can actually see, and to make its own coverage state machine-readable so an LLM can reason about it.

5.1 What discovery produces

A single machine-readable protocol catalog with two halves: (a) an operation inventory covering all first-party traffic encountered across supported workflows, and (b) a state record that says, for each operation, how well it is understood, and what has drifted since it was last validated.

5.4 Retaining enough to re-parse later

Adapter changes are the most common reason a record needs re-parsing. The app therefore retains, for a bounded window (default 30 days, configurable per class): the sanitized raw payload artifact for conversation_read, conversation_stream, and identity operations, together with the adapter version that first parsed it. A re-parse job can be run against retained evidence and produces new derived records while leaving the old ones intact and marked superseded. Beyond the window, only normalized records and the shape fingerprints survive; the app states this limit rather than implying full recomputability.

6.2 Evidence records and the reconciliation key

Reconciliation answers one question: given observations from different layers, which describe the same thing? The app uses a layered key, and it never uses content equality as identity.

conversation  ← (account_id, source_conversation_id)              // account-scoped, never global
branch        ← (conversation_id, branch_origin_ref, ordinal)      // origin = turn/revision it forked from
turn          ← (branch_id, ordinal, lane_position)                // lane = participant slot, stable within a branch
revision      ← (turn_id, revision_no)                             // regeneration/revision counter
part          ← (revision_id, part_seq, part_kind)                 // streamed part ordering
evidence      ← (observation_id) → may reference any of the above  // provenance is never merged away

Similarity is evidence, never identity:
  same_text_hash(a,b)      → link records, "probable_same_content", no merge
  same_source_id_across_accounts → ownership_conflict record, both sides kept, flagged for the user

Overlapping and repeated events. Streams reconnect; pages re-request; browsers replay. The adapter derives idempotency keys from (requestId, part_seq, content hash) and from SSE eventId where present, and discards replays that match an already-committed part. A replay that differs is not discarded: it produces a revision with a recorded cause (regeneration | reconnect_replay_changed | unknown).

6.3 Reconciling network against UI

L0 and L2 disagree often and usefully. The rules:

  • Content: L0 wins. Rendered text is a projection; if they disagree, the L0 text is canonical and the L2 text is retained as a render_divergence note (this is a genuinely interesting signal for a model-behaviour archive, because it can indicate post-processing, truncation, or rendering bugs).
  • Structure and labels: L2 often wins, because blind labels, lane letters, and vote controls are frequently UI state rather than payload state. L2 identity observations carry lower confidence and a narrower valid time range.
  • Completion: neither layer alone decides. Completion requires a terminal signal (see §6.4).
  • Ordering: L0 ordering is authoritative for what the server sent; L2 ordering is authoritative for what the user saw. They are stored as two orderings, and the transcript view can show either.

6.5 Navigation, workers, reconnects, late reveals

  • Navigation during a stream: the capture engine keeps the request alive in its own index, keyed by requestId, independent of the document that started it. If a terminal signal never arrives, the state is partial_stream. C1 test: navigate mid-stream and assert the record's state and retained chunks.
  • Target changes: every observation records the target it came from (targetId, type, and whether it was auto-attached), so a conversation that continues in a new page/target stays correctly attributed.
  • Workers and service workers: if the answer stream is fetched by a worker, L1 attach is what makes it visible. If attach fails, the coverage-suspect signal fires (§4.3.4) and the affected turns are marked observer_gap rather than silently missing.
  • Reconnects: dedup by idempotency key, revisions permitted (§6.2). The heuristic default is that a reconnect within one answer that re-sends overlapping content is a replay; a reconnect that sends new content after a terminal marker is a new revision.
  • Late model reveals: the reveal is an additional identity observation with its own timestamp and source. It never rewrites the earlier blind label; it adds a mapping (blind_label → revealed_model) with a valid-from time and the evidence reference. If the reveal contradicts an earlier inference, both remain and the conflict is visible (§8.3).
  • Post-vote events: vote submission and the subsequent model reveal are captured as separate observations so the archive can answer “what did the user see before voting?” — which is the only temporally valid basis for blind-comparison analysis.

6.6 The smallest vertical slice that proves the path

Before any of the archive or analysis workspace exists, one slice must work end to end. It is small enough to finish, and it exercises every boundary the rest of the system depends on:

  1. Launch the shell; create partition persist:ama-<id>; complete one account's Arena email sign-in.
  2. Send one prompt that streams an answer; capture the stream via L0; capture the rendered completion state via L2.
  3. Close the app during a second stream; reopen; confirm the second turn is partial_stream (not “complete”) and the first is complete.
  4. Query the transcript through the MCP server; run one deletion on a scratch conversation; confirm the deletion log and that other accounts are untouched.

If this slice cannot be made to work honestly — including the crash case — the architecture must be revisited before more is built.

7.2 Establishing account association and read behaviour

An endpoint name proves nothing. Before a backfill method is enabled for an account, the app must have:

  1. Ownership evidence. The read was issued inside that account's partition, using that partition's own session, and its result is consistent with that account's own identity observation (§8.3). A conversation ID appearing in results is not ownership evidence by itself.
  2. Read confirmation. The operation was observed to be idempotent: issuing it twice produced equivalent results and produced no observable server-side state change (no new conversation, no changed timestamp, no new mutation-class request in the trace). Recorded as read_evidence with dates.
  3. Pagination evidence. Two full traversals produce the same set of items and the same ordering, or a documented and stable cursor semantics. If ordering is unstable, the sync treats pages as a set and uses a conservative overlap window.
  4. Detail evidence. The detail read returns the same turns the live capture saw for at least one conversation captured both ways — the strongest available correctness check, and it is why every sync run reconciles a sample against live-captured records.

Until all four hold for an account, sync runs in inventory_only mode: it discovers and records operations but performs no replay. That mode is itself useful output for the maintenance agent.

7.5 If no reliable listing can be verified

Feasible, and planned for: the archive still works from live capture plus UI-driven traversal, and the coverage statement becomes a map of known conversations rather than a claim of completeness. Concretely, a rendered-history scrape yields a list of conversation identifiers and titles, which is enough to (a) detect conversations the archive has never seen, (b) mark them items_unknown_content, and (c) offer the user a one-click “open these so capture records them”. That is a materially honest and still useful outcome, and it is why the coverage statement carries a listing_method field rather than a quality adjective.

7.6 Interaction between sync and live capture

  • Both write through the same reconciler, so a conversation half-captured live and half-fetched by sync merges on the reconciliation key, not on text.
  • While a conversation is streaming live, sync skips it and re-visits it after the live capture reaches a terminal state, to avoid racing the same turn from two sources.
  • If sync and live capture disagree about a turn's content, both evidence records persist and the turn becomes a revision with cause source_disagreement — the archive does not pick a winner silently, and the transcript view can show both.

8 · Data, identity, provenance, and protection

8.1 Source of truth: a justified hybrid

The design uses three layers, each chosen because it answers a question the others cannot:

  1. Normalized records are the source of truth for what the archive says happened: accounts, conversations, branches, turns, revisions, parts, identity observations, sync runs, analysis runs. They are small, indexed, and queryable.
  2. Observations are the source of truth for why the archive believes it: one row per observed interaction or UI state, with mechanism, adapter version, target, timestamps, completeness, and a pointer to evidence.
  3. Encrypted evidence artifacts are the source of truth for what the server actually sent: sanitized payloads and stream frames, retained for a bounded window so that a parser change can be re-run.

Full event sourcing is explicitly not adopted. It would multiply storage and complexity for a single-user app, and the observation/derived split already provides the property that actually matters: a normalized record can always be traced to the observations that produced it, and can be re-derived when an adapter changes, without replaying the entire history of the app.

Transaction boundaries. One conversation's turns/revisions/parts are committed as a unit for a given source. Observations are appended before parsing. Sync checkpoints are committed in the same transaction as the items they cover, so a crash can never advance a cursor past uncommitted work. Deletion of an account's archive data is a single transaction over metadata plus a separate, resumable artifact-vault purge that is idempotent and records progress, because deleting large encrypted blobs cannot be transactional with SQLite.

Crash recovery. SQLite's WAL handles the database; the artifact vault uses a per-artifact .part file plus atomic rename, and an orphan sweep at startup. The capture engine's in-memory request index is reconstructible from observations; a crash therefore loses at most the tail of an in-flight stream, which is written as partial_stream on the next start with an explicit gap interval.

Migrations. Schema version is a table; every migration is forward-only and idempotent, runs inside a transaction, and writes a backup of the pre-migration database file to a rotation directory (encrypted like the original). Adapter versions are versioned independently of schema versions, because re-parsing is a data operation, not a schema operation.

Backup/restore. The supported backup is a versioned export (below) plus a copy of the encrypted database while the app is stopped. Restore is an import into an empty archive, which re-checks account scoping on the way in. The app refuses to import records whose account scope cannot be determined.

8.4 Account identity binding

Every account has a locally generated ID. Association between that ID and an Arena identity is established by evidence and re-checked: an identity probe observed in the session (profile/account surface or equivalent) recorded as an identity_observation. Rules:

  • Capture refuses to normalize records for an account whose identity is unverified at the time of observation — such records are held as observations with account_binding: unbound and are not shown in the archive until bound.
  • If the probe result changes for a partition (different account signed in), the app stops capture for that partition, records account_mismatch, and requires an explicit user decision: bind the new identity as a new account, or sign out and restore the expected one.
  • No automatic rebinding, ever. This is the mechanism that makes “never merge or reassign across accounts” enforceable rather than aspirational.

8.5 Encryption and key management

Database

SQLCipher, with the properties verified in this run's source review: AES-256-CBC per page, a per-page random IV, a per-page HMAC-SHA512 tag checked on read, and PBKDF2-HMAC-SHA512 key derivation with a per-database salt E12. WAL and journal pages are encrypted with the database key. The app must verify at build time that file-based temporary storage is disabled, because SQLCipher's own documentation says other transient files are not encrypted E12.

FTS5 lives in the same encrypted database, so the search index inherits the same protection rather than needing a second scheme.

Key

A single random 32-byte archive key, generated on first run, held in the macOS Keychain as a generic password item scoped to the app, and never written to a configuration file or environment variable. SQLCipher receives raw key bytes rather than a passphrase supported per the SQLCipher design notes, which avoids a second KDF layer and keeps the database's own KDF irrelevant to the app's key handling. A rotation procedure exists and is tested (re-key, then verify by attempting to open with the old key and expecting failure).

Artifacts

Payloads, stream frames, downloads, images, and DOM dumps are stored as chunked AES-256-GCM files: each artifact gets a subkey derived with HKDF from the archive key and the artifact ID; each 1 MiB chunk is sealed with a unique nonce and additional authenticated data binding the artifact ID and chunk index, so chunks cannot be reordered or spliced between artifacts. Deletion of an artifact is file removal plus row removal, with an orphan sweep.

9 · Full LLM operability

9.1 Transport, connection model, and trust boundary

The MCP server runs inside the running application (main process), because the capabilities it exposes are the application's own capabilities and duplicating them in a sidecar process would create a second source of truth. Two transports are supported:

  • Streamable HTTP on loopback (primary). One endpoint on 127.0.0.1 with an ephemeral port written to a discovery file. The specification requires Origin validation to prevent DNS rebinding, recommends loopback-only binding, and recommends authentication for all connections E13 — all three are implemented: Origin must match the app's own origin or be absent for non-browser clients; a bearer token is required; and any request failing either check is rejected and logged as a security event.
  • stdio proxy (convenience). For clients that can only spawn a subprocess, a small proxy executable speaks MCP over stdio and forwards to the loopback endpoint using the same token. It owns no state and has no privileged access; it is a transport shim, disclosed as such.

Token issuance. Tokens are created per client with a label, are stored only as a keyed digest, and are revocable. The plaintext token is shown once at creation in the GUI. This makes “which client did that?” answerable after the fact.

9.2 Discovery and diagnosis by the client

An LLM must be able to find out what it can do and why something does not work, without reading source. Therefore:

  • Capability resources. A resource returns the build's capability map: which tools exist, which are unavailable and why (e.g. “capture unavailable for account X: signed out”), which platforms/adapter versions are in play, and the archive's coverage statements per account.
  • Error taxonomy. Every error carries a stable code, a human sentence, a recoverable boolean, and one of a fixed set of categories: invalid_argument, not_found, scope_denied, authorization_required, capture_unavailable, sync_unavailable, account_signed_out, account_mismatch, challenge_unresolved, rate_limited, adapter_missing, adapter_drifted, evidence_expired, job_conflict, internal_error.
  • Self-diagnostics as tools, not as prose. diagnostics.report returns structured state; diagnostics.selftest runs the app's own checks (can it attach, can it read a body, is the vault writable, is the token valid) and returns per-check results.

9.5 Jobs, idempotency, pagination

  • Every long-running operation is a job with: id, kind, scope, state (queued|running|cancelling|cancelled|succeeded|failed|partial), progress (monotonic counters plus an explicit “unknown” rather than a fake percentage), cancel_requested, started_at/ended_at, a stable error object when failed, and a result summary.
  • Idempotency. Mutating job-initiating calls accept a client-supplied idempotency_key; repeating a call with the same key returns the existing job rather than starting a second one. This matters specifically for an LLM that retries after a timeout.
  • Pagination. All list/search endpoints use opaque cursors, never offsets, and include a next_cursor plus a stable_until note describing whether the underlying set can change during iteration.
  • Scope is mandatory and explicit. Every tool that touches content requires an account selector (single account, explicit list, or all). There is no default-to-all.

9.6 Content is not authority: the destructive-action guard

Archived prompts, responses, tool traces, and diagnostic strings are untrusted. An LLM reading them may be influenced by them. The design therefore does not rely on the model “being careful”; it makes content-driven destruction structurally impossible:

  1. Two-channel rule. Destructive operations require a token that can only be minted by privacy.delete.request_token, and that tool is available only on a trusted channel: an interactive confirmation in the app's own GUI, or a client that was explicitly configured as destructive-capable at token-issuance time with a human present. An MCP client that can read the archive but has not been granted destructive capability gets authorization_required — regardless of what any archived text says.
  2. Single-use, short-TTL, scope-bound tokens. The token commits to a digest of the exact scope. privacy.delete must present the token and the matching digest. A token minted for one conversation cannot delete an account; a token for account A cannot touch account B.
  3. The confirmation is shown in the GUI. The human sees the resolved scope in words (“delete all locally archived data for account label, 41,203 records, 881 artifacts”) before the token exists. Resolution happens in the trusted channel, so a hostile string inside archived content cannot define what “account” means.
  4. Content-derived identifiers are never authorization inputs. A conversation ID found inside a response body is not accepted as a deletion target unless it resolves to an archive record that the user's confirmation also displayed.
  5. Everything is logged. Token issuance, the confirmation text shown, the requesting client label, and the outcome are recorded in deletion_log and are immutable from the MCP surface.

Why this is not merely an instruction to be careful. The guard is enforced at the point where authority is created (token minting), not at the point where intent is expressed. An injected instruction in archived content can cause an MCP call to fail; it cannot cause a token to exist. The worst outcome of a hostile string is a rejected request and a security-event log entry.

9.7 GUI and MCP parity

Both the GUI and MCP call the same services (capture control, sync scheduler, archive service, analysis engine, deletion service) through one internal façade. The GUI is not a separate implementation path; it is a view over the same operations. Concretely:

  • The façade defines each operation once, including scope validation, job creation, and error mapping.
  • The MCP layer is a thin adapter: argument validation, JSON shaping, and the authorization checks in §9.6.
  • A parity test enumerates the façade's operations and asserts that every one is reachable from MCP and from the GUI, so a new capability cannot be added GUI-only by accident.
  • Capabilities that require a human step (completing a sign-in, solving a challenge) are modelled as jobs that report waiting_for_human rather than as operations that silently fail.

10 · Local analysis and later modalities

All analysis runs locally, on the encrypted database, with no network access. The first release is deterministic and explainable; anything probabilistic is gated.

10.1 Cohort discipline before metrics

Every analysis result names the cohort it used, and the cohort is a stored, digest-ed object, not an ad-hoc filter. A cohort definition always states:

  • Account scope. One account, or several (never silently pooled — if several, the result reports per-account values alongside any pooled value).
  • Identity basis. Which identity observation kinds are admissible: revealed only (strictest), revealed + selected-label, blind-only (for blind-comparison designs), or annotation-included (explicitly labelled as the owner's hypothesis).
  • Completeness basis. Default: only complete turns, with the excluded count reported.
  • Turn position rules. First assistant turn only for “opening behaviour” metrics; all assistant turns for length metrics — because mixing them silently is a common and invisible error.
  • Time window and mode (battle / direct / side-by-side / agent), and whether conversation-history context is held constant.

10.3 Limits of a single-heavy-user corpus — stated, not buried

  • Selection bias. The prompts are the owner's, and prompt style correlates with model choice in direct mode and with lane assignment in battle. Cohorts are therefore confounded by construction unless conditioned.
  • Conversation history. Later turns are conditioned on earlier ones, so turns are not independent samples. Aggregate metrics must state whether they are turn-level (pseudo-replication) or conversation-level.
  • Hidden system prompts, decoding settings, tools, and safety layers. None are observable. Two turns attributed to one label may differ because of a hidden variable. This is the single largest threat to attribution and it cannot be eliminated — only disclosed.
  • Aliases and routing. A displayed label may route to a different backend over time, or a route may change silently. This is why the catalog records config snapshots and why identity evidence carries valid-from/valid-to.
  • Temporal change. Models change. A corpus spanning months contains multiple populations under one label. Time-windowed cohorts are the default for any comparative claim.
  • Post-processing. The platform may transform output before display or before storage. L0 vs. L2 divergence detection is the only available probe, and it can only detect, not explain.
  • Label uncertainty. Blind turns without reveals are unusable for model-level claims. Analyses state the blind fraction.

What the data can support: descriptive, cohort-conditioned comparison of observed behaviour within this owner's usage; hypothesis generation; and detection of drift over time. What it cannot support: claims about a model's general properties, rankings against other users' experience, or identity attribution of any kind.

10.4 Do embeddings or local ML earn their cost?

Entry gate: they are adopted only if a specific, declared analysis cannot be answered by the deterministic layer — for example, deduplicating near-identical branches before splitting, or topic-clustering prompts to construct topic controls. If adopted:

  • Model weights are downloaded once, pinned by content hash, and stored in the vault; there is no runtime download and no network dependency afterwards.
  • Preprocessing and model version are recorded per embedding, so a changed model invalidates rather than silently mixes.
  • Costs are stated up front: a small sentence-embedding model is affordable on this machine; a large model or any per-token generative pass is not obviously so and needs a measured justification.
  • Embeddings are always auxiliary inputs to a declared procedure, never a source of “similarity means same model” claims.

10.5 Later similarity and fingerprinting experiments

Similarity to an archived corpus is a confidence-qualified hypothesis, never proof of authorship or model identity. Inferred identity lives in a separate namespace from observed identity, and any UI that shows both must visually and structurally distinguish them. Requirements before any such experiment may report:

  • Splits that respect structure. Split by conversation, never by turn; exclude near-duplicate branches and regenerations from different sides of a split (using an explicit near-duplicate rule, e.g. MinHash/LSH above a declared threshold, with the threshold reported).
  • Held-out conversations and, where possible, held-out time windows.
  • Prompt/topic controls built from the deterministic layer or from declared topic tags.
  • Negative controls: the same model across topics must look like the same model; different models on the same topic must be distinguishable — if the negative control fails, the experiment is inconclusive by construction and is reported as such.
  • Calibration and unknown handling. Any classifier must report a calibrated confidence and an explicit “unknown” outcome; a forced-choice design with no unknown class is not admissible.
  • Reproducibility. Every run records inputs, cohort digest, split digest, feature version, model weights hash, and parameters.
  • Minimum evidence. Thresholds are set per experiment from a pre-declared power/uncertainty argument, recorded before results are seen. The plan does not invent universal sample sizes; it requires that the threshold be justified by the experimenter and registered in advance.
  • Stopping rules. Pre-declared outcomes: continue, revise, or abandon — with abandonment required when the negative control fails or when confidence intervals overlap so broadly that no claim distinguishes the classes.

G0 · Foundation

Deliverable. An Electron app that launches, creates an encrypted archive with a Keychain-wrapped random key, writes and reads a record through the archive service, runs the sanitizer over a synthetic payload, stores a sanitized evidence artifact in the vault, and exposes a health check over MCP.

Machine-checkable acceptance.

  • archive.integrity returns schema version, key present, FTS healthy, vault writable.
  • A hex inspection test opens the database file and asserts no plaintext of a known marker string appears anywhere in the file or its WAL.
  • The sanitizer test injects a marker secret into each rule category (§5.3) and asserts zero occurrences in records, artifacts, log files, and MCP responses.
  • A forced-sanitizer-failure test asserts the record is quarantined with a shape-only signature and no payload is written.

Falsifying evidence. Plaintext marker found in the database or WAL → the encryption configuration is wrong (a build-flag problem, per SQLCipher's temp-store caveat) and must be fixed before anything else proceeds.

Decision. Continue; this gate has no architectural ambiguity.

A1 · Email sign-in inside the app partition kill switch

Deliverable. One Arena account signed in, entirely within a partition the app owns, with the verification step completed (in-app, or via the documented paste-link-into-the-correct-partition path from §4.4), and an identity observation recorded.

Machine-checkable acceptance.

  • The session persists across an app restart, in the same partition, without re-authentication.
  • The app records exactly one identity_observation binding the partition to an Arena identity, with a timestamp and a source.
  • The sign-in trace contains no credential-retaining records: assert that no header value, token, or code from the auth class exists in the database, artifacts, or logs.
  • No popup or navigation left the app-owned partition (assert on the window inventory).

Falsifying evidence. The verification link cannot be completed inside the partition; a CAPTCHA appears that cannot be presented to the human; the identity probe returns nothing after a successful-looking sign-in.

Decision. Pass → continue to G1. Fail → do not silently adopt a system-browser login. Choose explicitly between (a) a documented manual bootstrap path, (b) the WKWebView authentication-only fallback (F3) with its stated loss of capture, or (c) stop and report the blocker. This is the single most likely place for a real snag, which is exactly why it is a gate and not an assumption.

G1 · Simultaneous multi-account isolation kill switch

Deliverable. Two Arena accounts signed in at the same time in two partitions, actively usable, with no leakage in either direction.

Machine-checkable acceptance (automated, run on every build).

  • Cookies: a login in partition A produces no cookie visible in partition B's cookie store, and vice versa (compare cookie name/domain sets, never values).
  • Storage: a marker written to localStorage, sessionStorage, IndexedDB, and CacheStorage in A is absent in B.
  • Service workers: a registration in A does not appear in B's registration list.
  • Identity: the app reports two distinct identities, and neither is unverified.
  • Destructive scope: a deletion authorized for A deletes zero rows from B (counted before and after).
  • Failure isolation: forcing A to sign out or crash leaves B's capture state, coverage, and queue unchanged.
  • Resources: both accounts run simultaneously with capture armed; the app records RSS for the main process and each renderer, plus a capture backlog measure.

Falsifying evidence. Any cross-partition visibility; any single-account failure that perturbs another; or measured resource use that makes two-account operation impractical (the measurement decides, not a guess).

Decision. Pass → continue. Fail → the requirement “two accounts simultaneously” is not met; either fix the mechanism or reduce to a documented account-switching model and say so plainly rather than shipping a façade.

C1 · Capture-depth viability — the falsification spike hard kill switch

This is the gate the whole report turns on. It is designed to break the architecture, not to demonstrate it. It must be run with both systems where practical, so that “deeper than the extension” is measured rather than asserted.

Deliverable. A scripted spike that drives one signed-in account through a hostile test script and writes a machine-readable evidence report, plus an optional side-by-side run of the same script under the existing extension.

The test script (deliberately hostile, in this order):

  1. Cold start on about:blank; attach and enable capture; then navigate to Arena. Assert the first navigation's document request is observed, and that the first application request after load is observed with a retrievable body.
  2. Send a prompt that streams an answer. Record the transport classification and every CDP event family observed. Assert that each chunk carries an arrival time and that the answer's terminal state is decided by a terminal signal, not by a timeout.
  3. Mid-stream, navigate the window to another Arena page. Assert the in-flight stream is retained in the index and ends as partial_stream with a gap interval, and that nothing is silently dropped.
  4. Open history in the UI; open a known older conversation. Assert the backfill observation set is complete for that page and that the rendered transcript reconciles with the network evidence.
  5. Trigger any worker- or service-worker-initiated traffic the app can provoke (e.g. a background refresh, a preview, or an agent/tool action). Assert either that those requests are captured with a target attribution, or that the coverage-suspect signal fires. A silent third outcome — nothing happens and nothing is reported — is a failure.
  6. Perform a download or generate an artifact. Assert the artifact is intercepted, stored encrypted, and its hash verified after a decode round-trip.
  7. Cast a vote in battle mode if available; assert the vote submission and any subsequent reveal are captured as separate, ordered observations, and that the pre-vote blind state is preserved.
  8. Cause a stopped response deliberately; assert it is recorded as stopped_by_user, not as complete.
  9. Kill the main process mid-stream; restart; assert the turn is partial_stream with a recorded gap, and the app reports the event.
  10. Two accounts, both armed, both exercising steps 1–3; assert no cross-attribution of request IDs, observations, or artifacts.

Acceptance criteria. Every step produces either a confident observation or an explicit, visible gap record. Specifically: (a) step 3 and step 9 never yield complete for a stream that was cut; (b) step 5 never yields silence; (c) step 10 yields zero cross-account attribution errors; (d) step 7 preserves the pre-reveal state; (e) every observation carries an account binding, a target attribution where applicable, an adapter version, and a time.

C2 · Transport classification of the answer stream

Deliverable. A written classification of how each answer type is delivered, with the CDP event families observed, the terminal signal used, and the adapter chosen.

Acceptance. For each mode (battle, direct, side-by-side, agent) the app can name: the transport, the start signal, the content signal, the end signal, and what a mid-stream interruption looks like. Falsifying evidence. A mode whose stream provides no distinguishable terminal signal. Consequence: that mode's completeness ceiling is lowered and the limitation is displayed in coverage statements — an honest outcome, not a blocker.

C3 · Comparative evidence against the extension baseline

Deliverable. A side-by-side record from running the same workflow in both systems, on the known problem areas: stream completeness, worker/SW visibility, missed events across navigation and target changes, model/reveal evidence ordering, and downloads/artifacts.

Acceptance. For each area, either the new system is measurably better (fewer gaps, more retained content, earlier attachment, artifacts captured without a companion) or the difference is explained by a limitation that is named. Where the new system is not better, that is recorded — the purpose is to know the truth, not to win.

Falsifying evidence. If the dedicated shell cannot beat page-world interception on the majority of these areas, the premise of the whole project is wrong and the correct decision is to improve the existing exporter instead. This gate is the honest exit.

G2 · Reconstruction correctness

Deliverable. The normalizer with a fixed test corpus covering: complete streams, stopped streams, transport failures, reconnections with replay, reconnections with changed content, regenerations and branches, side-by-side lanes, late reveals, and account switching mid-capture.

Acceptance. Golden-file tests assert exact normalized output, and specifically assert that: no non-complete state is ever promoted without new evidence; dedup removes replays without removing legitimate revisions; branch ordering is stable under a re-run; and a re-run of the parser over retained evidence produces identical output for the same adapter version.

Falsifying evidence. Any silent promotion or any nondeterminism between runs.

B1 · Backfill viability kill switch for sync ambition

Deliverable. The four evidence items from §7.2 established for at least one account, with a written method record and the replay implemented behind a feature flag that is off until the record exists.

Acceptance. Two full traversals produce the same item set; a double-issued read changes nothing observable; a detail read reconciles against a live-captured conversation; and the sync run's coverage statement reports the traversal's boundaries honestly (including “we cannot prove there is nothing older”).

Falsifying evidence. Pagination instability, non-idempotent reads, or results that do not match live capture. Consequence: sync drops to UI traversal (§7.5) and the coverage statement says so. Do not proceed to B2 with an unverified method.

B2 · Sync robustness

Deliverable. Interruptible, resumable, rate-limited sync with per-account checkpoints and conflict records.

Acceptance. Killing the app mid-sync leaves a consistent checkpoint and no half-written conversation; a resumed run continues without duplicating or skipping; overlapping pages and repeated items are counted, not deduplicated into silence; two accounts syncing concurrently produce no attribution errors; a forced 429 slows the run rather than failing it; and a multi-account run where one account is rate-limited leaves the other unaffected.

Falsifying evidence. Any skipped item that the archive cannot explain, or any duplicate that appears as a separate conversation.

T1 · Data and trust integrity

Deliverable. The failure matrix of §8.9 implemented as automated tests, plus migration, backup/restore, and the three deletion scopes.

Acceptance.

  • Hostile-page test: a fixture page attempts to reach archive APIs, open privileged windows, and navigate the shell; all attempts fail and produce a security event.
  • Cross-account collision test: the same source ID in two accounts produces two records plus an ownership_conflict, never a merge.
  • Sanitizer failure, parser failure, and disk-full tests: no partial corruption, no secret leakage into logs.
  • Crash during write: the database reopens cleanly; the in-flight turn is partial_stream.
  • Migration: a synthetic v1 database migrates forward, is readable, and the pre-migration backup is recoverable.
  • Deletion (all three scopes): idempotent, resumable, verified by re-count, with other accounts asserted byte-for-byte unchanged in row counts.
  • Signed-URL test: a URL with a secret query parameter never appears in the database, logs, or MCP responses; only the safe reference and digest appear.

Falsifying evidence. Any leak, any cross-account mutation, any deletion that does not converge.

M1 · Agent operability

Deliverable. The complete MCP surface from §9.3, plus a written agent playbook: how to discover capabilities, how to read coverage statements, how to diagnose drift, and how to recover from each error category.

  2. Start, monitor, cancel, and resume a sync; read the resulting coverage statement.
  3. Diagnose a deliberately injected adapter drift: detect it via diagnostics.report, inspect the evidence via diagnostics.evidence, and fix it via diagnostics.reparse with a dry run first.
  4. Pause and resume capture for one account and observe the effects described in §9.4.
  5. Attempt deletion with a token minted for a different scope and confirm rejection.
  6. Adversarial content test: an archived conversation containing an instruction to delete the archive. Assert that the client cannot mint a token, that the deletion tool returns authorization_required, and that a security event is recorded. This test is run with the model explicitly told to comply with the archived instruction, which is the only version of the test that proves anything.
  7. Parity test: every façade operation is reachable from MCP and from the GUI.

Falsifying evidence. An essential capability that exists only in the GUI; a deletion reachable without a trusted-channel token; or an error category with no documented recovery path.

P1 · Analytical validity

Deliverable. The profile engine with stored cohorts, deterministic metrics, uncertainty reporting, excerpts linked to evidence, and a limitations block attached to every result.

Acceptance. Every result names its cohort digest, reports n, reports the count of excluded non-complete records, states whether aggregation is turn-level or conversation-level, and links at least one excerpt to its evidence. A test asserts that no result can be produced without a stored cohort, and that changing any cohort input changes the digest and therefore refuses to compare against older results.

Falsifying evidence. A result that pools accounts without saying so, or that reports a metric whose definition is length-dependent without its window (e.g. TTR).

S1 · Similarity and fingerprinting experiments

Deliverable. Pre-registered experiment documents (splits, controls, thresholds, stopping rules) and runs that either report calibrated, controlled results or are abandoned.

Acceptance. The negative controls pass before any positive claim is made; near-duplicate handling is demonstrated on the archive's own regenerations; and every run is reproducible from its recorded inputs.

Falsifying evidence / abandonment. Failing negative controls, or confidence intervals that cannot distinguish the classes. Abandonment is a legitimate, pre-declared outcome and is recorded as such.

Always-on falsification: what the first spike must try to break

The C1 spike is required to include, at minimum: a late attach (deliberately attaching after navigation, to see what is lost and prove the difference), a navigation during a stream, a target change, a worker-initiated request, a service-worker-served response, a streamed body over a threshold size, a stopped response, a failed response, a download, and a two-account interleave. A spike that only walks a happy path has not tested the architecture — it has decorated it.

12.1 Fatal assumptions, surfaced early

  1. That CDP-attached observation is materially better than page-world interception for this site. If false (C3), the project's premise fails and the right answer is to improve the existing exporter. Stated as a falsifiable test, not a belief.
  2. That the primary answer stream is reachable through a supported transport observation. If false, the fallback ladder applies; escalation is possible but expensive.
  3. That two accounts can be simultaneously signed in and used on this hardware within acceptable resources. Measured at G1.
  4. That email sign-in completes inside the app-owned session. Designed for, but genuinely uncertain, and gated at A1.
  5. That the archive's value does not depend on history that no supported read can reach. If the only content the app can obtain is what the user opens live, the archive is a live recorder with honest coverage maps — useful, and explicitly a smaller product.

14.4 Glossary

L0 / L1 / L2 / L3
The four observation layers: network, target lifecycle, DOM corroboration, UI-driven attestation (§4.3.2).
Completeness state
The explicit statement of how much of an answer the archive believes it has, and why (§6.4).
Observation
An immutable record of one observed interaction or UI state, with mechanism, time, target, and account binding.
Evidence artifact
A sanitized, encrypted payload retained so that a parser can be re-run after an adapter change.
Safe reference
A URL stored as scheme + host + path template + keyed query digest, so signed URLs never persist in clear (§8.7).
Coverage statement
The per-account, multi-part answer to “what do we have and what is missing”, replacing a single synchronized flag (§7.4).
Coverage suspect
The app's signal that it observed traffic it could not attribute to an attached target, i.e. a self-detected blind spot (§4.3.4).
Trusted channel
The app's own GUI confirmation path, or an explicitly destructive-capable client registered with a human present; the only place destructive tokens can be minted (§9.6).
