00 Decision summary

RECOMMENDED ARCHITECTURE

A dedicated Electron application (Chromium embedder, TypeScript end-to-end, arm64) acting as its own browser, with CDP-first capture through webContents.debugger — flattened Target.setAutoAttach with waitForDebuggerOnStart so every page, worker and service worker is observed from birth, before first network activity — backed by session-scoped webRequest metadata, session-scoped download ownership, and exactly one persistent Chromium session partition per Arena account. Archive: single SQLCipher-encrypted SQLite (FTS5 in-DB) plus per-file AEAD-encrypted artifacts; random archive key wrapped by macOS Keychain via Electron safeStorage. Primary interface: local MCP over Streamable HTTP on 127.0.0.1, Origin-validated, bearer-token gated, calling the same application services as the GUI. Deterministic, provenance-linked analysis in worker threads.

Consequential dependencies: Electron (current stable line, ~v44-era), better-sqlite3-multiple-ciphers (SQLite3MultipleCiphers/SQLCipher), libsodium via sodium-native, @modelcontextprotocol/sdk, Zod. CEF is the named, triggered escalation — see §11.4.

Why this wins

It is the only maintained stack that combines (a) out-of-process, session-scoped observability of streamed response bodies, WebSocket frames, workers and service workers from target birth; (b) true simultaneous account isolation (cookies, storage, cache, SW state per partition); (c) an application-owned download/artifact path; and (d) one TypeScript runtime an AI agent can build and verify autonomously. That is materially deeper than the rejected MV3 extension baseline (§3.2), not merely “the same monkey-patching inside an owned window.”

What it costs

One Chromium instance resident (only one — renderers per window, no second engine alongside WebKit), ~100+ MB on disk, explicit re-verification of bot-challenge compatibility (reCAPTCHA Enterprise is preloaded on Arena’s public homepage [S1]), and disciplined CDP plumbing (target/session lifecycle, body-eviction handling). Packaging is development-mode: run from source or an unsigned local build; no notarization quest.

What would reverse it

Four falsifiers, each wired to a gate: (1) Arena email sign-in cannot complete in an Electron window even with owner attendance; (2) Arena’s conversation transport is invisible to CDP Network/Fetch domains in practice (e.g., permanent body eviction without stream fallback); (3) service-worker traffic escapes both auto-attach and session webRequest; (4) memory floors exceed agreed per-window quotas. Each trigger maps to a descending fallback (CDP-Fetch streaming → protocol.handle tap → CEF escalation) with its capability loss stated in §11.4.

This report is organized to be argued with. §1 states what was actually researched this run and what was not (no Arena account access existed; every Arena-internal claim is a labeled strong inference or hypothesis with a test). §3 isolates the deciding question — capture depth — and separates owning the window from owning the observation layer. §4 disqualifies alternatives on documented grounds before §5 details the winner. §6–§9 specify capture, backfill, data/protection, and the full MCP contract. §10 keeps analysis defensible. §11 gives machine-checkable gates designed to falsify the architecture early, plus the risk register and reversal conditions. An implementation agent should be able to start at §11 and never need this document’s author.

02 Product contract & operating boundaries

Working title: LOGBOOK. A permanently private, single-operator macOS app. It exists to do one job extremely well: keep an accurate, provenance-rich, offline archive of your own Arena conversations across simultaneous accounts, and make every function operable by an LLM agent locally.

2.1 · Hard requirements absorbed by the design

  • Dedicated browser runtime. The app owns its browser. A conventional extension, chrome.debugger extension, extension+native-host, and extension+companion are excluded as primary architecture a priori; the existing MV3 exporter (musterm4nn-alt/arena-exporter) is the comparison baseline only (§3.2).
  • Simultaneous multi-account. ≥2 Arena sessions live at once, each fully isolated: cookies, web storage, cache, service workers, capture state, sync state, provenance, destructive scope. Not an account switcher.
  • Email-first auth. Arena email sign-in must work through Arena’s own flows inside the app, including owner-driven verification/OTP/steps. Google/OAuth/passkeys are explicitly non-requirements and were never used to disqualify a candidate.
  • MCP-primary operability. Every GUI capability has an equivalent MCP tool with identical semantics (§9).
  • Heavy usage, honest budgets. No measured footprint is invented; §5.7 sets quotas and the measurement plan instead.
  • Agent-buildable. Mainstream deps, reproducible setup, structured diagnostics, self-test suite an agent can run (§11, G6).

2.2 · Owner-session technical boundaries

  • Scope of access: only data belonging to currently signed-in Arena accounts, observed through that account’s own app-owned session. No cross-browser cookie/token import, no credential guessing, no enumeration of unrelated infrastructure.
  • Mechanism taxonomy kept distinct (used precisely throughout): authenticated read access = first-party endpoints driven by the correct account-scoped session, documented or not; automation compatibility = presenting a normal browser and completing owner-driven challenges; access-control workaround = circumventing a specific client-side restriction to reach data already belonging to the same account — each use in this plan names the control and the mechanism (§6, §7); an internal endpoint alone is never called a “bypass.”
  • Credential boundary: session tokens stay inside Chromium’s session storage; native code may transiently reuse them only in-memory for the same account’s session and never persists, exports, fixtures, or logs them (§8.6). Replay of owner-history reads therefore happens inside the page context of the correct partition, not via token-copied Node HTTP calls (§7.3).
  • Control surfaces: visible recording state; pause / cancel / stop per account and globally, with defined effects on in-flight work (§6.7, §7.5).
  • Degrade-safely triggers: sign-out, account mismatch, lost session authority, ambiguous ownership, schema drift, unresolved challenges, suspected unintended mutation → pause or use the documented fallback for that account only; one account’s failure must never corrupt, invalidate, or silently rebind another (§6.7, §7.6, §8.5).
  • Legal documents are out of planning scope per the brief; methods are judged on feasibility, security, robustness, maintainability for the owner’s own data.
Identity rule zero. Account/session scope is part of record identity. A conversation URL or opaque ID never establishes ownership. Records from different accounts are never merged or reassigned because IDs, titles, text, or timestamps look similar; cross-account collisions become explicit conflicts (§8.4).

03 The capture-depth question

The architecture decision reduces to one question: which stack observes Arena’s real traffic most completely, most reliably, with the earliest possible attachment, while isolating concurrent accounts? Everything else — UI polish, analysis — sits downstream of evidence quality.

3.1 · Owning the window ≠ owning the observation layer

An embedded shell can be shallower than the extension it replaces. WKWebView, for instance, gives a native app full control of pixels but no documented hook into http(s) request/response bodies VERIFIED [S15] — an MV3 extension in a conventional browser at least sees request metadata via webRequest. The evaluation below therefore scores out-of-band browser/network/target APIs (what the platform lets you see without injecting into page JavaScript), page-world capability separately, and explicitly names what each stack still cannot see. Not every transport needs the same instrument: fetches, streams, WebSocket frames, and service-worker relay each have their own observation path per stack.

3.2 · Anatomy of the baseline’s failure modes (rejected, re-used as the yardstick)

The existing MV3 exporter’s real-world failures — incomplete/missed capture, missing stream parts, lifecycle dependence, awkward downloads — are not bad luck; they are structural properties of MV3:

  • No response bodies. MV3 webRequest has no API for response bodies at all INFERENCE (long-standing platform design; the follow-up read is the current chrome.webRequest reference, §12.2). Extensions therefore monkey-patch fetch/XMLHttpRequest/ReadableStream in page world — which is exactly where the reported losses come from.
  • Page-world patching misses non-page worlds. Fetches issued by service workers or workers never traverse the page’s patched globals; wrappers installed after page scripts start miss early traffic; re-navigation can re-race installation. This matches the baseline’s “missing parts of conversations or streams.”
  • MV3 service-worker suspension. The extension’s own background context can be torn down from inactivity, dropping buffered events — “dependence on extension lifecycle behavior.”
  • Download friction. chrome.downloads and file-system constraints forced a companion bridge for comfortable archiving — removed here by session-owned downloads (§5.5).
Gate G3 (§11) formalizes this: capture-depth viability requires a head-to-head run of the same Arena workflow through the old extension and the new shell, with a diff report proving stream completeness, worker/SW visibility, navigation resilience, reveal-event capture, and download ownership. A synthetic fixture (§11.3) proves harness correctness but cannot substitute for the signed-in Arena check.

3.4 · What even the winner can still miss (stated plainly)

  • Body eviction. Network.getResponseBody can fail if Chromium has evicted a body before retrieval. Mitigation: Fetch-domain interception for conversation-critical operations, streaming capture during the response, plus a rendered-state reconciler (§6.4) that detects shortfalls per turn. Residual risk tracked as hypothesis H2 with a dedicated fixture test (Gate G2).
  • Bot-management differences. reCAPTCHA Enterprise / Cloudflare behavior inside an embedded session may differ from a commodity Chrome profile. Mitigation is owner attendance and challenge-aware degradation — never challenge solving (§6.7). Not a capture-depth issue; an operational one with its own gate (G1).
  • Server-side computation. Any post-processing Arena performs server-side before emitting (censoring, re-formatting, model post-hoc labels) is observed only as emitted; the archive records what was observed, with the transport as provenance — never the “true” server state (§6.5, §8.3).

04 Candidate architectures

Six candidates were assessed against the decisive capabilities, with documented mechanisms cited and decisive limitations named. Credible alternatives get fair trials here; detail concentration follows in §5 for the winner only. Unexplained numeric scores are deliberately avoided — each verdict names the property that decided it.

A · Native Swift + WKWebViewREJECTED — CAPTURE CEILING BELOW BASELINE

Best-in-class resource economy and native UX are irrelevant against the deciding property: WKWebView has no documented API to observe fetch/XHR/stream response bodies, WebSocket frames, or service-worker traffic over http(s) VERIFIED [S15] [S16]. Capture would fall back to WKUserScript page-world patching — the exact mechanism whose failure modes motivated this project, on an engine where it is the only option. An “owned window” with less observation depth than the rejected extension is a downgrade. Multi-datastore account isolation (WKWebsiteDataStore) exists but cannot rescue the ceiling. Private API traversal (WKBrowsingContextController) is unmaintainable and contradicts “agent-operable upkeep.”

B · Tauri (Wry → WebKit on macOS)REJECTED — INHERITS WKWEBVIEW CEILING

Tauri on macOS renders through Wry→WKWebView, so it inherits candidate A’s network invisibility; its custom-protocol handler cannot tap fetches to https://arena.ai. Rust+TS ergonomics and small binaries are attractive, and on Windows/Linux the engine changes (WebView2 has partial interception) — but this product is single-platform Apple Silicon. A cross-platform shell whose capture depth differs per OS is a maintenance trap for a private tool: rejected on the same deciding property as A, not on aesthetics.

C · Chromium Embedded FrameworkESCALATION PATH — TRIGGERED ONLY BY FALSIFIERS

CEF is the strongest rival and the only candidate with provably deeper capture than Electron: browser-process request handlers plus byte-level response filtering see every resource (page, worker, service worker) as chunks arrive, without CDP’s body-eviction class of failure VERIFIED [S13] [S14]; CefRequestContext gives per-account isolation; download handlers own artifacts. The focused comparison below is the deliberate Electron-vs-CEF duel the brief asks for. CEF loses as the default on implementability grounds — C++ toolchain and bridging for a one-user tool, slower agent iteration, more failure surface in glue code — while losing nothing as an escalation §11.4 already wires in. If Gate G2/G3 falsify Electron’s capture depth, the plan does not “re-decide”; it executes a pre-written trigger (§11.4) that ports the capture/controller layer, whose interfaces are deliberately engineshaped for that possibility.

05 Selected architecture — LOGBOOK

One Electron process family. TypeScript everywhere. The arena is observed through Chromium’s own debugging and session surfaces — never by patch-and-pray page injection as the primary mechanism.

5.2 · Trust rules (enforced structurally, not by vigilance)

  • T1 — No app capability below the line. Arena windows get nodeIntegration:false, contextIsolation:true, sandbox:true, no preload bundle, no IPC channel names, no remote. The only introspection is main-initiated webContents.executeJavaScript / CDP Runtime.evaluate reading sanitized values out; the page has no handle to push commands in.
  • T2 — New-window contenance. web-contents-created intercepts popups (Arena auth flows sometimes open them): popup webContents on an arena partition get the same restrictions + capture controller attached in the same tick; popups to non-Arena origins render read-only with navigation confined (allowlisted auth/verification hosts only).
  • T3 — MCP never listens beyond loopback and validates Origin per the spec’s DNS-rebinding guidance VERIFIED [S17]; the token lives in Keychain; archived content is data, and the delete path has a separate physical guard (§9.4).
  • T4 — Keys exist in one process (main). Renderers never see the archive key, MCP token, or artifact DEKs. Arena-controlled content cannot reference local files: navigation to file: is blocked; webSecurity stays on; no custom protocol is exposed to arena partitions.
  • T5 — One Privilege per Window. The GUI window is the only renderer with a preload, and its contextBridge exposes exactly the app-service surface — mirroring MCP semantics 1:1 (§9.5).

5.3 · The capture lattice (4 layers, CDP is the spine)

“Deeper than the extension” is made concrete as an enumeration of mechanisms — each with its documented basis, what still relies on page-world code (very little), and what each layer can miss:

L0 · webRequestsession metadata, redirects, errors · S7→ L1 · CDP Network/Fetchbodies, streams, WS frames · S6 S10→ L2 · DOM probesidentity/reveal/UI reconcile · transient eval→ L3 · protocol.handle tapescalation only, risk-gated · S8
  • L0 — session webRequest (metadata fabric). Every request lifecycle in the partition (timings, redirect chains, failure codes) without bodies. Purpose: operation classification, drift detection, completeness cross-check against L1 (an L0 event with no L1 body is a flagged gap, not silent loss). Can miss: visibility of SW-originated subrequests is hypothesis H4 (Gate G1 measures; absence changes only where completeness cross-checks come from — L1 worker sessions still cover bodies).
  • L1 — CDP spine (bodies + streams + frames). At window creation: attach, Target.setAutoAttach({autoAttach:true, flatten:true, waitForDebuggerOnStart:true}), then navigate VERIFIED [S6] [S10]. The order is the feature: no request can precede instrumentation, and each new worker/SW target arrives paused, gets Network.enable, then Runtime.runIfWaitingForDebugger — zero-gap attachment VERIFIED (mechanism); observed working in Electron previously [S11] [S12]. Bodies: Network.getResponseBody; long-lived conversation streams: Fetch-domain interception (requestStage:Response) with streaming reads and pass-through fulfill, so Arena’s transport is tapped in flight rather than re-requested. WebSockets: frame events directly. Can miss: evicted bodies (H2) → Fetch streaming on the conversation-operation URL families; pre-attach nothing, because nothing precedes attach.
  • L2 — DOM probes (page signals, not payload source). Transient Runtime.evaluate reads of selected properties/DOM deltas for blind labels, votes, reveal moments, and stop-button state. Deliberately not the payload path: L2 evidence is stamped mechanism=ui-probe and reconciled against L1 (§6.4). What it adds that L1 cannot: what the user actually saw was rendered, and when.
  • L3 — protocol.handle take-over (escalation, default OFF). ses.protocol.handle('https', …) can pass every request of that partition through app code VERIFIED [S8]. It re-implements parts of a network stack (caching, ranged requests, cookies continuity) inside the session — powerful, exactly the kind of cleverness that rots. Policy: compiled in, telemetry-instrumented, enabled per-partition only by an explicit operator flag after an L1/L2 shortfall is evidenced against Arena, and covered by its own fixture suite before first use. If even this cannot recover a required observation, the trigger routes to CEF (§11.4), not to a fork.

5.4 · Simultaneous-account partition model

Each registered Arena account is a first-class app object with one permanent Chromium partition persist:acct-<appuuid> VERIFIED [S7]. All bindings are structural:

  • Window↔account: an arena window is constructed with exactly one partition from its account record; the app asserts webContents.session identity on every capture batch (cheap object-identity check) so a code bug cannot silently cross streams.
  • Isolation contents: cookies, HTTP cache, localStorage/IndexedDB, service-worker registrations and their caches, code cache — separate on-disk roots per partition (Electron session storage), plus separate in-app capture state machines, sync cursors, and destructive-action scopes (§8, §9).
  • Concurrency: any number of arena windows; practical v1 target is 2–4 live accounts on 18 GB (quotas §5.7). Capture pipelines run per partition; the only shared gates are the global rate budget (§7.5) and the archive write queue.
  • Session authority check (anti-rebind): an auth probe per account (a very low-rate signed-in read discovered in D1, e.g. whatever the app itself calls to render the account chip) yields (signed-in, observed-handle/app-user-id). If the probe fails or the observed identity changes without an explicit account re-registration, the account enters SESSION_LOST/SESSION_AMBIGUOUS: capture pauses, sync aborts with checkpoint, and nothing re-targets to another account. Probe specifics are hypothesis H3 until D1.

06 Discovery & live capture

6.1 · Discovery as a maintained capability (not phase 0 folklore)

The first engineering objective is a Protocol Catalog: a living, machine-readable inventory of every first-party operation Arena performs across all supported workflows in each account session. Discovery is a permanent subsystem: adapters are versioned against catalog entries, and unknown operations persist as unknown until an agent investigates (unknown is a state, not an error to swallow).

  • Classification lattice: host (arena.ai subdomains incl. observed indexable.arena.ai VERIFIED [S1]) → first/third party → family (conversation.read | conversation.stream | conversation.mutate | auth.* | account.* | history.* | assets | analytics.config | telemetry | unknown) — analytics covers the observed PostHog feature-flag traffic VERIFIED [S1]; telemetry (Cloudflare beacon observed [S1]) is catalogued but never retained beyond metadata.
  • Record shape per operation: operation id (canonical name or unknown.<hash-of-signature>), transport (xhr/fetch/sse/ws/rsc/nav), initiator target (page/worker/sw), method+path template (secrets stripped), mutability evidence (observed effects, not just verb: “GET ⇒ read” is a finding requiring confirmation §7.2), payload family + schema fingerprint (shape-hash of keys), adapter version serving it, completeness stats, drift counters, first/last seen, per-account occurrence map.
  • Coverage vs retention: catalog captures everything first-party as metadata; payload retention is denylisted-by-default with per-family opt-in (conversation/history families in; auth headers/cookies/tokens never — see sanitizer §8.6). Discovery must never become a credential-dumping network console.
  • Sanitized evidence for drift: for each family keep the smallest artifact that can diagnose a schema change later: shape-hash diff, up to N exemplar payloads with secret-bearing keys redacted before write, and parser-error excerpts truncated+zstd’d. Re-parse source of truth = sanitized exemplars + live re-observation, never raw HARs (§8.3).

6.2 · Capture pipeline

6.3 · Stream reconstruction & turn boundaries

Arena-conversation streams (transport per family is H5 until D1: likely chunked JSON/SSE-style events — LMArena-family apps historically stream tokens, but this report does not import that lore as fact). The reconstructor is transport-agnostic:

  • Event algebra: per request id, an ordered seq of (t, bytes-or-frames) yields frames; per conversation, frames group into generation attempts keyed by (source message id if present, else fingerprint of [conversation, participant slot, attempt ordinal]). Deltas assemble monotonically; non-monotonic arrivals keep server order + local receipt order both.
  • Turn/branch boundaries: from network grammar where available (request/response pairs per send, regenerate = new attempt on same parent fingerprint) reinforced by L2 signals (composer submission, new message node, “branch” affordances). Branch detection consumes parent-conversation linkage and position labels; ambiguous structure → explicit structure.uncertain state, no flattening guesswork.
  • Reconnects & duplicates: same-attempt frames across reconnects merge by content-hash windows + attempt fingerprint; repeated events dedup by (attempt, byte-range/hash); late reveals attach as new identity observations on the existing attempt (§8.4), never rewriting stored text.
  • Navigation: renderer navigation does not end an observation: in-flight attempts persist in the controller keyed by request id; if the target dies mid-stream, the attempt closes as PARTIAL_OBSERVER with cause target-navigated — user advice: don’t navigate mid-answer, but the failure is visible, not silent.
  • Reconciliation (network vs UI): periodic L2 DOM snapshot deltas are compared with reconstructed text (normalized whitespace/markdown render). Divergence classes: (a) UI shows more ⇒ L1 gap → GAP marker + drift signal; (b) UI shows less ⇒ unrendered payload (retained, flagged); (c) transform-only ⇒ record transform note (e.g., citation enrichment) as provenance transform.ui-applied.

6.4 · Fallback capture & what it loses

If L1 body capture fails for a family (drift, eviction, new transport), the adapter falls back in order: (1) Fetch-domain interception per family; (2) L3 tap (risk-gate per §5.3); (3) DOM-render capture — explicitly lossy: loses exact framing/deltas, pre-render text, code-fence fidelity risk, and any unrendered payload parts. Every transcript notes its capture.depth; search/filter can exclude shallow captures, and analysis weighting treats DOM-rendered text as a different evidence class.

7.2 · Read-verification protocol (before any reliance)

  1. Association: the read returns records consistent with this account’s observed conversations (owner confirms sample via GUI compare), and the account’s auth probe (§5.4) is green.
  2. Read-only character: HTTP verb is a hint, not proof. Evidence set: verb GET/HEAD (or POST-with-query-body semantics), coefficient of change zero across N=3 replayed reads (same cursor ⇒ same page bytes modulo timestamps), no server-side ordering mutation attributable to the read, no side-effect counters observed in account surfaces (e.g., unread markers changing). Until all pass, the operation is catalogued mutability: unproven and sync uses Fallback 1.
  3. Pagination truth: cursor/offset semantics documented from observation; stability measured (re-read page k across sessions; overlap hashing); instability class recorded (pagination: stable|drifting|volatile) driving re-read policy.
  4. Completeness: can the listing enumerate everything (incl. Archived tab)? Evidence: total-count fields if present, convergence to empty page, tab-by-tab coverage matrix. Whatever is unproven remains a named coverage gap in sync.coverage — success on one opened conversation proves exactly one conversation.

7.3 · Sync engine

In-page replay executor (per account): requests issued via Runtime.evaluate on a quiet utility frame of the arena window (no UI manipulation), responses returned to the main process sanitized in transit; controller writes observations, projects, and advances cursors transactionally. The page does the fetching; Chromium holds the cookies; Node never holds credentials INFERENCE (verify in G4 that history fetches work from an about:blank-style utility frame vs requiring app-frame context; fallback: evaluate inside the real app frame during idle).

7.4 · Sync job laminate (states, idempotence, checkpoints)

QUEUED→LISTINGcursored pages→DETAILper-conversation fetch→CHECKPOINTcursor + stats txn→DONE / PAUSED / CANCELLED / DEGRADED
  • Idempotence: work items keyed (account, kind, stable item id); writes are upserts on reconciliation keys (§8.2); a rerun of the same page is byte-hash-compared before projection work begins (cheap no-op fast path).
  • Checkpoints: cursor + per-job counters committed in one DB txn per page; crash ⇒ resume at last checkpoint; overlapping pages and pagination drift handled by hash-dedup plus explicit page.overlap stats; sync.coverage records what ranges were proven (cf. §7.2.4).
  • Dedup within scope: conservative — only identical (account, source-conversation-id) merges; near-identical text never merges; retries attach to existing attempt records via attempt fingerprint.
  • Bounded retries: exponential backoff 1s→16m, 8 attempts, per-failure-class policies (429/“slow down” honor server hints; 401/403 ⇒ SESSION_LOST; 5xx ⇒ DEGRADED retryable).

7.5 · Concurrency, rate budget, interaction with live capture

  • Per account: strictly serial sync (one job) — pagination state is isolated per account by construction; global: N accounts may sync truly concurrently with an app-wide request budget (token bucket, default conservative: 1 in-flight history-class request per account, 2 app-wide) because isolation makes cross-account interference impossible and politeness is a choice, not an accident. Correctness does not depend on sequencing; scheduling exists for etiquette and memory.
  • Live-capture overlap: a conversation mid-stream during sync appears twice (live attempt + history read): reconciliation keys prefer live observations as primary evidence, history rows fill gaps and assert listing-level completeness; partially-captured conversations merge by (account, source id) with per-attempt provenance showing which mechanism provided what. Conflicts in content (edited titles, regenerate-rewrites) are stored as revisions, with newest observation marked current.
  • “Sync now” semantics: MCP/GUI accepts one account, an explicit list, or all enabled accounts (opt-in auto-sync per account, default off, interval config). Progress is account-scoped and MCP-visible (sync.status); cancel/pause/resume per account; everything else untouched.

7.6 · Degradation & the no-verifiable-listing floor

Per-account degrade map: rate limited ⇒ backoff that account; auth expired ⇒ SESSION_LOST for that account alone; challenge appears ⇒ sync paused, owner notified in chrome + MCP; drift ⇒ family-level hold (§6.7); redirect to unexpected origin ⇒ hard stop of that account’s replay executor pending review; suspected mutation ⇒ freeze that account’s sync (dangerous-promise rule §6.7). If no listing endpoint can be verified: Fallback 1 traversal still yields browse-order coverage with honest coverage: traversal labeling; “synchronized” then means “every history view reachable and walked,” with gaps enumerated (e.g., cannot prove archived-tab exhaustiveness). If traversal is also blocked, sync reports INFEASIBLE with evidence — live capture still works from install forward, and importing future exports remains open. The app never prints a green “SYNCED” badge without stating what the badge was allowed to mean.

8.1 · Source-of-truth design (proportionate hybrid)

Not full event sourcing; not raw-corpus-only. 8.3 · Provenance & evidence retention

  • Per-field provenance: every normalized row carries provenance = list of (observation, span, adapter). Analytical outputs carry cohort + input_digest so any number on screen traces to rows, and rows to observations, and observations to mechanism+adapter. “Which Arena account/session produced the evidence” is column one, not metadata.
  • What is retained, how long: normalized records: indefinitely (owner-controlled). Sanitized observation payloads: 90d default full, then compaction to exemplars+shape-hashes (config); GAP/drift exemplars: 1y; artifacts: per-kind retention (§5.7). Recomputation after adapter change: projection rebuild from retained observations where payloads survive, else targeted re-sync for that account scope — the sync engine doubles as the re-fresher.
  • Hash chain per account partition gives cheap tamper-evidence of local append-only behavior (not a legal ledger — it detects accidental reorder bugs in our own writer, its real purpose).

8.4 · Model identity without mythology

  • Participant position, a blind label (“Model A”), a provider name, a marketing model name, an internal route name, and “the exact build that answered” are six different claims. The schema stores them separately; the derived view ranks bases and exposes every conflict inline (e.g., reveal says X, network field said Y → both shown with timestamps, view marks CONFLICT).
  • Late reveals never rewrite history: a reveal appends an identity observation with turn scope; the usable view updates; earlier blind-label evidence remains displayable and exportable. Labels never propagate beyond applies_from/to_idx.
  • Unknown stays unknown: a battle generation with no reveal yields identity.basis=blind-label, model=UNKNOWN — analysis cohorts can still group on the blind label within its conversation to detect self-consistency (§10), without pretending to know what it was.

8.5 · Reconciliation keys & conflict handling

Keys, strongest first: (account_id, source_id) → (account, attempt fingerprint) → observation hash. Identical text is never a key. Cross-account source_id equality (plausible across accounts on shared infra) inserts a conflicts(type=cross-account-id-collision) row and nothing else happens — both records live, each bound to its account; only an explicit owner action can annotate them as pointing to the same conversation, and even then rows are never merged. Content forks (same source id, divergent bodies ⇒ rewrite/regenerate) are revisions with per-observation provenance; latest-current flag is queryable.

8.6 · Credential & secret hygiene (the sanitizer contract)

  • Denylist before persistence: request/response headers (authorization, cookie, set-cookie, x-csrf*, x-api-key, proxy-*), URL query/binary tokens (token=, sig=, signature=, expires=, credential=, code=, session=), body fields matching (password|passwd|secret|csrf|token|cookie|authorization|email_otp) case-insensitive, and whole-body drop for auth.* family operations (metadata kept to catalogue the flow timing, never content INFERENCE — exact flow unknown until G1; policy is independent of it).
  • Fail-closed: an unknown operation whose payload cannot be shape-verified against schema is stored shape-hash-only until an adapter claims it. Parser errors are themselves sanitized (message + truncated excerpt with denylist applied) — failure paths are not a secret leak.
  • Safe references: source URLs with secrets persist as url_template (host+path+redacted-param-names) + SHA-256 of the full URL for correlation; artifacts reference by hash, not by signed URL. Streaming downloads never write URL with token to logs.
  • Browser-managed session persistence: Arena cookies/tokens live inside the partition’s Chromium storage; Chromium encrypts cookie stores at rest using the OS keychain on macOS INFERENCE (follow-up: Chromium OSCrypt docs, §12.2). LOGBOOK adds: partitions’ on-disk roots inside the app container dir covered by the same Spotlight/TM exclusions (§8.8); ses.clearData powers account wipe (§8.9). Tokens are never copied out — replay executes in-page (§7.3); transient in-memory header handling exists only inside the sanitizer’s pre-write stage.

9.4 · The destructive guard — authorization is a physical fact, not a careful reading

  • Channel discipline: arming is possible only from the GUI (local input). MCP tokens of any profile can initiate but never complete; there is no “be careful” instruction anywhere in the trust chain — there is an unforgeable capability.
  • Untrusted content firewalls: archived text passes through evidence.get/transcript.get as escaped, length-bounded strings; the MCP server never executes, evaluates, or interprets archive content; system-prompt guidance for agents is a convenience, never a control.

9.5 · One service layer, two interfaces

GUI and MCP call the same AppServices modules with the same Zod contracts; the GUI is literally an MCP client over an in-memory transport. Consequences: no GUI-only workflow can exist by accident (a UI button without a service function is a type error); semantics can’t drift; and the browser-interaction integration is explicit — tools that need the arena window (auth probe, challenge surface, replay executor) are implemented in the same controllers the GUI buttons drive, with state machines shared (§6.7, §7.4). v1 GUI screens: (1) Accounts & windows, (2) Capture/coverage board, (3) Sync jobs, (4) Protocol catalog + drift, (5) Deletion guard, (6) Diagnostics — every one a projection of MCP data.

10 Local analysis & later modalities

10.1 · Model profiles v1 — deterministic, visible, humble

All analysis runs locally (worker threads over SQL-read cohorts). No opaque models at v1: transparent statistics whose every number links back to source evidence, so the owner can audit a claim to exact generations. Cohorts are defined only on observed/revealed identity evidence — never on inferred similarity.

  • Cohort key: (identity.basis, identity.label, mode, participant-slot?) with cohort basis filters: revealed-only | selected-label | blind-label | mixed; a cohort with basis=blind-label is displayable but bannered “identity unknown — internal-consistency profile”.
  • Metrics (each with provenance links): length distributions (response/paragraph/sentence/code-block, tokens & chars), lexical diversity (MATTR), top n-grams / recurring phrase inventory with counts, punctuation & casing signatures, markdown structure rates (headings/lists/tables/fences/citation patterns), code:prose ratio and fence-language histogram, opening/transition/closing lexicons, hedging/qualification/refusal/apology/uncertainty marker inventories, and stratifications by mode, prompt length class, topic tag (owner-tagged or keyword-classed, labeled as such), language, hour-of-day, position-in-conversation. Representative excerpts always resolve to transcript.get links.
  • Uncertainty machinery: every metric ships with n, % cohort captured at each capture_depth, excluded INFERRED_CONTENT share, drift-window flags, and bootstrap CIs where meaningful. Sparse cohorts (n < owner-set floor, default 30 generations) display but are watermarked “low evidence”.
  • Versioning: runs record feature-extractor version + adapter versions + input digest; changing an extractor bumps analysis-schema version, old runs keep their meaning.

10.2 · What one heavy user’s corpus can and cannot support

Defensible

  • Longitudinal drift of a revealed label: “provider-x/model-y outputs changed in March.” (Arena post-processing and routing changes confound — reported, not corrected.)
  • Intra-corpus consistency: two revealed cohorts differ in, say, listiness, at stated effect sizes with CIs.
  • Mode/condition effects within your own usage (battle vs direct) with prompt-mix caveats.
  • Blind-label consistency checks (“Model A across these battles behaves like one cohort”).

Misleading — the design must say so

  • “Model X is more verbose than model Y” — prompt mix, conversation history, hidden system prompts, decoding settings, tools, safety layers, and Arena-side post-processing confound identity-level claims from arena data.
  • Cross-provider generalization: one user’s topics, one time window, experiment-flagged UI (flags verified live [S1]), uncertain reveals, aliasing/routing opacity.
  • Any significance theater: p-values without cohort disclosure are suppressed by the UI, not trusted to taste.

Selection bias is structural (your prompts choose the models that survive voting), temporal change is certain, and labels are sometimes just wrong — profiles are “what this corpus shows under these labels”, full stop. This is why §8.4’s identity discipline exists.

10.3 · Later experiments — entry gates, not vibes

  • Embeddings/similarity features enter only when: (a) v1 profiles are in daily use; (b) a stated question needs them (duplicate-clustering for splits, corpus search); (c) the footprint budget (weights ~hundreds of MB, RAM during inference) is accepted by the owner. If accepted: onnxruntime-node, one pinned open-weights embedder fetched once with recorded SHA-256, stored encrypted as an artifact, fully offline thereafter; preprocessing + model version recorded per embedding table. Then — and only then — similarity projects may start…
  • Similarity/fingerprint experiments are hypothesis-testing rigs, not identity machines: (i) predefined config: train/test split at conversation-cluster granularity (near-duplicates and branch-families detected by minhash/embedding clustering and held whole on one side — leakage-resistant by construction); (ii) prompt/topic controls (stratified or matched subsets); (iii) negative controls (known-disjoint models must not cross-predict); (iv) calibration (score → probability mapping fit on held-out only, reported with error bars); (v) explicit UNKNOWN class via score thresholding; (vi) every run reproducible from input digest + seed. No universal sample thresholds are invented: minimum evidence is computed per experiment from its effect-size target; if the corpus cannot meet it, the rig reports “underpowered” and stops. Continuation policy: proceed only while calibration curves beat chance with held-out CIs excluding it and negative controls stay negative; two consecutive failed calibration windows ⇒ experiment state ABANDON with the write-up retained. Similarity output language is fixed: “confidence-qualified similarity to an archived cohort”, stored separately from observed identity (§8.4) and never overwriting it.
