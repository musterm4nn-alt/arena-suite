Arena Archive — private macOS conversation archive
for arena.ai: architecture & implementation plan

A dedicated local browser that owns multiple concurrent Arena account sessions, captures accurate transcripts at the network-protocol level (with page-level reconciliation), stores them in an encrypted local archive, and exposes every capability through a local MCP server for AI-agent operation.
Plan date: 2026-03 Target: Apple Silicon, macOS 14+ (dev/test on macOS 27, M3 Pro 18 GB) Owner: single human; all implementation by AI agents Delivery: single static report

00Verdict

Selected architecture

Electron (Chromium, arm64 macOS) as the dedicated browser runtime, with a Node/TypeScript main process that owns the entire capture pipeline. One Chromium engine in the whole process tree; no companion browser, no separate runtime, no extension.

  • Capture — Chrome DevTools Protocol via the first-party webContents.debugger API: full request/response metadata, complete response bodies, streamed byte chunks (Network.dataReceived), and WebSocket frames. A session-level webRequest census runs in parallel and diffs against CDP to detect observation gaps instead of hiding them. Page-world injection is demoted to reconciliation only (rendered UI state, labels, votes) — never the primary network source. VERIFIED API surface: Electron + CDP docs, §13.
  • Accounts — one persistent Chromium partition per Arena account (session.fromPartition('persist:acct-…')): isolated cookies, storage, cache, and service-worker state; ≥2 accounts concurrently live. Sign-in is Arena's own email flow, unchanged, inside the app. VERIFIED partition API: Electron docs; cross-restart session persistence: P0 test.
  • Storage — SQLite via better-sqlite3-multiple-ciphers (SQLCipher-compatible), master key in the macOS Keychain; artifacts as AEAD-encrypted files; FTS5 full-text search. VERIFIED npm package page, §13.
  • Interface — a local MCP server (Streamable HTTP, 127.0.0.1, token auth) inside the app; the diagnostics-first GUI shares the same service layer, so nothing is GUI-only. VERIFIED MCP spec 2025-03-26, §13.
  • Minimum macOS: 14 (Sonoma), Apple Silicon. Rationale in §03.

Key reason for this stack

Among mainstream maintained candidates, Electron is the only one that simultaneously provides (a) protocol-level network observation with full bodies and stream chunks from first-party APIs, (b) profile-grade partitioning for concurrent isolated account sessions, (c) application-owned downloads, and (d) a Node/TS ecosystem that AI agents can build and debug with mainstream, well-documented dependencies. CEF exposes an even deeper browser-process hook (CefResponseFilter) but at a large maintenance cost (no maintained first-party macOS shell tooling); the WebKit-based shells (native Swift/WKWebView, Tauri/Wry) provide no protocol-level network capture at all — owning the window there is the whole story. The full comparison, including where Electron still depends on page injection and what it can miss, is §02–§04. VERIFIED per-candidate mechanisms cited in §02/§13.

Honest statement about the selected stack The Electron plan does not rely on page-world monkey-patching for network capture: CDP Network is the primary source, the webRequest census is the completeness backstop, and page injection is confined to (a) UI-state reconciliation and (b) executing owner-scope fetch calls inside the account's own page world for backfill (§07). Custom Chromium fork

Mentioned only as the last-resort escalation: it is justified solely if a concretely identified required observation is impossible through both maintained CDP and CEF hooks (e.g., a protocol event neither surface exposes). It multiplies maintenance by an order of magnitude (per-CEF/Chromium-version rebase) and is not part of the plan.

Trust boundaries — the rules that must never break

  1. Arena content is untrusted input. Page worlds run with context isolation and no Node. They cannot read the Keychain, the archive, the MCP token, or other partitions. The MCP HTTP server binds 127.0.0.1, requires a bearer token, and validates Origin (per MCP transport security requirements VERIFIED6), so a hostile or compromised arena.ai page cannot drive the app server.
  2. Credentials stay in the browser. Session cookies live only in each partition's cookie jar, managed by Chromium (set/refreshed by Arena's own flows). The app's Node code never reads, copies, or exports them: backfill fetches execute inside the account's page world (§07), and token refresh is the page's own job. "Browser-managed session persistence" is a standard Chromium profile on local disk — protected by directory permissions (0700) and, when enabled, FileVault — with the same residual exposures as any browser profile (Time Machine, snapshots). This is stated as an accepted, bounded trade-off, not claimed away.
  3. Account binding is by construction. Every capture context is created from a named partition; the account_id is stamped at capture time from the partition identity, never inferred from URL, ID, or content. Cross-account joins are impossible in SQL because every row is single-account-keyed. Identical conversation IDs in two accounts are different records (§08).
  4. Per-account failure isolation. Sign-out, auth expiry, account change, or ambiguity in account i pauses account i's recording/sync, marks its window for owner re-auth, and touches nothing else. A record is never silently re-bound to another account; an account whose identity changed is flagged identity-changed and quarantined for owner review.
  5. Popups and redirects inherit the partition. setWindowOpenHandler routes any new window to a new BrowserWindow on the same partition, labeled with its account; one account can never inherit another's browser state, capture stream, sync authority, or destructive-action scope.
  6. Visible state + real controls. Per account and global:
    ControlEffect on in-flight workEffect on captured data
    Pause (account)CDP/census keep watching but new evidence is not admitted; in-flight streams are buffered to staging and admitted or discarded at resume per owner choice; sync jobs checkpoint and holdThe pause interval is recorded as a capture_gap — transcripts are honest about it
    Cancel (job)Current page/step finishes or is dropped (documented per job kind); cursor checkpointed for resumeNothing partial is promoted to complete
    Stop (account / global)All capture for the account (or all accounts) halts; staged in-flight bytes are flushed as stopped-user or dropped, never as completeStates reflect reality: stopped ≠ complete

Resource model on 18 GB shared RAM

Chromium spawns a renderer per site instance per partition, so memory scales with active windows. The app enforces a maximum of 2 concurrently active account windows; further accounts go dormant (webContents closed, partition state on disk — signed-in state survives because partitions persist, cross-restart persistence is a P0 check HYPOTHESIS: "Chromium persist: partitions retain sign-in across app restarts" — test: quit/restart, both accounts still signed in; consequence if false: dormancy becomes re-sign-in, a workflow regression the owner must accept or we cap at one active window). Memory is sampled via app.getAppMetrics() into diagnostics; a proposed soft budget of ~10 GB aggregate renderer RSS triggers an eviction suggestion (dormant the least-active window), never a silent kill. These are proposed policies, to be tuned with the measurement protocol in §12 — no usage numbers are assumed.

Minimum macOS version: 14 (Sonoma), Apple Silicon

Chosen as a floor, not a ceiling: it is comfortably inside supported ranges of current Electron/Chromium arm64 builds and of the native dependencies (SQLCipher fork prebuilds), keeps Keychain/ security behavior well-characterized, and leaves headroom below the owner's actual target (macOS 27 on M3 Pro). Older Apple Silicon (11–13) is possible in principle but buys nothing for a private app while enlarging the untested matrix. 04Capture architecture

Capture is a layered pipeline where each layer's weakness is made visible by the next layer down. No layer may silently declare completeness.

Capture layers (strongest first)
L1 — CDP Network, per webContents (primary network source)
webContents.debugger.attach() before any loadURL; Network.enable. Streams requestWillBeSent / responseReceived / dataReceived / loadingFinished|Failed, WebSocket frames, getResponseBody. dataReceived chunk accumulation is the canonical stream source; a stream is "complete" only on a transport-closed event and a protocol terminal event (or none — see states).
L0 — session.webRequest census (completeness backstop)
Browser-process view of every request in the partition — including early navigations and service-worker-initiated loads — with URL, method, status, sizes, timing (no bodies). Diffed continuously against L1 to produce gap events.
L2 — Service Worker / Worker / target lifecycle
ServiceWorker.enable (worker registrations, activation, version changes) and worker/target events per page session; request initiatorType attribution. Known boundary: Electron exposes CDP per page webContents; attaching to SW targets is not exposed. SW-initiated fetch bodies may be invisible in L1 → L0 still sees the request → gap flag; if material, §00 escalation to CEF.
L3 — Page-world reconciliation (secondary, explicitly shallow)
Preload bridge (context-isolated, no Node) + CDP Runtime/DOM sampling: rendered message structure, participant positions, blind labels, visible votes, post-vote reveals, stop buttons, error toasts. Versioned UI adapter (selector map + version). UI-only evidence is always labeled dom and carries lower confidence — it reconstructs what the page chose to show, not the wire.
L4 — Downloads & generated artifacts
session.on('will-download') → setSavePath into per-account artifact staging (no system dialog, no companion bridge); progress/cancel tracked; blob/data URLs observed in L1 resolved via getResponseBody. Artifact↔conversation link is attributed-by-context (foreground conversation at download time) and flagged as such, never asserted.

05Discovery & protocol catalog

Discovery is a maintained capability, not a one-time spike: the capture pipeline continuously classifies all first-party traffic across both accounts into a machine-readable protocol catalog, and drift is first-class data. The catalog is the agent's map for maintenance.

Catalog entry (one row per observed operation family)

protocol_operations {
  id, account_scope        -- partition identity (or 'global' for cross-account-identical ops)
  host, path_pattern, method, transport   -- http | chunked | sse | websocket | download
  klass                    -- conversation-read | conversation-write | stream | auth-account
                            | asset | analytics-config | mutation-other | unknown
  first_party_basis        -- origin-match | first-party-context | partition-association (which, stored)
  read_mutation            -- unknown | read-evident | read-verified | mutation   (see §07)
  payload_family           -- versioned schema fingerprint: normalized keyset + types hash
  adapter_version, completeness, drift_flags[], last_seen_at, sample_ref -- sanitized, capped
}
  • First-party origin evidence is stored per operation: origin match against the observed arena origin set (maintained, not hardcoded forever), initiation context (arena document/worker vs. third-party embed), and partition association. "Internal/undocumented endpoint" is recorded as undocumented-first-party — that label is descriptive, not an access-control claim.
  • Read vs. mutation is never inferred from HTTP method or name. read-evident = method + observed behavior consistent with read; read-verified = the owner-session verification protocol in §07 actually passed. Backfill will only replay operations that are read-verified.
  • Unknowns stay unknown. New families get klass=unknown until an agent (or owner) investigates through aa.catalog.show (sanitized sample + census history + attribution). Unknown operations are never retained as full bodies — metadata only — until classified.

Sanitization — applied before any persistence or diagnostic exposure

  • Never retained: Authorization, Cookie/Set-Cookie, OAuth codes/state, CSRF tokens, passwords, API keys, signed-URL secret parameters. They are replaced by redacted:<sha256-12> references so drift diagnostics can still correlate without exposing (a safe resource reference when the source URL carried a secret).
  • Headers retained: method, URL (secret queries stripped), status, content-type, sizes, durations. Bodies retained only for first-party operations in conversation/stream classes, or mutation-other ops explicitly under investigation (owner-visible in diagnostics).
  • Parser errors retain a redacted prefix (≤ 512 B) + error class, never the raw body. Diagnostics output (logs, MCP responses, crash context) passes the same sanitizer pipeline; a sanitizer failure fails closed (the record is stored as unparsed-sanitized, never as raw).
  • Diagnostic retention: census rows 90 days, DOM snapshots 30 days, parser-error samples 30 days (all configurable). Conversation-class sanitized bodies are the archive and are retained until explicit deletion (§09).

Drift handling

A payload family's fingerprint is a hash of its normalized shape (keysets, nesting, types — not values). Fingerprint mismatch on a known family → drift event with the sanitized new sample; the adapter stays pinned to its version for old records; new traffic is admitted under the new family id; backlog reparsing is offered as an explicit, owner-approved job (aa.catalog.drift lists everything and the recovery options: re-pin, re-parse with sanitized samples, or mark affected transcripts adapter-drifted). Frontend drift (selectors) is the same mechanism on the UI adapter. The agent never guesses: it reads aa.catalog.drift, sees exactly what changed and what is affected, and acts only on owner-approved jobs.

06Live capture & reconstruction

Transports and stream reconstruction

The v1 text release must cover battle, direct-model, and side-by-side modes over whatever transport Arena actually uses — SSE, chunked HTTP, or WebSocket are all hypotheses until P0 observes the real traffic HYPOTHESIS (H1, §13). All three are reconstructable in L1: dataReceived accumulation per request for SSE/chunked; per-frame capture with message reassembly for WebSocket (frames carry direction, opcode, and payload; terminal/close frames are first-class evidence). The adapters are per-family (catalog), so a transport change is drift, not a rewrite: the parser consumes the family's fingerprint-validated shape, not a hardcoded URL map.

Turn, branch, and participant boundaries

  • Turn boundaries: primary = protocol message/turn IDs (discovered in P0 and recorded in the catalog); cross-check = L3 UI message count/structure. If the protocol lacks IDs, the UI adapter supplies position with a ui-derived provenance flag.
  • Branches / revisions: a regeneration or re-ask is a new revision sharing a parent-turn reference (protocol) or a DOM branch indicator (UI). Branch trees are stored, not flattened — alternating-text flattening is explicitly insufficient and is never the stored form.
  • Participant positions: slots (A/B, or named in side-by-side) are stored per conversation; position is identity, not model — see §08.
  • Reconnects & repeats: the page may retry a stream after a transport drop. The app sees both attempts (census + L1); dedupe is by protocol event/message ID where present, otherwise by (turn, byte-range) overlap with a reconnect-retry flag. Duplicates are retained as evidence; normalized state keeps one logical turn with the retry documented.
  • Late events: post-vote model reveals, late title updates, and async metadata arrive after the turn closed → they append dated observations (identity, title) scoped to their supported range; no historical rewrite.
  • Navigation mid-stream: top-level navigation or target destruction while a stream is open → the stream is truncated in evidence (last byte offset recorded) and classified failed-transport or partial-gap per the census record — never complete. The census row is what proves the truncation point exists.
  • Missing events: any L0/L1 disagreement → gap event → completeness degrades → visible in every query, export, and diagnostic that touches the record.

Account binding

Every observation is stamped at capture time with the partition's account_id. A conversation's identity is the pair (account_id, source_conversation_id); the source ID (URL segment or protocol id) is correlation material only — it never establishes ownership, and identical source IDs across accounts are distinct records with an explicit cross-account collision note when encountered (§08).

Where fallback capture loses information (stated up front)

DOM-reconstructed turns lose: stream timing, token-level deltas, raw event/message IDs, aborted tails, and anything the UI chose not to render (truncated previews). Primary design: owner-read replay, credentials never extracted

Per-account sync worker (hidden webContents in the account's own partition)
1 — context
Dedicated sync frame webContents on persist:acct-…, navigated to a lightweight signed-in arena.ai route (e.g. the history surface). Same cookie jar as the owner's windows; distinct webContents, so its capture context is unambiguous and it never disturbs the owner's visible windows.
2 — read
CDP Runtime.evaluate executes fetch(<discovered listing op>, {credentials:'include'}) inside the page world. The app observes the response through L1 on this target (body, sha, timing) and receives the serialized result from evaluate — two independent evidence copies that must agree, else integrity event. Next page: cursor from previous response.
3 — commit
Per page: sanitize → stage → transactional upsert keyed (account_id, source_id) → checkpoint cursor. Detail fetches for items lacking content follow the same per-item pipeline, each read-verified operation only.
why not app-side fetch with copied cookies?
Would violate the credential boundary (§03.2): the app must not persist token/cookie copies anywhere, and extraction is exactly the class of mechanism the owner rules out. In-page replay keeps Arena in control of authentication, including token refresh.

Read-verification protocol (what "verified read" means here)

  1. Repeatability: identical call (same params, same page) executed twice in the owner session → identical (or semantically identical) response bodies. Byte identity or documented instability (e.g. embedded timestamps) with the diff explained.
  2. No side-channel writes: during the replay window, the census for that partition shows no mutation-class requests attributable to the sync frame beyond the reads themselves.
  3. No observable state change: subsequent owner-visible UI state (history listing) unchanged within the observation window.
  4. By construction: GET-style, idempotent params only; never a write-shaped call. Residual uncertainty, stated: server-side effects invisible to us (analytics, session liveness) cannot be excluded; this is accepted, documented, and is the price of staying on the owner-session side of the boundary.

Verification is recorded per (operation, account) with date and evidence refs, and expires after 90 days (proposed policy) or immediately on drift. Only read-verified operations are replayed. HYPOTHESIS H2: a paginated owner-history listing exists behind /history/search — P0 test: open the surface, read the census, identify the listing op, replay it twice, run the protocol above. Consequence if false: fall to Fallback 1/2 with documented partial coverage.

Sync job semantics — Sync now for one or selected accounts

  • Jobs & visibility: one job per account (never one job spanning accounts — scope must be unambiguous for cancellation and degradation). Progress: pages done/total-when-known, items reconciled, current phase (listing/detail/reconcile), visible in GUI per account and via aa.sync.status. Auto-sync is an explicit per-account setting (default off).
  • Checkpoint & resume: cursor persisted per account after every committed page; resume re-fetches the last page and dedupes. Cancellation: finish current page, checkpoint, state cancelled — resumable, no corruption path. Retries: bounded exponential backoff per account; a job that exhausts retries is failed with the reason, not silently half-done.
  • Overlapping / repeated pages & unstable pagination: dedupe is by (account_id, source_id) — identical text is not evidence of duplication (identical IDs with different content → both retained as revisions with a conflict flag; same ID, same content → skip). Cursor monotonicity is checked; detected instability triggers a bounded re-scan of the overlap window. Re-runs are no-ops.
  • Concurrency: partitions are isolated, so multiple accounts can sync simultaneously without correctness coupling. A global budget (≤ 2 concurrent sync jobs) protects rate limits and RAM; each account's scheduler is independent. One account's 429/stall/rate-limit affects only that account's queue.
  • Live-capture overlap: a conversation being live-captured on the same account and also reached by backfill reconciles under the same key; live stream state wins for content, sync adds metadata; evidence is unioned, turns never duplicated (ID+position, not text, decides identity).
  • Failures degrade per account: auth expiry → job paused-auth, owner re-signs in, resume; unexpected redirect / challenge / write-shaped response → job stops, suspected-mutation-or-challenge flag, no retry storm; drift → stop + drift event. Other accounts keep running.
  • Cross-account source-ID collision: explicit identity_conflict records, surfaced in diagnostics and UI; never automatic merges or rebinding (§08).

What "synchronized" means, and what remains when the endpoint disappoints

Per account, "synchronized" is a defined, inspectable claim: "the discovered, read-verified listing endpoint was consumed to its end-of-listing (or oldest supported page); N items reconciled; known residual gaps: [pre-endpoint window, failed pages enumerated, SW-gap windows, dom-only items, items pending detail]". The agent inspects all of it via aa.sync.status + coverage report; nothing is implied beyond it. If no reliable listing endpoint can be verified: Fallback 1 (rendered recording) + detail reads for known IDs (URLs from the owner or from live-observed traffic) still deliver partial, honestly-labeled backfill. Opening one known conversation successfully proves that conversation's detail path — and nothing about full-history coverage; the plan never makes that inference.

Reconciliation, conflicts, and deletion interaction

  • Deduplication: keyed on identity fields (source IDs + position), never on text equality — identical text is not evidence of duplication. Dedup markers (account, source_id, content_sha) survive conversation deletion as lightweight tombstones so future syncs stay no-ops; tombstones are removed with the account or the whole archive; the owner can force re-capture of a tombstoned conversation via MCP flag (new evidence, old normalized rows stay deleted).
  • Conflicts: cross-account source-ID collision → identity_conflict record, both records untouched, surfaced in diagnostics. Same-account same-ID different-content → revision + flag. Ambiguous ownership (e.g., a conversation reachable under two of the owner's identities) → quarantine state, owner decides, app never guesses.
  • Provenance retention & recomputation: conversation-class sanitized evidence is retained until explicit deletion — after an adapter changes, affected records can be re-derived (re-parse job, owner-approved, versions recorded). Metadata-class evidence (census, DOM) expires per §05 policy, so UI-derived facts older than that window are irreproducible — stated in their provenance, not hidden. Every normalized field that matters analytically carries (evidence_ids, adapter_version, confidence).
  • Transactions & crash recovery: one synchronous writer (better-sqlite3). Staging batch (time- or size-bounded) → single transaction per batch; a crash loses at most the open batch, and the gap detector records the boundary as capture_events so the loss is known. WAL mode; the app verifies no plaintext side-files escape the data directory (acceptance check, §12). Migrations: numbered SQL, forward-only, idempotent, run under a lock, with a pre-migration encrypted snapshot (backup is cheap because it is file-level).
  • Backup/restore: aa.backup.create → VACUUM INTO of the closed-transaction DB + artifact manifest; restore = replace files, version + checksum validation, then re-derive projections. Proportional to a single-user app: no replication, no continuous backup, no cloud (the owner's Time Machine is a convenience, not part of the trust model — §09).

09Protection, secrets, and deletion

Keys & encryption

  • Archive key: random 256-bit, generated at first launch, stored in the macOS Keychain (security CLI, generic password, WhenUnlockedThisDeviceOnly) — zero native dependencies, fully agent-operable. Key material lives in main-process memory; it is never written to disk, logs, fixtures, or crash reports (asserted by tests that grep logs/crash dirs for the key material and its derived prefixes).
  • Database: SQLCipher-compatible mode of SQLite3MultipleCiphers (SQLCipher 4 parameter set). Page-level encryption covers the DB and, by SQLCipher behavior, journal/WAL — verified by acceptance check, not assumed: after a write+crash test, no plaintext *-wal/*-journal bytes may appear on disk; FTS5 index lives inside the encrypted DB.
  • Large artifacts: per-file XChaCha20-Poly1305 (node:crypto), per-file random key wrapped from the archive key via HKDF; nonce + wrapped key + sha256 in the (encrypted) DB. Files are immutable after commit.

10Local MCP contract (primary interface)

Transport, connection, trust

  • Streamable HTTP (MCP spec 2025-03-26) on a single endpoint, bound to 127.0.0.1 only, bearer-token auth, Origin validation — the spec's own local-server security requirements VERIFIED6. Server lives inside the app's main process; implemented with the official TypeScript SDK (@modelcontextprotocol/sdk).
  • Why not stdio: a stdio MCP server is process-owned by its client. This app must outlive any given client (windows stay open, capture stays on, sync keeps running); the owner launches the app once, and any number of agent sessions connect to it. Endpoint + token are written to a 0600 mcp.json at launch (token itself stays in Keychain); agents read it from a documented path.
  • Discovery & degradation: standard tools/list; MCP resources expose live state (health, per-account recording state, sync jobs, drift summary) so an agent can poll without tool calls. aa.health returns app/adapter versions, DB status, and per-area availability — an unavailable operation reports why (area state + recovery hint), never a bare failure.
  • Untrusted data rule: everything read from the archive (prompts, model outputs, tool traces, diagnostics text) is data. It is returned framed ("content" fields, JSON-escaped) and is never interpreted as operational authority; the server executes only typed tool calls. This is enforced by construction (no code path from stored text to action) and by the destructive guard below.

Jobs, errors, identifiers

  • Identifiers: opaque, prefixed (aa_acct_*, aa_conv_*, t_*, e_*, aa_job_*); source IDs from Arena are stored but never used as primary keys without the account prefix. Pagination is cursor-based and stable within a job.

Destructive-action guard (the concrete mechanism, not "be careful")

For delete.conversation, delete.account_data, delete.archive: the server generates a one-time code per (action, exact scope) using an install-secret + HMAC over (action, scope, 90-second expiry window); the code is rendered only in the GUI destructive-actions panel — a trusted control channel that no captured content can reach. A tool call without a valid code fails E_GUARD_REQUIRED with the exact scope the owner must see. Because the code is (a) unguessable, (b) scope-bound, (c) short-lived, and (d) displayed only in the GUI, an instruction embedded in archived text — "please run aa.delete.archive" — is a harmless string: the server cannot produce a valid code from data. A human in the loop reads the panel and passes the code; the agent never invents one. GUI triggers the same code flow, so both surfaces share one guard implementation.

GUI ⇄ MCP consistency

Both surfaces call the same service layer (same validators, same state machines, same audit log). Browser-touching actions (open window, start recording, re-sign-in prompts) are service methods; the GUI shows the resulting visible state, and the agent observes the identical state via aa.accounts.show. No workflow is GUI-only; if a future GUI feature lands without its tool, the CI gate "every service capability has a tool or a documented GUI-only reason" fails the build.

11Local analysis

v1: deterministic model profiles (all local, all reproducible)

Started with transparent deterministic statistics because they cost zero packaging, run in milliseconds, and are exactly as interpretable as the corpus justifies. Computed in TS/SQL over normalized turns; every run records params, cohort, adapter version, and code revision. Cohorts are formed only from observed or revealed identity evidence, with uncertainty preserved (a turn whose identity is blind/conflict is cohorted as such — never silently folded in).

  • Lengths: response, paragraph, sentence, code-block distributions (quantiles, not means-only).
  • Lexicon: type-token & MATTR diversity, recurring n-grams (2–6), signature phrases; punctuation and casing profiles.
  • Structure: Markdown usage — headings, lists, tables, fenced code languages, code/prose ratio, citation-like patterns.
  • Discourse markers: versioned lexicons (hedging, qualifications, apologies, refusals, uncertainty, transitions); openings/closings n-grams; marker rates per 1k tokens.
  • Variation: by prompt type (heuristic, labeled), mode, language, time window, conversation position.
  • Excerpts: representative examples linked to source evidence IDs (clickable provenance), so a claim is always checkable against the archive.
  • Uncertainty: bootstrap CIs per cohort statistic; cohorts below 20 turns (proposed policy, tunable) are reported as insufficient sample — displayed, not suppressed.

What this corpus can and cannot support

Can: descriptive style statistics per identity cohort and time window; drift of an identity's style over time; within-owner comparisons across identities on the same prompt (where the owner reused prompts — a natural, if sparse, controlled design). Cannot (stated in every report output): causal claims about what produces a style (prompt, decoding, system prompt, tools, safety layers are unobserved); attribution of authorship or model identity from style; stable comparisons across prompt/topic distributions (confounding); generalization beyond this one heavy user's usage (selection bias). Alias/routing uncertainty and temporal model changes are carried as cohort caveats, not resolved by statistics.

Embeddings / local ML — evaluated, gated, not default

Not selected for v1: deterministic stats already answer the stated questions, and ML packaging (runtime, weights, preprocessing versions) adds irreproducible surface for no v1 benefit. Entry gate (all must hold): (1) a concrete question n-grams demonstrably cannot answer; (2) corpus ≥ ~10k turns (proposed floor) so the added machinery is measurable; (3) owner approval of the resource budget (M3 Pro / 18 GB is ample for small sentence models, but the budget is a policy, not an assumption). If entered: local inference only (onnxruntime-node or transformers.js), weights pinned with version + SHA-256, downloaded once, cached in the app dir, fully offline afterwards; preprocessing rules versioned inside each analysis_runs record so results are reproducible byte-for-byte.

Later similarity / fingerprinting experiments — protocol, not promise

Stylistic similarity to an archived cohort is an unverified, confidence-qualified hypothesis, never evidence of identity or authorship; inferred identity stays in a separate field from observed identity. Any such experiment must predeclare (stored in analysis_runs before running):

  • Hypothesis & decision rule: what signal, on what test set, would count as finding anything — including the case that says "none".
  • Leakage-resistant splits: conversation-level (never turn-level); sibling branches/revisions of the same conversation stay on one side; temporal holdout (train < T < test) to catch model-drift leakage through "same model, different era" confusion.
  • Controls: matched-prompt comparisons vs random-prompt baseline; negative controls — same identity across time windows (expected: similar) and different identities on matched prompts (expected: separable only if the signal is real); near-duplicate detection before any split.
  • Calibration & unknown class: reliability of the "similar/different" decision curve; an explicit undecidable region instead of a forced binary.
  • Minimum evidence, empirically justified: separation beyond the negative-control distribution, stable across k conversation-level folds, and surviving topic controls. No universal sample-size threshold is asserted; the budget (conversations × compute) is predeclared and, if the decision rule is not met within it, the experiment is revised or abandoned with a written reason. Results lacking scientific utility (e.g., separability that collapses under topic control) are stopped, not massaged.

P0 — Browser & capture-depth falsification spike

Deliverable: minimal Electron shell: 2 partitions, email sign-in in both, CDP+census capture on, raw diagnostics view. Checks (each with its falsifier):

  1. Two-account isolation. Canary probes: distinct localStorage values + a partition-distinct cookie per account; attempts to read the other partition's values fail; if Arena registers service workers, each partition's SW is distinct (if it registers none, that is itself a recorded observation). Falsifier: any cross-partition read succeeds → §00 reversal (CEF profiles) or stop.
  2. Attach timing. Falsifier: uncontrollable gap rate on real Arena navigations → re-architect attach once, then CEF.
  3. Stream completeness. One real battle prompt: dataReceived byte-sum == getResponseBody size; terminal event observed; a forced mid-stream network drop (throttling/offline) classifies failed-transport, never complete. Falsifier: bytes lost with no gap event recorded → capture core is unsound, halt P1.
  4. Stopped / partial turns. Owner-stop classifies stopped-user; UI/DOM fallback path produces a dom-reconstructed turn on a deliberately blinded synthetic page (synthetic: L1 muted) with correct labeling.
  5. Service-worker visibility. ServiceWorker.enable enumeration + request initiatorType attribution over real usage; if any conversation-class bytes are SW-initiated and invisible in L1, record the materiality verdict (share of conversation bytes affected). Falsifier: material → CEF escalation test (filter sees the bytes) before P1 commit.
  6. Downloads/artifacts. Trigger a file-producing Arena surface (code/webdev arenas) → will-download captures to the per-account staging with correct account stamp, no system dialog, no companion.
  7. No debug indicators / normal presentation. DOM+visual probe for any "being debugged" UI after attach; UA normalized to plain Chrome (recorded choice); email sign-in completes unmodified, including redirects/popups and any one-time code the flow demands. Falsifier: visible debugging UI that Arena's auth reacts to → presentation work or CEF (its filter has zero page-visible signals).
  8. Restart persistence. Quit & relaunch: both accounts still signed in (else dormancy-downgrade decision, §03).
  9. Memory characterization. app.getAppMetrics() samples over a heavy 30-minute session with 2 windows → the §03 soft budget is tuned from data (measurement protocol = sample every 5 s, persist to diagnostics; no numbers assumed beforehand).

Fixtures & evidence classes (kept strictly separate): (a) synthetic harness — local SSE/WS/redirect pages proving parser, state machine, and gap-detector behavior with zero credentials in fixtures (CI-greppable); (b) documented platform behavior — Electron/CDP contracts; (c) owner-session evidence — checks 1–9 above on real signed-in accounts. Each proves different things; none substitutes for the others, and the spike report must label every claim with its class.

Gate decision: all falsifiers clear (or escalations executed) → P1. Any fatal (isolation, restart, auth) → §00 table applies.
