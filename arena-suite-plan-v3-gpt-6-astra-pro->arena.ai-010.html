Arena Model Archive:
Embedded-Browser Capture, Local Provenance Store & LLM Interface

A technically rigorous plan for a private macOS application that owns its browser environment for Arena (arena.ai), records the owner's conversations accurately, backfills history where empirically verified, stores everything locally with strong provenance and account isolation, exposes essentially all functionality to an LLM through MCP, and later supports local model-behavior analysis. This report is the product. It does not implement the application.

1Executive architecture decision

One page that an implementation agent can execute against. Everything after this section is justification, mechanism detail, and falsification procedure.

DECISION

★ Recommendation Electron + Chromium, TypeScript application/service layer, SQLCipher-backed local store, stdio MCP server.

  • · One persistent Session partition per Arena account: persist:arena-<internal-uuid> (never raw email).
  • · One BrowserWindow/WebContentsView context per active account with its own capture coordinator.
  • · Primary capture: main-process webContents.debugger CDP observation (Network + target/worker lifecycle + WebSocket frames where applicable) attached as early as practical.
  • · Secondary evidence: minimal, privilege-less DOM/UI observation + Session download handling — reconciled, never trusted blindly.
  • · Sanitizer-before-persistence: no credentials/secrets ever reach the DB, logs, fixtures, exports, or diagnostics.
  • · GUI and MCP share one application-service layer; MCP is stdio-first, loopback-only if HTTP is ever added.
WHAT "OWNING THE BROWSER" BUYS (OUTSIDE PAGE JS)
  • · CDP transport in the main process: request/response metadata, response bodies, streamed chunks, socket frames — independent of page-world script and extension content-script injection races.
  • · Target/session lifecycle: visibility into navigation, new targets, workers where CDP exposes them — the extension baseline has no equivalent.
  • · Session partitions: OS-process-level cookie/storage/cache/service-worker isolation per account — an extension cannot partition the browser's own identity.
  • · Download pipeline: will-download interception per session — artifacts captured directly, not via page-triggered download scraping.
  • · Service-worker introspection: query running workers per session from the main process.
Not proven. No run has yet observed authenticated Arena traffic through this surface. Capture correctness against real Arena streams, workers, reveals, and backfill endpoints is an empirical acceptance gate (Spike 1 + Backfill Gate, §22), not an established fact.
Reversal rule. If Spike 1 falsifies Electron on any architecture-critical traffic class, run the focused CEF spike (§4.4). Switch to CEF iff native CefResponseFilter-family filtering demonstrably captures what maintained Electron/CDP cannot. Custom Chromium fork = last resort only.
Scope lock. Text modes first (battle, direct, side-by-side). Email sign-in only. Two simultaneous accounts minimum. No Google OAuth/passkey requirement. No cloud, no telemetry, no multi-user app accounts.

3Why Electron is recommended — and the exact reversal condition

AFFIRMATIVE CASE (PLATFORM FACTS → ARCHITECTURE FIT)
  1. 1. Chromium behavior without a fork. Arena is a modern web app; running it in genuine Chromium maximizes email-auth, CAPTCHA, redirect, popup, and anti-bot compatibility. No rendering-engine porting risk. ◐ Strong inference
  2. 2. Main-process CDP outside page JS (F1). webContents.debugger gives the main process its own CDP transport — attach, command, and receive instrumentation events — independent of page script, content-script races, and extension lifecycle. This is precisely the deeper surface the extension baseline lacks. ● Verified fact
  3. 3. Per-account persistent partitions (F2). session.fromPartition("persist:arena-<uuid>") is a documented isolation primitive for cookies/storage/cache/service workers per Arena account, with Session.clearData/clearStorageData scoping for per-account destructive operations. ● Verified fact
  4. 4. Download + worker introspection (F2/F3). will-download per session and session.serviceWorkers queries give artifact capture and worker-lifecycle evidence from the trusted process. ● Verified fact
  5. 5. Documented untrusted-content posture (F4). The security tutorial prescribes exactly this project's renderer lockdown (no Node, isolated context, sandbox, navigation/window gates, IPC sender validation). ● Verified fact
  6. 6. Agent maintainability. TypeScript across app/service/capture/MCP, npm ecosystem, no C++ toolchain, reproducible builds, machine-readable diagnostics — decisive for a project maintained mostly by AI coding agents.
WHAT ELECTRON DOES NOT PROVE (HONEST LIMITS)
  • · F1–F3 establish instrumentation capability, not Arena capture correctness. Whether every required byte is visible (H1/H3) is empirical. ? Hypothesis to test
  • · Exact CDP domain/method coverage (notably target auto-attachment and worker targeting) depends on the pinned Chromium/CDP revision and must be verified in-spike (I1). Method names in this report are provisional.
  • · CDP is a debugging protocol: attaching the debugger detaches Developer Tools for that target and changes some timing behavior. The spike must measure observer effect (missed-beginning/ending states, §11).
  • · Runtime footprint is heavier than WKWebView/Tauri (bundled Chromium per app). On an M3 Pro / 18 GB machine running two Arena partitions this is affordable but must be measured (§20), not assumed.
DECISION RULE (BINDING)

Ship v1 on Electron iff Spike 1 (§22.1) demonstrates reliable capture of every architecture-critical class: fetch/XHR bodies, Arena's actual stream transports, socket frames if used, worker/service-worker traffic without silent loss, navigation/target survival, stopped/failed/partial distinguishability, reveal association, direct downloads, partition isolation, and credential-free persistence. Any single critical-class failure triggers the CEF spike (§4.4).

6Requirements, boundaries & non-goals

OWNER-DATA BOUNDARY (BINDING)
  • · The app touches only the owner's own Arena accounts/data via authenticated first-party reads in the owner's current app-owned session.
  • · Internal/undocumented first-party endpoints are not "bypasses" when read with the owner's live session credentials — but they are also not self-evidently read-only. Every replayed operation needs Backfill-Gate verification (§22.2).
  • · A conversation ID/URL alone proves nothing about ownership. Every capture/sync operation binds to a verified account/session partition (§8); unverified binding = refused operation.
  • · No enumeration of unrelated infrastructure, no other users' data, no access-control workarounds. Ordinary automation/anti-bot compatibility (behaving like Chromium) is expected, not adversarial.
AUTHENTICATION (BINDING)
  • · Arena's own auth UI is authoritative. Required workflow: email-based sign-in, owner-driven, inside the embedded browser.
  • · The shell must tolerate email verification, OTP codes, MFA if encountered, CAPTCHAs/challenges, redirects, popups — i.e., do not gate or strip navigation flows (§7.4).
  • · Google OAuth / passkeys / third-party sign-in are explicitly not required and must not disqualify any architecture.
  • · No cookie/token import from Safari/Chrome/other apps. Browser-managed persistent state per partition is allowed; copied credentials must never persist into DB, logs, fixtures, exports, or diagnostics (§9.4, §15).
SIMULTANEITY (BINDING)

≥2 Arena accounts signed in and usable simultaneously — not a switcher. Isolated per account: cookies, local/session storage, HTTP cache, service workers, browser partition, capture pipeline, auth authority, provenance, sync state, destructive-action scope. A-sign-out/expiry/CAPTCHA/identity-change/sync-failure must not corrupt or rebind B. Design in §8.

NON-GOALS / NON-REQUIREMENTS
  • · No App Store, no public distribution, no hosted backend, no telemetry/cloud analytics, no multi-user app accounts, no public updater.
  • · No fabricated benchmarks, no calendar estimates, no invented Arena protocol in this report.
  • · v1 text modes only (§10.5); images/video/agents/uploads are extension points (§18.2), not v1 scope.
  • · No embeddings/heavy local ML in v1 — deterministic statistics first, empirical gate for anything heavier (§17–§18).

PROCESS / MODULE SEPARATION
  • · Main/browser process: owns Sessions, partitions, CDP debugger attachments, download handling, navigation/window gating, permission handlers. Never parses Arena content beyond framing/sanitization.
  • · Arena renderer per account partition: loads https://arena.ai (+ auth flows) only; nodeIntegration:false, contextIsolation:true, sandbox:true, webSecurity untouched; zero-or-negligible preload (ideally none in Arena content; any preload exposes no archive/MCP/key/IPC surface — F4).
  • · Capture coordinator per account: sequences CDP + DOM + download evidence, binds account/provenance, drives completeness states (§11).
  • · Sanitizer/parser pipeline: strips credentials/secrets before durability; parses via versioned adapters into the protocol catalog (§9).
  • · Application services: the single API behind GUI + MCP (conversations, sync, jobs, protocols, diagnostics, analysis, exports, deletion).
  • · Encrypted store: SQLCipher DB + encrypted blob store (§15).
  • · MCP server (stdio child or in-main): thin translation to services; no independent behavior.
  • · Diagnostics UI + optional analysis worker: minimal local renderer(s) on a custom protocol, isolated from Arena partitions.
IPC & CONTENT RULES (F4 → PROJECT POLICY)
  • · IPC is allowlisted and strongly typed: every channel has a schema, a direction, and a sender-validation rule (validate senderFrame origin; Arena frames get no privileged channels at all).
  • · No ipcRenderer (or wrapper with equivalent power) exposed in Arena preloads. If a preload exists for secondary DOM evidence, it exposes a single append-only evidence function with no return of privileged data.
  • · Archived prompts/responses/tool traces are untrusted data forever: rendered escaped, never executed, and incapable of authorizing anything — destructive actions require the intent-token flow (§15.5), which archived content cannot mint or satisfy.
  • · Navigation restricted to an allowlist (arena.ai + email-auth flows); setWindowOpenHandler denies-or-owns popups per partition (auth popups stay inside the owning partition); shell.openExternal never called with untrusted strings.
  • · Permission handler denies by default; per-partition grants only where Arena functionally needs them, logged as diagnostics.

  • · Partition names derive from random internal UUIDs, never emails or Arena IDs — directory names and logs stay non-sensitive.
  • · Account/session identity rides on every record (§13): observations, conversations, sync cursors, jobs, diagnostics all carry arena_account_id; cross-account source-ID collisions cannot merge because uniqueness is (account, source_id)-scoped and local PKs are UUIDs.
  • · Auth authority is per partition: coordinator A may only replay reads using partition A's live session; transient credential use never crosses columns and never persists (§15).
  • · Narrow failure scope: A signs out / expires / hits CAPTCHA / changes identity → pause A's capture authority + sync, surface NEEDS_OWNER_INTERACTION for A; B continues untouched. Identity change halts A's pipeline until re-verified (never silent rebind).
  • · Leak tests are machine-checkable (Spike 1): set marker cookie/storage/SW in A, assert absence in B, and vice versa; sign A out, assert B's session + capture + sync continue and B's provenance is unmodified.

15Encryption, local security & deletion

KEY + DATABASE DESIGN (F6 → PROJECT POLICY)
  • · Random archive key (256-bit, CSPRNG) generated once; stored in macOS Keychain (kSecClassGenericPassword, app-attributed, access-control with biometry-or-passcode option). Never in config, never in the DB, never logged.
  • · SQLCipher is the main store (F6): per-page AES-256-CBC, per-page IV, HMAC integrity, raw-key mode (no human passphrase as primary key — F6 supports raw binary keys).
  • · Harden per F6: force temp store to memory (SQLITE_TEMP_STORE=2 equivalent), keep FTS5 index inside the encrypted DB, ensure journal/WAL encryption is active and verified in tests.
  • · Large artifacts: filesystem blob store — each blob encrypted with a per-blob data key wrapped by (or derived from) the archive key (e.g., XChaCha20-Poly1305 blobs + Keychain-rooted KEK; exact construction pinned in Phase 4 with a documented rationale). Blob refs + digests in the DB; refcount GC on deletion.
  • · Exports are explicit, owner-directed plaintext escapes: confirm scope, write outside the archive, log the export event (not its credentials — exports contain none by construction).
PLAINTEXT EXPOSURE — HONEST ACCOUNTING
  • · Browser partitions necessarily hold live session cookies (persistent sign-in requires browser-managed state). Protected by OS file permissions + FileVault-at-rest on the owner's machine; this is not the same as copying credentials into the research archive. Residual risk (local malware with user privileges, forensic disk access without FileVault) is stated, not hand-waved.
  • · Plaintext also exists transiently in: renderer memory, CDP buffers pre-sanitizer, sanitizer working set, decrypted DB pages in process memory, analysis worker memory. Mitigate with最小 retention, locked/wiped buffers where practical — but do not promise protection against privileged local attackers or memory forensics.
  • · Cannot promise: deletion of data from Time Machine/Backups after the fact, from already-made exports, from swap beyond OS control, from Spotlight if plaintext ever escaped (prevent by never writing plaintext artifacts; exclude store dirs from Spotlight indexing).
  • · Crash logs/diagnostics carry digests and markers, never raw payloads or keys.
DELETION (LOCAL ONLY — NEVER TOUCHES ARENA CLOUD UNLESS A FUTURE EXPLICIT REMOTE FEATURE DOES)
  • · Scopes: one conversation · one account's local data · whole archive.
  • · Account/archive deletion requires a trusted explicit directive via two-step intent token: prepare returns exact scope + nonce token → confirm must present that token with an explicit destructive command. Archived content can neither mint nor satisfy the token (§16).
  • · Deletes: DB rows, observation links (retained raw blobs for scope), FTS entries, analysis derivatives/invalidation, blobs (refcount GC), sync cursors, dedup markers; partition-directory handling per scope (account deletion offers session-state wipe).
  • · Re-sync behavior is explicit: after local deletion, future syncs will re-observe still-present cloud conversations unless the scope is tombstoned — tombstone-by-scope is the default for account/archive deletes, optional per-conversation.

22.2 Backfill Gate — prove replay reads (H2) or downgrade honestly

  1. 1. Account binding: LIST/DETAIL issued in partition A return only A's data; cross-check against B's session (B's known conversation IDs must not resolve in A and vice versa).
  2. 2. Listing behavior: ordering, page size, cursors/tokens, total-vs-partial signals documented from observation.
  3. 3. Detail retrieval: conversation fetch returns stable, complete-enough payloads across repeats (digest-stability test).
  4. 4. Non-mutation proof: before/after state comparison (history order, read markers, vote state, server-observable side effects) across repeated LIST/DETAIL replays — plus a canary conversation whose cloud state is snapshotted. GET-ness proves nothing; this test does.
  5. 5. Checkpoint/resume + overlap: kill mid-walk, resume, assert idempotent convergence with no dupes and no holes (dedup-key audit).
  6. 6. Auth expiry + rate limits: forced expiry mid-sync → auth-blocked with resumable cursor; induced throttling → bounded backoff, no hammering.
  7. 7. Account isolation under concurrency: A∥B syncs interleave without cursor/provenance cross-talk.
  8. 8. Completeness boundaries: what LIST cannot see (archived? deleted? filtered?) is enumerated as known gaps, not assumed empty. One known conversation proves nothing — the gate needs a full-walk manifest.
