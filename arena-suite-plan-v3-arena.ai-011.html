Chapter 01

Decision at a glance

Recommended architecture — one line

A dedicated Electron (Chromium) application whose Node main process owns the browser, drives capture out-of-band via the Chrome DevTools Protocol at browser level (flat sessions, Target.setAutoAttach with waitForDebuggerOnStart, Network/Fetch domains, worker and service-worker targets), keeps every signed-in Arena account in its own persistent session partition, and stores everything in an SQLCipher-class encrypted SQLite archive keyed by a random archive key wrapped by macOS Keychain — with a local MCP server (Streamable HTTP, loopback-only) as the primary automation surface and a minimal diagnostics GUI sharing the same services.

Why: it is the only compared stack that gives an app owner browser-process-level observation (response bodies, chunked streams, WebSocket frames, EventSource, workers and service workers, early attach before first bytes) plus trivial, proven multi-session partitioning, plus a direct application-owned download/artifact path — in one mainstream, macOS-arm64-mature, AI-agent-friendly codebase. VERIFIED for mechanism availability; Arena-specific coverage remains HYPOTHESIS until Gate P2 runs on a signed-in session.

Fixed rejection confirmed

The existing Manifest V3 extension exporter (musterm4nn-alt/arena-exporter) is treated strictly as the measured baseline to beat, not a candidate. Its failure modes — missed capture, truncated streams, page-world interception gaps, lifecycle kills, awkward download handling — are structural to the extension sandbox (§2.3), so no extension+, chrome.debugger, native-messaging, or companion variant is eligible as the primary capture path. This plan does, however, prescribe an A/B evidence harness that runs the old extension and the new app over the same workflows to prove the depth gain instead of asserting it (§15, Gate P2-A).

Chapter 02

Context, constraints, and the rejected baseline

2.1 Hard constraints taken as given

Privacy
Permanently private, single owner. No distribution, App Store, hosted backend, multi-user support, telemetry, cloud analytics, or update infrastructure. This relaxes signing/notarization (dev/ad-hoc identity is fine) but not encryption: the archive is sensitive exactly because it is private.
Concurrency
≥2 Arena accounts signed in and usable simultaneously: isolated cookies, storage, cache, service workers, capture state, sync state, provenance, and destructive-action scope. Not an account switcher. This is an architecture-level requirement — it constrains the browser session layer (§6), the data keys (§10), the MCP contracts (§13), and the gate tests (§15).
Hardware
Apple Silicon only. Owner machine: M3 Pro, 18 GB shared RAM, macOS 27. No invented benchmarks: budgets are proposed (§16.4) and measured in Gate P1/P2 via app.getAppMetrics().
Operators
AI agents implement and operate. Consequences: TypeScript strict, mainstream dependencies only, reproducible npm-driven setup, machine-runnable gates (npm run gate:p1…), structured diagnostics, no bespoke protocols where a maintained library exists.
Primary UI
Local MCP server (or justified equivalent). Every GUI capability must also exist for an LLM. GUI v1 = diagnostics-first (recording/Live state, sync progress, catalog drift, approvals).
Auth
Arena email-based sign-in is sufficient. Google/OAuth/passkeys are explicitly not requirements and must not penalize an otherwise stronger architecture (§4.2). Owner-driven email verification, one-time codes, MFA, CAPTCHA, redirects, and popups must be completable in-app.
Baseline
Dedicated browser/runtime is fixed. Extension, chrome.debugger, extension+native-host, extension+companion are ineligible as primary architecture.

2.2 What Arena is (this run's verified baseline)

Arena is the rebranded LMArena (ex-LMSYS/UC-Berkeley model-evaluation platform), moved to arena.ai in January 2026 VERIFIED [S2][S1]. Its public homepage (fetched live during this run) exposes Battle Mode, prompt recipes for landing pages / dashboards / games / design-to-code / fullstack apps / storefronts, file attachment input, a leaderboard route (/leaderboard/agent), and — materially for §9 — a history search route (/history/search) VERIFIED (routes exist; behavior behind them not observed) [S3]. Battle/side-by-side/direct modes and post-vote identity reveals are described consistently across sources STRONG INFERENCE [S1][S2]. “Arena Code” is treated as the code/webdev arena family; its exact surfaces are HYPOTHESIS §4.3, T-4.

Chapter 04

Arena surface: knowns, unknowns, and tests

The plan never assumes an Arena protocol. It assumes a surface to be inventoried. This chapter fixes what is known, names what is not, and assigns every load-bearing unknown a smallest falsifying test. The discovery machinery that runs these tests is Chapter 07; the gates that make them pass/fail are Chapter 15.

Ownership discipline (invariant O-1): a conversation URL or opaque ID never establishes ownership. Ownership = the observation arrived inside a partition bound to a specific Arena account (account_id in §6.2), or a replay request executed with that account's session and the response reconciles with that account's views. Records from different accounts are never merged or re-assigned on similarity of IDs, URLs, titles, text, or timestamps (§10.5 conflicts).

4.2 Sign-in surface

  • The owner signs in in the app's own Chromium windows through Arena's own flows. Magic-link or code emails are handled owner-driven: the app exposes a per-account window where any emailed link can be opened (paste URL or route the link into the correct partition), codes are typed, CAPTCHAs shown, redirects tolerated — because this is a real browser RECOMMENDATION backed by E-verify: none of our capture mechanisms alter navigation.
  • Trickier details are HYPOTHESIS: whether Arena email auth uses magic links vs OTP vs both (T-1); whether cross-subdomain/subresource redirects or popup windows are involved. Popup flows are covered by setWindowOpenHandler routing new windows into the same partition (§6.3).
  • Google/OAuth/passkeys: out of scope as requirements. Consequence for the product: an account that can only be authenticated via Google SSO is unsupported in v1 — stated as an accepted limitation of the simplified auth surface, per the prompt's instruction. No cookies or tokens are ever imported from other browsers or apps; sessions are established only by completing Arena's own flow inside the app.

T-1 … T-8 — test definitions (runbook)

T-1 (auth & session issuance). In a fresh partition, complete one email sign-in while the catalog records auth traffic (sanitized). Settles: auth mechanism family, session-issuance surface (cookies vs storage tokens), redirect/popup topology, CAPTCHA presence. Produces the auth adapter contract. Synthetic proxy (a local server with OTP) exercises the harness first; cannot substitute for the live check.

T-2 (transport census). One captured conversation per mode (battle/direct/side-by-side; one code arena) with browser-level CDP attach: log every first-party request's URL family, method, transport, streaming vs buffered, target type (page/worker/SW), plus SW registration inventory. Settles S-2/S-8 and seeds the protocol catalog (§7).

T-3 (lifecycle & identity events). In battle mode: stream to completion, vote, observe reveal; stop one stream early; force one failure (block the stream origin via host mapping mid-flight); regenerate once. Correlates wire events with DOM states; settles S-3/S-6; defines terminal-event signatures per adapter.

T-4 (surface inventory). Enumerate routes for text/code/webdev arenas and Arena Code workspace; log entry/exit; identify which surfaces share the conversation transport vs their own (artifact endpoints etc.). Settles §14.6 modality entry conditions.

T-5 (history listing). Open history UI; capture the listing request(s); replay the identical GET from page context (same origin/cookies) and reconcile with rendered list; page to exhaustion once while recording cursors and item counts; check stability on re-run (same cursor → same page). Settles S-1/S-5 and the backfill primary method (§9.2 read-verification protocol).

T-6 (artifact handling). In code/webdev arena, trigger file generation/download; observe traffic vs will-download events; verify app-owned write path. Settles artifact adapter scope.

T-7 (two-account isolation probe). Sign account A and account B in two partitions; in A, set/read cookies + localStorage; assert from B nothing is readable; verify separate SW scopes; verify cookie-audit events attribute mutations to the right partition; kill A's session (sign out) and assert B's capture/sync state untouched. This test doubles as Gate P1 acceptance.

T-8 (anti-automation posture). Record challenge incidence across normal use vs replayed-read sync runs; check for webdriver-style gating. Determines whether sync must be throttled or scheduled, and whether challenges need owner-visible handling. Findings recorded; no stealth countermeasures are preplanned (honest-surfaces posture, §4.1-B).

4.4 Rule: no silent substitution of evidence classes

Synthetic protocol fixtures validate harness behavior; documented platform behavior validates mechanism availability; only owner-session observation validates Arena behavior. The gates in §15 require each class where it is valid and forbid substituting one for the others. Anything routing around this rule is a defect, not a shortcut.

5.2 The “window vs privilege” test, applied honestly

  • Swift + WKWebView would win on elegance, RAM, and native feel (one shared OS engine) — and loses the job: there is no supported http(s) interception surface. Everything network-true would fall back to page-world monkey-patching (evaluateJavaScript/wk userscripts) — i.e., shallower than the rejected extension baseline, with added engine UA tolerance risk for an agent-heavy site. Owning the window here buys nothing decisive. VERIFIED mechanism gap [S8]. → Rejected for capture; this is the most important honest trade-off in the report.
  • Tauri/wry inherits WebKit on macOS — same capture ceiling as WKWebView, plus Rust/TS split. Its security model is admirable, its capture surface is not. → Rejected.
  • Extension + companion: capture remains sandbox-bound (E5); a native host adds file access, not network truth; multiple account chrome-profiles are browser-owned, not app-owned. Ineligible and inadequate. The one thing it does well — trivial auth UX inside the user's daily browser — is matched by a dedicated Chromium shell. → Baseline only, used as the comparator rig in Gate P2-A.
  • Export/import without a browser: honest and robust for what an official export covers — but coverage, freshness, and whether an export even exists are all HYPOTHESIS (T-5); it cannot record live streams or prove completeness. → Not a primary architecture; retained as an optional ingestion adapter (§9.3-C) if an export exists.

Escalation path (kept narrow)

If — and only if — Gate P2 produces a named, required observation that CDP/Fetch demonstrably cannot deliver on Electron (worked example: a response family whose bytes are consumed before retrieval and not exposed via Fetch interception), the escalation is CEF with GetResourceResponseFilter as the capture adapter inside the same application architecture (data model, MCP, sync are stack-agnostic by design). 5.6 Why this wins; what could change it

The deciding fact pair: (a) the capture problem is a browser-process observation problem (streams, workers, SWs, early attach, bodies) and Electron's main process can drive full browser-level CDP against its own Chromium with zero sandbox in the way VERIFIED mechanisms [S4][S5]; (b) the product problem is many isolated sessions + app-owned files + agent-operated local services, which is precisely Electron's session partition + Node main competence set VERIFIED [S13]. The same reasons disqualify WKWebView/Tauri (no observation surface) and make CEF's marginal depth gain not worth a C++ hot path in a codebase owned by agents.

Reversal conditions (summarized from §17): R-1 a named observation unreachable via CDP on Electron → CEF capture adapter; R-2 Electron ground-truth failures in Gate P2 (e.g., Fetch streaming body loss at required rates, unfixable SW blindness) → CEF reevaluation; R-3 native DB module build failure with no maintenance path → switch DB driver, stack otherwise unchanged. None of these unwind the data model, sync, MCP, or gate structure — the architecture is deliberately layered so the browser adapter is replaceable.

6.4 Failure semantics under concurrency

Every work item (capture subscription, sync job, export, deletion, reparse) implements {pause,cancel,stop} with defined effects: pause = stop issuing new work at the next checkpoint boundary, keep state; cancel = finish current in-flight unit transactionally or roll it back, mark canceled; stop (global) = cancel all accounts, flush, close. In-flight network capture is append-only to the raw ring → a paused account simply stops projecting new observations; captured bytes already on disk are never discarded by pause/cancel (only by quota or deletion, both logged). States are observable per account and globally via MCP diag.state and the GUI — no silent losses: a stopped capture is a state, not a hole (§8.3).

The first engineering objective is not “capture conversations.” It is an instrumented inventory of every first-party operation the owner's sessions generate — conversation streams, listing reads, votes, auth, assets, analytics, artifact delivery — expressed as machine-readable state an agent can diff, diagnose, and extend. 7.3 Verifying “read” before replaying anything

  1. Observe: the operation occurs during ordinary UI use with method GET/HEAD, credentials=include, in ≥3 sessions across ≥2 days, with no corresponding mutation observed afterward on related resources.
  2. Reconcile: replay from page context (Runtime.evaluate same-origin fetch) returns byte-comparable (schema-hash-equal) content to what the UI consumed; UI state does not change on repeated replays.
  3. Side-effect probe: run N idempotent replays with unique etags captured; assert no new history/auth/mutation rows appear anywhere in the account's own surfaces (e.g., listed counters unchanged).
  4. Only then does the adapter set direction='read', direction_evidence={steps:[...]}, completeness='verified_read', and only then may the sync engine schedule it. Any anomaly (redirect login-wall, challenge, new field) demotes the operation and pauses dependent sync (Fail −→ §8.6 states).

Rationale: HTTP method or endpoint name proves nothing about read-only behavior; the prompt's own discipline is honored by making verified read a state machine, not an assumption.

8.4 Reconstruction rules (adapter contract)

  • Stream assembly: keyed by (account, target session, request id); chunk ledger stores offsets + hashes; dedupe on reconnect by adapter-reported event identity; if a reconnect produces a fresh stream for the same turn, the adapter links them (continuation_of) and overlap is resolved by event ids, not line counts.
  • Turn/branch boundaries: conversation → branch → turn tree is built from the family's payload semantics when the wire carries them (S-2 families, post-T-2); otherwise from UI-observed structure with reconstructed_from=ui. Regenerate = a new turn revision on the same branch point; branches keep full lineage.
  • Races & late events: identity reveals, title assignment, and votes may land after turn terminal — they are events on the conversation, applied to state projections with their own timestamps; earlier rows are not rewritten (§11).
  • Workers/SWs: payloads sourced from whichever attached target produced them; target-of-origin is recorded. A fetch seen in both page and SW sessions dedupes by request id family rules (T-2 settles which target owns truth per family).
  • Missing events ≠ invention: any absent anchor (no branch ids on wire, etc.) yields structured absence: the row stores what exists, marks the flag, and the transcript UI/MCP renders the absence explicitly.

9.2 Primary mechanics (A)

  • Account association & authority: replays execute from the account's own page context via CDP (same origin, same cookies, no credentials copied to Node) — satisfying “transiently reuse credentials issued to the correct session” without persisting copies. Node orchestrates; the browser session authenticates.

  • Listing → detail split: listing establishes the work-set (listing_coverage); details fetched per conversation with independent checkpoint so interruption never loses the boundary (§9.4).
  • Interaction with live capture: same observations pipeline (dedupe by source_ref); a live capture racing a backfill yields duplicate-watch — the later projection is a no-op update if identical, else a revision conflict in §10.5 wording — never a merge-on-similarity.

9.3 Fallbacks & degraded modes

  • B — UI traversal: a sync mode that drives the actual history UI (scroll/virtualized lists exhausted via repeated DOM+wire observation; each opened conversation harvested as a normal live capture). Rate ~ UI speed. Completeness claim: “all items the UI revealed during walk” — recorded as traversal_coverage with start/end markers, weaker than A and labeled as such.   • A': partially verified listing (cursor unstable): snapshot-window sync — freeze horizon H=now, walk until items older than previous run's newest, dedupe overlaps; mark non-contiguous regions as gaps rather than pretending order.
  • Nothing enumerable (T-5 fails): sync degrades to: (i) everything captured live from first-run onward; (ii) on-demand sync.conversation <url-supplied-by-user> for known conversations; (iii) optional export import (C) if it materializes. The archive then documents coverage as “from-date-forward + explicit additions,” never “complete.”

Composition rules (the “usable identity” view)

  1. Precedence by kind: reveal_event > selected_label > displayed_name > provider_name > blind_label > import > owner_annotation is never auto-lowered (owner words are authoritative for display but flagged as owner-sourced); inferred_analysis renders only in analysis contexts, visibly separate, with §14.5's caveats attached.
  2. Reveal handling: a reveal creates a new observation scoped to the turns it truthfully covers (typically the whole blind pair); the blind label row remains, linked (supersedes). The transcript shows “Model A → acme-orion-2 (revealed T+43s)” — one line, both facts.
  3. Never-equated: participant position ≠ blind label ≠ provider ≠ marketing name ≠ route/internal name ≠ exact build. The views only coalesce when a single observation's own evidence does (e.g., a reveal event carrying both names). Aliases are a reference table the owner curates (model_alias with provenance), used for grouping in §14 profiles — with the alias table itself versioned and shown.
  4. Conflicts: two reveals disagree, or wire-vs-UI identity mismatch → both kept; participant marked identity=disputed; appears in diagnostics; profile cohorts exclude disputed rows by default and can include them on demand with the flag shown.
  5. Temporal truth: a name seen in January is not the same backend in June (S-6 class issue); profiles bucket by observed_at windows and say so (§14.4).

What this makes impossible: silent promotion (“Model A was Orion”), silent erasure (blind state forgotten after reveal), and attribution smuggling (a selected label leaking onto a different branch than the one it was evidenced on). It also makes exports self-describing — identity data carries its own epistemics.

Chapter 12

Security, encryption & exposure

12.1 Key custody & database encryption

  • Archive key K = 32 random bytes generated at first launch (crypto.randomBytes), never on disk in plaintext. Wrapped via Electron safeStorage.encryptStringAsync (macOS Keychain; async API per docs [S12]) and stored as a small blob in the app support dir. Decryption every boot; K lives only in main-process memory. Rotation supported: rewrap K (Keychain side) without re-encrypting data.
  • Database: better-sqlite3-multiple-ciphers keyed with K in SQLCipher-compatible mode (AES-256-CBC + HMAC-SHA512 at page level, high-kdf); pragmas: cipher_memory_security=ON, secure_delete=ON, temp_store=MEMORY, WAL on with periodic checkpoint; the FTS5 index lives inside the encrypted DB (no separate plaintext index files).
  • Alternative considered and declined: FileVault-only + plaintext SQLite. Simpler, zero native risk — but fails “other logged-in users / casual file copy / unencrypted TM disk” threat cases the prompt cares about, so the SQLCipher-class path with its (bounded, tested-at-P0) native risk is chosen; fallback driver named in §5.4.

12.2 Keychain semester (honest caveat)

safeStorage docs note Keychain trust continuity wants a consistent code signature [S12]. Dev builds with shifting signatures may re-prompt. Mitigation: use one stable signing identity (a dedicated local identity or ad-hoc with fixed bundle id) across builds; document the first-run prompt; gate P0 verifies boot-to-decrypt on the owner's machine. Losing Keychain access (wipe) = archive unrecoverable → the backup flow (§10.5) offers an explicitly encrypted portable backup with an owner-chosen passphrase (separate from K) — opt-in, warned, documented.

12.3 Blob store

Large evidence payloads, raw rings, downloaded/generated artifacts: per-file key = HKDF(K ‖ blob_id), AES-256-GCM in 64 KB frames with monotonic nonces (frame index) + length header; footer tag verifies whole-file integrity; manifest row (sha256 of plaintext) detects tamper. No native crypto deps. Ring buffers are the same format with slot headers and strict quota accounting.

13.5 Untrusted content & the destructive-action guard

  1. Structural, not advisory: archived prompts/responses/tool traces live only in the archive service; the approval and account services never read archive content; there is no code path from a retrieved transcript to any authority-bearing call. 14.5 Embeddings & similarity experiments — gated, preregistered, abortable

  • Embeddings entry gate (all must hold): (i) a preregistered question deterministic stats cannot answer; (ii) corpus ≥ conversation-count where slice-Ns pass the run's own power check (computed at design time — no universal thresholds invented here); (iii) packaging cost accepted: onnxruntime-node with a pinned, hashed (SHA-256 at acquisition, recorded) small encoder (e.g. a MiniLM-class model), weights cached in the blob store, fully offline after first setup; pure-JS fallback (token overlap/MinHash) already exists, so ML must beat it on the preregistered metric to stay. Native risk of onnxruntime is the acknowledged cost; WASM SIMD backend is the fallback.
  • Similarity/fingerprinting protocol. Hypothesis class: “text T resembles cohort C.” Method commitments: leakage-resistant splits — split by conversation cluster (conversation + branches + near-duplicates found via MinHash/LSH banding, versioned params), so a paraphrase of a training item can never sit in test; prompt/topic controls via stratification on prompt-type and topic buckets; negative controls (label permutation must yield chance performance; held-out unknown-identity cohort must mostly trigger abstention, since unknown-class handling is explicit); calibration reported (reliability curves + abstention curve), not just accuracy; reproducibility: run record carries hashes of every input split.
  • Decision rule (predeclared): continue only if calibrated-abstaining performance clears the JS-overlap baseline by a preregistered margin on two consecutive windows; revise features/adapters on drift; stop when results lack scientific utility — two consecutive windows below the margin, or negative-control contamination, and the experiment is archived as “ran → stopped (reason),” which is a valid deliverable, not a failure.
  • Framing: any similarity conclusion is a confidence-qualified hypothesis about resemblance to a cohort of my own archive; it never updates observed identity (§11) and exports carry that sentence verbatim.
