Architecture & implementation plan · private, single-owner, macOS · one-run deliverable

A dedicated-browser archive for my own Arena conversations: Electron shell, CDP-level capture, per-account partitions, encrypted local ledger, MCP-first operation

This report selects one architecture for a private macOS application that lets me use arena.ai normally — in several simultaneously signed-in accounts — while it records accurate, provenance-carrying transcripts into a local encrypted archive that an LLM can browse, synchronize, analyze and administer through a local MCP server. It is a plan for AI coding agents to execute; it does not implement the application.

  • Selected runtimeElectron (single Chromium + Node) — not an extension, not WKWebView
  • Capture privilegeChrome DevTools Protocol attached before first navigation; flattened auto-attach to workers & service workers; isolated-world DOM observer
  • Account isolationOne persist: session partition + window + CDP session + capture/sync state per Arena account
  • ArchiveSQLCipher (SQLite3MultipleCiphers) in an Electron utility process; key wrapped by macOS Keychain
  • Primary interfaceLocal MCP server (stdio shim → Unix socket); GUI is diagnostics-only and shares the same service layer
  • Minimum macOS14.1 (Sonoma) — hardware floor of the target M3 Pro; Electron's own floor is lower

01The decision and why it holds

Build the archive as an Electron application that hosts one Arena browsing session per account in its own persistent Chromium partition, and derives its capture privilege from the Chrome DevTools Protocol (CDP) — attached to each account's page before its first navigation and extended to that page's dedicated workers and service workers — rather than from anything injected into Arena's page world. Everything the app persists is normalized into an SQLCipher database owned by a separate utility process that also hosts the MCP server. The GUI is a thin diagnostics client of that same service.

Why this stack, in one paragraph

The requirement that decides everything is capture privilege deeper than the existing extension: bodies of streamed responses as they arrive, WebSocket frames, worker- and service-worker-originated traffic, and no gap at navigation or target creation. Of the maintained, publicly embeddable engines on macOS, only Chromium-based shells expose an out-of-band instrumentation protocol with those properties; WebKit's public embedding API (WKWebView, therefore Tauri/Wry) has no supported way to read HTTPS response bodies outside the page world (Verified fact — Apple's documentation makes registering a scheme handler for https a programmer error, §03/§04). Between the two Chromium shells, Electron and CEF offer comparable observation depth, but Electron packages the browser, the Node runtime, per-partition sessions, download interception and process management behind a documented JavaScript API with an eight-week release train, prebuilt Apple Silicon binaries and a huge maintenance base — exactly what an AI-agent-maintained private app needs. CEF would require a C++/Objective-C++ integration layer with no maintained Swift or Node binding; it stays as a named fallback.

What "deeper than the extension" concretely means here
  • Body visibility without page patching: CDP Network events plus Network.streamResourceContent deliver streamed chunks to the app (Verified fact: method present in the tip-of-tree protocol, marked experimental — §05). The MV3 extension baseline only sees bodies by monkey-patching fetch/XMLHttpRequest in the page world.
  • Attach before the first byte: the debugger is attached to the webContents before loadURL; a content script at document_start runs after navigation has already begun.
  • Workers and service workers: Chromium's page-level auto-attacher also attaches scope-matching service workers and honours pause-on-start (Verified fact: Chromium source, §05). The baseline extension has no service-worker visibility at all.
  • Application-owned downloads and artifacts: session.on('will-download') redirects every download of an account session into the archive, with no chrome.downloads constraints and no native-messaging companion.
  • Structural account binding: every observation arrives on a CDP session bound to one webContents bound to one partition. Ownership is a property of the transport, not an inference from URLs or IDs.

  • No Arena endpoint, payload or transport is presented as verified by observation in this run; §03 separates what public bundles and the baseline extension's source show from what only a signed-in discovery run can confirm.
  • Owning the browser window is not the source of capture depth. In Electron the depth comes from CDP and session-level APIs; §04 states, for each candidate, what still depends on page injection and what can be missed.
  • The plan does not assume Arena offers an export or a documented history API. Backfill (§08) is designed around verified owner-session reads and degrades to UI traversal.

03Arena as observed: surfaces, signals, and what only a signed-in run can settle

Arena is the model-comparison platform formerly known as LMArena / Chatbot Arena; the rebrand to "Arena" at arena.ai is reported for 28 January 2026 (Verified fact that the rebrand happened and that arena.ai is the live domain — the site itself was fetched; the date rests on search excerpts of Wikipedia and secondary write-ups, which are secondary-source evidence). The product surfaces relevant here are the text Battle / Direct / Side-by-Side chat modes, the Agent mode, the code-generation surface the assignment calls "Arena Code", history search, and the leaderboard. Unrelated products named Arena are ignored.

Evidence from the public site (fetched this run)

  • Verified fact The root document is a Next.js App Router application: it ships React Server Components "Flight" payloads via self.__next_f, chunk paths under /_next/static/chunks/app/[locale]/(app)/(with-sidebar)/…, and deployment-pinned asset query strings. Consequence: page hydration data and RSC responses (text/x-component) are a payload family the catalog must classify, and every deployment can move chunk names — never key adapters on bundle names.
  • Verified fact The page preloads Google reCAPTCHA Enterprise (recaptcha/enterprise.js?render=…) and includes a ConnectedLoginModal component reference. Consequence: sign-in is a modal within the same document, and conversation-creating requests likely carry a reCAPTCHA token (the baseline's sanitizer explicitly strips "captcha values", corroborating this — Strong inference). Anti-automation scoring is therefore a first-order viability risk for any non-Chrome shell (§13, G1).
  • Verified fact Public navigation exposes /history/search and /leaderboard/agent; the rendered home screen advertises code-generation tasks ("Create a landing page", "Build a fullstack app") alongside "Battle Mode". Consequence: an owner-history search surface exists in the UI; whether it is backed by a paginated listing API is settled only by observation.

Evidence from the baseline extension's source (consulted this run)

The owner's existing MV3 exporter (musterm4nn-alt/arena-exporter, v2.1.3, verification notes dated within the last two weeks of this run) is the best available proxy for Arena's current first-party traffic because it was written against real sessions. Its source is treated as observed-by-a-third-party evidence: it establishes that these families existed when the extension was last exercised, not that they are the contract today.

Owning the window versus having privileges — per candidate

WKWebView / Tauri

Window ownership grants: navigation delegate callbacks, cookie store access via WKHTTPCookieStore, user scripts, script message handlers, download delegate. It grants no response bodies, no worker visibility, no request/response stream. Capture would be page-world patching — the baseline's technique with fewer guarantees (no webRequest metadata either). This is the case the assignment warns about, and it is why these stacks are rejected despite superior footprint.

Electron

Window ownership by itself grants only the same as above. The privilege comes from three additional surfaces: (1) CDP through webContents.debugger (Network/Target/Page/Runtime/Fetch domains, flattened child sessions); (2) session-level hooks (webRequest metadata, will-download, protocol.handle, serviceWorkers status, clearData); (3) process control (utilityProcess, per-partition renderers). What still depends on injection: rendered-state evidence (labels, votes, reveal banners) — implemented in an isolated world, not the page world. What can be missed: traffic from a renderer between crash and reload; the first request of a popup before its debugger is attached; a service worker that already existed and served the very first navigation before the page's auto-attacher picked it up (page-side events still show fromServiceWorker).

CEF

Ownership plus CefRequestContext-level handlers gives body streams for all requests in the context including SW-originated ones, and a CDP bridge per browser. Depth is at least Electron's; the cost is a C++/Objective-C++ host, CEF's release churn, and a much smaller pool of examples for agents to learn from. Downloads and sessions are first-class.

MV3 extension (+ debugger / native host / companion)

Could be improved with chrome.debugger (CDP with a persistent infobar, attach only after the tab exists, detach on DevTools use) and native messaging for archive writes — a different project, explicitly out of scope. It never gets pre-navigation attach, cannot own downloads without the companion, and lives inside a lifecycle it does not control.

An additional candidate considered: Chrome for Testing driven over browser-level CDP

Launching a stock Chromium/Chrome-for-Testing binary per account (--user-data-dir per account, --remote-debugging-pipe) from a Node supervisor gives browser-level CDP (full Target discovery, Browser.setDownloadBehavior) and the most Chrome-like anti-bot posture. It costs one full browser process tree per simultaneous account, puts the window outside the app, and moves session/download control from in-process APIs to protocol calls. It is the designated fallback A: it preserves capture depth if Electron is rejected by Arena's anti-abuse layer or if an Electron-specific CDP gap appears.

  • Archive service is a Node utility process (same Electron runtime, no second runtime installed). It is the single writer to SQLCipher, the host of all jobs and of the MCP endpoint. Restarting it does not disturb browsing; main buffers capture events (bounded) while it restarts.
  • Arena renderers run remote content under Electron's defaults (contextIsolation: true, sandbox: true, nodeIntegration: false) with no preload script at all. There is no IPC channel from Arena content to the app; the only way page state reaches the app is through CDP events, which the supervisor validates against schemas as untrusted input.
  • Diagnostics UI is a local page in its own window with a strict CSP and a minimal contextBridge; ipcMain.handle handlers verify event.senderFrame is the local UI before acting. It calls the same service commands as MCP.
  • MCP shim is a small Node script clients spawn over stdio; it connects to the service's Unix domain socket (mode 0600, inside the app's data directory) and relays MCP messages. It has no logic and no secrets.

Stream classification and body handling

On responseReceived the supervisor classifies the response by catalog op key and content type. Streaming classes (text/event-stream, text/x-component, application/x-ndjson, and the lane-prefixed text stream when identified by op key) request streamResourceContent immediately; the bufferedData return value covers bytes that arrived before the call, so nothing is lost by the round trip. Non-streaming JSON is fetched with getResponseBody at loadingFinished. If streamResourceContent is rejected (older or changed protocol), the supervisor falls back to completion bodies and flags the capture stream_progress_unavailable — content is still complete unless the buffer evicted it, which is detected by a failed getResponseBody and recorded as observer_gap(buffer_evicted).

Application-owned downloads and artifacts

  • Every account session registers will-download; the item is redirected with setSavePath into …/quarantine/<account_id>/<download_id>, progress is streamed to the service, and on completion the file is hashed, encrypted into the artifact store, linked to the conversation/turn inferred from item.getInitiatorOrigin() plus the L2 route observation at that moment, and the quarantine file is removed. No chrome.downloads, no companion host.
  • Files referenced by URL in streams (e.g., AI-SDK file parts) are fetched with ses.fetch(url, {credentials:'include'}) inside the same account session, so credentials stay browser-managed. If the URL carries a signature or token in the query string, the archive stores a safe reference (origin, path, query-key names, secret_stripped:true, content hash) rather than the URL.
  • Blob URLs generated by the page (e.g., "download JSON") surface as downloads and are handled identically.

Resource plan: quotas and measurements instead of guesses

No archive size or memory figure is assumed. The design fixes where resources are bounded and what is measured; the numbers are configurable defaults to be tuned from G1 measurements.

  • Per-account renderer: measured with app.getAppMetrics() at idle, during a two-lane stream, and after an hour of use; recorded by the harness into the diagnostics DB. A watchdog warns when total app RSS exceeds a configurable budget (proposed default: 25% of physical RAM on the 18 GB machine) and suggests closing idle account windows; it never kills a renderer with an in-flight capture.
  • CDP buffers: maxTotalBufferSize/maxResourceBufferSize set per session (proposed defaults 64 MiB / 8 MiB); streaming classes do not depend on them.
  • Capture back-pressure: the supervisor holds at most a configurable number of MiB of unacknowledged events per account; beyond that it flags observer_gap(backpressure) rather than growing without bound.
  • Evidence store: sanitized bodies compressed (zstd or gzip) and capped per record (proposed 4 MiB; larger bodies are chunked into artifacts); unknown-op samples limited to a few per op key; rolling quota per account with a diagnostics counter.
  • Artifacts: per-file cap (proposed 256 MiB) and total cap per account (proposed 20 GiB) with soft warnings; exceeding files are recorded as safe references with capture_state=skipped_quota.
  • Database: WAL, incremental vacuum, FTS5 external-content tables; growth per 1,000 turns is measured in G3 and reported.

06Discovery as a maintained capability: the protocol catalog

The first engineering objective is not "parse Arena" but "make what Arena does observable, classified and diffable". Discovery runs continuously: every first-party request seen on any account session is reduced to an operation key, classified, fingerprinted, and counted, and only the classes that need bodies retain sanitized bodies. The result is both the capture-adapter inventory and machine-readable state an AI maintainer can query through MCP (diagnostics.catalog).

Drift signals are computed on ingest: response fingerprint changes for a classified op; status-code distribution shifts (e.g., 200 → 403/429); appearance of new op keys in a conversation flow; change of a diagnostic header such as x-stream-version; parser failure rate above a threshold. Sanitizer: where sensitive data is excluded

CDP event ──▶ [1] header allow-list ──▶ [2] URL query scrub ──▶ [3] body class gate ──▶ [4] field scrub
           ──▶ [5] size cap + hash ──▶ evidence row (compressed) ──▶ normalizer
   failure at any step: keep metadata only + sanitizer_failed=true; never persist the unscrubbed payload
  1. Header allow-list (both directions): content-type, content-length, x-arena-chat-id, x-stream-version, x-session-settled, cache headers; everything else dropped. cookie, set-cookie, authorization never reach memory beyond the CDP client's frame.
  2. URL scrub: query values removed except an allow-list (limit, includeArchived, page); cursors are stored only in sync_state, not in evidence; fragments dropped.
  3. Body class gate: bodies retained only for the classes above; request bodies only for conversation.create/continue, vote, history.search.
  4. Field scrub: key-pattern deny-list (tokens, captcha, secrets, e-mail addresses other than the account's own hashed one, phone numbers), JWT-shaped and Bearer-shaped strings, signed-URL query parameters; nested JSON-in-strings is parsed and scrubbed too. Scrubbed fields are replaced by {"$redacted":"kind"} so structure survives for reparsing.

Parser and normalizer errors store the error class, adapter version and a bounded excerpt of the already-sanitized body; diagnostics never echo raw payloads. Stream reconstruction

Each streaming response becomes a stream record keyed by (account_id, CDP requestId, session id). Chunks are appended in arrival order with byte offsets. A framing adapter is selected by op key and content type (sse, ndjson, prefixed-lines, rsc-flight) and produces typed events: lane_text_delta, lane_reasoning_delta, tool_event, citation, file, heartbeat, lane_finish{reason}, stream_error, stream_abort, control{turn-complete}. Lanes map to participant slots (a, b, or single). Adapters are pure functions of bytes → events, so evidence can be re-run after fixes.

  • Turn boundaries: a user turn is the conversation.create/continue request body; assistant turns are the lanes of the corresponding response stream, correlated by request id (and by x-arena-chat-id / conversation id in the body when present).
  • Branches and revisions: if payloads carry message ids and parent ids (Hypothesis to test), the turn tree is built from them. Otherwise a regeneration is detected as a new response stream for a request that references the same prior user turn, producing a revision group; an edited prompt after an earlier point produces a new branch anchored at that point. Both fall back to positional keys with weak_key=true so later evidence can supersede them.
  • Reconnects and repeated events: streams that restart (new request id, same conversation/turn) are stored as separate stream records; the normalizer merges by lane using content-prefix matching and marks the merged turn reconnected. Duplicate frames with identical sequence markers are deduplicated by (lane, offset, hash) — never by text alone.
  • Late reveals: a reveal observed after the turn (vote response or L2 banner) creates an identity observation with the turn range it applies to; it never rewrites earlier observations (§09).
  • Navigation: the CDP session survives same-document and cross-document navigations within the webContents; a stream still open when the page navigates away is finalized by loadingFailed{canceled:true} → partial(navigated_away).
  • Workers / SW: events from child sessions carry their session kind; responses served from a service worker are recognised by fromServiceWorker and paired with the SW's own upstream fetch when both are seen, so the body is captured once from the upstream side and once as served — differences are recorded as a drift signal.
  • Missing events: gaps in byte offsets, a dataReceived without body after streaming was enabled, or a response with neither terminal record nor loading end after a timeout produce observer_gap with a reason code; the partial text is kept and clearly labelled.

Reconciling network and rendered evidence

  • Network is authoritative for text bytes and terminal records; L2 is authoritative for what the owner saw (labels, votes, reveal). When they disagree (e.g., L2 shows a model name for lane a that the network payload assigns to lane b), both observations are stored and the conversation is flagged identity_conflict for review — the baseline's label/tab mismatch becomes visible instead of silently wrong.
  • L2 observations are bound to the same account_id because the observer runs only in that account's webContents; its messages also carry the document URL and a monotonic sequence so they can be ordered against network events.
  • Rendered-only transcripts (no network payload) are stored with origin=rendered_only, lower completeness and are the primary target for a later history sync of that conversation.

Earning "read-verified" in the owner session

  1. Organic observation first. The op must have been observed being issued by Arena's own UI in this account's partition (catalog seen_count > 0 with initiator=page).
  2. Account association. Its response must contain items that the UI displayed for this account (cross-checked with L2 list entries) and no items from another account partition; the request is cookie-authenticated in the partition (no bearer token needed), otherwise the token path in §09 applies.
  3. Effective read behaviour. Method is GET or the request is documented read-only and two replays with identical parameters return identical or timestamp-only-different bodies and a subsequent organic listing shows no new or changed items and no Set-Cookie beyond session refresh is observed. HTTP method or endpoint name alone never suffices.
  4. Pagination stability. Walking two pages forward and re-requesting page one yields the same first page (or a documented newest-first shift); cursor semantics recorded (hasMore, cursor key names).
  5. Detail retrieval. For three known conversations, detail responses contain the message texts the owner sees, message ids (if any), timestamps, mode and participant/model fields; completeness of the representation is compared against a live-captured rendition of the same conversation.
  6. Owner acknowledgement. The GUI shows the evidence and the owner marks the op read-verified once; the catalog stores the evidence ids. Sync only uses read-verified ops.

Sync job design

 queued ─▶ running(list page k) ─▶ running(detail i/n) ─▶ completed
   │             │  ▲                    │                    ▲
   │             ▼  │ resume             ▼                    │
   │          paused(reason) ◀── blocked(rate_limited | auth_expired | drift | challenge | redirect | suspected_mutation)
   │             │
   └──▶ cancelled (at next checkpoint; committed pages kept)     failed(reason) after bounded retries
  • Scope: sync.start takes one account or a list; each account gets its own job with its own cursor, page index, pending-detail set, retry counters and token-bucket rate limiter. Jobs for different accounts may run concurrently (default concurrency 2) because they share no mutable state except the database, where every write is scoped by account_id; correctness does not depend on serialization. If the owner prefers, concurrency can be set to 1 — the scheduler then round-robins accounts.
  • Checkpoints: after every listing page (cursor, items seen) and after every committed conversation. Resumption re-requests the last page (overlap is expected) and relies on idempotent upserts.
  • Deduplication within an account: (account_id, source_conversation_id) is the conversation key; turns key on (conversation_id, source_message_id) when ids exist, else (conversation_id, branch_path, position, content_hash) with weak_key. Overlapping or repeated pages are absorbed. Text similarity alone never merges anything.
  • Update detection: listing fields such as updated_at/message counts (if present) decide whether a detail re-fetch is needed; otherwise a detail fetch per conversation is done on first sync and then only on explicit full:true.
  • Interaction with live capture: a conversation currently open and streaming in that account's window holds a per-conversation lock; sync skips it and revisits it at the end of the run. A previously partial live capture is supplemented, not overwritten: history-derived turns are stored with origin=sync next to live-observed turns, and the transcript view prefers complete over partial while keeping both.
  • Retries and pacing: bounded exponential backoff; on HTTP 429 or an anti-abuse challenge the job blocks with reason and a suggested wait; no automatic retry storms. Auto-sync per account is opt-in, interval-based, and uses the same job path.
  • Degradation is account-local: authentication expiry, sign-out, identity change, redirects to sign-in, drift on a history op, or any response that looks like a mutation (a listing changing after a read) block that account's job only.
  • Cross-account collisions: the same source_conversation_id appearing under two partitions is legal as two records; it is also raised as a cross_account_collision conflict for the owner to inspect (it may indicate a shared conversation or an identity mix-up). Never merged automatically.

What "synchronized" means, per account

An account is synchronized as of T when: the listing cursor was exhausted at T without a blocked state; every listed conversation has a detail state in {complete, unsupported_mode, parse_failed, detail_failed, rate_limited_deferred}; and the coverage report (sync.list_gaps) enumerates the non-complete ones with reasons. Listing coverage says nothing about conversations the listing does not return (e.g., ones Arena hides); the report states that limit explicitly. Successfully opening one known conversation proves only that detail retrieval works — never that historical coverage is complete.

If no reliable listing can be verified

Then the archive still gains: everything captured live from the moment the app is used; every conversation the owner opens from history (captured passively with full fidelity); UI-traversal fallback runs that open history entries at a paced rate with visible progress and cancel; and imports if an export appears. Coverage is reported honestly as "what was observed", and the MCP sync.status returns listing_unavailable rather than pretending completion.

Reconciliation keys and conflicts

  • Account scope is part of every unique key; identical text, ids, titles or timestamps across accounts never merge.
  • Within an account, source ids win; positional keys are marked weak and can be superseded when ids arrive (e.g., after a history sync of a live-captured conversation). Supersession keeps the old row's evidence link and records the merge in a reconciliations log.
  • Conflicts (identity mismatch between layers, cross-account collision, two complete renditions that differ) are first-class rows the MCP exposes (archive.list_conflicts); the transcript view shows the preferred rendition with the alternates.

Provenance carried by every important field

Normalized rows carry account_id, origin, evidence_ids, adapter/adapter_version, observation timestamps, and completeness. Identity observations additionally carry source and turn range. Analysis runs carry the cohort snapshot hash (the exact set of turn ids and their identity tiers), parameters and code version. Because sanitized evidence for conversation classes is kept indefinitely, every normalized field can be recomputed after an adapter change; diagnostics.reparse re-runs adapters over evidence and produces a diff report before committing.

Transactions, recovery, migration, backup

  • Transactions: evidence is committed first (small transaction per event batch); normalization runs in a second transaction per conversation update. A crash between the two leaves replayable evidence and an idempotent normalizer; on start-up a normalize_pending queue is drained.
  • Crash recovery: SQLite WAL; the service reopens, runs PRAGMA quick_check weekly and on unclean shutdown, and drains pending queues. In-flight capture states are finalized as observer_gap(service_restart) only if the event buffer in main overflowed; otherwise buffered events are delivered after restart.
  • Migrations: forward-only SQL migrations with a version table; each migration ships with a fixture DB test; a backup file is written before applying.
  • Backup/restore: the DB and artifact directory are encrypted at rest, so ordinary Time Machine copies are ciphertext; restoring them needs the Keychain-wrapped key from the same login keychain. For portability, export.backup produces a passphrase-protected bundle (Argon2id-derived key wrapping the archive key) that restores on a fresh machine. The plan does not promise erasure of external backups.

Credential handling and safe references

  • Browser-managed session persistence stays in the partition; the app never exports cookies, never imports cookies or tokens from other browsers, and never persists any credential copy.
  • If a future sync op needs a bearer token (i.e., is not cookie-authenticated), the supervisor may reuse a token observed on the account's own requests transiently in memory, scoped to that account's job, dropped when the job ends, and excluded from evidence, exports, fixtures and logs. This is the only credential path outside the browser, and the catalog marks such ops needs_token so the owner knows.
  • Signed URLs are stored as safe references (origin, path, query-key names, hash, secret_stripped:true); re-fetching happens only through the account session.

Keeping Arena content away from local privileges

  • Arena renderers have no preload, no Node, no IPC; CDP is a one-way observation channel whose payloads are schema-validated and size-capped. The L2 observer world is isolated; the binding it uses is not visible to page scripts.
  • Navigation and window-open handlers deny non-first-party top-level navigations in account windows except an allow-list for the sign-in flow (and open them in the same partition); webRequest blocks file: and app: schemes for those sessions.
  • The archive service, the key, the MCP socket and all files live outside any renderer's reach; the MCP socket is 0600 and validated as coming from the local user.
  • Isolation holds through failure: a renderer crash, a sign-out, or an identity change in one partition touches only that account's supervisor and job; another account cannot inherit its browser state (different partition), its capture stream (different supervisor), its sync authority (different job and cursor) or its destructive-action scope (ticket scope hash).

10Full LLM operability: the local MCP contract

Transport, connection model, trust boundary

  • Server: hosted in the archive service using @modelcontextprotocol/sdk, speaking Streamable HTTP (spec 2025-11-25) over a Unix domain socket at ~/Library/Application Support/ArenaArchive/run/mcp.sock with mode 0600. The socket path is the access control: only processes running as the owner can connect. Origin validation is enforced anyway (Verified fact: the spec requires Origin validation and recommends localhost-only binding and authentication).
  • Client entry: MCP clients spawn arena-archive-mcp (stdio) which relays to the socket; stdio is the transport clients are expected to support. An optional 127.0.0.1 HTTP listener with a bearer token from the Keychain exists for clients that prefer URLs; it is off by default.
  • Sessions: multiple clients may connect concurrently; each gets an MCP-Session-Id; server-initiated notifications (job progress, capture state changes) go to the session that subscribed.
  • Trust boundary: the MCP server runs where the key is; Arena renderers cannot reach it; tool results that contain archived text are marked content_origin:"archived_untrusted" and clients are told (in the tool description and in each result's metadata) that such text carries no authority.
  • Discovery: tools/list and resources/list describe every capability with JSON Schemas; a diagnostics.health resource reports which capabilities are currently unavailable and why (e.g., sync: listing_unavailable, capture: blocked(identity_changed) for acct_…), so an agent can diagnose rather than guess.

Shared service layer

Every capability is a command on the ArchiveService interface (typed request/response, zod-validated). MCP tools, GUI IPC handlers and the developer CLI are thin adapters over the same commands; semantics, scope rules and confirmation requirements are enforced inside the service, never in the adapter. Browser interactions the service needs (open a sign-in window, focus an account, navigate to a first-party URL, run a UI-traversal step) are commands the service forwards to main over the MessagePort — also exposed as tools, so no essential workflow is GUI-only.

Why the guard works, and what it does not cover

  • Authorization is a separate channel from content. A confirmation ticket can only be confirmed by a click in the app's own native window (trusted local input), bound to a hash of the exact scope shown there. No MCP call, no archived text, no diagnostic string can flip a ticket to confirmed. Tickets are single-use, expire, and are invalidated by any change to the scoped account's state.
  • Blast radius is graded. Per-conversation deletion needs confirm:true in the call and is a soft delete with a grace window visible in the GUI (restorable); account-wide and archive-wide deletion always require the ticket. Exports and annotations are non-destructive and need no ticket.
  • Content is data. Every field that originated from Arena or from diagnostics is returned under content with an origin marker; tool descriptions instruct clients accordingly. This does not make prompt injection impossible in the client — it makes the consequences bounded: the worst an injected instruction can achieve through this server is a read, an export to an owner-chosen path (exports also require an owner-configured allowed directory), or a restorable soft delete.
  • Threat model boundary. The guard protects against content-driven tool calls by an LLM client. It cannot protect against an agent that the owner has separately given full GUI or shell control; that would be an explicit owner decision, and the report says so rather than pretending otherwise.

What this corpus can and cannot support

  • Supportable: descriptive profiles of how revealed models wrote for this owner, in these modes, over a stated period; paired comparisons inside Battle/Side-by-Side conversations, where two participants answered the same prompt in the same context — the strongest design available here, because prompt, topic, history and time are held constant within the pair; drift of one model's formatting across time windows when the prompt-type mix is comparable.
  • Misleading unless controlled: cross-model comparisons pooled across unpaired conversations (prompt/topic confounding), comparisons across identity tiers (a "selected label" cohort may not be the served model), anything about models with few paired samples, comparisons that ignore hidden system prompts, decoding settings, tool availability, safety layers, aliases and routing, Arena-side post-processing, or temporal model changes behind the same public name. Each run's output lists these limitations explicitly with the cohort sizes.
  • Reporting: differences are shown with bootstrap intervals over conversations (not turns) to respect within-conversation correlation; no p-values without a pre-declared question.

Embeddings and local ML: gated

Recommendation Not in v1. Entry gate: a concrete question that deterministic statistics cannot answer (e.g., topic clustering to control confounding at scale) and at least one profile run that demonstrates the confounder matters. If entered: @huggingface/transformers in the utility process (ONNX runtime, arm64), a small sentence-embedding model chosen at that time, weights downloaded once, pinned by SHA-256, stored in the archive directory, loaded offline thereafter; preprocessing and model version recorded in every run; a reproducibility test that re-embeds a fixture set and compares vectors bit-for-bit across restarts.

Later similarity / fingerprinting experiments

Similarity of a text to an archived cohort is an unverified, confidence-qualified hypothesis about style, never proof of model identity or authorship. Inferred identity is stored only as analysis output, never as an identity_observation. Pre-declared protocol:

  1. Question and stop rule first: e.g., "can revealed models A and B be distinguished by formatting features on held-out conversations better than chance, with calibration?" plus the criteria for continue/revise/abandon.
  2. Leakage-resistant splits: split by conversation family (a conversation with all its branches and revisions, and near-duplicates by shingled-hash similarity above a declared threshold) into train/validation/held-out; never by turn.
  3. Controls: prompt-type and topic stratification; negative controls with shuffled labels (must collapse to chance); a "same model, different time window" control to detect temporal drift masquerading as identity.
  4. Models: start with linear models over interpretable features (formatting, function-word frequencies, character n-grams); report calibration (reliability curve) and an unknown class via a rejection threshold chosen on validation.
  5. Minimum evidence is learned, not asserted: learning curves on increasing training subsets; the experiment proceeds only when the curve has visibly plateaued and the held-out interval excludes chance. No universal sample threshold is claimed.
  6. Reproducibility: seeds, cohort hash, feature-extractor version and code version stored; a run can be re-executed byte-for-byte.
  7. Decision: continue if the held-out result beats controls with usable calibration; revise if only some pairs separate (restrict the claim); abandon if intervals overlap chance after the curve plateaus or if negative controls fail — recorded as a result, not deleted.
