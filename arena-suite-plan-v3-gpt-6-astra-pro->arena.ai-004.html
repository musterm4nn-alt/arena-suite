Executive architecture decision

Recommendation · v1 primary architecture
Electron (Chromium) + TypeScript application shell with per‑account persistent Session partitions and Chrome DevTools Protocol (CDP) capture attached from the main process.
One persist:arena-<partition-uuid> Electron Session per Arena account. Each active account gets its own BrowserWindow/WebContents tree, its own CDP capture coordinator, its own sanitizer/parser pipeline, and its own sync cursor. Arena renderers are untrusted content with nodeIntegration:false, contextIsolation:true, sandbox on, no privileged preload bridge, and no direct IPC to archive or MCP. All durable capture is mediated by main-process code outside page JavaScript.
If the first falsification spike demonstrates that Electron’s maintained CDP/Session surfaces cannot observe an architecture‑critical class of Arena traffic (service‑worker‑originated streamed responses, WebSocket frames carrying answer content, download bodies, or target‑lifecycle transitions that hide traffic) and a focused CEF spike shows that CefResourceRequestHandler::GetResourceResponseFilter on the IO thread can, escalate to a CEF native shell. Custom Chromium fork is last‑resort only.

Minimum supported macOS: 14 Sonoma. Rationale: Electron’s current stable line supports macOS 11+, but targeting 14 gives us (a) a known-good baseline for Apple Silicon, (b) modern Keychain and Security.framework behavior without deprecated shims, (c) the ability to use a small Swift native helper for Keychain/extended-attribute work if needed, and (d) no support debt for legacy Rosetta/Intel paths that the owner will never exercise. The owner’s development machine on macOS 27 is well above this floor.

Capture correctness is the primary requirement. Packaging aesthetics, binary size, and “native feel” are secondary. v1 is deliberately a research instrument first, a polished macOS app second.

What the application is, concretely

  • A macOS desktop shell that opens and owns one or more isolated browser windows logged into Arena.
  • A passive (non‑page‑world) network/runtime observer that reconstructs sanitized, versioned transcripts with full provenance.
  • An encrypted local archive (SQLCipher + FTS5 + encrypted blob store) with no cloud dependency.
  • A stdio MCP server exposing all archive/sync/analysis functionality to local LLM agents.
  • A deterministic analysis toolkit for studying stylometric and structural patterns without shipping model weights in v1.

Goals and non‑goals

In scope (v1)

  • Own an embedded Chromium browser; do not rely on Safari/Chrome/extensions or on exporting via Arena’s UI.
  • Simultaneous sign‑in to at least two Arena accounts with full partition isolation.
  • Accurate live capture of text‑mode Arena surfaces: battle, direct model chat, side‑by‑side, history views, stopped/failed/partial responses, branches, regenerations, revisions, votes, post‑vote reveals, titles, participant positions.
  • Backfill of the owner’s prior conversation history on a per‑account basis, subject to an explicit non‑mutation acceptance gate.
  • Local encrypted storage with per‑record provenance, full‑text search, and machine‑readable completeness states.
  • A complete stdio MCP server that every GUI action routes through; the LLM interface is primary for research use.
  • Deterministic local profiling of responses (length, n‑grams, structure, coding style, etc.) with cohort controls.
  • Explicit capture‑gap and drift diagnostics; the system must prefer saying “I don’t know” over fabricating completeness.

Explicitly out of scope (v1)

  • Any distributed backend, SaaS component, telemetry, analytics, update service, App Store submission, or multi‑user account system.
  • Support for third‑party sign‑in methods (Google OAuth, passkeys) as requirements. Email‑based sign‑in is the required path; if email‑link/OTP/MFA/CAPTCHA flows work inside the embedded browser, that is sufficient.
  • Local LLM inference or embedding models. v1 analysis is deterministic and transparent. ML/embeddings gate in later only if deterministic methods are shown insufficient.
  • Capture of other users’ conversations, scraping of content outside the signed‑in owner’s scope, or any access‑control circumvention.
  • Deleting remote Arena cloud conversations as part of local deletion (a future optional feature, but never implicit).
  • Anything that requires copying bearer tokens/cookies into the archive, logs, fixtures, or exports.

Focused comparison: Electron vs CEF

The only two serious dedicated‑browser contenders are Electron and CEF. Both use Chromium as the renderer, so Arena compatibility is essentially the same. The divergence is in the observation surface and the engineering cost.

Electron (recommended for v1)

Why it wins if it works. CDP is the public, maintained, documented observation surface for Chromium. VF Electron exposes it from the main process over a WebContents. Per‑account partitions are provided as a first‑class API VF. Downloads, service‑worker enumeration, cookie jars, and session‑level caches are all exposed. Implementation is TypeScript end‑to‑end. Coding agents can iterate quickly, tests run in Node/Vitest, and the protocol catalog and parser pipeline can live in the same language/runtime as the rest of the product.

What must be proved, not assumed.

  • CDP target auto‑attach (including workers and service workers) actually fires for Arena’s runtime and gives us either the streaming chunks or an always‑available full body at completion.
  • WebSocket frames carrying assistant content are observable via Network.webSocketFrame*.
  • Navigations, fragment changes, and history loads don’t detach the debugger mid‑conversation or orphan in‑flight chunks.
  • Electron’s persist: partition completely isolates cookies, SW registrations, and caches between Account A and Account B in practice, not only in the API doc.

CEF (escalation fallback)

Why it might win. GetResourceResponseFilter on the IO thread is a strictly more direct interception point than CDP for response bodies: every byte of every response (including those from service workers) can be filtered, including cases where no top‑level frame exists. SI There is no reliance on CDP’s “get body at end of request” model or on target‑attach races. This is a real advantage for high‑completeness capture.

Why it is not the default. Cost. CEF means C++/Obj‑C++, Chromium/CEF version management, a custom Xcode/ninja build, bespoke window chrome (or embedding CEF in a Swift host), and substantially more friction for AI coding agents that are far more reliable in TypeScript. The marginal gain in capture depth only matters if Electron’s CDP actually fails a falsification test; until then, paying that cost is premature.

Escalation trigger. The Phase 1 spike must produce a concrete counter‑example: a reproducible Arena workflow where Electron/CDP cannot observe a response, a streamed chunk, a SW‑served body, or a WebSocket frame that is observable via CEF response filtering on the same workflow. If that counter‑example is produced and is architecture‑critical (i.e., not a one‑off broken payload that can be handled by a targeted DOM supplement), escalate.

Other alternatives

  • Swift + WKWebView. Dismissed for v1. Strong security posture and low memory overhead, but the public network‑interception surface is materially weaker. WKURLSchemeHandler is explicitly not a hook for HTTPS, SI and while private APIs or a local proxy could be invented, that substantially increases implementation risk and maintenance while still not matching CDP’s richness (targets, workers, WebSocket frames, tracing).
  • Tauri / Wry. Dismissed for v1. Same WebKit interception ceiling as WKWebView; small binary size is not worth the capture‑completeness risk.
  • Custom Chromium fork. Last‑resort only. Only if Electron and CEF cannot expose a required capture primitive. Carries permanent Chromium‑merge debt. Must be justified against a specific, reproducible, unobservable traffic class.
  • Explicit export/import without embedded browser. Rejected. There is no documented official bulk export at this time, SI and ad‑hoc export would depend on undocumented endpoints discovered in the same session where we could have just done capture. Also misses live interactive capture.

The existing extension‑based recorder (rejected baseline)

The owner already maintains arena-exporter (GitHub: musterm4nn-alt/arena-exporter). It is useful as the baseline against which v1 must improve, but it cannot be the primary architecture because of the owner’s observed failure modes: incomplete/missed capture, missing partial/streamed content, dependence on page/runtime interception, extension lifecycle weaknesses (service worker suspension, missed events at cold start, navigation races), awkward artifact/download management, and the need for a companion native mechanism. v1’s dedicated‑browser design directly addresses each of these: capture happens in the main process outside the page world; partitions are app‑owned and persist independently of Chromium’s extension lifecycle; downloads are intercepted before the renderer sees them; and there is no companion split.

Trust boundaries

Hard rule

Arena’s renderer is untrusted remote content. Even after email sign‑in, even though the owner is the only user, the page runs arbitrary remote JavaScript and must not have direct access to Node, Electron main, the archive database, encryption keys, the filesystem, MCP stdio, or destructive operations.

Renderer configuration for every Arena WebContents RC:

new BrowserWindow({
  webPreferences: {
    partition: accountPartition,        // persist:arena-<uuid>
    sandbox: true,
    nodeIntegration: false,
    contextIsolation: true,
    webviewTag: false,
    preload: path.join(__dirname, "preloads/arena-untrusted.mjs"),
    // The preload exposes ZERO archive APIs. It is only used to:
    //  - inject a deterministic user‑agent shim if absolutely required (avoid)
    //  - forward UI‑side supplementary events (e.g. visible reaction) to main
    //    via a STRICT, typed, non‑returning "observe only" channel
    //  - install navigation‑blocking overrides
    allowRunningInsecureContent: false,
    enableRemoteModule: false,
  },
});

Navigation policy for each Arena WebContents is allowlisted in the main process. Only the Arena first‑party origin (and Arena’s documented auth/cookie/CDN origins as discovered in the protocol catalog) is permitted. External links open in the system default browser, not in the Arena partition.

New windows and popups (email‑link sign‑in often opens a popup or new tab) are routed via setWindowOpenHandler and new-window/did-create-window events into a new BrowserWindow assigned to the same account partition as the parent. No cross‑partition window adoption is allowed.

The trusted UI renderer (diagnostics, account manager, archive viewer, sync controls) is a separate renderer that never loads Arena URLs. It communicates with the main process through a strictly allowlisted, versioned IPC surface defined by TypeScript discriminated unions; there is no invoke("eval", …) escape hatch. The trusted renderer never receives captured bearer tokens; it only receives sanitized view models.

Simultaneous multi‑account isolation

Isolation is the responsibility of the main process, not of Arena’s UI. Each account has its own full stack:

Figure 2 — One isolated partition per Arena account

Partition IDs use opaque UUIDs generated on account creation. We do not derive partition names from emails, usernames, or other PII, to avoid leaking identity into partition paths or logs. The mapping from UUID to a human label lives in an internal, encrypted table only.

Sign‑in, MFA, OTP, CAPTCHA, and email‑magic‑link flows all happen inside the partition’s BrowserWindow (popups opened by Arena are adopted into the same partition). If Arena presents a CAPTCHA, that account enters auth_state: NEEDS_OWNER_INTERACTION; the capture coordinator for that account pauses and sync jobs for that account back off, while other accounts continue unaffected.

Two accounts may sync concurrently. The sync coordinator runs separate job queues per account and uses separate CDP/network sessions, so there is no cross‑account cookie reuse, no cursor mixing, and no rate‑limit state sharing. The only shared resource is the SQLCipher write connection, which serializes writes per transaction; this is fine.

Capture pipeline

Capture is outside page JavaScript. The primary transport is main‑process CDP instrumentation, supplemented by session‑level events (will-download, service‑worker lifecycle hooks), with DOM/probe evidence as a secondary channel used solely for reconciliation and UI‑only events (e.g., an owner‑visible vote animation that has no network correlate). DOM probes must never be the sole authority for a completed response.

Critical falsification target

Whether Arena uses chunked streaming fetch (read by page JS as ReadableStream) vs WebSocket vs EventSource per surface is HT. For streaming‑fetch responses, we will get Network.dataReceived and a final getResponseBody that returns the full body (decompressed, per CDP semantics). However, if Arena uses a WebSocket or a worker‑mediated channel for answer tokens, we must confirm Network.webSocketFrameReceived fires for those frames across targets, including dedicated/shared workers. Sanitizer

The sanitizer runs before any durable persistence. It is a fail‑closed component: if it cannot confidently classify a header/field, it redacts it. The redactor applies to request headers, response headers, cookies, URL query parameters, post bodies, and stored raw captures.

  • Redact by default: Authorization, Cookie, Set-Cookie, X-CSRF*, X-Auth*, bearer tokens, session IDs, any *.arena.ai cookie value, OTP/password fields in post bodies, OAuth code/state parameters, signed URLs with known sensitive sig/credential parameters.
  • Retain: HTTP method, URL (with query parameter allowlist/redaction), response status, mime type, timing, resource type, frame/target/session identifiers, protocol family, sanitized body bytes, content‑length where available.
  • Retain a stable salted hash (per archive, HMAC‑SHA256) of known-safe identity fields only when necessary for dedupe or join; never reverse‑lookup identity from a hash is not an offered feature.
  • Never write a HAR file to disk. Never log headers at debug level in production. In‑memory capture buffers are zeroized after the sanitized observation is persisted.
  • The sanitizer has versioned rule sets. Each sanitized observation is tagged with sanitizer_version so that reprocessing is possible if a rule is found to have leaked.

Protocol catalog

Discovery is a first‑class product capability, not a one‑time RE step. The catalog is a machine‑readable registry that records every first‑party operation observed, how to parse it, what confidence we have, and how to detect drift.

// packages/protocol/src/types.ts interface ProtocolCatalogEntry { entry_id: UUID; account_partition_id: string; // scoped; separate discovery per partition template url_family: string; // e.g. "/api/chat/stream" (path template, no secrets) method: "GET" | "POST" | "PUT" | "DELETE" | "WEBSOCKET" | "EVENTSOURCE"; transport: "fetch" | "xhr" | "ws" | "sse" | "nav" | "download"; direction: "request" | "response" | "both"; mutation_class: "read" | "suspected_mutation" | "unknown"; // must be empirically validated for sync ops schema_family: string; // e.g. "arena.chat.stream.v1" — refers to parser parser_adapter: string; // e.g. "ChatStreamParserV1" parser_version: string; capture_mechanism: "cdp-network" | "cdp-websocket" | "cdp-sse" | "session-download" | "dom-probe"; covering_targets: Set<"page" | "dedicated-worker" | "service-worker" | "shared-worker">; first_observed_at: Instant; last_observed_at: Instant; sample_count: number; drift_status: "current" | "drifted" | "unknown"; completeness_note: string; evidence: Array<EvidenceRef>; }

The catalog is not read from Arena source maps or spoofed from UI; it is built from sanitized observed traffic. New or drifted operations surface in diagnostics and do not crash the capture pipeline; their payloads are retained in sanitized form under drifted state for later parser development.

Capture completeness model

Every captured response and every conversation turn is tagged with a machine‑readable completeness state. We never silently label partial or inferred content as complete.

type CaptureState = // Lifecycle of a single operation/response: | { kind: "live-streaming"; start_observed: true } | { kind: "completed"; end_reason: "normal" | "stopped-by-owner"; bytes: bigint } | { kind: "failed"; reason: "network" | "server" | "parse-error" | "capture-error" } | { kind: "partial-missing-start"; bytes_present: bigint; reason: string } | { kind: "partial-missing-end"; bytes_present: bigint } | { kind: "parser-unsupported"; parser_adapter: string | null } | { kind: "schema-drift"; parser_version: string; note: string } // Reconciled / provenance states at the record level: | { kind: "reconciled-network-and-dom"; evidence: [ObservationRef, ObservationRef, ...ObservationRef[]] } | { kind: "network-only"; caveat: string | null } | { kind: "dom-only"; caveat: string } | { kind: "backfilled"; via: "authenticated-read" | "ui-traversal" } | { kind: "conflicting-evidence"; refs: ObservationRef[] };

These states propagate up to conversation/turn views. The MCP surface exposes them directly; the UI shows “incomplete”/“drifted”/“conflicting” badges rather than hiding them.

Reconciliation

Network observations and DOM/UI observations are separate, immutable observations. They are joined by the reconciler, which produces normalized records but never discards raw observations. Principles:

  • Idempotent ingestion: the same observation (keyed by a stable observation UUID derived from partition + requestId + monotonic capture counter) can be delivered multiple times without duplicating state.
  • Out‑of‑order delivery is allowed; observations are stamped with a fine‑grained capture sequence per partition and reassembled by sequence, not arrival order.
  • Stronger provenance beats weaker: a main‑process CDP Network observation beats a DOM probe observation. A direct getResponseBody beats an inferred token stream. A reveal event is a separate identity observation and does not retroactively rewrite earlier records (see §8).
  • Conflict is a first‑class state; two contradictory observations produce a conflicting-evidence record that is visible in diagnostics, not silently averaged.
  • Navigation does not lose history: observations are scoped by navigation/target IDs that persist in the archive even after the WebContents navigates away.

Model identity (never flattened)

Arena routinely masks model identity (blind battles, post‑vote reveals, routing changes). A single “model” field on a turn is the wrong schema. We model identity as a time‑series of observations attached to a participant.

interface IdentityObservation { observation_id: UUID; local_account_id: UUID; conversation_id: UUID; // internal arena_participant_key: string; // e.g. "A", "B", "sidecar:model-X", "direct" applies_to_scope: { turn_id?: UUID; branch_id?: UUID; revision_n?: number; from_instant: Instant; to_instant: Instant | null; }; source: "selected-label" | "battle-blind-label" | "post-vote-reveal" | "route-field" | "provider-label" | "owner-annotation" | "stylometric-inference"; mechanism: "cdp-network" | "dom-probe" | "sync-read" | "owner-input" | "analysis"; value: { marketing_name?: string; provider?: string; route_id?: string; blind_position?: "A" | "B"; }; confidence: ; // 0..1, not a probability; a coarse agreement score superseded_by: UUID | null; observed_at: Instant; }

Rules:

  • Stylometric inference is the weakest source. It can never overwrite or supersede a network‑observed or post‑vote‑revealed identity. It is stored as an analysis result that references an observation, not as an identity observation with elevated confidence.
  • A post‑vote reveal creates a new observation; earlier “blind” observations remain valid for their time window, supporting later analysis of blinding effectiveness.
  • “Same text as before” is never evidence of identical model identity.
  • When rendering a transcript, the UI/MCP can ask for the identity observation as of a given timestamp; it does not return a single denormalized string that silently absorbs later reveals.

History backfill / synchronization

Backfill is a separate subsystem from live capture. It uses the same sanitizer/parser/reconciler stack but runs as an explicit per‑account job. The crucial acceptance gate is non‑mutation.

Backfill gate

We do not trust the HTTP method, URL shape, or payload. An endpoint is only treated as read‑only after an owner‑session test that performs a known set of requests and verifies: (a) no new conversations appear in the owner’s Arena history list, (b) no existing conversation’s content changes (checked via a second listing), (c) no titles/metadata are altered, (d) no votes, stars, or archive flags change, (e) rate‑limit/error behavior is as expected. Until that test passes for a given endpoint family, we do not call it during sync; we fall back to UI traversal or skip with a diagnostic.

Preferred sync strategy (if gate passes)

  1. Use stable authenticated first‑party list and detail reads, observed in the protocol catalog, replayed through the account’s own Electron Session (via ses.fetch bound to that partition, preserving cookies without copying them out).
  2. Fetch in small bounded pages, respect observed rate limits, persist a per‑account opaque cursor (likely a high‑water‑mark timestamp + conversation ID pair, plus a de‑duplication bloom of the last window).
  3. For each conversation id, fetch detail; feed the response through the same parser pipeline as live captures.
  4. Re‑use identity, participant, and reconciliation logic from live capture.
  5. Idempotent: re‑running sync over known IDs is a no‑op at the record level; new observations are written only if they add information (e.g. a later reveal or an edited title).

Fallback

If no stable read API is found (or some API is gated behind mutation), perform bounded UI traversal: in the account’s BrowserWindow, navigate through the history UI, scroll to load, open conversations one at a time, and capture the resulting network traffic + DOM. This yields lower completeness (some threads may not load on demand) and is so labeled. Fallback sync is clearly distinguished from API sync in provenance.

Sync job semantics

  • Per‑account, cancellable, resumable; expose progress, cursor, last error, and coverage estimate via sync.status.
  • Two accounts can sync concurrently because each uses its own session/partition/queue; the only shared resource is the DB write lock.
  • On auth expiry, CAPTCHA, or forced sign‑out, the job pauses and surfaces NEEDS_OWNER_INTERACTION; other accounts continue.
  • On rate limiting, apply exponential backoff scoped to that account; never share backoff state across accounts.
  • On source‑ID collision within one account, dedupe; cross‑account collisions are not merged (see §6).
  • “Synchronized” means: for that account, we have observed the list window our cursor covers and attempted detail retrieval, and we have a known‑gap list for items where detail fetch failed or is unsupported. It does not mean “all of Arena history is on disk,” which would be unverifiable.

Data model & storage

We use a hybrid design: a normalized current‑state layer for efficient listing/search, plus an immutable sanitized observations table for provenance, drift detection, and parser reprocessing. We do not adopt full event sourcing of every UI micro‑event; that is overkill and would bloat the DB. But we do not denature observations to the point that re‑parsing is impossible.

Storage implementation notes

  • Use better-sqlite3 with SQLCipher support (the @journeyapps/sqlcipher fork or a built native binding; package choice is validated in Phase 0 for Apple Silicon compatibility). Synchronous API; much easier for Electron main‑process use and transactional correctness.
  • Run with PRAGMA journal_mode=WAL, PRAGMA temp_store=MEMORY (or build with SQLITE_TEMP_STORE=2 to avoid plaintext temp files), PRAGMA foreign_keys=ON.
  • Full‑text search: FTS5 with a dedicated external‑content table tied to the revision.text_content column (and to user prompts). FTS index lives inside the encrypted DB and is encrypted with everything else. VF (SQLCipher encrypts all DB pages including FTS pages).
  • All write paths use immediate transactions; long‑running analysis jobs copy snapshots through a read‑only connection so they don’t block ingest.
  • Schema migrations: apply sequentially at startup; each migration is numbered, runs in a transaction, and records its hash in schema_migrations so downgrades are detected explicitly (not silently).
  • Parser reprocessing: a “reparse from observations” job can rebuild normalized tables from sanitized observations without live capture, for one account or all. Observations have a TTL (configurable, default long) after which they can be purged; until then they enable drift recovery.
  • Backup/restore: document how to copy the SQLCipher file + blob directory while the app is locked; offer an explicit “export backup bundle” that wraps the DB with a one‑time export key derived from the archive key. The app does not write unencrypted backups implicitly.
  • Deletion cascades are explicit per local_account_id or per conversation_id; no accidental cross‑account cascade. FTS entries are removed in the same transaction as source rows.

Encryption, deletion, OS concerns

Key management

  1. First launch generates a 32‑byte random archive master key with SecRandomCopyBytes.
  2. Store that key in macOS Keychain under an application‑specific service name (com.<owner>.arena-archive.master-key) with ACL set to the app’s code‑signature identity, not to “all applications.” Treat it as a generic password item with no descriptive label.
  3. Open the SQLCipher database with that raw key (PRAGMA key = "x'...'";). Do not use a human passphrase as the primary key.
  4. Rotate the archive key by re‑encrypting (SQLCipher ATTACH with new key + sqlcipher_export) on explicit user action only.
  5. Per‑artifact DEKs are random 32‑byte keys wrapped by the archive master key (AES‑256‑GCM with a random nonce, stored alongside the blob). This makes it possible to share/artifacts without giving away the master key, and cheap to re‑wrap if the master rotates.

Plaintext exposure realism

The archive DB is encrypted at page level and WAL/rollback journals are encrypted when temp_store=MEMORY is set. VF Residual exposure exists at the following layers; we call each out explicitly rather than promising “zero exposure”:

  • Browser profile directories. Each persistent persist:arena-<uuid> session stores cookies, localStorage, cache, and service worker registrations on disk under Electron’s userData tree. This is not the archive DB; it is Chromium’s normal persistent state. It is protected by macOS Unix permissions (the owner’s home directory) plus FileVault full‑volume encryption (recommended, outside our control). It is not encrypted by the archive key. We do not copy or export cookies from here. If the owner wants the partitions cleared, they can sign out / clear data per account; this does not delete archived transcripts (which are a separate, app‑owned artifact).
  • Process memory. While the app is running, decrypted records exist in the Electron main process heap, in sanitizer buffers, and in the analysis worker. We keep decryption on demand (don’t hold full DB text in memory), zeroize sensitive buffers where possible, and rely on the OS to protect memory. SQLCipher zeroizes its internal buffers where possible. VF
  • Swap / memory pressure. macOS may page to disk; encrypted swap is a system setting we can encourage but not enforce. In‑memory temp stores for SQLCipher avoid plaintext temp files.
  • Diagnostic logs. All logging is through a structured logger that enforces a redaction list (same sanitizer rules) at the transport boundary. Debug logs must never include full headers/bodies. Crash reports (e.g., crashpad) are disabled by default for the private build or configured to exclude memory dumps.
  • Spotlight. Store user data under ~/Library/Application Support/<appid>/, with an .noindex marker on the archive directory, and set the NSURLIsExcludedFromBackupKey if/when we want to control Time Machine scope per directory.
  • Time Machine / backups. We cannot control already‑taken Time Machine snapshots or external backups the owner has made. Deleting local data from the live archive does not purge snapshots. We document this and offer a “prepare for snapshot deletion” checklist (delete account + re‑key DB) in the UI.
  • Exports. Exports (JSON / text / markdown bundles) are written encrypted by default if the owner chooses; plaintext export is allowed only with an explicit warning because once written, the owner controls the file.

Deletion

Three levels, all requiring an explicit destructive‑intent token (never issued from Arena content, never from archived text):

  1. Delete one conversation: scoped to (local_account_id, arena_conversation_id); removes normalized rows, observations (retained? optional: per‑account retention policy), FTS entries, analysis references, and blob references. Sync cursors are updated so a future sync does not re‑pull it if it still exists server‑side (unless owner explicitly asks to re‑sync).
  2. Delete all archive data for one Arena account: removes every row scoped to that local_account_id, all its blobs, its sync checkpoint, its catalog entries, but does not automatically clear the Electron partition (cookies etc.) or delete cloud data. Partition clearing is a separate explicit action (since the owner may wish to keep the login but wipe the archive, or vice versa).
  3. Delete the whole archive: removes DB, all blobs, all analysis runs, all catalog state, but does not delete partitions unless explicitly chosen (it’s an additional checkbox, destructive, requires re‑type).

Destructive intent protocol RC:

// Client (trusted UI or MCP tool called by a trusted agent acting for the owner) // Step 1: request a nonce‑bound intent intent = archive.prepare_delete_{conversation|account|all}({ scope: { conversation_id } | { local_account_id } | {}, owner_reason?: string }) // Response: intent { token, scope_summary, nonce, issued_at, expires_in_s } // Step 2: confirm with exact token (NOT something from Arena content) archive.confirm_delete({ token }) // Backend re‑validates that the token is unexpired and matches a prepare call // and that the caller's trust level is trusted UI or trusted MCP peer (stdio). // The token is single‑use; confirmation runs the deletion in one transaction.

Archived data itself (conversation text, Arena‑sourced messages) cannot mint or satisfy a token. MCP calls for destructive operations are only available over the local stdio transport (no HTTP), and the server rejects them unless the effective caller is the owner‑launched MCP client bound to the same code‑signed app.

OS integration notes

  • Code sign with the owner’s Apple Developer ID; Hardened Runtime; sandboxed? No — not App Store, but use the Hardened Runtime library validation and set appropriate entitlements. Specifically, do NOT add com.apple.security.app-sandbox unless necessary, because Electron’s network/process spawning and Keychain access get more complex; as a private app, this is a deliberate trade.
  • Keychain sharing groups are not needed (single app).
  • Use macOS system proxy settings via Electron’s default; no custom proxy.
  • Disable all auto‑update mechanisms (Sparkle, electron‑updater) in v1 since there is no distribution channel.

MCP / LLM interface (primary)

Every GUI action routes through the same application service layer that MCP calls into; there is no separate “GUI backend” and “LLM backend.” The MCP server is a stdio server launched as a child process of the Electron main (or a thread/module in the main process — either is acceptable, but a separate child process provides better isolation; if in‑proc, ensure a JSON parser bug in MCP can’t corrupt the main process event loop).

Transport choice

stdio, line‑delimited JSON‑RPC. VF The MCP spec recommends stdio wherever possible, and for a private local app stdio has the right properties: no listening socket, no DNS rebinding surface, no CORS concerns, and the MCP client is launched by the same owner account so OS permissions apply. Streamable HTTP over loopback is an optional future transport for attaching remote‑controlled agents, but v1 should not default to it.

Local analysis (deterministic first)

v1 analysis is transparent and reproducible. Runs happen in a separate Node worker process (or a child forked from Electron main) that opens a read‑only connection to the SQLCipher DB. Results are written to analysis_run and keyed by the deterministic hash of the input cohort + profile version, so re‑running the same profile on the same data yields the same run_id and does not duplicate rows.

v1 profile catalog

  • Length: chars, words, paragraphs; per‑turn and per‑revision; distributions by mode and identity.
  • Sentence/paragraph: mean/median length, variance, by participant position.
  • Code blocks: count, total lines, language labels (if we can infer from markdown fences), code/prose ratio.
  • Lexical diversity: type/token ratio over a rolling window; hapax legomena fraction.
  • N‑grams up to n=6 (configurable), with stop‑word handling and a “phrases” view that filters to sentence‑initial and sentence‑final n‑grams (opening/conclusion habits).
  • Punctuation: em/en dashes, colons, semicolons, exclamation marks, parentheticals, em‑dash vs comma ratios, bullet usage, ordered/unordered list frequency, table frequency.
  • Casing: capitalization patterns, all‑caps emphasis, camelCase/backtick usage.
  • Markdown habits: heading levels, fenced‑code usage, blockquote vs indented, bold/italic frequency, link/citation patterns.
  • “Qualification / hedging” lexicon: count of a curated (and versioned) list of phrases (“it depends”, “likely”, “may”, “might”, “generally”, “typically”, “usually”, “I think”, “as of …”, etc.).
  • Refusal/apology markers: curated list.
  • Transition phrases: curated list and discovered n‑grams that occur sentence‑initially.
  • Structure: number of sections, presence of “Here’s …”/“Sure,”/“Let me …” openers, sign‑offs.

Every result set reports cohort composition: account(s), mode(s), date range, sample counts, number of turns excluded due to capture state below min_completeness, identity‑source filter, and a “selection bias” advisory noting that this is a single owner’s data.

Major confounders explicitly surfaced

  • One user: the distribution is conditioned on the owner’s prompt patterns, not on world‑scale diversity.
  • Topic and prompt correlation: “this model is more polite” might really be “the owner asks this model for softer topics.”
  • Hidden system prompts and preambles that shape style even before the model begins.
  • Decoding parameters unknown to us (temperature, tool use) and variable routing; a single marketing label may correspond to multiple runtime configurations.
  • Arena post‑processing (markdown normalization, censor filters, formatting) that is not the model’s raw output.
  • Temporal drift: model updates, routing changes, Arena UI changes that move in calendar time.

Later modalities & fingerprinting experiments

Text is v1; extension points exist

The archive already treats artifacts as first‑class entities with the same provenance as text. Adding later modalities is a matter of writing new parser adapters that consume observations already captured, plus new artifact kinds:

  • Search results / citations. Arena’s web/browse tool calls, citation panels, source snippets. Capture via CDP Network; associate citations with revision_id.
  • Arena Code generated files. Downloaded files via will-download or fetches of zip bundles; store as encrypted blobs; index names/paths; capture previews separately if rendered.
  • Images / video / workflow artifacts. Same artifact model; store metadata (size, dimensions, MIME) inline; bytes in blob store.
  • Agent sessions & tool traces. Dedicated tables for tool calls, inputs/outputs, with capture_state and their own identity scoping (tool invocations do not inherit the assistant model identity silently).
  • Uploads. User uploads (files, images) are artifacts too, captured with the same provenance chain.

We do not build a universal “content graph” in v1. We add modality‑specific adapters only as evidence from the protocol catalog justifies it.

Fingerprinting experiments (post‑v1, gated)

Stylistic similarity is a hypothesis, never proof of identity. Any later fingerprinting work must satisfy:

  • Held‑out splits by conversation (not by turn); branches/near‑duplicates kept in the same split to avoid leakage.
  • Prompt‑type and topic controls (stratified sampling, not random sampling).
  • Negative controls: include participants with known identical routing (same model, same system prompt) to measure false‑positive rates; include participants known to differ to measure separation.
  • Unknown‑class rejection: the classifier must produce an “I don’t know” rather than forcing a label.
  • Temporal validation: train on earlier windows, test on later windows, because model updates are expected.
  • Reproducible preprocessing (tokenization, normalization, hashing) pinned by version.
  • Hard separation between observed/revealed identity (ground truth for evaluation) and inferred identity (analysis output). Inferred identity never writes to identity_observation as if it were observed.

There is no universal minimum sample count; empirical power analysis on the owner’s actual data determines whether an experiment is worth continuing. If calibrated classifiers perform no better than a simple n‑gram baseline with topic controls, the right answer is to stop rather than add more parameters.

Embeddings / local ML

Ship no embeddings model in v1. Add one only if a concrete analytical question (e.g. clustering by semantic intent, or near‑duplicate detection across branches) is not answerable with deterministic methods, and only after measuring the storage/compute cost on the M3 Pro/18GB target (with a strict quota; llama.cpp/Core‑ML‑accelerated small embeddings may be acceptable if they stay under ~200 MB resident and use <1 GB/s bandwidth during analysis). The capture pipeline itself does not depend on ML.

First falsification spike (Phase 1)

The first engineering activity is not building the app. It is a minimal harness whose sole purpose is to attempt to disprove Electron’s suitability. The spike is required before any commitment to the Electron architecture. If Electron fails, we pivot to CEF quickly rather than discovering this after months of work.

Spike harness

A minimal Electron app (separate from the main monorepo, under spikes/electron-falsify) that can:

  • Take a --partition-suffix argument and open a BrowserWindow with persist:spike-<suffix>.
  • Attach CDP before loadURL, enable the domains listed in §7, and log every event (through the sanitizer!) to a line‑delimited JSON file on disk, one file per run per partition.
  • Auto‑attach to worker/service‑worker targets and duplicate the observers.
  • Install a minimal will-download handler that records download metadata and captures the body to a temp directory (bypassing the page).
  • Support a “two‑account” mode that opens two windows with different partitions simultaneously.
  • Expose a tiny HTTP control endpoint on loopback for driving test scripts (start/stop/save log).

Testing strategy

Synthetic tests (run everywhere, no credentials)

These use generated fixtures and MUST NOT contain real owner data.

  • Stream reconstruction from chunked dataReceived events (including pathological splits: mid‑UTF8, mid‑JSON-token, mid‑SSE event).
  • Duplicate and out‑of‑order observations; idempotent ingestion; replay of same observation N times.
  • Reconnect / target‑reattach scenarios; orphaned in‑flight events after navigation.
  • Truncated streams at every byte offset (to ensure partial states are always detected, never silently “completed”).
  • Parser drift: payloads from future schema versions must produce drift records, not crashes.
  • Sanitizer redactor: feed it known cookie/header/token payloads and verify redaction; feed it benign bodies and verify content preservation.
  • Account‑ID collision attempts: two observations with same arena_conversation_id under different local_account_id must NOT merge; same under same account must dedupe.
  • DB crash recovery: simulated power loss (kill process mid‑transaction); verify WAL recovery does not corrupt; verify encryption still works.
  • Deletion: deleting one conversation/account/all removes rows, FTS entries, blobs, and cannot be accidentally triggered from archived content.
  • Migration: migrate a DB from N‑1 to N; verify round‑trip; verify down‑level DB detected on startup.
  • Corrupted encrypted blobs: a single bad blob does not crash analysis; it is reported and skipped with an error marker.

Platform tests (Electron/CDP surface, no Arena auth)

Use a local HTTPS test server (self‑signed cert added to the Electron session for the test) to verify that our platform behavior matches our expectations independently of Arena:

  • Chunked streaming responses (text/event-stream, NDJSON, WebSocket, fetch with ReadableStream) are all captured by CDP as expected.
  • Dedicated and service workers issuing fetches generate observable events on attached targets.
  • Persistent partitions really persist cookies/localStorage across relaunch, and different partitions really don’t leak state.
  • will-download hands us full bytes for binary downloads.
  • Navigation, popup handling, and new‑window adoption into the same partition work as documented.

Authenticated owner‑session acceptance tests

These run only on the owner’s machine against the owner’s real accounts, after informed consent, and are what the phases gate on. They cannot be replaced by synthetic tests because they verify claims about the actual Arena service.

  • The Phase 1 checklist (§15) is the first set.
  • Phase 3 live‑capture acceptance for each text mode.
  • Phase 5 backfill non‑mutation test and sync correctness test.
  • Phase 6 coverage of battles, reveals, branches, code, etc.

These tests write only sanitized output to the test results directory; never persist raw credentials or cookies into fixtures. The test harness imports the same sanitizer used in production.

Failure behavior scoping

  • One parser drifts → retain sanitized unknown observation, mark adapter degraded, surface in diagnostics.drift.
  • One account signs out → pause that account’s capture/sync authority; other accounts continue; no cross‑account wiping.
  • One account gets CAPTCHA → set auth_state: NEEDS_OWNER_INTERACTION, pause its jobs, surface via UI and accounts.needs_owner.
  • Rate limiting → bounded exponential backoff per account; never global.
  • Account identity appears to change mid‑session (e.g. cookie reassignment is suspected) → halt capture for that account and mark identity‑conflict; require owner verification before resuming; no silent rebinding.
  • Ambiguous source ID within one account → record conflict; never cross‑account merge.
  • Sanitizer failure (unknown credential shape detected) → fail closed; the raw observation is NOT persisted; a “redaction failure” diagnostic is recorded and the request is marked unsaved.
  • DB unavailable (SQLCipher open fails or write fails) → stop durable ingestion; do not silently continue with “in‑memory capture”; UI shows critical state; capture resumes only after DB is healthy.
  • MCP client disconnect → jobs continue; clients can re‑attach and observe via jobs.get. Explicit cancellation is required to stop a job.
