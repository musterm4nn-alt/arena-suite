Arena Model Archive
An owner-side, browser-owning capture, provenance and analysis platform for Arena

A dedicated-browser macOS application that keeps Arena as the authoritative product surface, records the owner's own Arena conversations with explicit provenance and completeness semantics, backfills existing history where the owner's authenticated session permits it, stores everything locally under SQLCipher + Keychain, exposes effectively all functionality to an LLM over MCP, and later supports deterministic local model-behavior analysis.

1Executive architecture decision

Decision

★ Recommendation Build v1 as a TypeScript Electron application that owns a Chromium browser runtime, with one persistent Electron Session partition per Arena account and a main-process Chrome DevTools Protocol (CDP) capture coordinator attached as early as possible to each Arena WebContents.

★ Recommendation Treat capture correctness as an acceptance gate, not an assumption. A minimal Electron harness (§21) must demonstrate that Arena's real traffic classes are observable before any product code is written on top.

★ Recommendation Define the reversal now: if that harness proves an architecture-critical traffic class is not reliably observable through maintained Electron/CDP surfaces, and CEF's native GetResourceResponseFilter does observe it, the architecture escalates to CEF (§4.4). A custom Chromium fork is a last resort only.

★ Recommendation Storage is SQLCipher-backed SQLite plus an encrypted blob store, keyed by a random archive key held in macOS Keychain. The LLM interface is a stdio MCP server sharing one application service layer with the GUI. v1 analysis is deterministic and transparent; no local ML.

1.1The problem, stated precisely

Arena is a web product the owner uses through a browser. The owner wants two things at once: to keep using Arena normally, and to hold an accurate local record of their own conversations that is good enough to study model behavior over time. The existing recorder — a Manifest V3 extension with a native companion — is the rejected baseline (○ prev-run evidence): capture was incomplete, stream segments were missed, artifact/download handling was awkward, and the whole design depended on page-adjacent interception plus extension lifecycle behavior.

The hard requirement is therefore not "record a webpage." It is: own the browser environment, and obtain an observation surface that is materially deeper than a content-script extension can reach, while keeping Arena's own authentication UI authoritative and keeping two or more Arena accounts signed in and usable simultaneously without any possibility of cross-account contamination.

The distinction that shapes everything below

Owning the browser window is not the same as holding deeper capture privileges. Embedding Arena in an app-managed window only helps if that embedding grants a capture mechanism that page JavaScript cannot reach or defeat. For every candidate architecture, §4–§5 states exactly which capture mechanisms exist outside page-world JavaScript. Where a mechanism is unproven against real authenticated Arena traffic, it is labeled as such rather than asserted.

1.2What the v1 release must cover

The first complete release handles Arena battle, direct-model, and side-by-side modes for text conversations, including completed, intentionally stopped, failed, and partial responses; conversations reopened from history; history views and observable search/pagination; blind participant labels and post-vote reveals; titles, timestamps, Arena source IDs, branches, revisions, and regenerations; per-record capture/completeness state, provenance, and owning Arena account. Structure is preserved — the archive never flattens a comparison into an alternating transcript (§13).

1.3Explicit non-goals

  • No App Store submission, public distribution, hosted backend, telemetry, analytics, updater infrastructure, or multi-user account system.
  • No access to other users' Arena data, and no enumeration of Arena infrastructure beyond what the owner's own sessions legitimately touch.
  • No cookie/token import from Safari, Chrome, or any other application.
  • No "bypass" of Arena access control. Undocumented first-party endpoints reached with the owner's own live session are authenticated first-party reads, not access-control workarounds (§2.3, §12.1).
  • No Google OAuth, passkey, or other third-party sign-in requirement. Email sign-in inside the embedded browser is the required, authoritative workflow.
  • No local ML/embeddings in v1 (§17.4).

3Why Electron is recommended — and the exact reversal condition

3.1The four properties the browser layer must supply

  1. A capture mechanism outside page JavaScript. The recorder must not depend on code running in the Arena page world, because that is precisely the tier the existing extension already occupies and precisely the tier that misses data.
  2. Coverage of streaming transports. Model output arrives incrementally by some mechanism; whichever it is, the capture layer must see the wire-level events, not a DOM diff.
  3. Coverage of non-frame request origins. Service workers, dedicated workers and other non-page targets must not silently vanish from the observation surface.
  4. Hard per-account isolation of browser state. Two accounts signed in at once, each with its own cookies, storage, cache, service-worker state and session, each bound to its own capture pipeline and provenance scope.

Only two realistic candidates satisfy all four plausibly: Electron/Chromium with CDP, and CEF with native resource response filtering. That is why §4 spends most of its length on that pair.

3.2The case for Electron as v1

  • ▣ Verified fact CDP is reachable from the Electron main process via webContents.debugger, giving request/response metadata, body retrieval and instrumentation events for the attached target — a genuinely non-page-world surface, and one that does not require injecting anything into the page.
  • ▣ Verified fact persist: partitions give one persistent, on-disk browser profile per Arena account, plus session-scoped serviceWorkers, webRequest, cookies, netLog and clearData(), and a cancellable will-download hook. That is nearly the entire account-isolation and artifact story in one API family.
  • ◈ Strong inference Because Electron is Chromium, Arena sees the same engine family it is built for. That maximizes compatibility for email sign-in, MFA, CAPTCHA, popups and redirects — the required authentication path — without any profile trickery.
  • ◈ Strong inference The service layer (capture, sanitize, normalize, store, sync, MCP, analysis) is one TypeScript codebase with mainstream dependencies, and every part of it is unit-testable without launching a GUI. That is the dominant factor for an AI-agent-maintained codebase: agents can run vitest, read typed interfaces, and reason about a single language.
  • ◈ Strong inference Build/packaging burden is far lower than CEF: no C++/Obj-C++ integration, no framework bundling, no Chromium version management, no bespoke windowing layer.

3.3What Electron does not give us

Honest limits

  • ◌ Unknown Whether Electron's maintained CDP/session surfaces observe every architecture-critical Arena traffic class. In particular: requests issued from a service worker context, and whether CDP attachment covers every target through navigation and target replacement. CEF's header explicitly documents service-worker coverage for its response filter; Electron's equivalent must be demonstrated, not assumed.
  • ◌ Unknown Whether CDP body retrieval is available and correctly ordered for every streaming mechanism Arena uses, and whether any body is unavailable after the response completes or the target navigates.
  • ◈ Strong inference Electron's CDP surface is a debugging surface, not a supported data-plane API. It can be disrupted by DevTools being opened on the same WebContents (▣ Verified fact: attaching webContents.debugger detaches on DevTools invocation), so the app must treat debugger detachment as a first-class capture-gap event, and must disable/monitor the DevTools path.
  • Electron carries a Chromium + Node runtime per app. That is acceptable for a private single-owner tool on an M3 Pro, but it is a real memory cost relative to a native Swift shell (§25).

3.4The reversal condition, stated exactly

Reversal gate (must be written down before the spike runs)

Switch from Electron to CEF if, and only if, all of the following hold after the Phase 1 spike on real authenticated owner sessions:

  1. At least one architecture-critical traffic class — meaning: without it, the archive cannot guarantee conversation completeness — is not observable through maintained Electron surfaces (CDP over webContents.debugger, session-scoped webRequest/serviceWorkers), after documented attempts including target discovery/auto-attachment with the exact current CDP method names verified at that time.
  2. The same class is observable through CEF's GetResourceResponseFilter (or an adjacent maintained CEF handler), verified by an equivalent focused CEF spike.
  3. The gap is reproducible across at least three independent runs and is not attributable to harness error (wrong attachment timing, wrong target filter, disabled domain).
  4. A written capability-loss memo records what Electron-only capability is abandoned and how CEF replaces it (§26).

If Electron fails a class and CEF also fails it, the escalation is a targeted Chromium customization — last resort only, requiring a specific named capability impossible through both maintained surfaces, and requiring the owner's explicit go-ahead. If Electron fails a class that is not architecture-critical, the correct response is to record the gap, mark affected records with the appropriate incompleteness state (§11), and keep Electron.

Note that this is a genuine reversal condition, not a rhetorical one. The report does not hide that CEF is theoretically deeper on one axis (documented service-worker response filtering) and that the spike exists to find out whether that matters for Arena.

4.2Reading of the comparison

CEF has one documented structural advantage: a native response filter whose contract explicitly contemplates requests with no browser and no frame, i.e. service-worker-originated traffic. Electron has a documented CDP surface whose service-worker reach is real but unproven for this application. Everything else — isolation ergonomics, downloads, security checklist, maintainability, iteration speed — favors Electron, in most cases strongly.

So the decision is not "which is better." It is: is CEF's one structural advantage necessary for Arena's actual traffic? Nobody can answer that from documentation. That is what the falsification spike is for, and why the reversal gate is written before the spike runs.

4.3Design consequence: build the capture coordinator so it is portable

★ Recommendation The capture coordinator is defined as an interface, not as CDP calls. Two implementations are anticipated from day one: a CDP-backed one for Electron, and a native-filter-backed one for a possible CEF shell. The rest of the system (sanitizer, protocol catalog, normalizer, storage, sync, MCP) must not know which is running.

5Other alternatives, and why they lose

5.1Native Swift + WKWebView

◈ Strong inference (prev-run evidence): WKURLSchemeHandler exists for custom URL schemes, and WebKit throws when asked to register a handler for a scheme it handles internally. It is therefore not a general HTTPS interception hook for Arena traffic. WKWebViewConfiguration exposes WKWebsiteDataStore for website state, which helps isolation but not observation. Multiple WKProcessPool instances no longer produce separate processes, so the old isolation trick is dead.

What native Swift genuinely offers: lowest runtime duplication, best macOS integration, Keychain/App Sandbox/Servicemanagement ergonomics, and the smallest memory footprint. What it does not offer is the one thing this product exists to obtain. ★ Recommendation Rejected as the primary browser layer; retained as the natural shape of a possible future CEF host if reversal occurs, since CEF is a native framework and the shell would then be Swift anyway.

5.2Browser extension + native companion (rejected baseline)

This is the owner's existing recorder and it is disqualified by requirement, not by argument: Manifest V3 / chrome.debugger / extension + native messaging / extension + companion daemon are all excluded as primary architectures. Structurally, a content-script-first design observes the page rather than the browser; its lifetime is governed by extension lifecycle rules rather than by the product; and its download/artifact handling and need for a companion process are exactly the weaknesses reported. It remains valuable as a comparison oracle in the spike (§21.3 row N): where the new harness and the extension disagree about what a workflow produced, the disagreement is a finding.

5.3Tauri / Wry (system WebKit on macOS)

◈ Strong inference (prev-run evidence): on macOS, Tauri/Wry uses the system WebKit webview. Its small footprint is attractive and irrelevant: it inherits WKWebView's capture surface, so it would need substantial custom native interception machinery to become eligible — at which point it is a custom project, not a framework choice. ★ Recommendation Rejected. Capture correctness outranks binary size.

5.4Explicit export/import without an embedded browser

A "no browser" design — the owner exports from Arena's own UI (or a future official export) and the app imports files — is honest, zero-risk, and completely fails the live-capture requirement: no stopped/failed/partial states, no reveal timing, no streaming, no account binding at capture time. ★ Recommendation Not eligible as primary, but implemented as a first-class ingest adapter (§12.2). If an official export appears, or the owner has files from another tool, they enter through the same provenance-bearing ingestion path as everything else, with completeness labeled backfilled/imported rather than live.

6Minimum supported macOS version

★ Recommendation Minimum deployment target: macOS 14 Sonoma, Apple Silicon only (arm64). Build and test on macOS 27; support the current major release and the two before it, and drop the oldest as soon as it no longer receives security updates.

7.4Two kinds of "untrusted"

Untrusted code

Arena's JavaScript runs in a sandboxed, isolated renderer with no privileged bridge. It cannot reach Node, the filesystem, the archive, the key, or MCP. Its only influence on the app is the traffic it produces and the owner interactions it hosts.

Untrusted data

Everything the archive stores from Arena — prompts, responses, tool traces, titles, filenames, attachment names, even instructions inside a response — is data. No stored string can ever authorize a destructive action, elevate an MCP call, or alter the app's own behavior. Prompts that say "delete the archive" are text with a completeness label, nothing more (§15.6).

Partition naming rule

Partition strings must not contain the Arena account's email address, display name, or any other human-identifying value. They are opaque: persist:arena-<partitionUuid>. The mapping from partition → human-readable label lives in the encrypted database, so a directory listing of profiles reveals nothing about who owns which account. Because ▣ Verified fact a Session's options cannot be changed after first use, the partition name and its creation options are decided once at account-registration time and are then immutable.

8.2Non-interference guarantees

  • Sign-out of A cannot affect B. Cookies, storage and service workers are partition-scoped, so A's sign-out touches only A's partition. The capture coordinator for A moves to NEEDS_OWNER_INTERACTION; B's coordinator and sync cursor are untouched.
  • Expiry, CAPTCHA, identity change. All are per-account states in the account state machine (§8.3). None is a global condition.
  • Source-ID collisions cannot merge records. Arena source IDs are scoped identifiers, never primary keys; all uniqueness involving a source ID includes the account scope. Identical text is never treated as evidence of identity (§13.4).
  • Rebinding requires explicit verification. If the owner signs a partition into a different Arena account, the app must not silently re-point existing provenance. It proposes a rebind, requires owner confirmation, and records the rebinding event as provenance rather than rewriting history (§24).
  • Concurrency limits are explicit. Two active Arena renderers plus background sync are the supported steady state. Beyond that, jobs queue (§25).

9.2Sanitization happens before durability

The catalog is built from observations, but a credential-dumping HAR is explicitly not kept. Raw request/response evidence is filtered by a ruleset before anything reaches disk:

Always removed before persistenceRetained (sanitized)
  • Authorization and any bearer/session token, in any header
  • All Cookie / Set-Cookie values
  • CSRF tokens and any header whose value is single-use
  • Passwords, one-time codes, magic-link tokens, OAuth codes/state
  • API keys, signed URLs, and secret-bearing query parameters or fragments
  • Account-identifying values not needed for provenance
  • Unrelated private response fields belonging to other users
  • URL family (path template + parameter shape)
  • Method, status, content-type, content-length, encoding
  • Structural shape of the payload (keys, types, nesting depth, array cardinality)
  • A bounded digest of the sanitized body (sha256) for change detection
  • Bounded sanitized text needed for parser debugging and reprocessing
  • Ordering, timing and target identity needed for reconstruction

Santizer failure is fail-closed

If the sanitizer cannot prove a payload is clean, the durable raw evidence is not written. The observation is still recorded — with a sanitization.failure marker and a redacted placeholder — so that completeness accounting remains truthful (§24). A capture pipeline that silently stores what it could not sanitize is worse than one that drops it loudly.

10.2Early attachment

Attaching after a page has loaded risks missing the beginning of a stream — which for a conversation is often the request itself. ★ Recommendation Attach in app.on('web-contents-created'), before navigation is triggered, and re-assert attachment on every did-start-navigation, target-created-equivalent event, and on detach. The coordinator records an explicit capture-gap whenever it can prove it was not attached for part of a target's life, rather than quietly presenting a truncated stream as complete.

10.3Why DOM evidence is secondary, not primary

The rendered UI is the product surface, and it is sometimes the only place a fact is visible (for example a blind label that Arena only reveals in the interface). But DOM evidence is lossy, order-dependent, and destroyed by navigation. ★ Recommendation Wire observation is the primary source; DOM/UI signals are a parallel, separately-provenanced evidence stream used for reconciliation, gap detection, and for facts that have no wire representation. When the two disagree, the record does not pick a winner silently — it records a conflict (§11.4).

10.4Backpressure

Capture must never be the reason Arena misbehaves, and must never silently discard data. The pipeline uses a bounded in-memory queue with explicit high/low watermarks. On overflow the coordinator degrades deliberately: it stops buffering bodies (keeping metadata), records a capture-gap with a reason, and resumes body capture when the queue drains. It never blocks the browser's network path, and it never writes unsanitized overflow to disk.

11.4Reconciliation rules

Observations arrive more than once, out of order, after navigation, after reconnect, after a model reveal, and during an overlapping history sync. Ingestion is therefore idempotent by construction:

  1. Idempotency key. Every observation carries a deterministic key — partition, conversation scope, turn scope, observation kind, and a content digest where applicable. Re-delivery of the same key is a no-op, not an update.
  2. Append observations, don't overwrite state. Normalized "current" rows are derived views. The observations that produced them are retained, so any derivation bug can be repaired by reprocessing (§13.3).
  3. Provenance strength ordering. observed-revealed > observed-wire > observed-dom > observed-ui > backfilled > imported > inferred. A newer, weaker observation never replaces an older, stronger one.
  4. Reveals add, never rewrite. A post-vote reveal adds an identity observation scoped from its own time forward. It does not retroactively claim the model was known earlier (§14.3).
  5. Conflicts are data. If wire and DOM evidence disagree on the same field, both are kept, the field is marked conflicting, and analysis can exclude or examine such records explicitly.
  6. Backfill never demotes live capture. A backfilled copy of a conversation the app already recorded live is merged field-by-field with provenance preserved, and only fills holes.
  7. Deletion wins locally. If the owner deletes a record locally and a later sync re-offers it, the tombstone is honored; the app does not resurrect data the owner deleted (§15.7).

export function isPresentationComplete(c: CaptureCompleteness): boolean {

12.4Can two accounts sync concurrently?

◈ Strong inference — yes, and here is why it is safe to say so: the isolation boundary is the partition. Each account has its own session, its own cookie jar, its own storage area, its own capture coordinator, its own cursor, and its own job. There is no shared mutable state between two accounts' sync runs; the only shared resources are the encrypted database (transaction-serialized, account-scoped rows) and the process's CPU/memory budget (governed by the concurrency limit in §25). Therefore:

  • Two accounts may sync concurrently up to the configured concurrency limit, because correctness does not depend on scheduling.
  • But correctness does not require it. If concurrency would starve interactive use, jobs are scheduled independently per account and simply run later. Never sacrifice correctness for parallelism.
  • One caveat is stated plainly: whether Arena's own backend applies per-account or per-IP rate limits is ◌ Unknown. If per-IP, concurrent syncing could increase friction for both accounts. The design therefore treats per-account rate limiting as independent but shares a global politeness budget that the operator can lower.

"Synchronized" has a precise meaning: for a given account and strategy, the sync adapter's enumeration reached its terminus, every enumerated unit was either ingested or explicitly recorded as a failure, and the account's coverage-gap list is empty. Anything less is partial, with the gaps enumerated. The word "synchronized" never appears in the UI or the MCP output without that qualification.

13.4Identity, uniqueness, and the "identical text" trap

Identical text is not identity

Two records with byte-identical content are not the same record. This matters concretely: the same prompt asked in two accounts, a regenerated response that happens to match a prior one, a conversation shared across accounts, or a coincidence — none of these may merge. Rules:

  • Arena source IDs are scoped source identifiers, never universal primary keys.
  • Every uniqueness constraint involving a source ID includes account_id.
  • Cross-account source-ID collision ⇒ two independent records, and a note that the collision exists (useful for studying account behavior, useless for merging).
  • Content digests index and deduplicate artifacts, never conversations.
  • Same account + same source ID + different content ⇒ a conflict record with both versions retained and both provenances intact.

14Model identity evidence

Model identity is the single field most likely to be silently corrupted by a naive design, because Arena deliberately hides it during a battle and reveals it afterwards. The archive treats identity as a stream of observations, never as a single column.

14.1Identity kinds that must stay distinct

KindMeaningMust never be conflated with
participant-slotPosition in the comparison — A or B, or a side-by-side columnAny model name
blind-labelWhat Arena shows before a reveal, e.g. "Model A"The real identity, even if the label looks like a name
selected-modelThe marketing/selected model name the owner chose or was shownThe route actually served
provider-labelThe vendor stringThe model version
route-stringWhatever internal route/model identifier the wire exposes, if anyThe marketing name
revealed-identityWhat a post-vote reveal assertsEverything above — it is a new fact from a new time
owner-annotationThe owner's own claim, editable, always labeled as suchAny observation
inferred-identityOutput of local stylistic analysisAll of the above, absolutely. It may never overwrite them (§17.3).

14.2What every identity observation carries

  • mechanism — how it was learned: revealed, wire, dom, ui, inferred, owner.
  • scope — owning account; conversation, turn and participant it applies to.
  • observedAt and appliesFrom — when we learned it, and from what point it is asserted to hold. These are different timestamps by design.
  • evidenceRefs — the observations behind it, so the claim can be audited.
  • confidence — with the derivation recorded, and a count of supporting samples.

14.3The reveal rule

A reveal adds an observation; it does not edit history

Before a vote, the correct record for a participant is: slot + blind label, identity unknown, with a stated confidence of "unknown." After the reveal, the archive gains a new identity observation of kind revealed-identity with appliesFrom = reveal time. Pre-reveal turns continue to report "identity unknown at generation time" — which is the truthful statement, and the only one that makes temporal analysis meaningful. Analysis queries explicitly choose whether to group by known-at-generation-time identity or revealed identity; the default report shows both sample counts.

◌ Hypothesis to test Whether Arena's reveal is available on the wire (in a response payload) or only in the DOM. If only in the DOM, revealed identities carry mechanism: 'dom' and their provenance strength reflects that; the record says so rather than pretending it was a wire fact.

14.4Inferred identity is quarantined

Stylistic inference may suggest "this looks like model X." It is stored with kind inferred-identity, a confidence value, the analysis run that produced it, and the cohort it was derived from. It can never be written to a normalized participant row. UI surfaces that show inferred identity must display the word inferred next to it, and MCP responses that include inferred identity must include the same marker plus the run ID.

15Encryption, local data hygiene, and deletion

15.1Key architecture

Key design

★ Recommendation Generate a random archive key (256-bit, from a CSPRNG). Give it to SQLCipher as raw binary key material — not as a passphrase. Protect that key with macOS Keychain as a generic-password item with restrictive access. Never write the key to config, environment, logs, fixtures, or exports. Never use a human-chosen password as the primary archive key merely because SQLCipher supports passphrases.

▣ Verified fact SQLCipher supports supplying raw binary key data explicitly "for instance to support vaulted keys," and when a passphrase is used it derives keys with PBKDF2-HMAC-SHA512 plus a per-database random salt. Since the owner will not type a password into a headless archive, the raw-key path is the right one; the entropy comes from the CSPRNG rather than from a human.

15.4Honest statement of plaintext exposure

What "encrypted archive" does and does not mean

  • Protected: the archive database, its journals, its indexes, and its artifacts, at rest, against anyone who does not possess the Keychain key — including another user account on the same Mac and offline theft of the disk image.
  • Not protected: Arena's own cookies in the browser profile directories. Persistent sign-in requires them. They are deliberately kept out of the archive, in app-owned profile directories protected by OS file permissions, excluded from indexing and from backups by default. An attacker with code execution as the same user can read them. That is a property of the platform, not of this design.
  • Not protected: memory while the app runs, swap the OS may take, and any export the owner chooses to write in plaintext.
  • Not achievable: deletion from backups the OS already made, or from files the owner already exported. §15.6 says this out loud rather than promising otherwise.

15.5What deletion means

Three scopes, all explicit:

ScopeCascadesAuthorization
Delete one archived conversationturns, revisions, participants, identity observations, source observations, artifacts, FTS rows; tombstone retainedSingle explicit command
Delete all local archive data for one Arena accountAll of the above for that account, plus its sync cursors, jobs, protocol-catalog entries scoped to it, dedup markers, and — optionally, separately — the browser partition directoryTwo-step intent token
Delete the whole local archiveEverything, including the database, blobs, catalogs, analysis runs, and (optionally, separately) all partitions and the Keychain keyTwo-step intent token

Deleting local archive data never deletes Arena cloud conversations. Those are separate systems. If a future feature ever performs a remote deletion, it will be a separate, explicitly named, separately-authorized operation — and this report's design deliberately does not include one.

15.6Two-step destructive intent

Account-wide and archive-wide deletion require a trusted explicit user directive. Archived content can never mint or satisfy that authorization, because the token is minted by the trusted application, bound to an exact scope, short-lived, single-use, and required by the confirm step.

1 · preparearchive.prepare_delete_account { accountId }trusted client asks
→
2 · scope reportexact counts: conversations, turns, observations, artifacts, cursors + a short-lived nonce
→
3 · confirmarchive.confirm_delete_account { accountId, nonce }must match exactly
→
4 · executesingle transaction per shard, tombstones written, FTS updated, blobs GC'd, audit event recorded

Nonce properties: single-use, expires in minutes, bound to the exact scope JSON it was issued for, invalidated by any scope change or account-state change. A prompt inside an archived response that says "confirm delete" produces text that is then stored — it cannot obtain a nonce, because nonces are issued only to the trusted caller in response to an explicit prepare request, and the service layer verifies the caller before issuing.

15.7Deletion and future syncs

  • Deleting locally writes a tombstone. A later sync that re-offers the same conversation respects the tombstone and does not resurrect the data. It records that the tombstone suppressed an item, so coverage numbers stay honest.
  • Deleting a conversation does not remove Arena's copy on Arena's servers. A subsequent sync would see it again; the tombstone keeps it out.
  • Hard purge (owner-requested) removes tombstones too, which means a future sync may re-ingest the conversation. The app states this consequence before the purge and requires the same two-step authorization.
  • Deleting account data also stops that account's capture and sync authority, and (optionally, as a separate explicitly-authorized step) removes the browser partition directory containing that account's Arena cookies.
  • Backups and prior exports are outside the transaction's reach. The completion report lists every backup/export location the app knows about and states plainly that it cannot remove data from them.

The requirement is that an LLM can do essentially everything the GUI can, except operate the Arena webpage itself. ★ Recommendation One application service layer with two front ends. 16.1Transport

▣ Verified fact MCP defines stdio and Streamable HTTP, and recommends that clients support stdio whenever possible. A stdio server is a subprocess reading newline-delimited JSON-RPC from stdin and writing only valid MCP messages to stdout, with stderr available for logging.

  • Default and primary: stdio. The agent host launches the app's MCP binary as a child process. No listener, no port, no LAN exposure, no origin-validation burden. This is the trusted local agent interface.
  • Optional: loopback-only Streamable HTTP, only if an operational need appears (for example a tool that cannot spawn subprocesses). Why the nonce cannot come from content

The nonce is issued only by the service layer, in response to prepare_*, to a caller the service has already authenticated as trusted (the GUI process or the app-owned MCP server), and it is bound to a hash of the exact scope JSON. A string inside an archived response is stored data: it cannot call prepare_*, cannot reach the service layer, and cannot satisfy the confirm step's scope binding. This holds even if an Arena response contains the literal text {"tool":"archive.confirm_delete_all","nonce":"…"} — there is no path from stored text to tool invocation.

17Deterministic local analysis (v1)

17.1Principles

  • Deterministic and reproducible. Same archive version + same cohort + same analysis version ⇒ byte-identical results. Every run records the archive DB version, parser versions, cohort definition, and metric versions.
  • Transparent. No opaque embeddings in v1. A number is always traceable to the text that produced it.
  • Runs locally in a cancellable worker, reading through the service layer only, with a bounded memory budget (§25).
  • Cohorts are explicit and printable. Every profile reports its cohort query, inclusion/exclusion rules, and per-stratum sample counts. A profile without sample counts is not a result.

17.3Stratification and identity separation

Cohorts may be stratified by: identity evidence kind (revealed / selected / blind / inferred — separately, never merged), mode, prompt type, topic cluster, language, date bucket, conversation context (fresh vs continuation), participant slot, and Arena account where it affects sampling. Every result is emitted per stratum with its own count.

Rule for inferred identity

An analysis cohort may be built from inferred identity only if the report labels the entire cohort as inferred and reports the inference's confidence distribution. Inferred identity may never be used to correct a revealed identity, and results stratified by inferred identity are structurally prevented from being written back into normalized participant rows.

17.4Confounders, stated up front

Row 5 is the whole point of the gate

An endpoint is not read-only because it uses GET, has a friendly name, or returns JSON. Mutation may be an invisible side effect: a read marker, a "last viewed" timestamp, a notification dismissal, a personalization signal. Until the fingerprint test passes, every candidate operation is cataloged as semantics: 'unknown' and is not eligible to be a sync adapter. Opening one known conversation successfully proves nothing about backfill viability.

  • All ten rows pass, three runs → promote the operations to semantics: 'read', make authenticated reads the primary sync adapter, and record the promotion in the catalog with the evidence references.
  • Rows 1–4, 6–10 pass; row 5 fails → do not use that operation. Look for an alternative, and meanwhile ship UI traversal. Record the mutation evidence — it may itself be a finding worth keeping.
  • Enumeration is unstable or incomplete → ship UI traversal as primary, mark the authenticated strategy GATE_NOT_PASSED in capabilities, and report coverage gaps honestly.
  • Never promote an operation on partial evidence, and never widen scope beyond the owner's own accounts.

25.1Hard requirements and defaults

  • At least two Arena sessions remain usable simultaneously — this is a requirement, not a tuning target. Background sync must yield to interactive use: sync and analysis are suspended automatically if the diagnostics sampler shows sustained foreground pressure, and never block the owner's typing or scrolling path.
  • Two partitions is the supported steady state. More accounts may be registered; their partitions are created on demand and their renderers discarded when not in use, while cookies and storage persist on disk.
  • Backpressure over capacity guesses. Every buffer in the pipeline is bounded with an explicit policy. Nothing in this report asserts a number of conversations, turns, or bytes the archive can hold, because that is a measurement, not a design fact.
  • Memory-safe analysis. The analysis worker streams over cohorts rather than loading a corpus, and reports the peak it observed with each run so growth is visible.
