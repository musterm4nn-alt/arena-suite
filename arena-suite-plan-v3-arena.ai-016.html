0Decision summary

Selected architecture

A single Electron (Chromium) application in which each Arena account lives in its own persistent session partition rendered by its own WebContentsView, and capture is performed out of band from the main process through the Chrome DevTools Protocol (webContents.debugger: Network.* including streamResourceContent, WebSocket and EventSource events, Fetch, Target.setAutoAttach), supplemented by session-level webRequest metadata, session.serviceWorkers lifecycle, and will-download ownership of artifacts. Storage is an SQLCipher-compatible encrypted SQLite (better-sqlite3-multiple-ciphers) keyed by a random key wrapped through macOS Keychain (safeStorage). The primary interface is a local MCP server (Streamable HTTP on 127.0.0.1 with a bearer token, plus a stdio shim) running inside the application and sharing the same service layer as the minimal diagnostics GUI. Recommendation

Why this and not the alternatives, in one paragraph each

  • Native Swift + WKWebView would be the lightest process and the most "Mac-like" choice, but WebKit gives the host no supported way to read https response bodies, streamed chunks, WebSocket frames or worker traffic; WKURLSchemeHandler is restricted to schemes WebKit does not already handle Verified fact (WebKit bug 138169 discussion; Apple DTS answer cited there). Capture would collapse back to page-world monkey-patching — the exact failure class of the extension baseline, with less tooling. Rejected for the primary capture path; kept as a rejected-with-reason entry, not a fallback.
  • Tauri / Wry renders through WKWebView on macOS and therefore inherits every WebKit observation limit above while adding a Rust toolchain. No capture depth is gained by the shell. Rejected.
  • Chromium Embedded Framework is the only candidate with an in-process, byte-level response filter (CefResponseFilter) and request-context isolation, and it is a serious contender on capture depth. It loses on implementability for an agent-run project on macOS: no first-party Swift/Node binding, C++/Objective-C glue, helper-app bundle layout, and a much thinner troubleshooting corpus. Kept as the escalation path if a concrete CDP gap is proven (§3.7).
  • Extension + companion (the existing arena-exporter) is the baseline; it is ineligible by requirement and, on the evidence of its own README, depends on a document_start interceptor and chrome.downloads — page-world capture plus an extension download path. The selected design must beat it on the specific problem areas in §10 gate G2, or the project changes course.
  • Export/import without a browser cannot be primary because no official Arena conversation export or history API was found in this run Unknown; it remains a supplementary importer if one appears.

The five things an implementation agent must not lose

  1. Attach before navigate. The CDP session for an account view is attached and Network.enable / Target.setAutoAttach issued while the view is still on about:blank; only then is arena.ai loaded. Capture gaps at navigation are a first-class state, never silently absorbed.
  2. Account partition is part of identity. Every observation, conversation, checkpoint, artifact and destructive action is keyed by account_partition_id. Nothing is merged across partitions on the strength of IDs, URLs, titles or text.
  3. Completeness is a recorded state, not an inference. complete, stopped_by_user, failed_upstream, observer_gap and unknown are distinct and exported as such.
  4. Secrets never reach persistence. Sanitization happens in the capture ingress before anything is written, including on parser-error paths; browser-managed cookies stay inside Chromium's partition storage.
  5. Archived text is data, not authority. Destructive MCP tools require a confirmation token minted by a trusted control channel and bound to the exact scope shown to the owner.

What would reverse the decision

The first spike (gate G1/G2 in §10) is designed to break the design. Reversal triggers: (a) Arena's email sign-in cannot complete inside an Electron partition after documented mitigations (reCAPTCHA Enterprise refusing the embedded UA/environment); (b) the account's conversation stream is not observable as complete bytes through CDP Network.streamResourceContent/getResponseBody/Fetch and the service-worker fallback (Network.setBypassServiceWorker or browser-level target attach) also fails; (c) two partitions leak cookies/storage/service-worker state to each other in the isolation test. (a) and (c) would also defeat CEF, so they change the project (fallback to UI-traversal capture, degraded); (b) escalates to CEF or, last resort, a patched Chromium.

3Architecture selection

3.1 Candidates and the decisive question

The decisive question is not "which shell owns the window" but "which shell lets the host read every byte of the account's first-party traffic, including streamed and worker-originated bodies, from outside the page, with per-account isolation and an application-owned download path". Owning a window is easy in all five shells; only Chromium-based shells expose an out-of-band protocol that reads response bodies.

Honest caveat about "deeper": CDP is a debugging protocol, not a network tap. It can drop body data if a request's buffer is exceeded, it reports per target, and it can be detached when DevTools opens on the same WebContents (Electron docs: the debugger detaches when DevTools is invoked) Verified fact. 3.5 Processes and trust boundaries

3.6 Simultaneous-account partition model

  • An account partition is created by the owner ("Add account") and receives a random partition_id (UUID) before any sign-in. Its Electron session name is persist:arena-<partition_id>. Browser state (cookies, localStorage, IndexedDB, cache, service workers, permissions) lives under Electron's per-partition storage path (ses.storagePath) Verified fact.
  • The visible account identity (email or display name and Arena user ID, once observable) is attached to the partition as an identity observation with source and time; it is never the primary key. If a partition later shows a different identity (owner signed out and into another account in the same view), the partition enters identity_changed: recording pauses, a new logical account binding is required, and prior records stay bound to the previous identity observation. This is what "account change" means throughout the plan.
  • Each partition has its own CDP session, capture stream, sync scheduler state, checkpoint table rows, download root, quota counters, and MCP job namespace. Global pause/stop fans out to each partition; per-partition controls never touch others.
  • Destructive scope is always a partition ID (or the whole archive), never an email string, because an email string could match two partitions.
  • Isolation is asserted by a test, not assumed (§10 G1): sign in to A and B; verify ses.cookies.get for A contains no B cookies and vice versa; verify serviceWorkers.getAllRunning() scopes are partition-local; verify B's history view never lists A's conversations (identity check via the discovery recorder).

4Discovery and live capture

4.1 Discovery as a maintained capability: the protocol catalog

Discovery is the first engineering deliverable and stays alive for the life of the app. It has two outputs: a capture-adapter inventory (what the code knows how to parse) and a machine-readable protocol catalog (what has been seen, per partition, with drift signals). Both are exposed through MCP (§7) so an agent can answer "what changed?" without a debugger.

What discovery records, and what it deliberately does not

  • Inventory coverage is broad: every first-party request seen by the partition's webRequest hooks (all frames, workers and service workers in the session) and every CDP Network.requestWillBeSent is classified by an operation key = (host, normalized path template, method, transport, initiator type, Next.js action/route hints when present in sanitized headers). Third-party hosts (reCAPTCHA, PostHog, CDNs) are counted by host only.
  • Payload retention is narrow: bodies are retained only for operations whose class is conversation, history, reveal, vote, artifact, or unknown-first-party and only after the sanitizer (below). auth, account, analytics, config, and asset classes keep counts, sizes, status codes and a redacted URL only. Unknown operations keep one sanitized sample (bounded to 64 KiB, secrets removed, string values longer than 256 chars hashed) until an agent classifies them.
  • Classification is conservative: a new operation starts as unknown. It becomes read only after the rule in §5 (observed in an owner-driven read-only UI action, idempotent on repeat, no state change visible afterwards). Nothing is promoted automatically.

Sanitizer: where secrets stop

The sanitizer is a pure function applied to every object before it can reach the database, logs, diagnostics, MCP responses or fixtures — including on the parser-error path, where the failing input is sanitized before being attached to the error record. Rules, in order:

  1. Drop request/response headers except an allow-list (content-type, content-length, status, and Arena diagnostic headers once verified, e.g. the x-arena-chat-id/x-stream-version names reported by the baseline Strong inference). cookie, set-cookie, authorization, x-csrf-*, x-xsrf-* never pass.
  2. Strip URL query strings and fragments from retained URLs; keep the path template. Signed URLs (query containing sig, signature, token, X-Amz-*, expires) are replaced with a resource reference {host, path-hash, observed_at, expires_hint}; the artifact itself is fetched once at capture time and stored encrypted, so the secret URL is never needed again.
  3. Redact JSON fields by key pattern (token, secret, password, otp, code when in auth-class ops, captcha, recaptcha, jwt, refresh, session, api_key) and by value pattern (JWT shape, Bearer …, Basic …, 32+ char high-entropy strings inside auth/account classes).
  4. For auth/account classes, retain no body at all.
  5. Emit a sanitizer_version with every record; the sanitizer is versioned and has its own fixture suite of synthetic secrets that must never appear in output.

4.2 Capture pipeline

Transport handling, with what each still cannot see

  • Chunked fetch streams (expected primary transport Strong inference): streamResourceContent must be called after responseReceived; Chromium buffers bytes until then and returns them in bufferedData. Gap risk: if the call fails (request already finished), fall back to getResponseBody; if the body exceeded the buffer, mark observer_gap:buffer. The webRequest onCompleted for the same URL provides an independent "a response of N bytes happened" signal to detect the gap.
  • WebSocket: frames are delivered as text/base64 with direction and timestamp; reconnects create new request IDs — the adapter keys logical channels by (partition, URL template) and treats overlapping frames after reconnect as candidates for dedup by message ID when the payload has one, otherwise by content hash within a short window and flagged dedup:heuristic.
  • EventSource: native events if the page uses EventSource; raw text/event-stream over fetch is parsed by the same stream adapter.
  • Dedicated/shared workers: auto-attached sessions get Network.enable; their events carry their own sessionId. Coverage is asserted in G2 by making the harness page issue a fetch from a worker and confirming capture.
  • Service workers: detection is certain (ses.serviceWorkers, response.fromServiceWorker); body capture of SW-originated network fetches is the open question. Order of attempts: page-session auto-attach → SW preload script (Electron 35+) used only as a detector of SW fetch activity, never as a capture path → Network.setBypassServiceWorker on account views (capability loss: Arena's SW caching) → browser-level CDP endpoint. Whatever the outcome, the catalog records transport = sw-fetch for such operations so the gap is visible.
  • Navigation and target changes: in-flight buffers at Page.frameNavigated (main frame) are closed as observer_gap:navigation unless loadingFinished already arrived; because CDP sessions survive same-process navigation, most streams complete. Cross-process navigations (rare for same-site) produce Target.attachedToTarget for the new target; waitForDebuggerOnStart guarantees Network.enable before the first request.
  • Rendered/page state: DOM probes via Runtime.evaluate in an isolated world (Page.createIsolatedWorld) read model labels, vote buttons, reveal banners and the final rendered text; they are read-only, never patch page globals, and their results are stored as ui-source observations. This is the only "page-world" touch and it is not the capture path.
  • Downloads and generated artifacts: will-download → item.setSavePath into a partition-scoped temp dir → on done, hash, encrypt into the artifact store, delete temp, record artifact_observation linked to the conversation active in that view at initiation time (via item.getInitiatorOrigin()/frame and current URL). Blob URLs use ses.getBlobData.

4.4 Reconciliation of network and UI evidence

  • Turn and branch boundaries come from network payload IDs when the adapter recognizes them (message/node IDs, parent references) Strong inference from the baseline's schema, which distinguishes message/node IDs; the UI probe provides participant position (left/right, A/B) and visible ordering as a cross-check. Regenerations create sibling turns under the same parent; edits create a new branch root; both are represented as nodes in a tree keyed by source IDs, never by text.
  • Repeated events (replayed realtime batches, reconnect resends): dedup only within (partition, conversation, source message ID); identical text without a matching source ID stays as two turns flagged possible_duplicate.
  • Late reveals (model names after vote): stored as an identity observation with the turn range it applies to; the projection updates, the earlier blind label remains.
  • Conflicts (network says A, UI says B): both retained, projection marks conflict, and the catalog raises a drift signal for the operation involved.
  • Binding to a partition is structural (which session emitted the event); binding to an account identity is by the partition's current identity observation. A mismatch between a payload's embedded user ID (if any) and the partition's identity triggers identity_changed degrade.

5.2 Establishing a verified read

An operation is promoted from unknown to read-verified for a partition only when all of the following are recorded in rw_evidence:

  1. Account association: the operation was first observed while the partition's identity was known, and its response contains only conversations that also appear in that partition's UI sample (spot check of ≥3 items), or embeds the same user identifier the identity observation recorded.
  2. Effective read behaviour: issuing the identical request twice produces equivalent results, and the UI state after the calls (history list length, most-recent item, unread/archive markers when visible) is unchanged. HTTP method is not evidence; a GET could be a "mark as read" and a POST could be a pure query (Next.js server actions are POSTs).
  3. Pagination semantics: the cursor/offset parameter is identified, the ordering key is identified, and overlapping pages are observed to overlap on identical source IDs.
  4. Detail retrieval: a detail operation for one ID returns the same turns the live capture recorded for a conversation captured in that partition (structural agreement, not text equality alone).

Native replay then reuses the partition's cookies transiently through ses.fetch/net.fetch bound to that session (Electron's net with useSessionCookies) — credentials never leave Chromium's jar and nothing is copied to disk. If the operation needs a bearer token from page storage, the token is read via an isolated-world probe into memory only, used for the job, and zeroed; it is never logged or persisted. Should token refresh be required, the app triggers Arena's own refresh by navigating/probing the view rather than reimplementing it.

5.3 Sync job design

  • Scope: a job is always for one partition. "Sync selected accounts" creates one job per partition; jobs run concurrently by default because their sessions, cookie jars and checkpoints are disjoint. A global concurrency cap (default 2) and per-partition request pacing protect against rate limiting; if pacing alone cannot keep one partition healthy, that partition's job degrades without touching the others.
  • Checkpoints: sync_checkpoint(partition_id, phase, cursor, last_src_id, page_hash, updated_at) written after every page and after every N details; cancellation stops at the next checkpoint; resume replays from the last durable cursor and tolerates overlap by source-ID dedup within the partition.
  • Pagination instability: each page's ordered ID list is hashed; on re-run, if a page hash differs while the cursor is identical, the job records pagination_unstable and switches to ID-set reconciliation (union of IDs seen in this and previous runs) rather than trusting page boundaries.
  • Overlap with live capture: the reconciler treats history-sourced turns as a second observation; if a conversation is currently streaming in that partition, its detail fetch is deferred until the live stream closes to avoid mixing partial states.
  • Bounded retries: per operation 3 attempts with jittered backoff; on HTTP 429/503 the partition job pauses for the Retry-After (or 60 s default, doubling to 15 min) and reports it. Authentication expiry (401/redirect to sign-in) degrades the partition to auth_expired; recording continues in inventory-only mode until the owner signs in again in that view.
  • Suspected mutation: if a supposed read is followed by a UI state change in that partition (list length or "last opened" marker changed beyond the item itself), the operation's rw_status is demoted to mutation-suspected, the job stops, and an agent must review the evidence before it can run again.
  • Cross-partition collisions: the same conversation source ID appearing in two partitions is an explicit conflict record (possible if Arena shares an ID space across accounts or the owner had a conversation under both, e.g. a public link). The two conversations remain separate rows with separate provenance; the conflict is visible through MCP and never auto-resolved.

5.4 What "synchronized" means, and what stays feasible without a listing

A partition is synchronized when: the listing has been exhausted from newest to the oldest cursor at least once since the last fingerprint-changed on the listing op; every listed ID has a detail observation or an explicit failure record; and the coverage report lists (a) IDs known only from live capture and absent from the listing (possible archived/hidden items), (b) IDs listed but whose detail failed, (c) conversations with turn-level gaps. That report is a resource in MCP (§7), so an agent can inspect the gap list instead of trusting a green checkmark.

If no listing can be read-verified, the feasible mode is UI-traversal-triggered capture: the app scrolls the history sidebar and opens items in the account view under owner-enabled automation, and the live pipeline records what the page fetches. The denominator is then "items that appeared in the UI during exhaustive scroll", coverage is labelled ui-traversal, and search/archived views are traversed as separate passes. Opening one known conversation proves nothing about the rest; the coverage report says so explicitly. Automatic per-account sync is opt-in, off by default, and never runs UI traversal while the owner is interacting with that view (input events in the view pause automation).

6Data, identity, provenance and protection

6.1 Source of truth: observations with rebuildable projections

Recommendation A hybrid: an append-only observation layer (sanitized evidence + adapter output, partition-scoped) is the source of truth; projections (conversations, turns, participants, identity views, FTS index) are derived and can be rebuilt per partition after adapter changes. Full event sourcing is not needed: observations are coarse (one per captured turn/stream/page), and projections are updated synchronously in the same transaction as the observation insert. Raw sanitized stream chunks are kept as evidence blobs with a retention policy, not as the queryable model.

Transactions, recovery, migration

  • One SQLite transaction per ingested observation: insert evidence ref, observation, upsert projections, update FTS. WAL gives crash atomicity; on startup the app replays the stream-buffer spool (chunks spooled to encrypted temp files during streaming) for buffers without a closing observation and records them as partial_observed:crash.
  • Schema migrations are forward-only numbered SQL files applied in a transaction with a pre-migration backup copy of the encrypted DB; projections can be rebuilt with archive.rebuild_projections(partition_id) after adapter upgrades.
  • Retention of sanitized evidence: reparse-class blobs (conversation streams) kept indefinitely by default because they are what makes an adapter fix retroactive; diagnostic samples kept 90 days or until classified; both subject to quota (§9). What can be recomputed after an adapter change: turns, branches, participant views, FTS, all analysis runs. What cannot: anything the sanitizer removed, and anything the observer never saw.

6.2 Model identity

Identity is a set of observations, each with a label kind, a source, a turn range and a time. The view an owner or agent sees is a projection with a confidence class. The rules:

  • Position (A/B/left/right), blind label ("Model A"), selected label (owner's choice in Direct/Side-by-Side), revealed label (post-vote), provider name, marketing name, route/alias name, and exact build are distinct label kinds. None is silently equated with another; a selected label proves what the owner chose, not what served the response (the baseline README makes the same distinction).
  • A reveal creates a new identity observation scoped to the turns that existed at reveal time; turns after the reveal in the same conversation inherit only if Arena's UI/network indicates continuity, otherwise they stay at observed confidence with the last known label.
  • Conflicts (UI shows one name, network another; two reveals differ) set confidence = conflict and are preserved with both observations; unknowns remain unknown.
  • Owner annotations are a further source, never overriding observed evidence in exports — they are exported alongside.

6.5 Keeping Arena-controlled content away from local privilege

  • Account views: sandbox:true, contextIsolation:true, nodeIntegration:false, webSecurity default, no preload, setWindowOpenHandler confining popups (auth popups allowed only for the account's partition and only to the arena.ai origin and the sign-in provider's origins observed in the flow; everything else opens in the system browser), navigation guard that degrades capture on off-site redirects.
  • The GUI renderer is a different WebContents with its own app:// origin and a preload exposing only typed service calls; it never loads remote content.
  • The MCP server listens on 127.0.0.1, validates Origin (rejects any browser origin), requires a bearer token stored in the app container (mode 0600) and optionally rotated per launch; Arena pages cannot reach it because they have no token and browsers send an Origin header the server rejects Verified fact that the spec requires these checks.
  • Archive keys live only in the main process; utility processes for analysis receive an opened read-only DB handle path plus the key over a private IPC channel, not through argv or env.
  • Sign-out, identity change, concurrent use and account changes do not alter which session a WebContentsView is bound to; a partition's Electron session object is immutable for the life of the partition, so inheritance of another partition's state is structurally impossible rather than policy-prevented.

Representative contracts

7.4 Guarding destructive actions against content-driven authority

The guard is a token bound to scope, minted only by a trusted control channel:

  1. delete.request computes a scope_digest over the canonical scope and returns a confirmation_id. Nothing is deleted.
  2. The app shows a native confirmation sheet (GUI) and prints the same summary in a local terminal helper (arena-archive confirm cf_…) — both are channels an LLM cannot write to. The owner sees the exact scope (partition label, identity label, counts) and receives a short one-time token. For a single-conversation scope the token is still required but auto-approved after a 5-second undo window if the owner enabled "quick delete" in settings; account-wide and archive-wide scopes never have a quick path.
  3. delete.execute verifies the token's HMAC over (confirmation_id, scope_digest, expiry) using a key held only by the main process. A token for one scope cannot execute another; expired or reused tokens fail with confirmation_mismatch.
  4. Authorization is therefore distinguished from retrieved content by origin of the token, not by the model's judgment. No prompt text, transcript, or diagnostic string can produce a valid token, because none of those channels can compute the HMAC.

The same pattern (request → out-of-band token → execute) is applied to accounts.rebind_identity, sync.resolve_conflict, diag.classify_operation when promoting an op to read-verified for sync replay, and archive.backup(include_key:true), since these change trust decisions.

7.5 GUI and MCP share one service layer

All tools are thin adapters over services/*.ts functions with zod-validated inputs; the GUI's IPC handlers import the same functions and schemas. A contract test enumerates the tool registry and asserts each service capability is reachable from both surfaces, and that no GUI-only IPC handler exists without an MCP twin. Browser interaction required by workflows (sign-in, challenge solving) is explicit: MCP tools can focus the right account view (accounts.open_signin) and report state, but the owner performs the interaction; the tools return partition_degraded:challenge_pending until it completes.

8.3 Limits of a one-user corpus, stated in every run

Each run's result carries a caveats block generated from the cohort: selection bias (the owner chose which models to talk to and when); prompt/topic confounding (models are not seen on the same prompts unless the stratum is Side-by-Side/Battle pairs — the only comparisons the run labels paired); conversation history and hidden system prompts; unknown decoding settings, tools, safety layers and Arena post-processing; aliases and routing (a revealed marketing name may map to several builds over time — the run buckets by month and flags label changes); temporal model change; uncertain labels (selected ≠ served). Supported comparisons: paired within-conversation A/B differences in Battle/Side-by-Side; within-model drift over time on similar prompt types. Misleading comparisons the tool refuses to present as findings: cross-model differences from Direct-mode-only cohorts without a prompt-type stratum; any statement about model identity from style.

8.4 Embeddings and local ML: gated

Recommendation Not in v1. Entry gate: a concrete question that deterministic metrics cannot answer (e.g. topic-controlled comparison needs topic clusters better than keywords) and ≥ the underpowered threshold of complete turns in ≥2 revealed cohorts. If entered: ONNX Runtime (Node binding) with a small multilingual sentence-embedding model, weights downloaded once, pinned by SHA-256 in-repo, stored in the app container, fully offline afterwards; preprocessing version and model hash recorded on every run; memory budget ≤1.5 GB during runs on this 18 GB machine, runs in the utility process and can be cancelled.

8.5 Later similarity / fingerprinting experiments

  • Output is always inferred_identity with a calibrated score, stored separately from observed identity and never written into participant_view.
  • Splits are by conversation (all branches and near-duplicates — MinHash over turn text — kept on one side), stratified by prompt type and month; held-out conversations never touch feature selection.
  • Controls: prompt/topic-matched negatives; a shuffled-label negative control that must produce chance-level accuracy; an unknown class with an abstention threshold chosen on validation data; calibration curves reported.
  • Predeclared criteria per experiment (written to analysis_run.params before running): minimum paired-accuracy over chance with CI excluding zero, calibration error bound, and abstention rate ceiling. Continue if met on the held-out set; revise once if near-miss with a documented change; stop and archive the experiment if the negative control fails or the criteria are missed twice.

10Implementation sequence and acceptance gates

Each gate lists a deliverable, dependencies, machine-checkable criteria, the evidence that would falsify the approach, and the decision. Fixtures are split into three kinds and the gate says which it needs: synthetic protocol fixtures (a local Node server emitting chunked/SSE/WS streams with known content, workers and a service worker), documented platform behaviour (Electron/CDP docs), and owner-session evidence (the owner signed into real Arena accounts inside the app). No kind substitutes for another.

Deliverable
Electron app (arm64) with one BaseWindow, partition factory, sanitizer library with its secret-fixture suite, encrypted SQLite opened with a Keychain-wrapped key, structured logging through the sanitizer, MCP server skeleton with diag.run_selfcheck.

G2Capture-depth viability: the falsification spike
Deliverable
The vertical slice from §4.5. A harness that (a) runs synthetic fixtures and (b) records real Arena sessions while the baseline extension runs in Chrome on the same prompts.
Synthetic criteria
Chunked fetch of 2 MB delivered in 500 chunks captured byte-exact; SSE via EventSource and via raw fetch captured; WS frames both directions; fetch from dedicated worker captured; fetch made by a service worker on behalf of the page captured under the chosen SW strategy (record which); attach-late test (navigate before attach) correctly reports observer_gap:attached-late rather than silently missing; navigation mid-stream reports observer_gap:navigation; stopped fetch (AbortController) → stopped/canceled; 500 response → failed_upstream; download via anchor and via blob captured to the artifact store.

Falsifiers
≥1% of complete turns with missing bytes after Fetch-domain fallback; SW-served bodies invisible under all four strategies; debugger detaches spontaneously under load. Any of these → CEF spike with identical fixtures (§3.7) before further investment.

Turn boundaries unrecoverable from payload → adapter relies on UI probes with reduced confidence (documented), not a block.

Deliverable
