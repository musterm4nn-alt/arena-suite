0Five findings that shape everything else

1Arena's own client already contains a resumable, replay-safe transport. The public evaluation bundle fetches a short-lived stream credential for a message, then reads a server-sent-event stream that supports Last-Event-ID resume and a batch replay path with client-side de-duplication by record id. Capture therefore does not have to be a best-effort tap on a live socket; gaps can be repaired after the fact. Verified factS6
2Owning the browser window is not the same as deeper capture. An embedded shell that only runs JavaScript in the page has the same privileges as the extension baseline. Depth comes from three specific planes: the host process, the browser network service (CDP), and the page world. The recommendation reaches all three and treats the page world as advisory only. Recommendation
3Electron/Chromium is the right shell; WKWebView and Tauri/Wry cannot reach the network plane at all. WebKit-based shells expose no supported response-body, WebSocket-frame, worker-target or service-worker observation surface; Electron exposes documented CDP attachment plus session-owned authenticated reads plus per-session proxy and certificate control. CEF reaches one plane deeper in C++ but costs a custom toolchain that agent-led development cannot iterate on. Recommendation Strong inference
4Email sign-in is the only flow that must be seamless, and it has one honest cost. Arena's email flow sends a confirmation link to a mailbox. A mailbox click opens the default browser, not this app. The app must therefore offer an in-app "complete sign-in by pasting the link" path, and accept that first-time sign-in is a two-step owner action. Nothing about multi-account isolation depends on it. Verified factS1
5The archive's weakest link is not capture depth but identity attribution and deletion semantics. Arena reveals battle participants only after a vote, Agent's orchestrator may never be revealed, and a remote delete is permanent after archiving. The data model must make unknown identity and remote-absence first-class states rather than filling them in by guesswork. Strong inferenceS10S2

1Decision

Build Arena Archive as a single Electron application that owns one Chromium instance, one persistent browser session per Arena account, a three-plane capture stack, an encrypted local archive, and a local MCP server that exposes every capability the GUI has.

The recommendation in one paragraph

A single-process Electron 44.x app (Chromium-embedded, Node main process) opens Arena in app-owned windows, one per Arena account, each bound to its own persistent Chromium session created with session.fromPath(). Capture is attached to each Arena page before its first navigation, using the documented webContents.debugger CDP attachment with per-target auto-attach for workers and service workers; streamed responses are assembled from the Network domain (chunk events, plus streamResourceContent/IO.read for in-flight bodies), with Fetch used for deliberate interrogation rather than as the hot path. History backfill and gap repair are performed by the app itself against Arena's own authenticated routes using session.fetch() in the correct account partition — including the observed per-message stream-credentials call plus Last-Event-ID resume that the Arena client itself uses. Page-world instrumentation is injected out-of-band via Page.addScriptToEvaluateOnNewDocument and is treated strictly as advisory UI evidence. Everything lands in one SQLCipher-encrypted SQLite database whose key lives in the macOS Keychain, with large artifacts encrypted separately, and every record carries account, mechanism, adapter version and completeness provenance. A local MCP server (stdio primary, loopback HTTP optional) is the primary interface, and destructive operations require a single-use directive minted by a trusted channel.

3.4 Four design implications taken from this section

  1. Capture the parts, not the prose. The protocol is a typed event log. The archive's turn model stores typed parts (reasoning, tool call, tool result, text, finish reason) and derives text for display. A design that stores concatenated text has thrown away the most interesting research material before it reaches the database. Verified factS6
  2. Treat resume as a first-class repair tool. Because the client resumes with Last-Event-ID, the archive can too — from the host process, with the account's own session. That converts "observer missed data" from a permanent loss into a retry with an expiry the app must measure (how long a stream stays resumable).
  3. Never infer identity from structure. Blind labels and participant positions are not models; a reveal is an event. The data model (§8.4) keeps identity claims with scope and source, and a resolved view that remains explicitly incomplete for Agent sessions. Strong inferenceS10
  4. Mirror the remote lifecycle locally, but never destructively. Arena has archive and delete operations with a server-side deletion queue. The archive records remote-absent observations as evidence; it does not delete its own copy because a remote listing stopped showing it. Verified factS2

4Stack selection: who can see what, and why Electron

4.1 Separate the window from the privilege

A dedicated browser shell is a fixed requirement. But "dedicated browser" says nothing about how much of the traffic the shell can actually observe. Four privilege planes determine that, and every candidate must be placed precisely:

Plane 0 · Page worldJavaScript running inside the page. Can wrap fetch, XMLHttpRequest, WebSocket, EventSource, Worker. Loses everything that happens before injection, in other targets, or while the script is broken. This is the extension baseline's plane.
Plane 1 · Network service (CDP)The browser's own network stack, observed over the Chrome DevTools Protocol: request/response metadata, response bodies, streamed chunks, WebSocket frames, EventSource messages, per-target sessions for workers and service workers. Read-only by default in this design.
Plane 2 · Host processSession ownership: cookie jars, certificate verification, proxies, permissions, downloads, target discovery, and the ability to issue the account's own authenticated requests without the page. Only a host process gives this.
Plane 3 · OSKeychain, file encryption, file-flag exclusions, backups, swap. Where storage protection actually lives.

The recommendation reaches Plane 1 and Plane 2 for every account, and uses Plane 0 only for UI-only signals. The extension baseline reaches Plane 0 and, when the user is willing to attach it, a borrowed form of Plane 1 that it does not own.

The honest note on depth

For observation-only capture of the same targets, Electron's CDP surface and chrome.debugger's CDP surface are the same protocol at the same layer. Electron does not win by being "closer to the metal"; it wins because the host owns attachment timing, the partition, the download path, and the ability to make the account's own requests — and because an app-owned proxy (a plane no extension can reach) remains available as a strictly deeper instrument if CDP proves insufficient. Anyone evaluating this plan should judge it on those four ownership properties, not on "embedded vs. extension". Recommendation

4.4 What Electron does not give, and what the design does about it

  • No documented browser-level CDP endpoint. webContents.debugger attaches to a web contents; child targets are reachable through Target.setAutoAttach / Target.attachToTarget with flat sessions — the Debugger API accepts a sessionId argument, which is the documented mechanism.S11 Consequence: the design attaches per web contents and auto-attaches children; P0 must confirm that worker and service-worker targets appear and that their events are attributable (U1, check A0.5).
  • webRequest.filterResponseData is not in the current documentation. It must not be part of the design. This is a change from older Electron guidance that some plans still repeat; verified by absence in docs/api/web-request.md on main.S11
  • Only --remote-debugging-port is documented among remote-debugging switches (notably not --remote-debugging-pipe).S11 Consequence: if a browser-level client is ever needed, use the documented port bound to loopback and treat it as a second trust surface with its own token, or skip it entirely — the page-attached path is sufficient for v1.
  • Electron does support a subset of Chrome extensions (ses.extensions.loadExtension).S11 The design deliberately uses none: the point of this project is to stop depending on extension lifecycle. This is a design choice, not a platform limitation, and it should be stated that way in review.
  • Chromium's own HTTP cache is not readable through any of these APIs. Cached responses are a blind spot; the mitigation is server-side re-read (§6) plus honest completeness states (§5.5).
  • Per-session certificate verification is possible (ses.setCertificateVerifyProc), which is what makes an app-owned, app-trusted MITM proxy safe to add later without touching the system trust store.S11

4.5 Resource and build posture

Runtime shape

5Capture architecture

Five observation layers, ordered by trust: the browser's network service (L1), app-owned authenticated reads from the host (L2), an optional app-owned intercepting proxy (L3), injected page instrumentation used only for UI-only signals (L4), and download/artifact control (L5). Layer 4 is never the primary path for conversation content, and the report says so explicitly wherever it appears.

5.2 L1 — the CDP observer

The observer is created for every Arena web contents, in a fixed order that leaves no window for a missed first request:

// Pseudocode for attachment ordering. This order is the whole point of L1.
on('web-contents-created', (e, wc) => {
  if (!isArenaPartition(wc.session)) return            // never touch other partitions
  wc.debugger.attach('1.3')                            // before any load is issued
  await wc.debugger.sendCommand('Network.enable', {
    maxTotalBufferSize:    budget.cdp_buffer_bytes,    // measured, then tuned in P0
    maxResourceBufferSize: budget.cdp_resource_bytes
  })
  await wc.debugger.sendCommand('Page.enable')
  await wc.debugger.sendCommand('Runtime.enable')
  await wc.debugger.sendCommand('Target.setAutoAttach',
    { autoAttach: true, waitForDebuggerOnStart: false, flatten: true })
  attachFilters(wc)                                    // see below; observe-only
  wc.loadURL(arenaEntryUrlFor(account))                // navigation only after attachment
})

Hot path. For responses, the observer consumes Network.responseReceived, incremental Network.dataReceived, and Network.loadingFinished, then asks for the canonical body with Network.getResponseBody. For resources still in flight whose bytes we need before completion (the chat stream is exactly this case), it calls Network.streamResourceContent and drains the returned handle with IO.read. All three commands and both events exist in the protocol definition consulted this run.S12

Interrogation path. The Fetch domain is reserved for cases where the observer needs to act deliberately: capturing a request body that Network.getRequestPostData cannot return, or taking a response body as a stream when the resource is large and the buffer policy would evict it (Fetch.takeResponseBodyAsStream). When enabled, it is enabled for narrow URL patterns, at response stage by default, and the request is always continued unmodified.S12

Observe-only is a hard rule

The capture path never rewrites requests or responses, never injects headers, never alters bodies, and never fabricates a response. Anything that could change what Arena sends or what the page receives is out of scope for capture, because a capture system that perturbs its subject cannot be trusted as evidence. The only writes to Arena's servers come from L2 reads and the owner's own navigation.

Boundaries and budgets. Buffers are finite; the design therefore records, per response, whether the body was obtained in full, in part, or not at all, and treats "no body" as a first-class outcome rather than an error. Third-party hosts are inventoried by name and response metadata but their bodies are not retained, which keeps discovery broad (§12.2 protocol catalog) while retention stays narrow.

5.3 L2 — app-owned authenticated reads

From the main process, session.fetch() issues requests through Chromium's network stack in the context of a specific session partition.S11 This is the single most useful host-plane capability for this project because it lets the archive perform the account's own reads without the page, without CORS, and without touching page JavaScript: backfill (§6), gap repair, identity probes (/api/me), and artifact retrieval all run here. Cookies never enter application code; the session's cookie jar supplies them. The per-message stream credential observed in the bundle (§3.2) is handled the same way: fetched from the authenticated route, held in memory for the lifetime of one stream attempt, and never persisted or logged.

Hypothesis to test that session.fetch() attaches the partition's cookies by default (U3). If it does not, the fallback is to perform the same read inside the partition's page via CDP Runtime.evaluate; that is a smaller step than it sounds, but it increases coupling to page internals and must be recorded in provenance as a page-context read.

5.4 L3 — the gated loopback proxy

An app-owned HTTP proxy on 127.0.0.1, configured per account session with session.setProxy(), terminating TLS with a locally generated CA whose certificate is accepted only by our own sessions through session.setCertificateVerifyProc().S11 Nothing is installed into the system trust store, and no other application can use it: the proxy binds to loopback with a per-run secret path/token and refuses any request that does not carry it.

What it adds

  • Byte-level ground truth for request and response bodies independent of CDP, including chunk framing, which makes "did Arena send it?" separable from "did our observer see it?".
  • Visibility into worker- and service-worker-initiated requests, which CDP sees only when the right target session is attached.
  • A second, independent implementation to reconcile against — the strongest available gap detector.
  • Raw WebSocket frames and handshakes without depending on CDP event completeness.

What it costs

  • TLS interception complexity: per-host leaf certificate generation and caching, ALPN handling; interception is simplest over HTTP/1.1, so intercepted hosts negotiate HTTP/1.1 (a measurable latency cost).
  • QUIC must be out of the path for proxied hosts; a proxy configuration is expected to disable QUIC for proxied destinations, which must be confirmed in P0 rather than assumed.
  • A new failure surface: if the proxy dies, the affected account's browsing must fail open (direct connection) with capture marked degraded, never fail closed.
  • Significant implementation effort, which is exactly why it is gated rather than default.

Entry gate: enable when A0.2 or A0.5 shows CDP-only capture produces more than incidental incompleteness for a mode the owner uses, or when a specific research question requires byte-level evidence that CDP cannot supply. Exit gate: disable the proxy for an account if it produces no additional observations over a defined observation window, or if it introduces browsing failures.

5.9 Reconciliation and gap detection

  • Continuity checks: event-id monotonicity within a stream, expected part ordering (for example, a terminal finished after content), and response accounting (bytes/chunks seen vs. declared length when one exists).
  • Cross-layer diffs: when the proxy is enabled, request and response sets are diffed per account; a request seen by exactly one layer becomes an investigation item in diagnostics.
  • UI reconciliation: after a turn, the rendered conversation is compared to the captured parts — only to detect missing content, never to overwrite captured content with rendered text.
  • Remote reconciliation: the periodic sync compares remote listings and details against local records; differences become new observations or conflicts, never destructive updates.
  • Quarantine: traffic that cannot be attributed to an account, a conversation or a target is stored as an unattributed observation with its evidence, visible in diagnostics, and is excluded from transcripts. Attribution is never guessed from content similarity.

6.2 Evidence required before any read is used

An endpoint name, an HTTP method, or a successful page navigation proves nothing about replayability or read-only behavior. Before the sync engine performs a read autonomously, all of the following must be recorded as verified evidence for that operation:

  1. Owner-session binding: the request was issued with the specific account partition's cookies, and the response echoed an identity consistent with that account (for example the account route observed in the bundleS7). A conversation URL or opaque id alone never establishes ownership.
  2. Read behavior: repeated identical calls return equivalent data, and a canary observation shows no state change (no new conversation, no modified timestamp, no altered vote) after the call.
  3. Effective scope: the result set is the account's own data — verified by comparing a short listing against what the account's own UI shows, not by trusting the route name.
  4. Pagination behavior: cursor or offset, ordering guarantee, page-size limits, and behaviour under concurrent writes (a page re-fetched must produce a reproducible boundary, recorded as a page fingerprint).
  5. Detail retrieval: whether the listing carries enough content or a detail read is required per conversation, and whether that read is stable and idempotent.
  6. Failure vocabulary: what auth expiry, rate limiting, and "not found" look like from this endpoint, so the engine can classify rather than guess.

Each verified operation is written into the protocol catalog (§12.2) with an adapter version. Sync refuses to use an operation whose catalog row is not marked verified-read in the partition context that is asking.

6.3 Sync semantics

Job model

  • One job per account per resource kind (conversations, details, artifacts). Jobs are independent state machines with persisted checkpoints.
  • States: queued → running ⇄ paused → completed | failed | cancelled, plus blocked reasons: auth_expired, rate_limited, challenge_present, drift_detected, account_mismatch.
  • Progress is a checkpoint, not a percentage: last committed cursor/page fingerprint, items seen, items new, items changed, conflicts raised.
  • Cancellation commits the current transaction and leaves a resumable checkpoint; nothing partial is promoted to complete.

Correctness rules

  • Identity of a record is (account_id, source_kind, source_id). Source id collisions across accounts are conflicts, never merges.
  • Overlapping or repeated pages are expected; upserts are idempotent and compare a content hash over normalized structure, not raw bytes.
  • Instability (a cursor that shifts, a page whose fingerprint changed) raises a pagination_instability observation and triggers a re-examination of the affected window rather than a silent skip.
  • Concurrency: two accounts may sync in parallel because their sessions and budgets are independent; a governor caps total concurrent network reads, and each account has its own token bucket, backoff (with jitter) and respect for server-provided retry hints.
  • Only the affected account is degraded. Auth expiry pauses that account; it never signs in again on its own and never touches another partition.

6.4 What "synchronized" means

The app never reports "history synchronized" as a boolean. Each account has a coverage report that states: the last successful listing window; the number of conversations seen remotely versus archived locally; the modes and date range represented; known gaps (pagination boundaries not covered, records whose detail read failed); unresolved conflicts; records that are remote_absent; and a confidence statement that listing completeness has not been proven — only observed. The report is machine-readable and exposed through MCP, so an agent can act on it rather than on a green check mark.

6.5 Interaction with live capture

  • Sync skips conversations that are currently streaming in any partition; it records them as "in flight" and reconciles afterwards.
  • A sync that discovers a conversation whose local capture has a gap raises a repair task instead of overwriting; repairs go through the same resume or re-read paths and produce a new observation, preserving the original.
  • Capture and sync never share a mutable buffer: sync writes normalized records; capture writes observations and parts. Reconciliation happens in one place.

6.6 If the listing cannot be verified at all

Documented degradation, not a redesign

If no replayable listing exists (U2 fails) the archive still works, with reduced coverage: live capture covers everything used in-app from then on; owner-driven "open this conversation to capture it" harvesting fills specific holes; imports cover older material; and the coverage report says plainly that historical completeness is unknown. What the design must not do is claim a full history because one known conversation opened successfully — a failure mode the baseline's documentation warns about in exactly those terms.S10

7.6 Keeping Arena-controlled content away from local privileges

  • No bridge into Arena renderers. Arena pages load with contextIsolation, no Node integration and no preload script. There is no IPC path from a page to app services; the only way page-world code influences the core is the validated, size-capped, one-way instrumentation binding (§5.5), which cannot mutate the archive.
  • Permission denial. Every permission request in an Arena partition is denied by policy (setPermissionRequestHandler / setPermissionCheckHandler), including media, geolocation, notifications, clipboard read and file system access.S11
  • Loopback blocking. Requests from Arena partitions to 127.0.0.1, ::1 and localhost are cancelled at the session level, so page content cannot address the MCP endpoint, the proxy control port, or any other local service. This is a deliberate, testable guard against content-driven access to the local control surface.
  • Navigation policy. setWindowOpenHandler routes Arena-targeted popups into the same account partition and opens everything else with the system browser; will-navigate rejects navigation away from Arena hosts inside an account window.S11
  • Host allow-list for observation. The observer classifies traffic as first-party, third-party or unknown. Unknown hosts are inventoried as names and counts only, which keeps discovery honest without turning the archive into a general traffic recorder.

7.7 Key custody and encryption operations

Archive key
32 random bytes generated once, stored as a Keychain generic-password item scoped to this app and unavailable to other users. Only the key reference is stored in configuration; the value never touches disk through app code.
Unlock
The app requests the key at launch after an explicit owner action; the key lives in main-process memory and is dropped on lock or quit. MCP operations never trigger a Keychain prompt: if the archive is locked, MCP writes fail with E_LOCKED and reads return nothing rather than prompting.
Database
SQLCipher-format encryption via better-sqlite3-multiple-ciphers, key supplied in raw hexadecimal form.S11S16 WAL and journal pages are encrypted by the same cipher; temp_store is memory-only; secure-delete is on for deletion hygiene (§8.7).
Artifacts
Each artifact is sealed with AES-256-GCM under a per-artifact key derived from the archive key with HKDF and a random salt recorded in the artifact row; the blob is content-addressed by its ciphertext hash, and the plaintext hash is stored inside the sealed envelope for integrity checks.
Rotation
A rotation operation re-encrypts the database (SQLCipher rekey) and re-seals artifacts; it is a maintenance tool, not a background process.

8Data, identity and provenance

8.1 Source of truth

The design is a deliberate hybrid, because three different questions need three different shapes of storage, and full event sourcing would add ceremony without answering any of them better:

Observation log (append-only)

Sanitized evidence as it was seen: request/response metadata, stream segments, UI signals, downloaded artifacts, sync page results. Encrypted, bounded, and the only place raw evidence lives. Never edited; only appended and eventually pruned per policy.

Normalized core (relational)

Accounts, conversations, branches, turns, parts, participants, identity claims, artifacts, sync checkpoints, conflicts, analysis runs. This is what queries, exports and the MCP surface read.

Derived views (rebuildable)

Full-text index, resolved identity view, coverage reports, analysis metrics. Rebuildable from the other two by a versioned reducer, which is what makes adapter changes safe.

Offline by construction: browsing, search, branch-aware transcripts, provenance inspection, exports, quotas and profiles all run against local state and require no network. Only sign-in, capture and synchronization touch the network; if the network is gone, the archive remains fully usable and every operation reports which capabilities are unavailable and why (the same discipline as the MCP capability report in §9.2).

The rule that keeps the hybrid honest: every normalized field that came from observation carries a provenance reference to the observation that justified it. If a field cannot point at an observation, it must be marked as derived, inferred or owner-entered.

8.3 Identity: claims, not conclusions

Arena exposes several different things that all look like "the model": the label the owner selected, the catalog row behind that label, an opaque id sent in the request, a blind label shown during a battle, and — only after a vote in some modes — a reveal. These are different evidence types with different scopes, and the archive treats them that way.

  • Claims are append-only and scoped. A reveal that applies to a battle round creates a claim scoped to that round; it does not retroactively relabel other rounds or other conversations.
  • Resolution is a view, not a mutation. The resolved identity view applies a documented precedence (arena_reveal > request_catalog > request_payload > ui_label) with the scope of each claim respected, and exposes the remaining uncertainty. Nothing in the view can lose the underlying claims.
  • Unknown stays unknown. If an Agent session's orchestrator is never revealed, its resolved identity is "not revealed", with the selected label preserved separately — mirroring the baseline's own conclusion that an undisclosed orchestrator is a valid result rather than a capture failure.S10
  • Similarity is never identity. Style-based inference lives in a separate table with a different label, cannot feed the resolved identity view, and is always presented as a hypothesis (§10.4).

8.5 Transactions, crash recovery, migration

  • Write unit: one transaction per stream segment batch, per sync page, per artifact seal. Observers append to the encrypted spool first (cheap, sequential), and a reducer applies spool records to normalized tables in batches.
  • Crash recovery: on start, the reducer resumes from the last committed spool offset; unapplied spool records are replayed. Because parts are idempotent by (stream, event id), replay cannot double-append.
  • Partial writes: a turn whose reducer run was interrupted keeps its capture state and gains a "reducer interrupted" observation; nothing is promoted.
  • Migrations: a schema_migrations table with forward-only numbered steps; adapter versions are tracked separately from schema versions so that a parser change does not imply a schema change; a migration takes an encrypted backup before running, and downgrades are explicitly unsupported (restore from backup instead).
  • Consistency checks: an integrity tool verifies that every normalized row's provenance references resolve, that FTS matches its source tables, that artifact rows have sealed blobs, and that no record lacks an account.

9Full LLM operability: the local MCP surface

The primary interface is a local MCP server in the app's main process. Every capability the GUI has is reachable through it; every long-running operation is a job with status, progress, cancellation and resumability; and every destructive operation requires an authorization artifact that archived content cannot produce.

9.1 Transport, connection model and trust boundary

stdio (primary)

  • The app runs the MCP server on a stdio channel for a client process it starts or that starts it. There is no listening socket, so there is no remote-content access path and no DNS-rebinding class of risk.
  • Implemented with the official TypeScript SDK (@modelcontextprotocol/sdk), which the app already depends on for schema validation and transport handling.S13
  • Lifecycle: the server is always available while the app runs; if the archive is locked, write tools fail with E_LOCKED rather than blocking on a Keychain prompt.

Loopback HTTP (optional)

  • Only if a target client cannot speak stdio. Binds 127.0.0.1 on an ephemeral port; requires a bearer token generated at launch and stored in the Keychain; validates the Host header; rejects browser-style cross-origin requests.
  • Arena partitions are already blocked from loopback addresses by session policy (§7.6), so page content cannot reach it even without the token.
  • Documented as a degradation of the security posture: an additional listening surface that must be explicitly enabled by the owner, and can be disabled at any time without losing capability.

9.2 Capability discovery and diagnosing unavailability

  • The server advertises tools, resources and (optionally) prompts at initialization; tool descriptions state scope requirements and side effects, and every tool name is prefixed by domain (archive_, capture_, sync_, accounts_, diagnostics_, analysis_, maintenance_).
  • diagnostics_capabilities returns the current, machine-readable state of every subsystem: capture per account, proxy enabled/disabled, adapters and versions, drift counters, storage health, encryption state, MCP transport in use, and for each tool a degraded or unavailable reason where applicable. An agent must be able to answer "what can I do right now, and why not the rest?" without reading logs.
  • Unavailable operations return a typed error rather than disappearing, so a client's capability cache never silently misrepresents the app: for example, a mode with no verified adapter returns E_UNSUPPORTED with a remediation hint.
  • Progress for long jobs is reported through the protocol's progress notifications where the client supports them, and always through *.status tools that can be polled.

9.4 The destructive-action guard

The archive contains text written by models, pages, tool traces and possibly the owner's own notes. None of it may authorize deletion. Authorization is a separate, unforgeable-by-content artifact:

  1. Directive minting is a trusted-channel-only operation. Directives are created by the GUI's native confirmation dialog or by a local CLI that requires a terminal interaction. Neither is reachable from Arena renderers, from MCP tools, or from archived content.
  2. A directive binds exactly one scope. It contains the canonical account ids, the conversation ids (or "all" for archive scope), a count, a hash over the canonical scope representation, the creation time, and a random id. The scope is shown to the owner in human-readable form before minting.
  3. Consumption is single-use and time-bounded. A destructive tool requires directive_id plus the scope hash; the core verifies the hash matches the arguments actually presented, consumes the directive, and logs the consumption. A second call fails with E_CONFIRM_REQUIRED.
  4. Content cannot influence authorization. No tool accepts a natural-language instruction, a file path from archived content, or a "confirm" flag as authorization. The tool schema contains only typed identifiers; the directive is a separate field that only trusted channels can produce. Prompt-injection payloads in a transcript therefore cannot cause deletion — the worst they can do is waste a call.
  5. The strongest confirmation is reserved for the widest scope. Archive-wide deletion requires typing the archive label in the GUI or CLI; account-wide deletion requires a native confirmation listing the account and counts; single-conversation deletion requires a native confirmation that displays the conversation title and id.
  6. Deletions refuse while work is in flight. Any capture or sync job for the affected scope must be paused or completed first, so a deletion cannot race a write.

9.7 One service layer, and where the browser must be involved

  • Parity by construction: the GUI renderer and the MCP server both call the same service layer in the main process. No capability lives only in a menu handler and no capability lives only in a tool handler. A contract test enumerates GUI actions and asserts each maps to a service call that a tool also exposes.
  • Browser interaction is explicit: only two workflows genuinely require the GUI — completing a sign-in (or pasting a verification link) and resolving a challenge. Both are represented in MCP as pending owner actions with a handle and instructions, so an agent can drive everything up to the point where a human must click, and detect that state instead of hanging.
  • Everything else is drivable: browsing an account partition to a known route (capture_open_route) exists as a narrowly-scoped tool limited to Arena hosts and read-only navigation — it never submits forms, never votes, never archives or deletes on Arena's side.

10Analysis and later modalities

10.1 Principles

  • Local only. No analysis calls a network service. Later-stage model weights, if any, are downloaded once under an explicit gate and pinned by hash (§10.5).
  • Deterministic first. Start with statistics a reader can recompute by hand from the transcript. Anything less transparent must justify itself against that baseline.
  • Identity evidence gates cohort formation. Cohorts group by observed or revealed identity only. A guessed identity is not a cohort; it is a separate, clearly-labelled experiment.
  • Uncertainty is part of the output. No metric is returned without its sample count, and no comparison is returned without its caveats.

10.4 Later similarity and fingerprinting experiments

The archive's most tempting claim — "this model's prose resembles that model's" — is allowed only as a confidence-qualified hypothesis that never feeds the identity view. Before any such experiment runs, it must declare:

  • Leakage-resistant splits. Train and test split at the conversation level, with branches and regenerations of the same prompt kept on one side, since near-duplicates across a split inflate results.
  • Prompt and topic controls. Matched-prompt comparisons where possible; otherwise stratification by prompt features with only matched strata reported.
  • Negative controls. Same-model, different-topic pairs (should score low if the signal is stylistic) and different-model, same-prompt pairs (the actual question).
  • Calibration and unknown handling. The classifier must be able to answer "unlike any known cohort", with a calibrated threshold rather than a forced choice.
  • Predeclared minimum evidence. No universal sample-size folklore: the run must compute, on this corpus, the sensitivity of the intended test to plausible effect sizes, and the analysis is only permitted to report a result if that simulation was recorded beforehand.
  • Reproducibility. Pinned preprocessing, versioned code, recorded seeds, and the same corpus-hash discipline as profiles.
  • Abandonment criteria. If performance collapses once prompt and topic are controlled, or if calibrated confidence intervals straddle chance on held-out conversations, the result is recorded as negative and the experiment is stopped rather than re-tuned on the test set.

Entry gate for embeddings or local models

Embeddings and local classifiers cost packaging, memory, weight acquisition and reproducibility discipline. They are admitted only when a specific, written research question exists that deterministic profiles cannot answer, the question's test has a recorded sensitivity analysis on the actual corpus, a pinned model is available for fully offline inference, and measured runtime cost fits the machine's budget. Otherwise they stay out; the deterministic engine is the product.

11.3 Fixtures

Synthetic (harness behaviour only)

  • Stream fixtures for both parser versions: contiguous, gapped, duplicated, reordered, truncated, malformed-record, unknown-part-type, late-terminal.
  • Sanitizer fixtures: headers, cookies, JWTs, bearer strings, nested JSON-in-JSON credentials, signed URLs, verification links — asserting that none survive any write path, including parser-error paths.
  • Isolation fixtures: two synthetic identities, interleaved writes, asserting partition and attribution separation without any real account.
  • Pagination fixtures: shifting cursors, repeated pages, and a page fingerprint that changes between fetches.
  • Directive fixtures: valid, expired, replayed and scope-mismatched directives.

Limits, stated plainly: fixtures prove the harness behaves as designed. They say nothing about Arena. They must contain no real credentials and no unrelated private data.

Owner-session acceptance (cannot be substituted)

  • One real streamed turn per mode the owner uses, with completeness verification against what was rendered.
  • One resume repair in a real mode, with event-id continuity recorded.
  • One full sync of a real account, including interruption and resume, with the coverage report inspected by the owner.
  • One real download or generated artifact attributed to its conversation.
  • Two real accounts signed in simultaneously, interleaved, with an isolation probe afterwards.

Platform documentation and synthetic fixtures cannot establish any of these; they are the gates that decide whether the product is trustworthy.
