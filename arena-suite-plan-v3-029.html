01 / THE DECISIONChoose CEF for its request-context capture path. Make it earn the choice.

Recommendation Use the Chromium Embedded Framework in a small Objective-C++ AppKit shell, with a Rust archive service. Keep one Chromium engine, independent persistent request contexts for concurrently active accounts, browser-process response filters for HTTP bodies, and in-process DevTools protocol observers for frames, targets, and UI evidence.

Store normalized conversations plus bounded sanitized observations in SQLCipher; protect its random key with macOS Keychain. Use independently encrypted artifacts. Expose all services through a local stdio MCP bridge. Start with a plain native diagnostics window, not a second web UI or a Python analysis server.

The decisive distinction is not ownership of a window. CEF documents a request-context handler for requests whose browser/frame may be absent, including service-worker requests, and a response filter that receives response content. This lets the app install the observation path before navigation instead of reconstructing every body through page monkey-patches or debugger buffers. [CEF]

But not every byte necessarily traverses that path. WebSocket messages, cache/service-worker synthesized responses, worker startup, and renderer-local artifacts require different checks. The recommendation is conditional on signed-in tests; “network filter” is not synonymous with complete transcript.

Why not Electron first?

Electron is easier to build and offers good partitions and downloads. Its documented webRequest interface supplies request/response metadata, not a general streaming response-body filter. Bodies and WS messages instead come through webContents.debugger/CDP, with target lifetime and buffering constraints. CEF buys a less target-dependent HTTP body path. [Electron]

What forces a change?

If CEF misses required Arena bodies or cannot maintain email login/sandboxed ARM64 operation, run the same falsification suite on Electron. Switch only if Electron passes the failed cases. If neither passes, ship no claim of complete v1 text capture; retain an explicitly partial browser recorder while reassessing. A Chromium fork is last resort, not the initial plan.

CEF versus Electron: what the extra native work buys

  • Fetch/XHR and streamed HTTP: CEF's filter is installed with the context before navigation. It can tee response chunks without asking a debugger to preserve/retrieve them. Electron's debugger can also capture streams, but experimental CDP enrollment/buffer support must match the bundled Chromium. Neither implies Arena's payload parser is known.
  • Workers/SWs: CEF headers explicitly describe null-frame SW requests. They also warn that contexts sharing storage may supply an arbitrary non-null handler; therefore do not share storage between accounts. SW CacheStorage/synthesized responses may evade ordinary network filtering. In both stacks, test CDP related-target capture; autoAttachRelated is browser-target-only, not guaranteed through an embedded page target. setAutoAttach may need recursion. [CEF] [CDP]
  • WebSocket: a response filter is not a WS message decoder. Use CDP frame events and reassemble application framing. Target attachment matters here in CEF just as in Electron. If required WS targets are unavailable in CEF but available in Electron, that is a genuine reversal condition.
  • Downloads: both provide native application-owned destination and lifecycle control. Neither callback is an encryption writer. CEF download data normally lands in an app-controlled staging file before encrypted ingestion; the residual plaintext is addressed explicitly below.
  • Cost: both ship a Chromium engine and multiple processes. CEF removes a resident Node runtime but adds native glue and a Rust service; lower total RSS is a hypothesis, not the justification. Measure process-tree footprint, CPU, swap and pressure with two active accounts. No fixed archive size or invented benchmark is assumed.

Custom Chromium fork: last resort only. Consider it only after a required, observed Arena transport cannot be captured through maintained CEF or Electron APIs, the owner accepts ongoing browser security maintenance, and a narrowly scoped upstreamable change has been identified. Until then, explicit capture gaps are preferable to an unmaintainable browser.

Persistent account scope is not the same as a login session

Use three separate identifiers:

  • account_scope_id: immutable local archive identity, established by observed first-party account evidence and owner confirmation. It survives logout.
  • partition_id: random persistent browser profile identifier. Exactly one account scope can bind to it at a time. Dedicated cache/storage directory; never CEF global/default context.
  • session_epoch: increments on auth loss, sign-out, mismatch, restart/revalidation. Every capture envelope and sync capability includes the epoch. Old in-flight replies cannot become observations under a new login.

Create a new unbound partition before login. On sign-in, observe account settings/self-identification from the correct first-party page/read (field unknown until discovery), display a local alias plus the visible identity, and ask the owner to confirm the binding through trusted controls. Owner confirmation alone does not prove a random conversation's ownership. Repeated login may rebind to an existing scope only with the same verified account subject and an explicit owner action; email/title/URL similarity is insufficient. If a stable subject cannot be established, keep that partition's observations provisionally scoped and disable automated history replay until page-backed ownership can be verified. Two unrelated scopes may contain the same source ID without conflict in storage; never merge them.

CEF isolation setup: unique absolute cache_path under each profile, non-shared CefRequestContext::CreateContext(settings, handler), no context created by copying another context, common root only where CEF requires a parent path. Assert IsSame=false and IsSharingWith=false; then actually test cookies, local/session storage, IndexedDB, HTTP cache and service-worker registrations across two accounts. Contexts may share a browser/GPU process, not storage authority. The host-side registry binds a context object to a partition at creation, so null-frame requests still have scope. Browser-specific resource handlers delegate to the same context policy rather than shadowing it.

Email authentication and navigation

Use normal headed Chromium presentation and Arena's own email UI. Handle browser-created popups via the originating context; intercept window creation early enough to install capture, and visibly label every window with its partition outside page-controlled chrome. Verification links received by email are opened with a partition chooser in trusted native UI; one-time links/codes enter a secure transient channel, are not logged or retained in MCP history, and are forwarded only to that partition. MFA/CAPTCHA remain owner-driven; an MCP request can present or resume the flow, but human secrets and challenges need not be exposed to the LLM. An OS link opening in another browser does not authorize importing its cookies. Keep an “open verification link here” path as the documented workflow trade-off.

Access categories: discovered first-party authenticated reads are not access-control bypasses just because they are undocumented. Replay is allowed only after ownership/read verification. Normal browser presentation and manual challenge completion are compatibility measures; do not build stealth plugins, automation-signal masking or challenge evasion into the plan. A UI hidden/disabled control may represent availability, payment or authorization state—not simply an API inconvenience. No required control-bypass technique was established here; encountering one is a pause-and-investigate condition, not permission to guess endpoints or escalate access. Expired authority must be restored through Arena, not worked around.

04 / DISCOVERY & LIVE CAPTURECapture observations first. Earn transcript completeness separately.

The smallest useful vertical slice

Before building a history browser or model profiler: open an owner account in an instrumented CEF context, submit one benign text prompt normally, capture one HTTP or WS response, sanitize it, write one observation and normalized participant revision in SQLCipher, then retrieve it through transcripts.get with provenance and a completeness verdict. Repeat with a deliberately stopped response. In parallel establish the second partition and verify no account contamination. A synthetic transport proves the harness, not Arena support.

Discovery is a maintained inventory, not a credential console

Observe all traffic encountered by supported workflows, but retain different classes of information. Session-level request metadata covers known conversation reads/writes, auth/account operations, assets, analytics/configuration, artifacts, and unknown/unrelated origins. A hostname containing “arena” or a CDN URL alone does not prove first-party ownership. Mark an origin as first-party only with evidence from Arena's observed initiator chain, application configuration or an owner-session workflow; otherwise keep it “unknown/external.” Record encountered external-origin counts without retaining unrelated bodies. Do not scan undisclosed infrastructure.

Protocol catalog entries are versioned and exportable as sanitized JSON. Unknown operations have no replay permission. Authentication/password/token exchanges are classified using ephemeral routing metadata, never body retention; response schema discovery uses field names/types and bounded structural signatures, not sample secret values. Assets/analytics retain route templates, safe media type, status/size buckets and timing, not content.

Observation pipeline and transport-specific mechanics

  1. Install context policy before creating a navigable browser. Every context gets its handler and immutable partition handle. The resource request callback records sanitized metadata and selects a retention policy. Filters copy only eligible payload families; pass-through output must be byte-identical regardless of parser state. CEF's documented filter ownership/partial-buffer rules are followed exactly. Never keep callback-buffer pointers after return. [CEF]
  2. Bound the tee. Copy accepted chunks to a per-partition bounded queue for the Rust sanitizer library in the browser host. Never block the CEF IO thread on the database or LLM. If capacity is exceeded, let Arena continue normally, drop capture bytes, emit a gap with byte/request range, and degrade affected observations. Reserve a small independent control queue so overflow itself cannot disappear. During explicit unknown-payload inspection the raw memory queue is smaller and short-lived.
  3. Parse HTTP incrementally. Byte chunks are not tokens or events. Use a streaming UTF-8 decoder and adapter-selected framing: JSON documents, newline-delimited records, SSE line/event framing, or another observed family. Handle split multibyte characters, CRLF, nested JSON and boundaries across any chunk. Preserve logical event IDs/sequences if supplied; otherwise assign local ordered offsets. Compression behavior of the filter is a test, not an assumption. Completed HTTP status or EOF alone does not prove model completion.
  4. Observe CDP separately. Register AddDevToolsMessageObserver before active navigation; enable Network/Runtime/Page only where supported. Attach related worker/frame targets recursively with session IDs; track attach/detach/crash/navigation timestamps. Waiting targets must be released with a watchdog, even on observer failure. Do not await a command that needs an active target while keeping that target paused: consulted CDP documentation explicitly warns about durable-message enablement deadlocks. Only invoke supported commands in the pinned protocol. [CDP]
  5. WebSockets and EventSource. Use CDP webSocketFrameReceived/Sent and per-target request correlation; decode text/binary according to the observed protocol. Application records can span messages; reconnecting sockets are new transport instances. EventSource events provide parsed messages; fetch-based SSE is not necessarily native EventSource, so byte framing remains necessary. Never count the same event from filter and CDP as two model deltas. Retain the secondary mechanism as corroborating evidence.
  6. Worker/SW and cache coverage. Match context-level metadata/filter counts against CDP and UI for dedicated/shared workers, SW network fetches, CacheStorage and synthesized responses. A missing filter with visible content is a gap, not a no-response result. CDP getResponseBody or experimental stream/durable-message facilities are per-request fallback when supported; they can fail due to eviction or navigation. Do not globally bypass/disable service workers or caching to manufacture a passing test: this changes the user's normal Arena workflow.
  7. UI evidence. Use app-owned CDP DOM snapshots/isolated-world reads at navigation readiness and relevant UI changes, narrowly scoped to transcript, participant labels, titles, branch/revision controls, vote and reveal widgets. A document-start script/MutationObserver may report DOM changes but gets no archive bridge. Page-world wrappers are a diagnostic last resort, never the primary capture path. Cross-origin frames, virtualized content, canvas and closed shadow roots may remain incomplete. Remote text is still untrusted even when rendered.
  8. Persist sanitized projections atomically. The host strips unrelated fields and credentials, emits typed observations to the core, and discards raw buffers. Core revalidates schema, scope/epoch and quotas before inserting observation + normalized changes + search updates in one transaction. The host cannot access archive keys or read existing transcripts. Sanitizer failure closes retention for that operation; it never falls back to saving the raw body.

Stream reconstruction, branches and conflicting evidence

Use source conversation/turn/branch/revision IDs only after their meaning is observed. Without a reliable ID, create local provisional IDs plus an observation relationship; do not hash text into identity. A comparison owns participants (left/right or other displayed positions), each with its own response revisions. A user turn may fan out to two responses; regeneration adds a revision, editing/rebranching adds a branch edge, and late reveals add identity evidence with an applicable range. Preserve observed source sequence numbers, event IDs and predecessor links; do not invent missing ones.

Duplicate transport delivery can be collapsed only using an established source event ID and payload fingerprint within the same account/conversation/stream generation. A repeated cumulative snapshot replaces that source snapshot's projection; it must not append as a delta. If the adapter cannot distinguish snapshot from delta, mark parser ambiguity instead of guessing. Reconnect attempts carry separate stream IDs until source continuity is proven. Late events update their original epoch/response only; navigation never silently assigns them to the new page. Network and UI text differences remain two evidence values with a conflict (possible server snapshot, rendering transformation or missed segment); the usable transcript records its chosen source and alternative, not last-write-wins.

Source timestamps retain raw safe value, parsed value, precision/time zone if known; local wall and monotonic capture times are separate. Titles can change. Votes store visible choice, time and source; an observed click is “vote attempted,” while a visible confirmed state or proven response establishes “vote observed.” Unknown modes/participants remain unknown. Required v1 coverage includes battle, direct, side-by-side, history/search/pagination/archived views, selected and blind labels, late reveal, titles, branches/regenerations and failed/stopped/partial states when observable; unavailable source fields receive explicit capability/gap flags, not fabricated values.

Download and artifact capture

Verified fact CEF offers OnBeforeDownload and OnDownloadUpdated with destination/lifecycle control; callbacks do not supply an encryption stream. [CEF downloads] Choose an app-controlled, random-name, mode-0600 staging file in a mode-0700 account directory; never honor a remote path or filename as a filesystem path. Track originating context/browser/gesture, transfer state, byte count and safe media type. A null/unattributed download cannot inherit the most recently focused account.

For verified replayable GET resources the service may use an owner-session authorized read to feed encryption directly, avoiding download staging. Do not automatically repeat a POST or signed one-shot action. Browser-generated blob downloads use native download staging; renderer blob extraction is an explicitly tested fallback without new local privileges. After completion, sanitize supported textual artifacts, encrypt, verify length/authentication, then atomically publish the blob row and unlink staging. Failed/interrupted transfers are retained only as marked incomplete encrypted artifacts when useful; otherwise remove staging. Direct application ownership is achieved without an extension/companion bridge, but temporary plaintext is a disclosed limitation.

Qualification procedure: no “GET means read-only” shortcut

  1. Observe the owner opening history, searching, paging, toggling archived inclusion and opening known details. Associate each action with context/epoch, identity evidence, initiator and response. Do not automate speculative endpoints or unrelated object IDs.
  2. On owner-selected harmless records, capture before/after state (content, revision, votes, archive flag, counts and visible read/updated markers). Classify effects across normal navigation and controlled replay. A request that marks “last viewed” is not strictly side-effect-free: declare that bounded effect and require opt-in; a request that votes, modifies, deletes, launches a tool or alters content fails sync qualification. HTTP verb/name alone is insufficient.
  3. Establish owner association by verified account identity plus history membership/details reached from that account's own listing or a captured own-creation chain. Shared/public URLs opened in a signed-in account are not automatically its conversations. Where detail ownership is ambiguous, store an isolated non-projected observation and ask for evidence; no archive reassignment.
  4. Observe cursor/offset behavior, archived/nonarchived filters, search scope, detail response completeness and termination. Compare overlapping pages, repeat scans while creating a new conversation, and re-open first/last samples. Confirm any server count is scoped and semantically understood. A “no results” search may be a filter, not global exhaustion.
  5. Approve a signed/versioned adapter manifest listing allowed read operations, schemas, redirect origins, side effects, identity proof and evidence IDs. Bind short-lived execution capabilities to account/partition/epoch. Unknown operations remain non-replayable; drift automatically removes qualification until retested.

Credentials and replay implementation

Prefer a browser-context native read (CefURLRequest with the account request context, where the pinned API supports the needed semantics) or a constrained same-origin page read through the app-owned browser when session/browser-bound state demands it. Prove cookie, CSRF and token-refresh behavior in Gate D; do not assume native requests reproduce browser fetch/CORS/client-bound token behavior. Network replay still uses Arena's authenticated authority, not an alternate login.

Browser context-managed cookies need not be exported. If an observed flow uses bearer/CSRF material that native code needs, keep copies in host memory only, in short-lived handles scoped to the epoch; refresh only through the observed, allowed same-session flow. Do not send these secrets to archive-core or the LLM. Restart/expiry requires browser revalidation. Scope-specific 401/403, challenges or redirects end that attempt; no credential import, brute-force retry or automatic fallthrough to another account. A sanitized checkpoint stores an opaque secret handle only if reconstructible, never a credential-bearing URL. If a cursor itself contains authority, keep it in volatile memory; restart with a conservative rescan after a crash instead of persisting it.

Sync now, resumption and concurrent live capture

sync.start accepts an explicit nonempty list of account scopes; creates one parent job and independent child jobs. Default one network read at a time per account, at most two accounts syncing concurrently; live capture has priority over backfill. Under memory pressure serialize scheduling, not account state. One account's backoff/challenge/sign-out never changes the other's epoch, cursor or authority. Automatic sync is off by default, explicitly enabled per account, and scheduled only after identity revalidation.

What “synchronized” means

A per-account report specifies filters (including archived), scan interval, endpoint/adapter version, authority proof, pages visited, unique listed IDs, details attempted/succeeded, failures, suppressed local deletions, branch/state coverage and termination reason. “Synchronized for the observed listing scope” means that qualified enumeration reached its observed end and every eligible listed detail was retrieved/reconciled or explicitly accounted for. It never implies inaccessible/deleted conversations, transient revisions, all modalities or legacy history absent from the listing have been recovered.

If no reliable listing/pagination is verified, Sync now becomes a bounded UI-assisted collection job returning coverage=visited_only. Maintain a frontier of IDs actually encountered in owner history; collect those details, saved known-own creation chains and future visits. Do not guess IDs. Without complete detail representations, preserve page snapshots with UI-only coverage. A user-supplied known conversation can be captured with ownership evidence, but does not improve the claimed coverage of all history. If an export later proves richer, merge by same-account source identity and provenance, not content similarity.

Transactions, crashes, migration and recovery

  • One SQLCipher writer actor; WAL mode, foreign keys on, full synchronous durability initially, short batches bounded by count/time. Commit observation + projections + field evidence + FTS changes together. A response may span transactions; only a proven terminal signal promotes outcome. On crash, dangling active observations become gap:process_exit; do not relabel them as model failures.
  • Artifacts use random local names: encrypt to temporary ciphertext, finalize/authenticate, fsync, rename, then insert reference. If DB commit fails, startup GC removes unreferenced ciphertext; if a referenced file is absent, mark artifact missing rather than silently deleting its record. Recover interrupted staging via an explicit bounded cleanup journal.
  • Migrations are numbered, transactional where possible, and preceded by a verified encrypted backup. Data rewrites run into a new DB then atomic swap, retaining the old encrypted copy until verification. Verify SQLCipher authentication and SQLite structural integrity separately; cipher_integrity_check and integrity_check are not interchangeable. [SQLCipher]
  • Backups use a keyed SQLCipher backup/export path into another encrypted DB, plus encrypted blobs and a manifest of hashes/schema/keys required. Never copy only the live main DB and ignore WAL. Restore to a new directory, validate, then switch while all jobs are stopped. Browser profiles are excluded by default; restored archive data is offline-readable, but browser login must be re-established independently.

Encryption and secret handling

Generate a cryptographically random 32-byte archive key in archive-core. Store it as a non-synchronizing Keychain item with a stable local app identity/access policy; unlock is an explicit owner operation, with unattended session use only if the owner chooses that policy. Fetch the key directly through security-framework, never via command-line args, environment, shell output or logs. Code-sign the local app/helpers with a stable owner-controlled identity where feasible; development rebuilds may trigger Keychain approval. Do not claim an ad-hoc build creates a robust same-user security boundary.

Use SQLCipher default encrypted header and authenticated pages; key every connection before access, ensure WAL contains encrypted pages and configure temp storage in memory. Verify the actual compiled cipher version/provider and FTS5 availability. Enable SQLCipher memory wiping with measured performance impact; Rust secret buffers use zeroizing wrappers where possible, but CEF, allocator copies and OS memory remain residual risks. [SQLCipher]

Artifacts use the age crate's streaming X25519 recipient format. Generate a separate identity per account archive generation; store its private identity inside SQLCipher. Individual artifacts include only encrypted content and nonsecret format headers; source names, digests and references are in SQLCipher. Default FTS and deterministic analysis outputs stay inside SQLCipher; no external plaintext vector/search index. Large binary artifacts cannot be reliably scrubbed of embedded credentials: unsupported binaries are reference-only by default; retaining the owner's actual binary file requires explicit artifact-retention consent and is not treated as safe diagnostic evidence. Textual code/tool artifacts are parsed and filtered before retention.

A concrete destructive-action guard

MCP cannot reliably tell a direct user instruction from a model echoing retrieved text. Therefore no ordinary tool argument such as user_confirmed=true authorizes deletion. The core's approval broker accepts only a direct owner decision in trusted native chrome, or a separately paired client control channel whose human-approval event is authenticated and unavailable to the model/tool-result stream. The approval binds manifest hash, exact named accounts/archive generation, action, scope flags, expiry and nonce; it is one-use and invalidated if impact changes. Require this for conversation deletion too, and always for account/archive deletion, restore-overwrite, browser-profile erasure and suppression reset.

The agent can prepare, explain, request approval, commit, monitor and recover the entire workflow through MCP. When no trusted client approval channel exists, it receives APPROVAL_REQUIRED and opens the native confirmation via the same service; the owner makes only the authorization decision. Browser automation cannot click native approval chrome, inspect approval tokens, or type into that channel. Pairing exposes read/control capabilities, not an unrestricted approval minting tool. The OS owner remains able to delete files directly; that is outside the app threat model.

Archived prompts, responses, tool traces and diagnostic text always carry content_trust=untrusted; display them as quoted data and never translate their imperative text into actions. Retrieved content cannot change tool permissions or approval requirements. Restrict browser action automation to the explicit user-requested workflow; no generic shell/CDP evaluation, arbitrary filesystem paths, or remote endpoint execution provides an escape hatch around this policy.

Long profiles run in a cancelable, bounded background job, never on CEF IO threads.

What one heavy user's corpus can and cannot support

It can describe this owner's observed responses under Arena's presentation and selection conditions. It cannot estimate a model's universal style, capability or authorship. Selection into Arena modes, repeated preferred topics, prompt wording, language, conversation history and branches confound model comparisons. Hidden system prompts, decoding settings, tools, safety layers, aliases/routing, temporal backend changes and Arena post-processing may dominate measured differences. Sparse model/time/topic cells need visible counts and withheld conclusions, not smooth charts that imply evidence. Vote preferences are not independent performance labels. Treat temporal windows and source label changes as separate cohorts until justified otherwise.

Embeddings and local ML: deferred, not quietly installed

Recommendation No embeddings or local LLM in v1. FTS and deterministic feature vectors answer initial browsing/profile needs at lower packaging/resource cost. Entry gate: a predeclared retrieval/topic-control task with relevance labels must beat FTS or transparent features on held-out owner conversations sufficiently to justify latency, memory and maintenance. If it passes, use an on-demand isolated local runner, e.g. a pinned llama.cpp embedding-capable build and a compatible licensed GGUF embedding model selected by that experiment; do not assume every model file supports embeddings. Record weight origin, license, SHA-256, conversion provenance, prompt template, tokenizer, normalization, dimensions, runtime and numerical settings. Download only with owner approval; disable network after setup. Store vectors in SQLCipher initially and shut down the runner when idle. Reject the feature if the 18 GB machine experiences sustained memory pressure or benefit is indistinguishable from the baseline.

Later similarity / fingerprinting experiment protocol

  1. Predeclare the question: “How similar is this response to the archived labeled cohorts, under controlled prompts?” Output is an unverified, confidence-qualified similarity hypothesis, never proof of identity/authorship. Store inferred candidate labels in analysis output only, not identity observations.
  2. Deduplicate or group near-duplicates, prompt templates, regenerated branches and related conversations before splitting. Split at conversation/family level, not response rows; hold out prompts/topics and later time intervals. Avoid including the same prompt in train and test via two accounts.
  3. Compare transparent feature baselines with any embeddings. Use same-prompt controls, topic-matched subsets, shuffled-label and prompt-only negative controls, withheld model/unknown classes and temporally shifted tests. Treat identity aliases as uncertain groupings, not convenient labels.
  4. Fit/calibrate on validation data only; freeze feature selection, thresholds and abstention rule before final test. Measure calibration, error by cohort, unknown rejection, stability and uncertainty with conversation-clustered resampling. Include open-set/unknown outcomes instead of forcing the closest label.
  5. Determine minimum evidence empirically from learning curves, effective independent conversation counts, class/topic coverage and precision of held-out estimates. No universal “N samples proves identity” threshold. If controlling for prompt/topic removes the effect, or negative controls perform similarly, abandon identity interpretation and retain descriptive similarity only.

Continue only if predeclared held-out improvements, calibration and unknown-class behavior remain useful across topic/time controls and resources fit. Revise if useful signal is narrow: name the supported subset. Stop if leakage/confounding explains it, labels are too ambiguous or confidence is uncalibratable. A failed experiment is a valid archived result.
