01 · Verdict

The architecture, and the six decisions that carry it

Everything below follows from one constraint that the extension baseline proved by failing it: a recorder that can only see what the page chooses to expose in the page world cannot guarantee completeness. The plan therefore selects the only maintained, public embedding surface that gives an app document-start control and browser-process network observation inside the same partitioned session that holds the Arena cookies: Electron, driven through the Chrome DevTools Protocol.

1.2 — What this buys, in the four terms that decide the design

Capture reliability

Durable-message buffering and browser-process observation remove the two structural causes of the baseline's gaps: hooks that install after the app bundle, and stream consumption that can be truncated by the page or by service-worker teardown. Bodies are observed where they are produced, not where JS happens to wrap them.

Email-auth compatibility

The owner types the password and any one-time code into a real Chromium renderer with no automation flags. Nothing about the flow is faked: no headless signal, no synthetic UA, no credential proxying. Redirects and popups stay inside the same partition and are audited, not bypassed.

Multi-account isolation

Isolation is architectural, not bookkeeping: distinct persist: partitions mean distinct cookie jars, storage, caches and service-worker registrations. The capture session, sync job, provenance key and deletion scope are all derived from the same account_id, so a record cannot silently change owner.

Maintenance

Frontend drift is absorbed by a protocol catalog with adapters and drift alarms rather than by CSS selectors. Every diagnostic an agent needs is a machine-readable resource; every action it can take is a typed tool with structured errors.

1.3 — The honest cost of this choice

  • Engine size and RAM. The app ships its own Chromium. On 18 GB of shared RAM the budget must be explicit (§5.8), and the app must be able to run capture for one account with the other account's views discarded-but-persisted. I deliberately do not quote a benchmark here; §5.8 specifies the measurement that replaces my estimate.
  • DevTools mutual exclusion. Electron's debugger detaches when DevTools is invoked for that webContents. So the app must own the DevTools affordance (or forbid it) for Arena views — otherwise opening DevTools silently stops capture. This is a real failure mode, and it is guarded (§5.5, gate G2).
  • Protocol-message ceiling. DevTools responses are capped at roughly 256 MB per message in Chromium's HTTP handler; oversized bodies must be read incrementally rather than with one getResponseBody. Treated as a design constraint, not an edge case (§5.4).
  • Not the system WebKit. Choosing Chromium means the app's renderer is not the one Safari/WKWebView use. For an archive tool that is correct — capture surface beats footprint — but it is the reason Tauri/Wry loses (§4.3).

What Electron provides that is not merely "a Chromium window"

  • Attach before anything runs. app.on("web-contents-created") fires before navigation for every WebContents, including views created for accounts. Attaching there and driving Target.setAutoAttach({autoAttach:true, waitForDebuggerOnStart:true, flatten:true}) freezes new targets before script execution; I enable Network first, then resume. V parameters are protocol-documented; the freeze/resume ordering hazard is described independently by binding implementations.
  • Bodies outside the renderer. Network.configureDurableMessages exists precisely so response bodies survive a cross-process navigation — the failure class the baseline hits when a route change or reload discards an in-flight stream. V
  • Incremental reads without consuming. Network.dataReceived carries an experimental data field alongside dataLength/encodedDataLength, so the recorder sees bytes and lengths without wrapping the page's ReadableStream. If data is ever absent for a request class, dataLength alone still converts silent truncation into a measured gap — which is the difference between an archive and a guess. V
  • Session authority. Named persistent partitions; per-session cookie, cache and storage control; setPermissionRequestHandler; per-session setProxy (used only in the flagged escalation); per-session download routing. V
  • Privilege separation is explicit. Arena content renders with nodeIntegration:false, contextIsolation:true, sandbox:true, and no app preload in the Arena partitions. Remote pages receive zero app API; observation happens from outside the renderer via the debugger. V

Cost, stated plainly: a bundled engine, a native-module rebuild loop for one dependency, and the DevTools-exclusivity hazard. Addressed in §5.5, §5.8, §11.6 respectively.

CEF is the only candidate that also ships a private Chromium, so it gets a direct comparison rather than a dismissal.

  • Capture depth: loses. CEF's embedding API exposes request/response metadata and cancellation through request handlers; a maintained public path to read a response body from the resource handler lineage is not available in modern CEF. In practice CEF body capture means cefQuery injection (tier 1 again) or enabling Chromium's remote-debugging port — at which point CEF and Electron use the same protocol, with more glue. I — I did not re-audit CEF's current handler surface line by line; this is recorded as a verification gap with test T-C1: a 30-minute CEF probe that reads one streamed body with no injection. If it succeeds cleanly, CEF becomes a serious alternative and Electron's lead narrows to ergonomics and build risk.
  • Downloads and partitioning: comparable. Download callbacks give app-owned save paths; isolated request contexts are a real concurrency primitive.
  • Maintenance and agent-repairability: loses harder. CMake, a C++ build of a very large project, patch-cycle coupling to Chromium releases. For a project where agents do the implementation and the troubleshooting, the failure mode of a broken CEF build is materially worse than npm rebuild.
  • Licensing: BSD-family vs MIT — immaterial for private, undistributed use.

Net: CEF is not excluded on principle. It is excluded because Electron reaches the same protocol surface through a documented, scriptable API, with a cheaper build and a far larger troubleshooting corpus.

The strongest argument against Electron is the one in the brief: 18 GB of shared RAM, and a preference against duplicated engines. WebKit paths answer that argument directly — WKWebView uses the system engine, and WKWebsiteDataStore(forIdentifier:) is a clean multi-account isolation primitive.

They fail on one criterion, and it is the one this project exists to satisfy:

  • There is no supported way to read an https response body from WKWebView. Delegate callbacks cover navigation and policy; WKURLSchemeHandler serves custom schemes only; the Web Inspector protocol is private and unsupported for programmatic use. Body capture therefore falls back to script injection — exactly the tier-1 ceiling.
  • Tauri/Wry inherit that ceiling, add a Rust boundary, and rely on newer per-webview data-store plumbing for isolation.
  • Consequence: with WebKit I would have to declare that the primary capture path is page injection — the explicit disqualifier — or route bodies through a proxy, which forfeits the footprint advantage (a local CA, a proxy, and their own failure modes).

WebKit is therefore preserved as fallback F1 (§17), triggered only if measured Electron residency on this machine is unacceptable and a strictly weaker capture contract is acceptable — DOM and injection witnesses only, with declared gaps as a first-class state.

The rejected branch, stated on its merits: an MV3 extension could approach tier-3 depth by adding chrome.debugger, which exposes the same Network/Target domains, and could approach multi-account isolation only by escalating to separate browser profiles — an ownership problem I do not want to solve inside a browser's permission model.

  1. Lifetime. The capture authority would be a service worker the browser may evict. A recorder's lifetime must not depend on a browser scheduling decision.
  2. Ownership of the debug session. chrome.debugger surfaces the "being debugged" banner, competes with the user's DevTools, and is governed by policy I cannot extend.
  3. Artifacts. Downloads traverse browser UI and the downloads API. The baseline grew a Swift companion to feel complete, and its own verification notes record what still fails there.
  4. Scope. Keychain, SQLCipher, FTS, MCP, analysis and a privileged confirmation UI all live outside an extension anyway. If a native app is unavoidable, the part that matters most should not live in the weakest possible place.

Non-goals, restated so nobody drifts

No chrome.debugger extension, no extension + native messaging host, no extension + companion app as architecture or primary capture path. No custom Chromium fork except as a flagged escalation with a concrete trigger (§5.9). Google OAuth, passkeys and third-party identity flows are not requirements; email sign-in is, and nothing here is gated on the others.

5.4 — Buffering, ceilings, and why numbers are configured not guessed

  • Explicit buffer sizes. Network.enable defaults are tuned for a DevTools panel, not for an archival recorder. Defaults are overridden from vault.capture.netBuf* config, sized as a function of the retention quota (§14.4) — the point being that they are configurable and observable, and that overflow is reported as observer-gap:buffer.
  • Protocol message ceiling. Chromium's DevTools transport has a documented hard cap around 256 MB per message, so getResponseBody is not a strategy for very large payloads. Streaming bodies are therefore assembled incrementally from dataReceived, and getResponseBody is used for bounded JSON reads with a size guard V (cap reported via a Chromium source reference in the baseline issue thread; treated as a limit to respect, not a fact to bet on).
  • Backpressure over loss. The ingest queue is bounded. When full, CaptureBus marks the affected requestId as observer-gap:overflow and continues — an explicit, agent-visible state change, not dropped events.
  • Frame-rate discipline. DOM probes are event-driven (on responseReceived for classified conversation ops, on mutation burst, on idle), never a fixed 100 ms poll: the archive must survive a 200-round session without the profiler becoming the workload.

5.6 — What still depends on page injection (no marketing)

5.9 — Escalation ladder (each rung needs a trigger; nobody skips to rung 3)

  1. Rung 0 · default. CDP Network/Target/Page + bootstrap witness. Expected steady state.
  2. Rung 1 · ordering and coverage fixes. Attach earlier per frame, add Page.getScriptExecutor-style evaluation into specific frames, widen target filter, enable Network on each child session before resume, add flush-on-navigation. Trigger: a classified gap whose cause is sequencing.
  3. Rung 2 · partition-scoped local proxy. For one account only, session.setProxy() to a 127.0.0.1 CONNECT-capable proxy with an app-generated, per-install CA added to that partition's trust path; decrypts only what the proxy sees for that partition. Trigger: T-A4 demonstrates traffic that is invisible to rung 0 and cannot be fixed by rung 1 — i.e. real worker/SW traffic the archive must have. Costs: a CA trust decision by me, pinning complexity, and loss of any expectation that TLS-embedded signals remain pristine. Preserves: complete body capture and ownership of the download path. Forfeits: "we never touch the transport" simplicity.
  4. Rung 3 · custom Chromium fork. Explicitly a last resort. Only trigger: a named, reproduced observation required by v1 that is impossible through both rung 0 and rung 2 and is not a policy block on Arena's side. Then and only then does a fork with a small patch set (e.g. a dedicated unload-safe network tap with durable spill-to-disk) become worth its maintenance cost. Nothing in the current evidence set suggests that trigger; the plan records this so the escalation is a decision, not a mood.

Decision 5-B · why the utility process exists

Parsing untrusted, drifting payloads and running analysis is the likeliest thing in this app to crash or loop. Putting it in vaultd means a bad adapter costs a job, not the archive or the browser session, and restart is a no-op replay from the journal. It also gives the agent one clean place to run reparse --from=<adapterVersion> without touching live capture (§10.6).

07

Discovery as a product feature, not a pre-work phase

The first objective is not "capture Arena". It is "know what Arena does, across every workflow I use, for every account, and notice the day it changes". That knowledge needs a schema, a state machine and a queryable surface, because the agents maintaining this cannot read my mind about which endpoint was which.

7.0 — Three different things that all get called "bypass"

Keeping these separate is what lets the design be described accurately instead of defensively:

  1. Authenticated read access — an undocumented first-party endpoint used with the correct account-scoped session. This is not an access-control issue: the control (session ownership) is satisfied, not evaded. Catalog state owner-verified-read exists precisely to describe when this is safe to automate (§7.2).
  2. Automation compatibility — being a normal browser so the site works: real Chromium, no automation switches, no synthetic fingerprint, popups kept in-partition, challenges left for me. This is about not being broken, not about defeating a control. The plan explicitly does not attempt to defeat a challenge; it pauses and asks me.
  3. Access-control workaround — reaching data that the session is not authorized for. Nothing in this design does this, and the boundary is concrete: requests are only ever issued from inside the partition that already holds the account's session, so an unauthorized read cannot be constructed even by an agent driving MCP — there is no API that takes a token argument, no cookie import, and no ID-guessing routine to call. An opaque conversation ID is therefore never a capability, only a lookup key inside a scope that already owns it.

Assumption, ownership evidence, session binding, failure behaviour and maintenance cost are then stated per operation in the catalog — which is why no separate "is this allowed for my own data" argument is needed anywhere else in this document.

08

Capture semantics and the completeness state machine

An archive whose only claim is "here is text" is untrustworthy by construction. The archive's real product is text plus a defensible statement about how much of it is known. This section is the contract that makes that statement mechanically derivable rather than a mood.

8.1 — Turn assembly

StreamAssembly {                        // in-memory, per (account, requestId)
  account_id, view_id, target_id, frame_id
  op_key                  // catalog key once classified
  chunks: [{seq, t, byteLen, sha256_12, kind: data|ws|es}]
  expectedLen?: number     // from encodedDataLength / Content-Length when present
  terminalSeen: boolean    // adapter-defined end-of-turn marker
  uiWitness?: {renderedTextHash, blockCount, stoppedAt}
  state: assembling → {complete|truncated|stopped|failed|gap}
}

Boundaries are established by conjunction, never by a single signal:

  • Turn boundary = a classified request whose op is adapter-ready for turn creation, correlated with a user-visible prompt node in the same frame; a stream ending is not by itself a new turn.
  • Participant attribution = (requestId → participant slot) from the payload family, corroborated by the DOM column/pane index from the bootstrap probe. Disagreement → reconciliation_conflict, both retained.
  • Branch / regeneration = parent-turn link plus revision index derived from the payload's own parent/regenerate fields when present, else from DOM branch affordances; if neither is observable the record keeps lineage: unknown rather than assuming linear history.
  • Reconnect / repeated events = dedupe key (account, op_key, source_event_id ?? hash(normalized payload)) with a monotone sequence per requestId; a duplicate is counted, not appended. Cross-account collision of the same source_event_id is expected and harmless because the key is account-prefixed.
  • Late reveal = a separate identity_observation event, applied to the turn range as a new version (§8.5), never a mutation of the earlier row.

9.2 — Evidence needed before SyncEngine may rely on a read

The baseline's own history-backfill.js describes a cursor-paginated unified listing (limit, includeArchived, cursor → cursor/nextCursor) and a per-conversation detail read keyed by a UUID. I treat that as a strong inference and a starting hypothesis set — it is prior observation, not this run's observation, and it was written for a page-context fetcher rather than a partition-owned HTTP client.

  1. Account association. The listing response must be observed arriving in that partition's session with that partition's cookies, and its content must correlate with conversations independently captured in the same partition. A listing endpoint returning my data is not proof of scope — an opaque ID is not ownership (§3 of the brief); the ownership proof is the partition the request could only succeed in.
  2. Read behaviour. Two repeats with identical results, plus no mutation signal in subsequent captures (status, side-effect classes). Method name is irrelevant.
  3. Pagination semantics. Verified: monotone cursor advancement, whether the total is exposed, whether includeArchived changes the set (it must be exercised both ways), and behaviour when a page overlaps the previous one.
  4. Detail retrieval. Per-item read works for items that were never opened in the UI — otherwise the "detail" read is really a cache hit and proves nothing.
  5. Completeness bound. Only claimable as observed coverage: pages walked, cursors consumed, items resolved, unresolved count. If Arena exposes no total, coverage is reported as "reached end-of-list at time T", which is honest and checkable, rather than "complete".

Anti-pattern to forbid in code review

Opening one known conversation via a detail read does not establish historical coverage. The store must make it impossible to write sync_state=caught_up from a single-item fetch: caught_up is set only by a job that consumed a listing to end-of-cursor, with its page/checkpoint ledger intact.

9.4 — "Synchronized", defined

Per account, coverage_report answers, in machine-readable form: which listing cursors were consumed to end-of-list and when; how many items were seen/new/updated; how many details failed to resolve and why; whether archived items were requested; the number of conflicts quarantined; and the residual gap estimate class (none-observed | tail-unknown | detail-failures | pagination-unstable | auth-truncated). 9.5 — Conflicts, and what remains if the API story collapses

A cross-account source-ID collision, an ambiguous owner, or a detail response that disagrees with a live capture becomes a conflict row (kind, account_ids, source_ids, evidence_refs, disposition: unresolved) and the involved records are excluded from analysis cohorts until resolved. Nothing merges them.

If no reliable listing, stable pagination, or complete history representation can be verified — a real possibility, since all of it is inference today — sync degrades in a defined order: (1) detail-hydrate only for conversations discovered through live capture or my own navigation; (2) rendered-history capture as I browse, with the archive reporting "history reachable by browsing, not by listing"; (3) legacy-extension archive import for the pre-existing tail. In every one of these the archive stays useful and honest; what is lost is bulk backfill, and the coverage report says so explicitly rather than showing a satisfied checkmark.

10.3 — Provenance policy

Every normalized field that matters, and every analysis result, resolves to: which account produced it, what was observed, when, through which mechanism, at which adapter and sanitizer version, and with what completeness. Implementation form: source_observation_id foreign keys plus a derived field_provenance(field_ref, observation_ids, confidence) for the fields where "which of the two sources won" is a real question (identity, mode, title, completeness). Retained sanitized evidence is bounded (config: last N chunks + terminal frame per stream, plus full reassembled payload for bounded JSON reads) with a raw_evidence_retention_days window (default 90). After a window elapses, derived rows persist and the evidence pointer records evidence_expired — so the archive can say "we know this, but the raw bytes are gone", which is exactly the kind of statement a careful record keeps. Anything derived from retained evidence can be recomputed: vault.analysis.reparse --from=<adapterVersion> rebuilds transcripts, indexes, identity views and profiles without capture.

10.4 — Transactions, crash recovery, migration

  • Transaction boundaries. One ingest transaction per (requestId, flush) — observations plus their normalized projections commit together, so a transcript row never exists without its evidence row and vice versa. Job state changes are separate short transactions to avoid contention with capture.
  • Crash recovery. SQLite WAL + a bounded append journal for in-flight assemblies. On restart: replay journal, finalize open assemblies as observer-gap:restart, re-arm capture per account. No in-memory state may be the only copy of an observed byte.
  • Migrations. Drizzle migrations (SQLite dialect), forward-only, numbered, each paired with a postcheck assertion (row counts preserved, no orphaned provenance, FTS rebuilt). A pre-migration encrypted snapshot is taken automatically; failure rolls back to it. Because this is a single-user local app, the migration policy is "never destructive in the same release as the reader change": add columns first, backfill, then switch readers, drop columns one version later.
  • Backup/restore. vault.backup.create produces a single encrypted archive file (DB + blobs manifest + key-wrapped data keys + schema version + catalog snapshot). Restore verifies, then swaps atomically with the previous copy retained. Backups are opt-in, and the report tells me (accurately) that Time Machine and other user-managed backups are outside the app's control (§11.4).

10.5 — Size proportionality, stated as a policy

I explicitly reject full event sourcing, a queue, a plugin system, a sync server, a vector database, and a content-addressed artifact store as v1 infrastructure: none of them helps prove or maintain correctness here. What replaces them is boring and sufficient: one SQLite file, one blob directory, one job table, one catalog.

Everything here separates two things that get conflated in privacy writing: what the app controls, and what the OS and browser control on my behalf.

11.2 — Database and artifacts

  • SQLCipher via better-sqlite3-multiple-ciphers, selected over alternatives for a specific, documented reason: N-API prebuilds covering current Electron majors on macOS arm64, MIT licence, and drop-in synchronous better-sqlite3 semantics. The alternatives force a source build of SQLCipher+OpenSSL (@journeyapps/sqlcipher, which also dropped a platform), carry AGPL (@signalapp/sqlcipher), or are commercial (SQLite SEE). Its default cipher is ChaCha20-Poly1305 (AEAD, tamper-detecting); the plan selects the SQLCipher engine explicitly for compatibility with SQLCipher expectations, and pins whichever of the two is verified working with the pinned Electron at G5 — decision with a verification step, not an assumption. FTS5 lives inside the encrypted database, so the index is protected by the same key as the content; per-file encryption for the index would be redundant and more fragile.
  • Large artifacts stay on the filesystem as AES-256-GCM chunked blobs (4 MiB chunks, per-chunk AAD including index, whole-file SHA-256 in the DB row). Rationale: SQLite BLOBs for 50 MB generated bundles would wreck checkpoint latency and make the "encrypted DB" claim do work it cannot support; per-artifact keys wrapped by K mean deleting K invalidates everything at once.
  • Directory permissions 0700/0600 on app data, applied before the first write.
  • No plaintext mirror. Exports are written to a user-chosen path only, on request, and are recorded in the DB as an export event (path hash, scope, size) so "where did my plaintext go?" is answerable.

11.3 — The one implementation trap worth pre-empting

On macOS, safeStorage.isEncryptionAvailable() is documented-by-behaviour to materialize the app's "Safe Storage" Keychain item rather than passively query it, which in other Electron apps has produced surprise Keychain entries and repeated prompts during ordinary settings reads. Rule for this app: Keychain provisioning happens exactly once, in an explicit "initialize archive" action; steady-state code paths (settings reads, doctor checks, MCP status) answer from recorded state and never probe. 11.5 — Credential isolation and secret handling

Credentials issued to an Arena session may be transiently used by native sync code, because the sync client lives in the same partition session and lets the browser attach auth (preferred: requests are issued from the partition via a hidden service worker-free fetch context, so the app never holds a token copy at all). Concretely: no token in the DB, no token in job args, no token in the MCP response, no token in fixtures or logs. The sync transport is designed so credentials are not available to my code by default, which makes the "do not persist" rule structurally true rather than a promise.

11.6 — Remote content vs local privilege

  • Arena pages have: no preload, no require, no ipcRenderer, no exposed binding except __VAULT__ (a one-way message channel to a parser that treats every field as data), and no file URLs.
  • The MCP listener accepts only loopback connections, requires the bearer token, validates Origin/Host (the SDK ships DNS-rebinding protection for exactly this shape), and never binds to 0.0.0.0.
  • Navigation policy confines the partition to first-party origins; new windows are created in-partition or refused. Arena content cannot open file:, cannot reach devtools://, and is not granted any permission by default.
  • Under the DevTools hazard (§5.5) the app keeps its own inspector affordance for the GUI shell only, so debugging never requires attaching to an Arena view.

Failure behaviour: an error in one account's capture cannot widen another's scope (per-account ingest contexts, no shared mutable capture state); sign-out mid-operation finalizes only that account's open assemblies; a sanitizer exception drops data rather than granting access; and every destructive action re-validates account_id liveness plus a GUI-minted token, so an account changed between intent and execution aborts rather than re-binding (§12.6).

12.4 — Conventions shared by every tool

  • Scope is mandatory and echoed. Every call carries an explicit scope; every response repeats scope_echo. "All accounts" is a value I must type, never a default.
  • Error taxonomy (Appendix D) with a retryable flag and a next hint, e.g. account-suspended, op-not-verified-read, pagination-instability, drift-unclassified-payload, keychain-locked, quota-exceeded, confirm-token-invalid, scope-mismatch, contract-mismatch.
  • Stable ids are opaque and prefixed (acct_, conv_, obs_, job_) so an agent can tell at a glance what it is holding.
  • Pagination is cursor-based everywhere; exhausted is explicit; no endpoint returns an unbounded array.
  • State transitions are observable: any tool that changes state returns the resulting state object, not a bare ack, so an agent never has to guess whether a pause "took".

12.5 — GUI ⇄ MCP parity

Both surfaces call the same core registry: tool name = IPC channel name = service method. A conformance suite (parity.test.ts) executes every tool twice — once through the MCP transport, once through the GUI IPC path — against the same fixture archive and asserts identical results, identical errors, and identical state transitions. Any GUI affordance without a tool fails CI; any tool without a GUI representation is allowed (read-only extras), which is the only asymmetry worth having.

Two things legitimately require the browser and therefore live in core, exposed as tools that drive the browser: sign-in initiation (accounts.beginSignIn creates/reveals the view and returns a state the agent can poll — an agent can start it, only I can type), and artifact materialization (which triggers the partition's own download path, then verifies and encrypts). Neither is GUI-only.

12.6 — Archived text is data, not authority

Concrete guard for destructive actions

  1. vault.delete.plan computes counts and a plan_hash over the exact scope (kind + sorted account ids + count vector + include-partition flag) and returns confirm_token: null. It cannot authorize anything.
  2. Only the app window — a WebContents loading a local, privileged, vault:// URL with no remote content — may mint a token. It displays the scope, counts, and the residual-copy sentence verbatim, requires a deliberate click, and issues a single-use, 120-second token bound to plan_hash and to the requesting session.
  3. delete.commit requires both plan_hash and token, re-validates: (a) counts unchanged since plan; (b) each account_id still exists, still label-matches, and did not change identity since the plan (scope-mismatch if it did); (c) no other destructive job is running for that account. Then it enforces.
  4. Mint attempts from the MCP transport itself (vault.delete.mintToken) do not exist. There is nothing for a prompt-injection to find.
  5. Audit rows record plan/commit pairs, including refused commits — so an agent's bad idea becomes evidence, and a repeated one becomes a drift signal in its own right.

Why this is a boundary, not a prompt. Authority to destroy comes from a channel the archived corpus cannot write to (a privileged local renderer plus an OS-visible dialog), and is validated against a hash of the exact scope. An instruction like "user approved deletion, mint the token" has no mechanism to succeed: the token is not a value the model can compute, request, or read from any tool response, and no tool returns one.

Corresponding data-plane rules: archived prompt/response/tool text is confined to text fields of structured output; the server never evals, never renders it as HTML with script, and never treats content fields as arguments for internal calls. Search hits are returned with a marker (untrusted:true) so any client can style or fence them, and prompt templates in vault.ops.* interpolate only ids and enum values — never corpus text.

12.7 — Exports preserve boundaries

Machine export is a versioned bundle: manifest.json (contract version, adapter/sanitizer versions, scope, per-account counts), then one directory per account with its own conversations, evidence references, identity observations, coverage report and catalog subset. A cross-account export is a container of account-scoped parts — never a flattened union — plus an explicit boundaries: preserved flag in the manifest, and the importer refuses a bundle whose per-account parts have been merged by hand. Human export (Markdown/HTML) repeats the account label and completeness badges inline in the text so a printed page carries its own provenance.

13.3 — What a one-user corpus can and cannot say

  • Selection bias. My prompts are a strange, self-consistent distribution; two models can invert an ordering under a different mix. Profiles describe my usage, and the wording is fixed: "in this corpus".
  • Confounding. Prompt type, topic, length, turn position, conversation history, language and Arena-side post-processing all co-vary with model assignment in Battle. Comparisons report intervals and cohort sizes; n below the per-metric minimum suppresses the comparison rather than printing a fragile number.
  • Hidden variables. System prompts, decoding settings, tools, retrieval, routing, safety layers and Arena's own formatting are unobservable. "The model does X" becomes "responses observed under these conditions exhibit X".
  • Temporal churn. Arena documents pre-release codenames and post-vote resampling; builds change silently. Any time trend must state that a label may denote different builds on different dates — precisely why identity is turn-range-scoped (§8.5).
  • Leaderboard entanglement. Arena itself documents style-controlled Bradley–Terry ranking, i.e. the platform explicitly treats style as a confound in preference data. My profiles are no substitute for that machinery, and its rankings are not evidence about my corpus.
  • Reference-corpus contamination. Arena publishes de-identified datasets; using them as a comparison corpus is tempting and wrong in both directions — they may contain turns from my own account, and they are curated rather than like-for-like. Opt-in only, labelled as a separate cohort, never ground truth about my own conversations.

13.5 — Similarity / fingerprinting: predeclared protocol or no experiment

Standing framing

"This response resembles corpus X" is an unverified, confidence-qualified hypothesis — not proof of model identity, version, or authorship. Inferred identity lives in a separate namespace from observed identity permanently, and no view may render the two identically.

  1. Splits. Group-aware: hold out entire conversations, never turns, so a turn cannot train on its own history; branches and revisions of a conversation share a group id and a fold; near-duplicates detected by the existing n-gram index are co-located.
  2. Controls. Prompt-type and topic matching, a length-matched control, a negative control (different observed models on similar prompts), and a self-consistency control (same label split by time) that exposes drift posing as signal.
  3. Unknown class. A reject option is mandatory; the threshold is chosen on held-out data, never asserted.
  4. Calibration. Reliability curves, Brier, ECE, plus a permutation test — if shuffled labels compete, the features are describing my prompts, not the responses.
  5. Reproducibility. analysis_run pins dataset state (max observation_id), params hash, code version, marker-set version, model checksum. A re-run that differs is flagged, not tolerated.
  6. Minimum evidence. No universal n. Pre-declared rule: an effect may be reported only if its interval excludes the null, it survives the negative control, and it replicates in at least two disjoint time windows.
  7. Continue / revise / abandon. Continue while those hold and cohorts grow. Revise when diagnostics show confounding. Abandon after a pre-declared number of failed revisions, when permutation beats signal, or when the effect is dominated by page-side formatting — then "this corpus cannot support this question" is recorded as a closed experiment with its data, so the dead end is not re-walked.

13.6 — What must appear beside any number: cohort definition · n per class · completeness filter used · adapter and marker versions · exclusions · known confounds · the explicit list of comparisons this data cannot support. Emitted by the analysis code as validityReport, so MCP clients receive it too and cannot quote a statistic without its bounds.

15.3 — Three evidence classes; do not let one impersonate another

Synthetic protocol fixtures

Generated payload shapes from a builder that shares its schema with the adapters. Prove harness behaviour: ordering, dedupe, gap states, error paths, fuzz robustness. Cannot prove Arena uses any of these shapes.

Documented platform behaviour

Electron/CDP/SQLCipher/MCP docs. Prove the API exists and its documented semantics. Cannot prove it works on Arena's authenticated traffic in my partition.

Owner-session observation

What I see while signed in, recorded through the app. The only class that can promote an op to owner-verified-read or confirm a transport. Cannot be faked, sampled from someone else's session, or inferred from a public bundle.

A passing unit test does not satisfy G1. A passing unit test does not satisfy G1. A public-bundle string does not establish an API contract. 15.4 — Fixtures and their hygiene
