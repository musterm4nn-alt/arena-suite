§01Executive decision summary

DECISION — RECOMMENDED ARCHITECTURE

A single Electron application is the dedicated Arena browser. Each Arena account lives in its own persistent Chromium partition inside that app (cookies, storage, cache, service workers, capture state, sync state all separated). The Electron main process attaches Chrome DevTools Protocol (CDP) sessions to every page, iframe, and worker target before the first navigation of that target, and observes Arena's traffic — request/response bodies, streamed chunks, WebSocket frames, EventSource messages — at browser-network level, without depending on page-world monkey-patching. A local pipeline sanitizes, normalizes, and stores transcripts into a SQLCipher-compatible encrypted SQLite database; a local MCP server (Streamable HTTP on loopback, plus a stdio bridge) exposes every capability to LLM agents; a minimal diagnostics-first GUI is the owner's control surface.

Rejected as the primary architecture: browser extension of any flavor (the existing baseline), extension + native host, native Swift + WKWebView, Tauri/Wry/WebKit, and export/import without an embedded browser. CEF was the strongest alternative and loses on implementability for AI-agent development at equal capture depth (§05.4). A custom Chromium fork is named only as a last-resort escalation with a concrete trigger.

The five load-bearing reasons

  1. Electron's main process has a documented, in-process CDP transport. VERIFIED The webContents.debugger class is an "alternate transport for Chrome's remote debugging protocol"; its message event carries a sessionId, so flattened multi-target sessions (page → iframe → worker) can be multiplexed through one attach point. This is the same observation plane DevTools uses, which is materially deeper than the baseline extension's document_start page-world interceptor (§04, §06.3).
  2. Chromium's Network/Fetch domains cover every transport family that plausibly carries Arena conversations. VERIFIED CDP emits Network.eventSourceMessageReceived with full message payloads for EventSource, Network.webSocketFrameReceived/Sent with frame payloads, Network.getResponseBody for buffered bodies, and Fetch.takeResponseBodyAsStream + IO.read for incrementally streamed bodies. HYPOTHESIS Arena's actual live transport (SSE vs WebSocket vs fetch-stream vs other) is unverified in this run; the discovery phase (§07) determines it, and the capture fabric implements all documented paths so the answer selects wiring, not architecture.
  3. Multi-account isolation is a first-class, one-line-per-window property. VERIFIED Electron sessions created with partition: 'persist:<name> give each account its own cookie jar, cache, storage, and service-worker registry, with main-process APIs (ses.serviceWorkers, ses.cookies, clearStorageData) to inspect and purge them independently. The same partition object is the unit that capture scope, sync authority, and destructive-action scope bind to.
  4. The app owns downloads and artifacts directly. VERIFIED Session's will-download event and DownloadItem.setSavePath route Arena Code outputs and any generated files straight into the app's encrypted artifact store — no chrome.downloads quota dances, no companion bridge, no "folder path to paste into your file manager" (the baseline's documented workflow).
  5. One runtime, one engine, mainstream dependency health. Electron bundles Chromium and Node in a single process tree, which suits an 18 GB machine and "avoid duplicated engines"; it is among the most-documented desktop stacks in existence, which matters because AI agents will implement and operate it. Current stable is electron@44.4.1 VERIFIED (npm registry, 2026-09-17); platform floor is macOS 13 Ventura with Apple Silicon binaries VERIFIED (Electron README, main branch).

What this buys over the existing extension baseline

The owner's current recorder is musterm4nn-alt/arena-exporter v2.1.3, a Manifest V3 extension whose capture is a page-world interceptor injected at document_start, with archive writes via chrome.downloads or an optional native messaging host plus a Swift reader app. Its own verification notes (consulted this run; §13 source 2) record the failure modes this project exists to escape: a stream-completeness warning on a three-round battle archive, a battle already running before a bridge repair being "only partially recoverable from the page", missing historical prompts and hidden reasoning, and model labels not matching the visible tabs. Top risks, at a glance

  • Arena's live transport may not be EventSource (fetch-streamed SSE would bypass eventSourceMessageReceived) — mitigation: Fetch-domain interception with streamed body reads; tested in gate G1/G2 against the baseline on identical workflows. HYPOTHESIS
  • Opening DevTools detaches the app's debugger from that webContents VERIFIED — mitigation: re-attach watcher, in-app "capture detached" banner, DevTools discouraged in capture windows; residual risk documented (§06.9).
  • Service-worker-shielded traffic could be invisible if Arena routes API calls through a SW fetch handler and auto-attach cannot reach it — mitigation: Network.setBypassServiceWorker per session (verified CDP method), SW inventory per partition, coverage-gap state rather than silent loss (§06.5).
  • Arena schema drift breaks adapters — accepted as routine; the protocol catalog and adapter versioning make drift a first-class, machine-readable state (§07.2), not a silent failure.
  • CDP is a DevTools contract, not a frozen API — pinned per Electron major; acceptance tests re-run on every Electron upgrade; escalation path to CEF/fork exists but is not expected to trigger (§05.6).

The implementation sequence (§12) is built to falsify this architecture early: the first spike deliberately attacks late attachment, target churn, workers, streamed bodies, stopped/failed turns, downloads, and two-account isolation, before anything else is built.

§03Product context & constraints

The platform being recorded

Arena (arena.ai) is a model-comparison and ranking platform. Public observation this run confirms four conversation surfaces relevant to capture — Battle (two anonymous models, vote, post-vote reveal), Side-by-Side (two chosen models), Direct (one chosen model), and Agent mode — plus leaderboard and history surfaces (/history/search), and template-driven creation flows for landing pages, dashboards, games, design-to-code, full-stack apps, and storefronts, which are the Arena Code / web-development family of outputs. VERIFIED (homepage observation) The baseline extension additionally works against subtypes text, code, web-search, image, video and captures tool-call records and workspace ZIPs for agent conversations, which indicates the v1 text scope below is the right first target and that files/previews are the next modality. STRONG INFERENCE

Operating context (fixed by the owner)

  • Permanently private, single owner. No distribution, App Store, hosted backend, second app user, telemetry, or public update infrastructure. This licenses a proportionate security posture (§09.5) and a diagnostics-first GUI.
  • Multiple own Arena accounts, simultaneously live. Not an account switcher: two or more windows, each with an isolated browser session, each recorded, synced, and deletable independently. This requirement shapes the partition model (§06.2), record identity (§09.1), MCP scoping (§10.4), and acceptance tests (G1, G5).
  • Hardware/runtime. Apple Silicon only (M3 Pro, 18 GB shared RAM, macOS 27). The app's stated minimum is macOS 13 Ventura, inherited from current Electron's platform floor VERIFIED; nothing in the design requires newer OS APIs, and Ventura remains the floor only because Electron drops older macOS releases as Chromium does. One engine, one process tree (§06.1); no resident Python/Node side-services in v1.
  • Agents build and operate it. Mainstream dependencies, reproducible setup, structured diagnostics, machine-checkable gates (§12), and an MCP surface that is the primary interface — every GUI capability is also an LLM capability (§10).
  • Auth workflow. The owner signs into Arena inside the app using Arena's own flows; email-based sign-in suffices. Google/OAuth/passkeys are non-requirements and must not disqualify any architecture. If email flows use verification codes, MFA, CAPTCHA, redirects, or popups, the owner completes them in-window (§06.6).
  • Heavy usage, unknown scale. No assumed archive size; quotas are configuration with alerts, and a measurement plan replaces invented numbers (§06.8).

Owner-session scope and boundaries

The app observes and automates only the owner's own concurrently signed-in Arena sessions. Three mechanism classes are kept distinct throughout, per the brief: authenticated read access (first-party endpoints, documented or not, used with the correct account-scoped session — an internal endpoint is not by itself an access-control bypass); automation compatibility (presenting as a normal browser, not tripping bot challenges); and access-control workarounds (defeating a client-side restriction to reach data — if ever needed, the actual control and mechanism will be named, not euphemized). The current design requires no workarounds: everything flows through sessions the owner authenticated inside the app.

Hard boundaries the design enforces mechanically rather than by policy prose: operations bind to exactly one account partition, and a conversation URL or opaque ID alone never establishes ownership (§09.1); credentials issued to a session may be reused transiently in memory by sync code but never persisted to disk, exports, fixtures, or logs (§08.3); recording has visible state and per-account and global pause/cancel/stop with defined effects on in-flight work (§07.6); and one account's sign-out, drift, or failure never corrupts, invalidates, or silently rebinds another account's records or sync state (§08.6, G5). Records are never merged across accounts because IDs, titles, text, or timestamps look similar — cross-account similarity is a conflict, not a match (§09.4).

Legal documents (ToS/AUP/privacy policies) are out of scope per the brief and were not researched; acceptability of the owner's private usage is the owner's responsibility. Methods are evaluated on technical feasibility, security, robustness, and maintainability only.

§04The capture problem: what "deeper than the extension" means

Required observation surface

A complete v1 text archive needs, at minimum: conversation-turn traffic for all four modes; streamed token deltas for completed, stopped, failed, and partial responses; the history surface including search, pagination, and archived views; model-selection evidence, blind-participant labels, visible votes, and post-vote/reveal events; titles, timestamps, source IDs, branch/revision structure, participant positions, completion state; Arena Code downloads and generated files; and the account/session scope of every observation. The baseline extension's schema (consulted this run) already models most of this semantically — its failures are not conceptual but observational: page-world interception that misses what happens before injection, inside workers, or after bridge breakage. The architecture question is therefore: which stack can observe the network and target lifecycle at browser level, not page level?

The "owning the window" trap

An embedded browser shell does not automatically see more than an extension. WKWebView gives a native window and zero network-level response-body access for https (no CDP; NSURLProtocol unsupported in WKWebView per WebKit bug 138169; WKURLSchemeHandler only handles custom schemes) — a Swift app would be forced back to page-world injection or an out-of-band MITM proxy with a custom trust root, which is worse for isolation and for the machine. Tauri/Wry inherits the same WebKit core on macOS, with interception still an open feature request in wry (issue #1087). CEF genuinely does have native request/response interception (CefResourceRequestHandler) and is treated as a real candidate in §05.4. Electron's depth comes specifically from the in-process CDP transport plus app control of navigation and downloads — and where this plan still depends on anything page-world, it is stated: capture v1 depends on page-world injection nowhere; page-world code is used only for optional deep-diagnostics, clearly separated, and DOM access happens through CDP, which is not visible to or blockable by ordinary page CSP in the same way injected scripts are.

What can still be missed, honestly

  • Traffic inside a service worker in the window between SW activation and setBypassServiceWorker taking effect (mitigated: bypass set before first navigation; SW inventory logged; any residual gap degrades to an explicit coverage-gap state).
  • Frames/workers created before auto-attach in pathological cases (mitigated: attach-before-navigate protocol; G1 test manufactures late-created targets deliberately).
  • Bodies exceeding buffer limits when using non-intercepting getResponseBody (mitigated: Fetch interception with streamed reads for conversation-relevant URL patterns).
  • DevTools-opened detaches (re-attach watcher + visible degraded state; §06.9).
  • Encrypted or exotic transports (WebTransport exists in CDP events too — webTransportCreated/Closed observed in the Network domain listing VERIFIED — but payload-level WebTransport capture support is not claimed and is a discovery-phase question).

Every one of these has a detection signal and a degraded-but-correct behavior; none silently produces a fake-complete transcript. That property — incompleteness is always visible — is the actual product requirement the architecture must satisfy.

WKWebView route, closed definitively

Worth stating plainly because "native Mac app" is the aesthetically tempting answer: the entire macOS-native path hinges on observing response bodies of ordinary https loads, and WKWebView provides no supported way to do that in-process. The community stopgaps are (a) route traffic through a local MITM proxy and install a custom CA — a system-wide trust change that undermines exactly the isolation this app exists to provide, and brittle against certificate-pinned endpoints; or (b) inject JavaScript — precisely the mechanism the owner is escaping. Until Apple ships a WKWebView equivalent of CDP's Network domain (no such roadmap exists to my knowledge and none was found this run HYPOTHESIS — trivially testable per OS release), this route cannot meet the fixed requirement, regardless of its excellent memory footprint.

Focused comparison: Electron vs CEF

Both embed Chromium, both can reach browser-level capture. The decision is made on six axes the brief names:

  • Capture depth: CEF intercepts natively in C++ (CefResourceRequestHandler, streaming resource handlers) — slightly more direct than Electron's CDP round-trips, and not subject to the DevTools-detach quirk. Electron's CDP path adds eventSourceMessageReceived/WebSocket frame events with documented payloads. Net: equal for this app's needs; both must prove stream completeness in G2.
  • Worker/service-worker observability: CEF has runtime flags and its own SW support caveats; Electron has the verified setBypassServiceWorker + ses.serviceWorkers inventory. Neither is perfect; both have a workable story.
  • Download control: both own downloads outright. Electron's is a two-line JS handler; CEF's is a C++ client handler.
  • Session partitioning / simultaneous accounts: Electron partitions are a documented, per-window string; CEF request contexts are equally real but require more boilerplate in C++ and careful cache-path management.
  • Packaging/resource: CEF is leaner on disk; Electron carries Node. On an 18 GB single-user machine, the difference is not decisive, and Electron's single runtime replaces the separate Node service CEF would need for SQLCipher+MCP anyway — the "avoid duplicated runtimes" test effectively ties.
  • Maintenance and agent fitness: decisive. Electron: npm-installable, current (44.4.1, 2026-09-17), enormous documentation corpus, prebuilt arm64 binaries, and the exact APIs needed are in the official docs the agent can re-read. CEF: binary distribution management, C++ build chain, thin documentation, and the maintained-binding ecosystem on macOS has repeatedly rotted historically (cefpython et al.). An AI agent troubleshooting a CEF service-worker interception issue at 2am has far worse odds than the same agent in Electron.

DECISION Electron wins on equal capture depth with decisively better implementability, which the brief weights heavily ("AI agents will perform almost all implementation, operation, and troubleshooting"). CEF is the named fallback with a trigger (§05.6).

  • R1 — Capture depth falsified: in the G2 A/B against the extension baseline on identical Arena workflows, Electron's fabric fails to beat the baseline on stream completeness, worker visibility, missed events, or reveal evidence. Consequence: escalate to CEF (preserves: full native interception, partitions; loses: JS single-language, in-process Node, npm ergonomics).
  • R2 — Target fabric unusable: Electron's debugger transport cannot deliver flattened child-target (worker/iframe) sessions reliably (G1), and the --remote-debugging-port fallback is also insufficient. Consequence: CEF, or a scoped custom-Chromium escalation (below).
  • R3 — Auth incompatibility: Arena's email flow (CAPTCHA/MFA/POP) cannot complete inside the app's windows under any configuration. Consequence: before switching stacks, test channel differences; if WebKit-specific it would paradoxically favor WKWebView, which still fails depth — more likely resolution is an app-level cookie/import bootstrap, with capture-depth requirement intact.
  • R4 — Resource ceiling: measured steady-state memory with 2–3 live partitions exceeds a practical budget on 18 GB. Consequence: lazy window loading + partition suspension before any stack change.

Custom Chromium fork is named as a last resort only: it becomes justified solely if a specific required observation proves impossible through maintained public surfaces (Electron CDP, CEF handlers, CDP over loopback). No such observation is currently identified; if one appears, the fork would carry a patch pinned to a narrow Chromium milestone and a maintenance budget stated in writing. The --remote-debugging-port browser endpoint (Puppeteer-style attach) already covers most "CDP from outside" needs without forking.

§06Recommended architecture

Process and trust model

One Electron application; two process kinds that matter. Renderer processes host the Arena windows — their content is Arena-controlled and untrusted. The main process (Node) is the trusted core: it owns window creation, attaches CDP sessions, runs the capture fabric, adapters, storage, sync, analysis, and the MCP server. Nothing in the renderer world is ever asked to cooperate with capture; the page world stays pristine. All privilege crossings are explicit and drawn in the figure below: CDP sessions (in-process), the loopback MCP endpoint (token-gated), safeStorage (Keychain), and encrypted disk writes.

Account partition model

Each Arena account the owner adds gets a partition slot: a UUID-named persistent Electron session (persist:arena-<uuid>) plus a matching record in the accounts table. Windows are created against exactly one slot; popups and new tabs inherit the same partition via setWindowOpenHandler VERIFIED (web-contents docs). Partition state — cookies, localStorage/IndexedDB, cache, service-worker registrations — is isolated by construction VERIFIED (session docs), which is the browser-level half of the isolation requirement; the data-model half (account-scoped record identity) is §09.1, and the acceptance half is gate G1's leak test.

A slot's session epoch begins when the owner signs in and ends at sign-out or credential invalidation. The capture fabric binds every observation to (account_slot, session_epoch); provenance records which epoch produced which evidence. On sign-out, the app pauses that account's capture and sync, marks in-flight conversations with their last completeness state, and requires a fresh epoch before destructive or sync operations resume — it never guesses that "the same browser window" implies "the same account". If Arena's account display changes (different visible identity), sync halts for that slot and raises a mismatch conflict rather than rebinding silently.

Capture fabric internals

The fabric is a small set of main-process services:

  • Target supervisor. Tracks every target (page, iframe, worker) per partition window; owns the attach-before-navigate protocol (§06.4); maintains the CDP session map keyed by sessionId; watches detach events and re-attaches with backoff, raising a visible degraded state when it cannot.
  • Network collector. Per session: Network.enable (+ setCacheDisabled for capture-critical windows, so responses are fresh and observable), subscription to the §04 matrix events; for URL patterns classified as conversation-relevant by the protocol catalog, arms Fetch.enable at the Response stage and streams bodies via takeResponseBodyAsStream/IO.read. Non-relevant traffic contributes only sanitized inventory rows (method, host, classification), never bodies.
  • Stream reassembler. Rebuilds logical messages from SSE events / WS frames / streamed chunks by requestId; detects logical completion signals, transport termination, and gap signatures (e.g., heartbeat stalls followed by loadingFailed); emits candidate turns with completeness states (§07.5).
  • Sanitizer. Sits between collectors and anything persistent. Strips credentials, cookies, authorization headers, signed URL parameters, CSRF material, and unrelated private fields before evidence storage; failures are fail-closed — an unsanitizable payload is stored as a redacted stub plus a parser-error record, never raw (§07.3). The baseline's redaction inventory (credential keys, JWT patterns, nested JSON strings, query parameters, header pairs) is adopted as the starting checklist and extended.
  • Protocol catalog. The machine-readable inventory of observed operations (§07.2): classification, first-party evidence, account binding, transport, read/mutation status, payload family, adapter version, completeness, drift signals.

Attach-before-navigate protocol

Because the app is the browser, it controls the one thing extensions cannot: when a target starts loading. Window creation sequence: create hidden BrowserWindow with the account's partition → attach webContents.debugger → Network.enable, Fetch.enable, Target.setAutoAttach(flatten), Network.setBypassServiceWorker(true) → verify acks → loadURL('https://arena.ai/…') → show window. Navigations within the window keep sessions attached; new targets arriving via auto-attach get the same domain setup before they are resumed. This converts the baseline's "race at document_start" into a guaranteed ordering. Late-arriving targets (e.g., an iframe injected seconds later) are the G1 falsification target, not an assumption.

Service-worker policy

DECISION For capture windows, Network.setBypassServiceWorker(true) is set per session VERIFIED (CDP method exists for exactly this). Consequences and honesty: requests that Arena's SW would intercept become ordinary network requests observable by the page-session Network domain — this is the point — but any genuine offline-caching behavior the SW provides is disabled for these windows, and if Arena's client depends on SW-mediated request shaping (e.g., custom headers injected in SW), the server may see slightly different requests. If SW-shaping proves load-bearing, the mitigation ladder is: (1) attach to SW targets via auto-attach and run Network/Fetch there; (2) browser-level endpoint attach; (3) leave SW enabled for that flow and record the coverage gap explicitly. The ladder is walked by evidence, not preference.

Authentication and normal presentation

The owner signs into Arena inside each partition window using Arena's own email flow; the app adds no automation to that flow. If the flow uses email codes, MFA, CAPTCHA, redirects, or popups, they render and complete in-window like any ordinary Chromium usage; setWindowOpenHandler keeps popups in the same partition. The app does not pass --enable-automation or any automation switch, so navigator.webdriver remains false and no automation banner exists STRONG INFERENCE (standard Chromium behavior; asserted as a G1 assertion test, not assumed). The user-agent is normalized to a stock Chrome-on-macOS string (dropping the Electron/<version> app token) — a normal-presentation choice in the automation-compatibility class, disclosed here: it reduces gratuitous uniqueness; it does not defeat bot detection and is not intended to. If Arena serves the app a challenge (the baseline's outcome taxonomy proves CAPTCHA can appear mid-conversation STRONG INFERENCE), the affected request is marked captcha_rejected-style, capture continues, and the owner resolves it interactively; nothing retrries aggressively.

Downloads and generated artifacts

Each partition's session subscribes to will-download; the handler stops default behavior, streams the item via DownloadItem.setSavePath into an intake directory inside the app container, encrypts it into the artifact store (AES-256-GCM, content-addressed, provenance-bound), and securely deletes the plaintext intake copy. This is the app-owned artifact path the extension could not offer without its native host. Arena Code workspace ZIPs, generated files, and any download the owner triggers in an Arena window land here with account + conversation linkage when inferable from the triggering context.

Resource plan: quotas as configuration, measurement as a first-class feature

No usage numbers are invented. Instead the app ships with a resource panel and these defaults, all configurable: per-partition Chromium cache cap (with periodic ses.clearCache sweeps), SQLite cache pages and WAL autocheckpoint tuned for an 18 GB machine, artifact-store soft quota with alerting (the store never silently drops data; it warns and the owner decides), sanitized-evidence retention window (default 90 days, per-family override), and a snapshot exporter (JSON) of measured sizes: DB pages, FTS terms, artifact count/bytes, per-partition cache, event-bus queue depths. The measurement plan runs at every sync and is itself queryable via MCP (diagnostics.resources), so the agent can tune quotas from data. If steady-state footprint with two live partitions proves too heavy (R4), windows become lazily loaded and background partitions suspend — before any architectural retreat.

Known operational limits, owned

  • DevTools detach: opening DevTools on a capture window detaches the app's debugger from that webContents VERIFIED. Mitigations: re-attach watcher with backoff; a persistent "CAPTURE DETACHED" indicator per window; documented owner rule (use a separate diagnostics window with capture intentionally off). Residual: a window whose DevTools stays open records a coverage gap for that span — visible, not silent.
  • Single in-process debugger per webContents: the app's fabric is the sole attacher; user DevTools therefore conflicts with capture by design (above). The browser-level --remote-debugging-port path, if enabled, is loopback-only, off by default, and used for diagnostics sessions — its local exposure is disclosed (any local process could connect while it is on), which is why it is not the primary transport.
  • CDP drift: the protocol is a DevTools contract that moves with Chromium milestones. The fabric pins its domain usage to Electron's major version; every Electron upgrade re-runs the G1/G2 gate suites as a hard CI check before the app adopts the upgrade.
  • Electron event-delivery bugs: an open Electron issue records missing Page.frameAttached delivery through the debugger client (consulted via search snippet). The plan's answer is deliberate: primary domains are Network/Fetch/Target (not Page), and G1 includes a target-churn test that would catch this class of bug immediately.

§07Discovery & live capture

Discovery as a maintained capability (phase D1)

Before any adapter is written, the app runs a discovery campaign across the owner's normal Arena usage in every connected account slot: browse, battle, direct, side-by-side, agent, history views, votes, reveals, downloads. Discovery output is dual-purpose by design — it is both the capture-adapter inventory and machine-readable diagnostic state that AI maintainers consume when Arena drifts. Coverage is across all first-party traffic encountered, classified into: conversation traffic, authentication/account operations, assets, analytics/configuration, mutations, and unrelated. Two hard rules keep discovery honest: inventory coverage is separated from payload retention (classifying an operation never implies storing its body), and unknown operations remain classified unknown until investigated — the catalog has no "guess" bucket. Where the owner's baseline extension already accumulated protocol knowledge (History API usage, request-attempt taxonomy, the x-session-settled/x-stream-version/x-arena-chat-id headers, pagination hasMore semantics STRONG INFERENCE), the new discovery re-verifies each fact first-party before relying on it; the extension's knowledge seeds the catalog's expectations, never its assertions.

Sanitization and sensitive-data exclusion

The sanitizer is the only component allowed to write to the evidence vault, and it is fail-closed. Excluded before persistence and before any diagnostic exposure: credentials and passwords, Authorization headers, cookies and Set-Cookie, OAuth codes and tokens, CSRF secrets, signed URL parameters (the safe reference form keeps origin + path + a hash of the redacted query), and unrelated private fields. Parser-error paths run the same pipeline — a payload that cannot be parsed is still sanitized before its stub is retained, because malformed payloads are precisely where hidden credentials leak in practice. Retention is bounded (default 90 days, per-family override) and sized to diagnose drift and support re-parsing: truncated bodies, header whitelists (the three Arena diagnostic headers above are the initial whitelist), and event counts. The baseline's two-stage filter (storage-time and serialization-time) is retained and a third stage added: export-time, so exports re-sanitize regardless of stored state.

Capture and completeness states

The single most important correctness rule in this system: a complete transcript is a positive claim that must be earned by evidence. The turn-state machine makes the distinction mechanically:

Observation → sanitized evidence → transcript (illustrative path)

The following walk-through is explicitly illustrative; nothing in it is claimed as observed Arena protocol. A battle round begins: the page session's Network collector sees a request matching the catalog's conversation family (inventory row created; headers whitelisted to the three diagnostic headers; no cookies retained). The response is intercepted at the Response stage; its body streams through IO.read chunks into the reassembler, which emits ordered deltas. A logical completion signal arrives; the fabric snapshots the rendered conversation DOM via CDP and compares message-node counts and text hashes against the reassembled content. The sanitizer writes a bounded, redacted evidence object (schema hash, event counts, truncated framing samples) into the vault. The adapter (version pinned) parses the family into normalized records: a turn with role assistant, lane position, completeness state COMPLETE, and provenance pointing at the evidence object, the adapter version, the epoch, and the mechanism (network). Normalizer inserts under transaction; FTS indexes the text. An MCP conversations.search for the round's phrases returns it with full provenance. That entire path — one account, one battle round, network-plus-DOM reconciliation, queryable result — is the vertical slice that must exist before anything else is built (§12 G2).

Recording controls and their exact effects

Per account and globally: pause stops admitting new observations for that scope; in-flight streams finish reassembly and are stored with a paused_tail marker so no partial is lost or double-counted on resume. Cancel (sync or capture scope) drops only un-persisted intermediate buffers and marks affected turns INCOMPLETE with the cancel reason; nothing already normalized is rolled back. Stop detaches the domain subscriptions for that scope and finalizes a coverage report (what was observed, what was missed while stopped). All three are exposed in the GUI and over MCP with the same semantics, and every transition is an auditable event.

Read verification before reliance

HTTP method or endpoint name proves nothing. An operation is marked read in the protocol catalog only after, in the owner's own session: (a) its request family has been observed issuing from normal page usage; (b) replaying it produced responses consistent with read semantics (no new server-visible state: no new conversation IDs, no mutation-shaped responses, unchanged subsequent reads); (c) repeated invocation is idempotent across at least three replays in one epoch; and (d) the response body's family matches the observed page-driven response. Anything failing any step stays unknown and is not used by sync. Mutation-class operations discovered anywhere (vote, send, delete, settings) live behind a hard allow-list that only the owner's interactive window usage ever triggers — sync code cannot invoke them, structurally.

Credential handling during replay

Replays execute as in-page fetch calls issued via CDP Runtime.evaluate in the partition's Arena origin, so they use exactly the session the owner authenticated — cookies, CSRF tokens, and any bearer tokens are applied by the page context itself and are never extracted into the app. Where a flow requires assembling headers in the main process instead (fallback path via Electron net against the partition's cookie jar), credentials read from the session are held in memory for the request's lifetime only, never persisted to disk, exports, fixtures, or logs, consistent with the brief's transient-reuse allowance. The capture layer observes the replay traffic like any other, which doubles as a self-verification loop: a replay whose response diverges from page-driven shape is a drift signal, not a silent difference.

Sync engine semantics

Concrete semantics: Sync now runs for one account or a selected set; automatic per-account sync is opt-in. Progress is visible per account (pages enumerated, conversations fetched, items normalized) and cancellable; checkpoints persist after every page so interruption (crash, quit, network) resumes without re-reading stable pages. Pagination instability is handled by keyset-agnostic re-enumeration with conservative deduplication: within one account, identical source IDs reconcile; overlapping pages re-yield known IDs and are skipped; identical text alone is never deduplication evidence (the brief's rule, kept verbatim in code review checklists). Re-runs are idempotent by construction. Live capture and sync may overlap: live observations win provenance live, sync history; the same turn seen twice reconciles on (account, conversation, turn identity) with a conflict record if payloads disagree materially. Multiple accounts may sync concurrently — jobs are independent and rate-limit budgets are per slot — but the engine caps concurrent replays per account (default 1) to keep request patterns indistinguishable from ordinary pagination and to make rate-limit handling clean.

What "synchronized" means, and what remains open

A slot is synchronized as of watermark W when: the history listing has been enumerated to a stable end under the current epoch (no hasMore pending), every listed conversation has either a complete turn set or an explicit recorded gap, and the watermark plus coverage report are persisted. The report — queryable via MCP — states exactly which conversations have gaps, why (rate-limited page, challenge, drift, deleted-at-source), and what a re-run would attempt. This definition intentionally does not claim history the platform will not enumerate; if listing ends early or a detail read is capped, that is a visible coverage gap, not a silent success. Opening one known conversation successfully proves nothing more than that conversation.

§09Data, identity, provenance & protection

Source of truth: normalized records with evidence-backed observations

Full event sourcing is unnecessary for a private single-user archive and would multiply migration surface for no analytic gain. When an adapter changes (protocol drift, bug fix), affected conversations can be re-parsed from retained evidence where it still exists; where retention has expired, the normalized record stands with its historical provenance and a reparse_unavailable note — the archive degrades honestly rather than pretending reproducibility it no longer has. Transactions, recovery, migration, backup

Storage runs on better-sqlite3-multiple-ciphers (maintained fork of better-sqlite3 adding SQLite3MultipleCiphers encryption; current 13.0.3, released 2026-08-07, positive release cadence VERIFIED npm/Snyk/GitHub), configured for SQLCipher v4-compatible AES-256-HMAC-SHA512 so the database remains openable by standard SQLCipher tooling in an emergency. Synchronous in-process transactions (WAL mode) wrap each normalization batch; crash recovery is SQLite's own plus a write-ahead intent log for multi-step operations (sync checkpoints, deletions) so an interrupted operation resumes or rolls back atomically on next launch. Migrations are forward-only numbered scripts with a pre-flight consistency check (per-account row counts, key-uniqueness assertions) and an automatic pre-migration backup. Backup/restore is explicit export of the encrypted database plus the artifact store — the master key is deliberately not in the backup; restore re-wraps against the restoring machine's Keychain, and the app refuses a restore whose ciphertext hash mismatches its manifest. Deletion semantics below; all of these paths have dedicated G5 acceptance tests.

Encryption, keys, and the honest threat model

  • Key hierarchy: a random 32-byte master archive key, generated on first run, wrapped with Electron safeStorage (Keychain-backed on macOS; official docs state keys are stored "in Keychain Access in a way that prevents other applications from loading them without user override" VERIFIED) and stored only in wrapped form. Per-artifact keys derive via HKDF from the master key with the artifact's content address as context — no key database to protect separately.
  • Databases: SQLCipher-compatible encryption covers the primary DB and, because all pages are encrypted, the WAL and journal files as well; a G5 test greps WAL/journal bytes for known plaintext canaries.
  • Artifacts and indexes: artifacts AES-256-GCM per file with random IVs and provenance-bound AAD; FTS lives inside the encrypted DB; any auxiliary index is encrypted with derived keys or not created.
  • Plaintext exposure matrix (app-controlled vs residual): controlled — DB/WAL/artifacts/intake (wiped after encrypt)/logs (structured, sanitizer-gated, secret patterns rejected at the logger)/crash reports (disabled for content payloads; stack traces only)/fixtures (synthetic only). Residual and disclosed — browser-managed partition state (cookies, storage) is not encrypted by the app: it is the live session the platform itself maintains, protected by macOS user account boundaries, and scoped per partition; Spotlight can index app-container files unless the owner excludes the container (the app sets the containment flag it can and documents the rest); Time Machine and other backups will contain ciphertext for the archive but the partition directories and swap are OS-level residuals the app cannot promise to erase. STRONG INFERENCE on safeStorage internals (third-party analyses suggest same-user process reachability and a legacy AES profile; official wording "without user override" is consistent with a determined same-user attacker being out of scope) — the design assumes the master key is safe from other users, not from code already running as this user, which is also why renderer isolation matters more than key-encryption heroics.
  • Secrets exclusion: credentials, authorization headers, cookies, OAuth codes, CSRF secrets, passwords, signed URLs, and unrelated private fields are excluded from retained capture and diagnostics by the sanitizer (§07.3); resource references from signed URLs keep origin + path + hash. Renderer windows run with Electron's modern defaults — contextIsolation on, nodeIntegration off, no privileged APIs exposed to page scripts — so Arena-controlled code cannot reach Node, the file system, the master key, or the MCP server by construction; the only bridge into pages is the CDP fabric, which is main-process-side and not callable from page JS. The MCP endpoint binds to 127.0.0.1 with a bearer token and origin validation; pages cannot read the token (it never transits any renderer). Account/session isolation under stress is a G5 test set, not an aspiration: sign-out mid-capture, mismatch injection, crash-mid-deletion, and cross-account canary-string contamination checks are automated.

§10Full LLM operability — the local MCP surface

Transport, trust, and discovery

DECISION The automation surface is a real MCP server (@modelcontextprotocol/sdk, current 1.30.0 VERIFIED npm) hosted inside the Electron main process, exposed as Streamable HTTP bound to 127.0.0.1 on a random port with a random bearer token (generated at first run, stored wrapped, shared to clients via a 0600 config file the owner places). A tiny stdio bridge executable (arena-mcp-stdio) is shipped for clients that only speak stdio: it forwards JSON-RPC to the loopback endpoint, so both standard transports from the MCP specification work against the same server VERIFIED (spec: stdio and Streamable HTTP; session management and resumability defined). Trust boundary: MCP clients are semi-trusted operators — the token authorizes reading and starting work, but never archive-wide destruction (§10.6). The server validates the Host header (loopback only, DNS-rebinding defense per the spec's security guidance) and the bearer on every call. Capability discovery is standard MCP tools/list/resources/list; operations unavailable in the current app state return structured error results with a reason class and a machine-readable hint (e.g., sync.not_authenticated + "sign in inside window B"), so an agent can diagnose rather than guess. If the connected client lacks elicitation support, confirmation flows fall back to the GUI's native dialogs automatically — the guard never weakens, only the interaction surface changes.

One service layer, two faces

There is no capability that exists only in the GUI: the GUI is a thin view over the same service modules the MCP server exposes (window/control surface, capture control, sync engine, query/search, catalog, exports, analysis, diagnostics, deletion). This is enforced in code review by a lint rule — service modules may not be imported from GUI-only contexts without a matching MCP tool registration — and verified in G6 by scripted MCP clients completing every supported workflow end-to-end, including signing in is impossible without the owner but everything after is not. Browser-interaction integration is explicit: MCP actions that need a window (open a conversation, resolve a challenge, confirm a sync account) address windows by slot_id; the app brings the right partition window forward; nothing requires the agent to guess which window is which.

Error taxonomy and state transitions

Every tool shares one error envelope: {error_class, message, detail, retryable} with classes invalid_scope · account_mismatch · not_authenticated · challenge_pending · rate_limited · drift_detected · sanitizer_failed · confirmation_required · confirmation_expired · not_found · internal. This taxonomy maps 1:1 onto the sync failure reasons of §08.5 so an agent reading one vocabulary diagnoses everything.

The destructive-action guard

Archived prompts, responses, tool traces, and diagnostic text are untrusted data: they are inputs to queries and never sources of authority. The guard is structural, not instructional: (1) delete-class tools accept only server-generated scope tokens (slot UUIDs, conversation UUIDs, the literal archive token) — strings that cannot be sourced from archived content because they are minted by the app; (2) execution requires an out-of-band confirmation through a trusted channel — a native macOS dialog in the app, or MCP elicitation when the client supports it — that displays the exact scope, counts, and residual disclosure, and expires; (3) confirmations are one-shot, time-limited, and bound to the displayed scope — a confirmation for one conversation cannot be replayed for an account; (4) the confirmation broker has no code path that reads archived content while deciding. "Be careful" prompts inside transcripts, tool-trace text claiming to be the owner, or injected instructions in diagnostics all fail at step 1 or 2 by construction, and G6 includes a prompt-injection corpus that attempts deletion through archived content as an acceptance test. Global pause of all automation is a single GUI action and is also exposed as capture.stop global scope.

§11Local analysis & later modalities

Initial model profiles — deterministic, identity-honest, local

All analysis runs on the Mac, offline, and v1 is deliberately boring: transparent deterministic statistics over cohorts defined only by observed or revealed identity evidence, with uncertainty preserved on every number. A profile is a versioned computation (analysis_run) whose inputs are a named cohort (participant identity observations + filters), whose code version is pinned, and whose outputs carry the cohort's limits inline. The v1 metric set, each implemented as a pure function with unit fixtures:

  • Lengths: response, paragraph, sentence, and code-block lengths (distributions, not just means).
  • Lexicon: lexical diversity, recurring phrases and n-grams, punctuation and casing habits.
  • Structure: Markdown feature ratios — headings, lists, tables, citations, code fences — and code-to-prose ratios.
  • Rhetoric: common openings, transitions, conclusions; qualifications, hedging, refusals, apologies, uncertainty markers (curated marker lexicons, versioned like adapters).
  • Variation: the above sliced by prompt type, topic cluster, mode, language, time, and conversation context (first turn vs deep-in-history).
  • Excerpts: representative excerpts linked back to source evidence, so any claim in a profile can be clicked through to its transcript provenance.

Profiles never emit "model X is Y" identity claims; they describe cohorts and attach their own limitations.

What a one-user corpus can and cannot support

Stated up front because it constrains everything downstream: this archive is a heavy single user's conversations. Selection bias (the owner's prompts are the sampling frame), prompt/topic confounding (models answered my prompts, not a benchmark), conversation-history effects, hidden system prompts and decoding settings, platform tool layers, Arena post-processing, aliases and routing, temporal model changes, and uncertain labels (pre-reveal blind slots) all bound the inferences the data can support. Defensible: descriptive characterizations of observed cohorts ("participants revealed as A in this period produced longer code blocks on my web-dev prompts, n=41"). Misleading: leaderboard-style superiority claims, authorship attribution from style alone, or cross-period comparisons without epoch controls. The profile UI and every export repeat this framing mechanically — the limitation text is part of the artifact, not a footnote the agent can strip.

Embeddings and local ML — an explicit entry gate

DECISION v1 ships no ML runtime. Embeddings/local models are admitted only when all of these hold: (a) a concrete analysis question exists that deterministic stats cannot answer; (b) a cohort with enough labeled participants for a leakage-resistant evaluation exists (measured, not assumed — no universal threshold invented here); (c) the 18 GB machine runs it inside a measured memory budget with capture live. When the gate opens: transformers.js with a pinned ONNX encoder (weights acquired once, SHA-256-pinned, offline thereafter; preprocessing versioned with the run), embeddings stored as derived artifacts with full provenance and deletable per account. Until then, the analysis surface stays reproducible and cheap — which also keeps agent-operated reruns trustworthy.

Later similarity / fingerprinting experiments

Similarity-to-corpus is an unverified, confidence-qualified hypothesis, never proof of identity or authorship. Inferred identity stays a separate namespace from observed identity (§09.2 projections already separate them). If experiments are run, the pre-registered methodology requires: leakage-resistant train/test splits with near-duplicate and same-branch detection (branch-aware transcripts make this possible); held-out conversations; prompt/topic controls; negative controls (participants known-different); calibration reports; unknown-class handling (an open-set decision, not forced classification); reproducible runs (code version, input hashes, seeds); and empirically justified minimum evidence per claim — sample thresholds emerge from the calibration data, not from vibes. Continuation criteria: experiments continue only while they produce calibrated, useful discrimination on held-out data with honest uncertainty; they are revised when calibration degrades across epochs (Arena-side model changes will do this); they are abandoned when results lack scientific utility — and "abandoned" is a recorded state with its evidence kept, so a later agent does not silently retry the same dead end.

A.1 · Storage DDL sketch

Condensed to the load-bearing columns; indexes and constraints omitted for brevity. Illustrative of shape, not final migration text.

CREATE TABLE account_slot (
  slot_uuid TEXT PRIMARY KEY,            -- app-minted, also partition name
  label     TEXT, created_at TEXT,
  visible_identity TEXT,                 -- latest observed identity, display only
  deleted   INTEGER DEFAULT 0
);

CREATE TABLE session_epoch (
  epoch_id TEXT PRIMARY KEY, slot_uuid TEXT REFERENCES account_slot,
  started_at TEXT, ended_at TEXT, end_reason TEXT   -- signout|invalidated|manual
);

CREATE TABLE conversation (
  conv_uuid TEXT PRIMARY KEY,
  slot_uuid TEXT NOT NULL REFERENCES account_slot, -- identity includes account
  arena_conversation_id TEXT NOT NULL,
  mode TEXT, state TEXT, created_at TEXT, updated_at TEXT,
  UNIQUE (slot_uuid, arena_conversation_id)
);

CREATE TABLE turn (
  turn_uuid TEXT PRIMARY KEY, conv_uuid TEXT REFERENCES conversation,
  parent_turn TEXT, position INTEGER, role TEXT,
  lane TEXT,                              -- A|B|solo|orchestrator when observable
  content_md TEXT, completeness TEXT,     -- state machine of FIG.2
  completeness_detail TEXT,               -- gap list, reasons
  source_turn_id TEXT, content_hash TEXT, -- hash = dedup marker ONLY
  captured_via TEXT                       -- live|history|import|reveal|annotation
);

CREATE TABLE identity_observation (
  obs_id INTEGER PRIMARY KEY, turn_uuid TEXT REFERENCES turn,
  kind TEXT, value TEXT, source TEXT, observed_at TEXT,
  epoch_id TEXT, adapter_version TEXT, confidence TEXT, superseded_by INTEGER
);

CREATE TABLE source_observation (
  obs_id INTEGER PRIMARY KEY, turn_uuid TEXT,
  evidence_uri TEXT,                      -- evidence://sha256:...
  mechanism TEXT, adapter_version TEXT, uncertainty TEXT, captured_at TEXT
);

CREATE TABLE artifact (
  content_key TEXT PRIMARY KEY,           -- sha256 of ciphertext layout
  slot_uuid TEXT, conv_uuid TEXT, kind TEXT, size_bytes INTEGER,
  encryption TEXT, derived_from TEXT, created_at TEXT
);

CREATE TABLE sync_state (
  slot_uuid TEXT PRIMARY KEY, watermark TEXT, page_cursor TEXT,
  coverage_gaps TEXT,                     -- JSON array, inspectable
  updated_at TEXT
);

CREATE TABLE conflict (
  conflict_id INTEGER PRIMARY KEY, kind TEXT,      -- cross_account|diverged|payload
  refs TEXT, detail TEXT, state TEXT, created_at TEXT
);

CREATE TABLE analysis_run (
  run_id TEXT PRIMARY KEY, cohort_def TEXT, code_version TEXT,
  input_hash TEXT, outputs_uri TEXT, limitations TEXT, created_at TEXT
);
