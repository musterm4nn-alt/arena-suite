Arena Model Archive_

Architecture & implementation plan for a private macOS application that owns a dedicated browser for Arena (arena.ai), records the owner's own conversations with strong provenance and per-account isolation, backfills existing history where feasible, stores everything in a local encrypted archive, exposes essentially all functionality to LLMs over MCP, and later supports local model-behavior analysis.

Electron + Chromium, TypeScript service layer

The v1 application embeds and owns its Chromium runtime via Electron. One persistent session.fromPartition("persist:arena-<uuid>") per Arena account gives isolated cookies, storage, cache, service workers, and downloads. A main-process webContents.debugger (Chrome DevTools Protocol) attachment provides a capture surface outside page-world JavaScript. All durable state lives in a SQLCipher database whose key is wrapped by the macOS Keychain, and a local stdio MCP server exposes the whole system to LLMs.

Electron (Chromium) TypeScript CDP capture Per-account Session partitions SQLCipher / FTS5 macOS Keychain stdio MCP server Deterministic analysis
Explicit reversal condition — do not hide this

Electron is the v1 choice only if the falsification spike proves it can reliably capture the required Arena traffic classes (fetch/XHR, streamed responses, WebSocket frames where used, worker/service-worker traffic, navigation lifecycle, downloads, multi-account isolation) through maintained CDP/Session surfaces. If a required traffic class cannot be observed that way, but CEF's native GetResourceResponseFilter demonstrably solves it, switch the architecture to CEF. A custom Chromium fork is a last resort only if neither maintained surface suffices.

02 What is verified vs unknown

The single most important honesty statement in this document.

Established (mechanisms exist)
  • Verified Electron gives a main-process CDP channel and per-account persistent partitions — the two pillars of the recommendation.
  • Verified CEF gives a deeper native response-body filter — the credible fallback.
  • Verified SQLCipher + raw key + Keychain wrapping is a sound encryption story; MCP stdio is the right agent interface.
  • Verified Tauri/WKWebView ride the system WebKit with a weak public interception surface.
Not established (must be proven empirically)
  • Unknown Arena's actual transports, schemas, and history endpoints. No authenticated browser was ever connected — in either run.
  • Hypothesis That Electron's CDP/Session surfaces capture all required Arena traffic with completeness.
  • Hypothesis That any history list/detail endpoint is genuinely non-mutating and account-bound.
  • Hypothesis That simultaneous multi-account partitions stay clean under real Arena behavior (service workers, CAPTCHA, sign-out).
Hard rule

This document makes no claim that authenticated Arena capture has been verified, and names no endpoint read-only. Every such claim is deferred to an owner-session acceptance gate. "The page loads" is never success; only machine-checkable capture output counts.

Rejected baseline — browser extension + companion

The owner's existing recorder (musterm4nn-alt/arena-exporter) is a Manifest V3-style extension plus native messaging. It fails on exactly the axes that matter here: capture lives inside page/runtime interception, so it misses streams, suffers extension-lifecycle gaps, and needs companion plumbing. It is the baseline to beat, not a candidate.

Rejected — owning the window is not enough; the capture must sit outside page JS. An extension cannot be the primary architecture.

Also rejected — explicit export/import, no embedded browser

Export-then-import cannot satisfy the core requirement that the owner uses Arena normally inside the app while capture happens live, and it provides no multi-account live isolation or ongoing stream capture. It may exist later as an import path for user-supplied archives, but not as the architecture.

Rejected as primary — acceptable only as an auxiliary import adapter.

Why WKWebView and Tauri lose

Previous-run Apple's WKURLSchemeHandler only serves custom schemes and explicitly throws if registered for a scheme WebKit handles internally — so it is not a general hook for Arena's HTTPS traffic. WKProcessPool multiplicity is deprecated (a no-op), removing the naive isolation primitive. Verified Tauri/Wry simply rides that same system WebKit on macOS. Being "native" or "lightweight" buys no deeper capture, and capture correctness is the first priority.

04 Why Electron, and the exact reversal rule

The recommendation and the condition under which it is withdrawn.

Electron is the pragmatic v1 because it is the only option that combines, in a mainstream TypeScript ecosystem, all four primitives the project depends on:

  • Chromium behavior — so Arena's real app (auth, streams, workers) behaves as it does in a normal browser.
  • Direct CDP via webContents.debugger Verified — a capture surface in the main process, not page JS.
  • Per-account persistent partitions via session.fromPartition("persist:…") Verified.
  • Session introspection + downloads — serviceWorkers, will-download, clearData, storagePath Verified.

Strong inference These primitives make reliable capture likely, but they prove instrumentation capability, not Arena-specific capture correctness. That gap is deliberately left open and is exactly what spike #1 exists to close.

Reversal gate — the architecture is falsifiable
  1. If Electron cannot reliably observe an architecture-critical traffic class through maintained CDP/Session surfaces, run a focused CEF spike.
  2. If CEF's native GetResourceResponseFilter Verified demonstrably captures that missing class, switch to CEF.
  3. Only if both maintained surfaces fail do we even consider invasive Chromium customization — a last resort, never a starting point.

05 Browser ownership & the capture surface

The owner's key insight: owning the browser window is not the same as having deeper capture privileges. For each architecture we must name exactly what capture mechanisms exist outside page JavaScript.

ArchitectureCapture mechanisms that exist OUTSIDE page JSDepth gained over the extension baseline
Extension + companion Effectively none. Content scripts + webRequest sit inside the page/runtime or see metadata only; streams and worker traffic escape. Baseline (insufficient)
WKWebView Custom-scheme handler (not for HTTPS), navigation delegates, message handlers. No general response-body interception. Not deeper
Tauri / Wry Inherits WKWebView's surface on macOS; no bundled-engine hooks. Not deeper
Electron CDP: Network.* (request/response, dataReceived, getResponseBody, webSocket*, EventSource), Target lifecycle + auto-attach, Page/Runtime events; plus Session.serviceWorkers, will-download, webRequest. Materially deeper — main-process instrumentation
CEF Native resource pipeline: CefResourceRequestHandler + GetResourceResponseFilter on the IO thread, incl. service-worker / CefURLRequest origins; CefRequestContext isolation; download handler. Potentially deepest (fallback)

The design consequence: in Electron, the primary capture transport is the main-process CDP channel (Network + Target + streaming events), not anything injected into the page. A tiny, optional DOM/page instrumentation layer exists only as secondary evidence to reconcile against network evidence — never as the source of truth.

07 Simultaneous multi-account partition design

Two (or more) Arena accounts stay signed in and usable at the same time. This is not an account switcher. Each account is a fully isolated universe.

  • Destructive-action scope

  • Cookies · localStorage · sessionStorage

Shared services + ONE encrypted archive Rows are account-scoped. Cross-account source-ID collisions create a conflict, never a merge. Signing out / CAPTCHA / re-auth on A pauses only A's capture authority — B is untouched.
  • Partition naming: persist:arena-<internal-uuid>. Never derive the name from an email address or other sensitive identifier; map uuid ↔ account in the encrypted DB.
  • Identity is provenance: the owning account/session partition is a field on every archived record.
  • No cross-account merge: identical text does not prove sameness; dedup keys always include account scope. Ambiguous source IDs produce a recorded conflict, never a silent merge.
  • Fault isolation: one account's sign-out, CAPTCHA, identity change, or sync failure degrades only that account's pipeline.
  • Credential hygiene: browser-managed persistent sign-in state legitimately lives in each partition's profile (that's how sign-in persists). It is materially different from copying bearer tokens/cookies into the archive — which is never done, and never persisted to DB, logs, fixtures, exports, or diagnostics.

08 Discovery & the protocol catalog

Discovery is a maintained product capability, not a one-time reverse-engineering session. The app keeps a machine-readable protocol catalog of first-party Arena operations it has observed.

Broadly inventory first-party traffic during supported workflows, but never persist a credential-dumping HAR. Authorization headers, cookies, CSRF secrets, passwords, OTPs, OAuth codes, bearer tokens, sensitive signed URLs, and unrelated private fields are sanitized before durable persistence. Keep only enough sanitized raw evidence for parser debugging, drift detection, reparsing, and provenance.

Protocol catalog entry — representative TypeScript
interface ProtocolCatalogEntry {
  id: string;                       // stable local uuid
  operation: string;                 // e.g. "conversation.stream", "history.list", "history.detail"

  firstPartyOrigin: string;          // origin host only, no secrets
  urlFamily: string;                 // templated path family, secrets stripped
  method?: "GET"|"POST"|"PUT"|...|"unknown";
  transportClass: "fetch"|"xhr"|"sse"|"websocket"|"eventsource"|"navigation"|"download"|"unknown";
  semantics: "read"|"suspected-mutation"|"unknown";  // never trust GET/friendly names
  requestSchemaFamily?: string;
  responseSchemaFamily?: string;
  parserAdapter: { name: string; version: string };
  captureMechanism: "cdp-network"|"cdp-websocket"|"cdp-target"|"session-sw"|"download"|"dom-secondary";
  sanitization: "clean"|"failed-closed"|"pending";

Reconciliation rules

  • Idempotent ingestion: observations may arrive duplicated, out of order, after navigation/reconnect, after a reveal, or during an overlapping history sync.
  • Never downgrade provenance: newer, weaker inference does not overwrite stronger historical evidence.
  • Reveal is additive: a model-reveal adds an identity observation; it does not retroactively pretend the model was known earlier.
  • Conflicting evidence is preserved as a flag, not resolved by silently picking one side.

10 History backfill & synchronization

Backfill is a separate capability from live capture, with its own falsification gate.

Backfill gate — authenticated history replay was NOT verified

Opening one known conversation proves nothing. An owner-session test must demonstrate, per account: operation is bound to the current authenticated account; listing + pagination work; detail retrieval works; the operations are non-mutating; checkpoint/resume work; overlap/repeat pages are handled; account isolation holds; auth-expiry and rate-limit behavior is sane; and completeness boundaries are known. Do not call an endpoint read-only just because it's a GET with a friendly name — verify absence of mutation empirically.

Preferred strategy (if the gate passes)

If discovery identifies stable, authenticated, account-bound owner-history LIST and DETAIL reads and verifies they are non-mutating, use them as the primary sync adapter. This yields the highest completeness for backfill.

Fallback

Automated browser/UI traversal + capture, with visibly lower completeness guarantees and an explicit BACKFILLED / lower-confidence provenance tag. Official export or a future documented API, and user-imported archives, slot in as additional adapters later.

Sync must support: one or many selected accounts; per-account progress, checkpoint, cancellation, resume, bounded retries, idempotent page processing, overlap handling, auth expiry, challenges, rate limiting, source-ID collisions, live-capture overlap, partial histories, and drift.

Concurrency: two accounts may sync concurrently only if their sessions are fully independent partitions and the server-side rate-limit risk is per-account. The safe default is to schedule accounts independently so one account's throttling never starves or corrupts the other — correctness over throughput. "Synchronized" has a precise per-account meaning and always exposes known coverage gaps.

12 Model identity evidence

Distinct kinds of "which model" are never silently equated.

Keep these strictly separate: participant position A/B, blind Arena label, selected marketing model, provider label, route/model string, post-vote revealed identity, owner annotation, and inferred stylistic identity.

Each identity observation stores: source, applicable account, conversation/turn/participant scope, timestamp, evidence mechanism, and confidence/completeness.

Inviolable rule

Inferred model identity from text must never overwrite an observed or revealed identity. Inference is a hypothesis attached alongside evidence, ranked below reveal < observed < selected-label < inference.

13 Encryption, local data & deletion

Random key → macOS Keychain → SQLCipher. No human passphrase as the primary key.

Verified SQLCipher provides transparent AES-256-CBC page encryption with HMAC-SHA512 integrity and accepts raw binary keys — so we generate a random archive key, wrap/store it in the macOS Keychain, and hand the raw key to SQLCipher (not a passphrase). WAL and journal pages are encrypted. Configure SQLCipher with file-based temp storage disabled (SQLITE_TEMP_STORE memory) to avoid plaintext temp files.

Plaintext exposure — realistically

  • Browser profiles: each persistent partition legitimately contains Arena auth cookies (that's how sign-in persists). This is OS-account-permission-protected browser-managed state — different from deliberately copying credentials into the archive (never done). Residual risk: anyone with the macOS login can read the profile directory; full-disk access/backup snapshots may retain it.
  • Exports, crash logs, fixtures, diagnostics: sanitized; never contain keys/tokens/cookies.
  • Swap / OS residuals: SQLCipher mlock/wipes memory where possible; swap and OS-level residue cannot be perfectly eliminated — acknowledged, not promised away.
  • Spotlight / Time Machine / external backups: the encrypted DB is opaque to Spotlight content indexing; Time Machine will back up the (encrypted) files. We do not promise to delete already-made external backups or already-exported files.

Deletion with a two-step destructive intent token

Support: delete one conversation; delete everything for one account; delete the whole archive. Deletion never touches the owner's Arena cloud data unless a future feature performs a separate, explicit remote operation. Account/archive-wide deletion requires a trusted explicit owner directive — never something found in archived content.

Two-step destructive authorization — representative JSON

14 MCP / LLM interface — primary, not an afterthought

Everything in the GUI has a machine equivalent, except literally interacting with the remote Arena webpage. Verified MCP clients SHOULD support stdio, so a local stdio server is the default trusted agent interface. GUI and MCP share the same application service layer.

Transport posture

Default = stdio (server spawned as a subprocess by the desktop app). An optional loopback-only Streamable HTTP transport may be added for operational convenience, but — per the MCP spec's security guidance — it binds only 127.0.0.1, validates Origin, and never exposes privileged archive operations to the LAN.

  • Opening phrases · transitions · conclusions
  • Qualifications, hedging, refusal/apology language, uncertainty markers
Stratification
  • By model-identity evidence · mode (battle / direct / side-by-side)
  • By prompt type · topic · language · date
  • By conversation context · Arena account (sampling)
  • Every profile reveals its cohort and sample counts.

Major confounders — always disclosed with results

One-user selection bias · repeated prompting habits · topic · conversation context · Arena hidden prompts · model system prompts · decoding parameters · tool availability · routing/aliases · temporal model updates · safety layers · Arena post-processing. These are reported alongside every cohort so a statistic is never over-read as a "model fingerprint."

Recommendation Embeddings / local ML are optional future additions, admitted only after an empirical gate shows deterministic methods are insufficient — not added to v1 because they sound sophisticated.

16 Later fingerprinting experiments & modalities

Stylistic similarity is a hypothesis, never proof of model identity.

Fingerprinting experiment discipline
  • Held-out conversations with leakage-resistant splits; branches/near-duplicates kept in the same split.
  • Prompt/topic controls and negative controls; calibration; unknown-class rejection; temporal validation.
  • Reproducible preprocessing; preserve observed-vs-inferred identity separation.
  • No invented universal minimum sample threshold — let empirical power/stability analysis decide whether an experiment is worth continuing.

Later modalities — text first, extension points ready

Extension points (not built big in v1): search responses + citations · Arena Code generated files/previews/DB metadata/tool events · images + metadata · video/workflow artifacts · agent sessions + tool traces · uploads and derived artifacts. The approach is shared observation/artifact provenance primitives + modality-specific adapters, avoiding a gigantic universal content framework.

18 Falsification spike #1 — try to disprove Electron

The strongest section of the plan. Build the smallest dedicated-browser harness that attempts to break the recommendation.

Probes (all must produce machine-checkable output)

  1. Arena email sign-in works in the embedded Chromium (email code, MFA, CAPTCHA, redirects, popups handled by the owner).
  2. Account A and Account B stay signed in simultaneously via separate persistent partitions.
  3. Cookie / localStorage / cache / service-worker state does not leak across partitions.
  4. CDP attaches before/through relevant Arena navigation.
  5. Fetch/XHR traffic is observable.
  6. Streamed response content can be reconstructed where Arena uses streams.
  7. WebSocket frames observable if Arena uses WebSockets.
  8. Worker/service-worker traffic does not disappear silently.
  9. Capture survives navigation/target changes.
  10. Stopped / failed / partial generations are distinguishable.
  11. Late model-reveal / vote evidence associates correctly.
  12. Downloads / generated artifacts captured directly.
  13. Sanitizer retains no credentials (leak test = 0).
  14. Disconnecting/signing out A does not damage B.
  15. Where practical, run the same workflow against the existing extension and compare completeness.

Machine-checkable outputs

Capture manifest · event counts · source/target IDs · sanitized payload hashes · response-reconstruction digest · expected-vs-observed workflow markers · a gaps list. Success is defined by these artifacts, never by "the page loaded."

Reversal gate (restated at the point of use)

If Electron can't reliably capture an architecture-critical traffic class via maintained CDP/Session mechanisms, run a focused CEF spike using native response filtering. If CEF demonstrably solves the gap, switch architectures. Only if both fail do we consider more invasive Chromium customization.

19 Testing & failure behavior

Three strictly separated test classes. Synthetic tests never substitute for owner-session evidence.

Synthetic
  • Stream chunk splitting · duplicate/out-of-order events · reconnect · truncated streams
  • Parser drift · sanitizer failure · account-ID collisions · DB crash recovery · deletion · migration · corrupted encrypted blobs
Platform
  • Documented Electron/CDP/Session behavior tested independently of Arena (partitions, CDP attach, downloads).
Owner-session (authenticated)
  • Real stream protocols · capture completeness · reveals · auth flows · backfill · simultaneous accounts. No real credentials/raw traffic in fixtures.

Failure behavior — scope failures as narrowly as possible

  • One parser drifts → retain sanitized unknown observation, mark adapter degraded.
  • One account signs out → pause that account's sync/capture authority only.
  • One account hits CAPTCHA → expose NEEDS_OWNER_INTERACTION for that account.
  • Rate limiting → bounded backoff for that account/job.
  • Account identity changes → halt/rebind only after explicit verification.
  • Ambiguous source ID → create a conflict, never cross-account merge.
  • Sanitizer failure → fail closed for durable raw evidence.
  • DB unavailable → stop durable ingestion rather than silently pretend capture succeeded.
  • MCP client disconnect → long-running jobs have explicit continuation/cancellation semantics.

Minimum supported macOS — a concrete choice

Decision

Recommendation Minimum supported macOS is macOS 14 (Sonoma), Apple Silicon only. Rationale: (a) it is the oldest broadly-current Apple Silicon baseline, giving a small, agent-maintainable support matrix; (b) it comfortably predates the dev machine (macOS 27) without dragging along legacy Intel/old-OS complexity; (c) Electron, SQLCipher bindings, and Keychain (SecItem) access are all well-supported there; (d) because this is private software with no distribution, there is no reason to support very old releases. The dev/build machine running macOS 27 is the build target; 14 is the deployment floor.

Native module / build risk — discussed, not version-pinned

The two native surfaces are a SQLCipher-enabled SQLite binding and Keychain access via the Security framework (SecItem) through a maintained binding or a small native addon. Both require rebuilding against the chosen Electron ABI (an electron-rebuild/prebuild step in CI). We deliberately do not pin version numbers here; instead we pin the Electron line and validate the bindings in Phase 0. Choosing CEF would replace this modest native risk with a far larger C++/Obj-C++ build, framework-bundling, and CEF/Chromium version-management burden — a key reason it is the fallback, not the default.

Resource use — measure, don't invent numbers

On an M3 Pro / 18 GB unified machine we do not fabricate capacities. Instead, instrument and set configurable quotas with backpressure, and require that at least two Arena sessions remain usable simultaneously. Measure: per-active-partition renderer memory · main-process memory · capture queue depth · encrypted DB growth · artifact-store size · sync/analysis concurrency limits · background sync load. If a quota is hit, backpressure (drop to UI-only capture, pause low-priority sync) engages rather than the app degrading silently.
