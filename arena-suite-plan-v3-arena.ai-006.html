Architecture & implementation plan · single-user, private, Apple Silicon macOS

Arena Conversation Archive
for macOS — Architecture Plan

A permanently private macOS application for the owner of multiple concurrent arena.ai accounts, recording accurate local transcripts of the owner's own conversations for offline search and local research. This document selects one dedicated-browser architecture, defers every consequential decision to primary sources, and specifies falsifiable gates an AI implementation agent can execute.

1Executive decision

Recommendation: build the archive on Electron — a current stable Chromium embedded as a dedicated macOS application — with one persistent session partition per Arena account, browser-level Chrome DevTools Protocol (CDP) capture, a Node-based service core, an encrypted SQLite archive, and a local MCP server as the primary automation surface.

Decisive reasons. The capture requirements — full response bodies of streamed and chunked traffic, WebSocket frames, Server-Sent Event (EventSource) messages, worker and service-worker traffic, early-attach before first paint, direct download control, and simultaneous isolated sessions — are exactly what the Chromium DevTools Protocol exposes and exactly what a dedicated application can own but an extension cannot. Electron is the maintained, mainstream embedding that exposes all of it through ordinary APIs plus one well-trodden CDP channel, while keeping a single Node runtime and a single browser engine. ✓Electron’s session.fromPartition('persist:…') gives each account its own persistent cookie/localStorage/IndexedDB/cache store, and its clearStorageData covers service workers ✓; the CDP Network domain exposes requestWillBeSent, responseReceived, dataReceived, eventSourceMessageReceived, webSocketFrameReceived/webSocketFrameSent, and bodies via Network.getResponseBody ✓; Target.setAutoAttach with flatten/waitForDebuggerOnStart is the documented mechanism for observing child targets (workers, service workers, iframes) ✓; and MCP’s TypeScript SDK ships both stdio and Streamable-HTTP server transports ✓.

What this is not. The recommendation is not a browser extension, a chrome.debugger MV3 extension, an extension plus native host, or an extension plus companion — those are the already-tried, rejected baseline. The app owns the browser window and the browser process; capture is a first-party capability of the host, not a page-world or extension-lifecycle hack. It does not depend on Google sign-in, OAuth, or passkeys. Arena’s own email sign-in (including its verification-email step) runs inside the embedded Chromium exactly as in a normal browser ✓ (help.arena.ai confirms email and Google sign-up; email uses a verification link).

Reversal conditions. The recommendation is conditional on Gate 0/2 (§12). If Electron’s CDP surface cannot deliver streamed bodies, SSE/WebSocket frames, or worker/service-worker visibility in practice, the fallback is CEF (same Chromium, C++ embedding, CefRequestHandler::GetResourceResponseFilter/CefResponseFilter for bodies ✓), which preserves capture depth at the cost of Node-ecosystem velocity and maintenance. If partition-level service-worker isolation leaks, the fallback is a single-account-at-a-time mode or CEF. Detailed fallbacks and detection signals are in §13.

Minimum macOS. Electron 44+ requires macOS 13 (Ventura) per its Chromium floor ✓; this app targets macOS 14 (Sonoma) as the application minimum and Apple Silicon only (arm64), which also matches the owner’s M3 Pro machine and keeps Keychain/sandbox behavior modern.

2Scope, constraints, and operating context

2.1 Product scope

  • Permanently private, single owner (the user) and the owner’s own Arena accounts. No distribution, no multi-tenant users, no App Store, no hosted backend, no telemetry, no cloud analytics, no public update infrastructure.
  • Normal use of Arena (including Arena Code and the broader conversation surfaces: Battle mode, Direct mode, Side-by-Side mode, Image/Video Arena where supported) while the app records accurate local transcripts of the owner’s own conversations.
  • Multiple Arena accounts signed in and usable simultaneously, with isolated cookies, storage, cache, service-worker state, capture state, synchronization state, provenance, and destructive-action scope.
  • Offline browsing, search, filtering (account, date, mode, observed/revealed model, state, provenance), branch-aware transcripts, versioned machine-readable export, human-readable export, local research into model behavior, prose, formatting, and stylistic similarity.

2.2 Hard constraints

  • Dedicated browser application/runtime is a fixed requirement. No extension, chrome.debugger extension, extension + native host, or extension + companion as the architecture or primary capture path.
  • Apple Silicon only. No duplicated browser engines, no unnecessary resident runtimes. Optimize for local development and running the app, not public packaging.
  • Email sign-in is sufficient. Google sign-in/OAuth and passkeys are not requirements and must not disqualify a stronger architecture.
  • MCP is the primary interface. Every capability available through the GUI must also be available to an LLM through a local MCP surface.
  • AI agents perform almost all implementation and troubleshooting: prefer mainstream, well-documented dependencies, reproducible setup, structured diagnostics, and autonomously checkable gates.

2.3 Owner-session scope and boundaries

  • Access is limited to data associated with the owner’s currently signed-in Arena accounts, and every operation is bound to the correct account/session scope. A conversation URL or opaque ID alone never establishes ownership.
  • Authenticated read access to first-party endpoints with the correct account-scoped session is in scope (an undocumented endpoint is not an access-control bypass; the session proves ownership). Automation compatibility (normal browser presentation, no masked-automation theater, bot-challenge handling by the owner completing flows in-app) is in scope. Access-control workarounds that reach data belonging to the owner’s own accounts by working around client-side restrictions are out of scope unless the actual control and mechanism are identified and defended; the design does not need any of them.
  • Credentials: native sync code may transiently reuse credentials issued to the correct app-owned session (including token refresh) but must never persist copies to disk, exports, fixtures, or logs. Browser-managed session persistence (cookies in the partition) is explained and isolated in §9.
  • Visible recording state and meaningful pause, cancel, stop controls per account and globally, with specified effects on in-flight work and captured data (§6).
  • Stop or degrade safely for the affected account on sign-out, account mismatch, loss of session authority, or ambiguous ownership. Failure in one account must not invalidate, corrupt, or silently rebind another account.

2.4 Resource posture

Archive size is heavy by expectation, not by assumption; practical quotas and measurements are proposed in §11.4. On an 18 GB shared-RAM machine, two to three concurrent Chromium sessions plus the Node core are comfortable; the design caps concurrent sessions, suspends idle partitions, and records renderer RSS as a first-class diagnostic.

4.2 Why Electron over CEF (focused comparison)

Both embed Chromium and both can observe bodies, workers, and downloads. The differences are operational:

  • Capture depth: equivalent in principle — CDP (Electron) vs. CefRequestHandler/CefResponseFilter (CEF). CEF additionally routes all network through the browser process, which simplifies worker/SW accounting; Electron compensates with browser-level Target auto-attach. Neither is a decisive advantage after Gate 0.
  • Worker/SW observability: CEF’s single-browser-process model is structurally cleaner; Electron relies on standard Chromium CDP behavior, which is well-proven (the same mechanism DevTools itself uses) ✓.
  • Session partitioning & simultaneous accounts: both support it; Electron’s partition API is documented and trivial to operate ✓.
  • Downloads: both direct; Electron’s will-download is a one-liner.
  • Resource cost: both ship a full Chromium; parity.
  • Maintenance: Electron wins decisively for a small team: Node main process, TypeScript MCP SDK, prebuilt native modules, release tooling, documentation. CEF means C++ build chains and owning Chromium patches. CEF is the designated fallback, not the default.

4.3 What still depends on page injection (honest disclosure)

Even with CDP, the app injects one small read-only content script per partition (via session.webFrame/executeJavaScript on navigation) to (a) reconcile network-observed conversations with rendered UI evidence (titles, vote buttons, reveal banners, completion state), (b) recover fields the network payloads do not expose, and (c) provide a DOM fallback when payload shapes drift. This is not the extension-baseline pattern of monkey-patching the page’s own runtime: the script never mutates page behavior, never talks to remote endpoints, and is app-controlled IPC to the main process. The network layer remains the primary source of truth; the DOM layer is reconciliation and fallback, and its losses are explicit (§6.5).

4.4 Why the engine choice is safe for the email flow

Google/OAuth/passkey support is not a requirement. Email sign-in — including Arena’s verification-email step — runs inside the embedded Chromium like any browser ✓. If the owner ever uses Google sign-in, it works too. The architecture does not change the owner’s authentication workflow; it records it.

5.1 Process model and trust boundaries

  • Renderer processes host only Arena content. No Node integration, no ipcRenderer access to privileged channels, no filesystem, no Keychain. Arena JavaScript cannot reach the archive, the DB, the MCP server, or the control plane. This is enforced structurally (separate sessions, no preload bridge into partition windows) rather than by policy.
  • Main process is the only privileged component and owns every capability: capture, storage, sync, exports, deletion. The GUI and MCP layers are thin clients of the main process through the control plane; neither can bypass service-layer rules.
  • Untrusted-content guard. Archived prompts, responses, tool traces, and diagnostic text are data, never instructions. The server never executes instructions found in archive content (no eval, no dynamic tool invocation, no shell). Destructive actions require a token minted only by a human action in the trusted GUI control channel (§10.7). Authorization is distinguished from retrieved content: only the GUI’s trusted event path can issue an authorization, and the token is scope-bound and short-lived.
  • MCP server process. A separate Node executable bundled with the app, spawned by the MCP client, speaking stdio MCP (and optionally Streamable HTTP on loopback). It connects to the app’s control plane over a Unix-domain socket with a Keychain-wrapped token. If the app is not running, the server reports app_not_running with a clear message instead of failing silently.

5.2 Session/partition model for simultaneous accounts

  • One Arena account = one persistent partition persist:acct-<uuid>. ✓Electron partitions provide isolated cookie stores, localStorage, IndexedDB, HTTP cache, and (per Chromium’s storage-partition model) service-worker registrations; clearStorageData can clear each storage class per partition ✓. Partition state lives under the app’s per-partition directory; sessions are independent ✓.
  • Capture context is partition-bound. The CDP client tags every event with the partition/session it came from (via the target’s session id and the mapping of targets → partitions). Every normalized record carries account_id; no record is ever written without it.
  • Destructive-action scope is partition-bound. Deleting one account’s data clears that partition’s storage and that account’s rows; other partitions, sessions, capture streams, and sync jobs are untouched.
  • Failure isolation. Sign-out, account mismatch, challenge, or session-authority loss in account A pauses A’s recording and sync; B and C continue. Cross-account contamination is prevented by construction (separate stores, per-account streams, per-account checkpoints) and tested in Gate 0/1.
  • Verification gate. Partition isolation (including service-worker state) is explicitly tested in Gate 0/1 with two simultaneous accounts: sign into A, perform actions in A, repeat in B, then assert no cookie/storage/SW/capture-state leakage across partitions, and that quitting/reopening the app restores each session correctly.

5.3 Capture surface (the deeper-than-extension mechanism)

Capture is a first-party host capability built on the Chromium DevTools Protocol, attached at browser level before any Arena navigation:

  1. At app startup, before any session loads: app.commandLine.appendSwitch('remote-debugging-port', <ephemeral>) ✓, binding to loopback only.
  2. The capture core connects to the browser CDP endpoint (/json/version, /json/list) with a small ws-based client, issues Target.setAutoAttach({autoAttach:true, waitForDebuggerOnStart:true, flatten:true}) on the browser target, and for every attached target issues Network.enable ✓. waitForDebuggerOnStart is the late-attach countermeasure: newly created targets (pages, service workers, dedicated workers, iframes) are paused until the client attaches ✓.
  3. HTTP/fetch: requestWillBeSent → responseReceived → chunk stream via dataReceived → loadingFinished/loadingFailed; bodies reconstructed from chunks and finalized with Network.getResponseBody where available ✓.
  4. WebSocket: webSocketCreated, frames via webSocketFrameReceived/webSocketFrameSent (payload is the complete message, not fragments), errors via webSocketFrameError ✓.
  5. EventSource/SSE: eventSourceMessageReceived delivers each SSE data event ✓.
  6. Service workers and workers: reached through the same auto-attach mechanism (child targets) ✓ for the CDP mechanism; Electron-specific behavior is Gate 0’s falsification target ◐.
  7. Downloads: session.on('will-download', …) gives the app the item, the suggested path, and progress; the app moves it into the encrypted artifact store. No extension download restrictions, no companion bridge ✓.
  8. DOM reconciliation: one read-only content script per partition (§4.3).
Honest disclosure — what still depends on page injection

CDP observes network perfectly; it does not observe the page’s JavaScript variables. Fields that exist only in the DOM (rendered vote state, post-vote reveal banners, completion UI, some titles) come from the read-only content script. If Arena changes its DOM without changing its network payloads, the DOM layer absorbs it; if it changes payloads, adapters version (§6.6). Neither layer mutates page behavior.

5.4 Remote-debugging-port exposure and mitigation

A CDP endpoint on loopback is a local attack surface: any local process could connect while the app runs. Mitigations: ephemeral high port; loopback bind only; the endpoint is enabled only for the app’s own lifetime; macOS application firewall remains the OS backstop; the control-plane socket requires a Keychain-wrapped token. Residual risk is disclosed and accepted for a single-user machine; the fallback (per-webContents.debugger attach, which loses browser-level service-worker visibility) is specified in §13 if the owner considers the exposure unacceptable.

5.5 GUI (minimal, diagnostics-first)

The v1 GUI is a diagnostics console, not a browser chrome replacement: account list with sign-in state and recording controls, per-account capture/completeness state, sync jobs with progress and cancellation, the protocol catalog and drift report, failure list, export controls, and the trusted deletion controls. Arena interaction happens in the partition windows themselves (the site’s own UI), so the GUI never re-implements Arena workflows.

6Capture pipeline: observation to normalized state

6.1 Principles

  • Raw before normalized. Every first-party response body that matches a retention policy is stored (sanitized, encrypted) in a raw payload store; normalized records are derived. This makes adapter changes reparsable (§8.2) and drift diagnosable (§6.6).
  • Idempotent ingest. Every CDP event carries a stable (target, requestId, kind, seq); ingest is idempotent by event id, so replay and re-runs never duplicate.
  • Sanitize at ingest. The sanitizer runs before persistence and before any diagnostic exposure; parser errors store a sanitized fragment plus the error class, never the raw payload in logs.
  • Never promote incomplete to complete. Completeness is a first-class, per-record state (§6.3).

6.2 Stream reconstruction and turn/branch boundaries

  • WebSocket transport: frames → messages per webSocketCreated/webSocketClosed handle; message type and order preserved; gaps (missing frames, reconnects) recorded as transport events.
  • SSE transport: eventSourceMessageReceived events → messages; each event keeps its eventName/eventId so partial streams can be distinguished.
  • Chunked fetch: dataReceived chunks assembled into the full body; large or binary bodies skipped by content-type policy (classification still recorded).
  • Turn boundaries: a turn is a request→response/message pair keyed by conversation id and participant seat; a new prompt starts a new turn; regenerations/branches are detected from payload branch fields, updated_at/revision markers, or DOM revision controls.
  • Conversation identity: from the URL and/or the first-party payload (arena_conversation_id). Identity is always scoped to account_id; identical text across accounts never merges (§8.3).
  • Participant positions: seat labels from the payload (e.g., model A/model B) or, in Direct mode, the single selected model; blind labels and post-vote reveals are recorded as identity observations with sources, never silently equated (§8.4).

Rules. (1) complete requires a clean transport finish and successful reconciliation. (2) partial-stopped and failed keep their content and their state; queries can filter them out. (3) observer-gap is raised by the completeness tracker when the adapter detects missed events (sequence discontinuity, target recreated, replayed session after gap) and is the primary signal that distinguishes “the model stopped” from “we missed data.” (4) State transitions are recorded in provenance so a later re-parse can explain how a record reached its state.

6.4 Reconciliation of network and UI evidence

The normalizer correlates network-observed conversations with DOM-observed evidence via conversation id, URL, title, and timestamps. Disagreements (e.g., network says complete, DOM shows a stopped spinner) are logged as reconciliation conflicts with both sides’ evidence; the network side wins for transport truth, the DOM side wins for UI-only fields, and the conflict itself is retained. A fallback capture loses exactly the UI-only fields; the loss is enumerated in the record’s provenance.

6.5 Where fallback capture loses information

  • Payload-shape drift: unrecognized payload families fall back to DOM-only capture (titles, turns as text) — loses transport metadata, exact ordering of interleaved streams, and machine-readable fields until an adapter is updated (re-parse from raw payloads fixes historical data).
  • Opaque/binary bodies: classification recorded, body not stored (size/type recorded).
  • Observer gaps: the affected range is marked observer-gap, not guessed.
  • DOM fallback only: votes/reveals that never hit the network remain UI-sourced with lower confidence.

6.6 Discovery as a maintained capability: the protocol catalog

Discovery is not a one-time spike; it is an inventory that the app maintains and that agents can query. Every observed first-party operation is represented as a catalog entry with:

  • operation_key (method + path pattern or WS message-type family), classification (conversation / auth-account / asset / analytics-config / mutation / unknown), first_party_evidence (host, how origin was established), transport (fetch / SSE / WS / other), read_or_mutation (observed; HTTP method alone never proves read-only — §7.2), schema_family, adapter_version, completeness, and drift_signals.
  • Drift detection: schema validation failures, new fields, changed message types, changed pagination cursors, changed URLs — each raises a sanitized drift record with the adapter version and a reparse hint. Unknown operations stay unknown in diagnostics until investigated; inventory coverage is distinct from payload retention (broad discovery never becomes raw credential-dumping: the sanitizer excludes credentials at ingest, §9.3).

7.2 Evidence needed before backfill is trusted

  • Account association: the history listing must be observed inside the account’s own session and carry the account’s visible identity; records are stamped with account_id at capture time.
  • Effective read behavior: a verified read is one whose captured request/response the owner-session context shows is read-only (no mutation side effects observed across runs). HTTP method or endpoint name alone never proves read-only.
  • Pagination and detail retrieval: capture a listing page, its cursor, and a detail payload; confirm the cursor advances, pages overlap conservatively, and detail payloads include full turns and branch/revision info.
  • Completeness: compare listing count vs. captured conversation count; record gaps (pagination drift, deleted-by-server, partial pages) in coverage_gaps.

7.3 “Sync now” semantics

  • Per-account jobs. sync_now(account_ids?) starts one job per selected account (default: all signed-in accounts). Jobs are independent: separate checkpoints, separate cursors, separate rate-limit state, separate failure scope. More than one account can sync concurrently without reducing correctness; concurrency is capped (default 2) to protect responsiveness and to be polite to the service.
  • Checkpointing. Each job persists {listing_cursor, processed_ids, per-conversation updated_at+content_hash}; interruption resumes from the checkpoint. Overlapping or repeated pages are handled by idempotent ingest keyed (account_id, arena_conversation_id) plus content-hash dedup — identical text is never sufficient evidence of duplication, and cross-account source-id collisions are explicit conflicts, never automatic merges.
  • Interaction with live capture. Sync and live capture share the ingest pipeline; a conversation updated during sync is re-checked at job completion (stale flag) or re-queued; partially captured conversations are completed from the listing side, not merged blindly.
  • Failure handling. Rate limits (respect Retry-After, exponential backoff, bounded retries); auth expiry or sign-out → job paused with sync_auth_expired for that account only; redirects/challenges → owner completes in-app, job pauses with a visible state; drift → adapter re-parse attempt, else observer-gap coverage. A failure in one account never touches another.
  • “Synchronized” definition. For each account: all conversations reachable via the verified listing representation at job completion are ingested with recorded completeness; remaining gaps are enumerated in coverage_gaps (listing drift, deleted-server-side, partial pages, unverified reads). Opening one known conversation proves only that conversation — never full historical coverage.
  • Agent inspection. get_sync_job, list_sync_jobs, get_coverage_gaps(account_id) expose state, progress, checkpoints, and gaps per account.

8.1 Source of truth: proportionate hybrid

Not full event sourcing. Three layers: (1) normalized records (the queryable archive), (2) a sanitized raw payload store (encrypted, retained per policy, reparsable when adapters change), (3) an artifact store (encrypted files: downloads, generated images, later modalities). The raw store is the reparse source; the normalized layer is the source of truth for queries; provenance links them.

8.3 Reconciliation keys and conflict handling

  • Conversation identity: (account_id, arena_conversation_id). Turns: (conversation_id, branch_id, seq, revision_index). Dedup on sync: same key + same updated_at + same content hash → no-op; same key + different hash → new revision or explicit conflict, never an automatic overwrite of the other account’s record.
  • Cross-account collisions (identical IDs/text/timestamps across accounts) are conflict records surfaced to the owner; the app never merges records across accounts.
  • Idempotency: event-level (capture) and job-level (sync) keys make re-runs safe.

8.4 Model identity handling

  • Preserve: selected labels, blind labels, displayed provider/model names, post-vote reveals, timestamps/turn ranges, and observation sources (UI, network, reveal event, import, owner annotation).
  • Never silently equate participant position, blind label, provider name, marketing name, route name, or exact build. identity_observations is a timeline; a later reveal adds a new observation with scope (turn range, reveal time) and updates the usable identity view (most recent observation per participant) without erasing earlier evidence or attributing a label beyond its supported scope. Conflicts and unknowns remain visible.

8.5 Transactions, crash recovery, migration, backup/restore

  • Transactions: synchronous better-sqlite3 transactions per ingest batch; WAL mode; synchronous=FULL; temp_store=MEMORY; foreign keys on (SQLCipher pragmas; ✓ per SQLCipher/SQLite practice).
  • Crash recovery: sync jobs checkpoint before each batch; idempotent ingest replays safely; raw payload writes are atomic (write-then-rename).
  • Migration: versioned SQL scripts; the raw store + adapter versions allow re-parsing history after schema/adapter changes (recompute normalized layer without re-capturing).
  • Backup/restore: the encrypted DB file + artifact store + Keychain-wrapped key constitute the archive; backup copies the encrypted artifacts (residual copies in Time Machine/backups are disclosed, §9.2). Restore re-verifies key availability and DB integrity.

8.6 Deletion semantics

  • One conversation: remove turns/revisions, raw payloads, artifacts (with secure-delete intent), and index entries; provenance of the deletion is recorded.
  • One account’s local data: clear the partition (cookies/storage/SW), remove that account’s rows, artifacts, sync jobs, and checkpoints; future sync re-creates from the service. Deduplication markers are account-scoped, so cross-account records are unaffected.
  • Whole archive: destroy DB, artifacts, Keychain key (after explicit confirmation), logs, and temp files; residual copies in external backups/swaps are disclosed, not promised away (§9.2).

9Security and encryption

9.1 Key management

  • Database: SQLCipher via better-sqlite3-multiple-ciphers with PRAGMA cipher='sqlcipher' + PRAGMA key='…' (AES-256 page encryption with HMAC, PBKDF2 KDF; ✓ SQLCipher 4 semantics). The key is a random 256-bit value wrapped by the OS: macOS Keychain via Electron safeStorage (encryptString/decryptString, Keychain-backed on macOS ✓). The app must be code-signed for consistent Keychain behavior ✓.
  • Artifacts: AES-256-GCM per file with keys derived (HKDF) from the master key per account/artifact; the DB and artifacts share the Keychain-wrapped master key. (Comparable protection with better safety/maintainability than a second DB engine; SQLCipher remains the DB cipher as required.)
  • Browser-managed session persistence (cookies in the partition) is separate from the archive key: protected by OS filesystem permissions (0700 app container) and, at rest, by the OS; its exposure is the partition directory (readable by the OS user and by Time Machine) — disclosed below. The archive key is never written into any partition.

9.3 Credential handling and sanitization

  • Excluded from capture, raw store, diagnostics, logs, fixtures, exports: authorization headers, cookies, Set-Cookie, OAuth codes, CSRF secrets, passwords, signed URLs, and unrelated private fields. A deny-list sanitizer runs at ingest; URL query strings are scrubbed (token patterns); parser-error paths store sanitized fragments only.
  • Transient reuse of session credentials (token refresh, same-origin API calls during sync) is permitted only in memory, never persisted. The design’s primary sync path (navigation-based replay) needs no credential export at all.
  • Safe resource references: when a source URL contains secrets, the record stores a scrubbed URL plus a local artifact reference; the original URL is never persisted.

9.4 Privilege separation (reprise)

Arena-controlled remote content (partition renderers) cannot reach: the archive key (Keychain via safeStorage is main-process only), local files (no Node, no filesystem bridge in partition windows), privileged APIs (control-plane token is main-process/GUI-only), or the MCP server (separate process, socket-authenticated). These boundaries hold during errors, sign-outs, concurrent use, and account changes because each is structural (separate processes/sessions), and they are exercised in Gate 5.

10Local automation contract (MCP)

10.1 Transport and connection model

  • Primary: stdio MCP. The app bundles a standalone Node executable (arena-archive-mcp) that the MCP client spawns; it speaks MCP over stdio using the official TypeScript SDK (StdioServerTransport) ✓ and connects to the running app’s control plane over a Unix-domain socket (…/Application Support/Arena Archive/control.sock) with a Keychain-wrapped per-connection token.
  • Optional: Streamable HTTP on 127.0.0.1 with bearer-token auth (same SDK’s HTTP transport) for clients that prefer HTTP ✓.
  • Lifecycle: if the app is not running, the server returns a structured app_not_running (or waits with a bounded retry) rather than failing silently. Capabilities are discovered via MCP tools/list and resources/list; unavailable operations return structured errors (§10.4), never silent no-ops.

10.2 Trust boundary and access controls

  • The socket and HTTP endpoints are loopback-only, token-authenticated, and the token is per-connection and Keychain-wrapped. The MCP process has no filesystem access to the archive beyond forwarding calls.
  • Archived content is untrusted data. Tool responses return data; the server never executes instructions found in archived text (no eval, no dynamic tool invocation from content, no shell). Prompt-injection-style content in an archived response has no authority over the server.
  • Destructive actions require a user directive from a trusted control channel (§10.7): account-wide or archive-wide deletion cannot be triggered by content or by an unconfirmed LLM call.

10.5 Long-running and retryable work

Sync, analysis, and export share one job model: queued → running ⇄ paused → completed | failed | cancelled, with progress {done, total, phase}, cancellation, and idempotency keys (kind + account_id + cursor/checkpoint). Cancellation is cooperative at batch boundaries; retries are bounded with exponential backoff and respect Retry-After.

10.6 GUI and MCP share one service layer

GUI actions (Electron IPC from the first-party GUI renderer) and MCP actions both call the same service layer (RecordingService, SyncService, ArchiveService, ProtocolService, AnalysisService, ExportService, DeletionService). Semantics, state transitions, and error categories are therefore identical across surfaces; no essential workflow exists only in the GUI. Browser-interaction tools (start recording, sync now) are app operations on the account’s partition — the MCP layer never touches the DOM.

10.7 Destructive-action guard (content can never authorize deletion)

  1. Mint (trusted channel only): a human presses Delete/Confirm in the GUI (first-party renderer, OS-level user gesture). The main process mints a token: HMAC-SHA256(keychain_key, account_scope | conversation_ids | action | expiry(5 min) | nonce), displayed to the user as a short code.
  2. Relay: the user tells the LLM the code (out-of-band); the LLM passes it to the delete tool.
  3. Validate: the server checks signature, expiry, single-use (nonce table), and exact scope equality with the requested operation before executing.

Authorization comes from the trusted GUI event, never from retrieved content; archived text cannot mint or alter tokens. This is the concrete guard for the “archived instructions must not delete the archive” requirement.

11Local analysis and later modalities

11.1 Initial model profiles (local only)

  • P1 — descriptive statistics per (account, mode, revealed-model cell): response/paragraph/sentence/code-block lengths; lexical diversity and recurring n-grams; Markdown structure counts (headings, lists, tables, citations); code/prose ratios; common openings, transitions, conclusions, hedging/refusal/apology/uncertainty markers (curated lexicons, versioned); variation by prompt type, topic, mode, language, time, conversation context; representative excerpts linked to source evidence.
  • P2 — comparative: pairwise differences between model cells with bootstrap confidence intervals; effect-size reporting; explicit cohort definitions.
  • P3 — embeddings (gated): only if P2 shows semantic structure that statistics cannot separate (§11.3).

Validity limits (stated per profile): one heavy user → selection bias; sparse samples; prompt/topic confounding; conversation history; hidden system prompts; decoding settings; tools; safety layers; aliases/routing; temporal model changes; Arena post-processing; uncertain labels. Profiles expose their cohorts and limitations; comparisons are supported only where the data and design justify them.

11.2 Statistical validity discipline

Deterministic statistics first (transparent, reproducible). Minimum evidence thresholds are predeclared per profile (cohort size, cells with ≥k observations), calibrated during validation; profiles below minimums are not run and say so. Later similarity/fingerprinting experiments are confidence-qualified hypotheses, never proof of identity or authorship: leakage-resistant splits (conversation-level; near-duplicate branches clustered so related branches never split across train/test), prompt/topic controls, negative controls, calibration curves, unknown-class abstention, reproducible runs, and empirically justified minimum evidence. Continuation/revision/abandonment criteria are predeclared (§12, G7).

11.3 Embeddings entry gate

P3 runs only when: (a) P2 demonstrates stable clusters needing semantic separation; (b) the corpus justifies it (sample sizes); (c) a small local model (e.g., a pinned small encoder run offline) is chosen with weights pinned and cached, preprocessing versioned, and offline operation after setup. The gate prevents speculative packaging costs.
